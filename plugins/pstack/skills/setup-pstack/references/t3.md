# Configure pstack models in T3 Code

Use this only when T3 Code tools are available. Keep setup-pstack's roles,
panel semantics, confirmation, and optional verification-skill offers. Replace
its backend-specific discovery, storage, validation, and inclusion steps below.
Read [the T3 mapping](../../poteto-mode/references/t3-tools.md) for dispatch.

## Discover and choose

Use the host's `orchestrator_capabilities` catalog and current tool schemas.
Respect the host's discovery cadence. Search for a requested model missing from
the short catalog before declaring it unavailable. Only offer provider instances
that can run child tasks, and check cross-provider support when applicable.
Use each provider's exact `providerInstanceId`, full model ID, and supported
option IDs and values. Do not restrict the choices to Claude Agent's family enum
or normalize full Claude model IDs to family aliases.

Ask for user or project scope unless the request already specifies it. T3 sheets
use these OMS paths on the agent's filesystem, regardless of the parent provider:

| Scope | Sheet |
| --- | --- |
| User | `~/.t3/pstack-models.md` |
| Project | `.agents/pstack-models.t3.md` at the repository root, or the session's starting directory outside Git |

The project sheet replaces the user sheet as a whole. Read the chosen sheet if
present. Without a T3 sheet, show the current backend's effective role choices
as starting choices, resolving their provider explicitly before saving them.
Do not copy the native sheet's hook setting. Leave native model sheets,
CLAUDE.md, AGENTS.md, and hook trust unchanged. A hook-only request still follows
the existing backend procedure for the hook, independently of T3 model rows.

Show the existing setup-pstack role table and confirm changes. Preserve the
upstream role labels and panel counts. Get them from the skill's generated
override-sheet block, not a second role list. Partial sheets are valid. Report
retired or invalid rows and resolve them before writing.

## Save and validate

Keep the existing Markdown role-row format. A real target is
`<providerInstanceId>/<full-model-id>`, optionally followed by `@<effort>`.
Split on the first slash because model IDs can contain slashes. Panel entries
remain comma-separated. `auto` and `inherit-parent` keep the parent provider
and model, including when they occur in a panel.

For example, substitute confirmed provider and model IDs in this partial sheet:

```markdown
# pstack T3 model configuration

how explorer: <codex-instance>/<codex-model-id> @medium
judgment and prose: <claude-instance>/<claude-model-id> @high
arena runners: <codex-instance>/<codex-model-id> @medium, <claude-instance>/<claude-model-id> @high

default effort: session
```

Validate each target and its effective effort against that target's catalog
entry before writing. A suffix wins over `default effort`. No default line means
`session`. Resolve `session` from the active parent's options, never a catalog
default. Across providers, carry the active effort value only when the target
supports it. If the active effort is unknown or unsupported, request an explicit
choice. Do not translate `ultrathink` to `ultra`, or silently drop an effort.

Write the confirmed sheet idempotently, then read it back and validate every
saved row. Only a missing role uses the backend's existing effective choice.
An invalid configured target must be reported, not replaced with a default.
Do not add an `@include` or paste T3 rows into backend instructions. The T3
mapping loads this sheet before role dispatch. Report the saved path, scope,
and whether a project sheet shadows the user sheet. Configuration alone starts
no workers and does not change the parent conversation's model or effort.

## Verify when requested

Use a small authorized task with a configured role. Reload the saved sheet and
resolve the target from that role. Check the host's actual provider, executed
model, and effort, as well as the task result. Report configuration validation
and a real dispatch separately. Do not claim a saved sheet proves execution.
