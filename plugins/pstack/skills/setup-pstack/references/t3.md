# Setup pstack

Write the model sheet, `~/.config/t3-pstack/models.md` (`$XDG_CONFIG_HOME/t3-pstack/models.md` when that is set), one per machine. It sets pstack's T3 provider and model per role, and every pstack skill reads it before it dispatches.

## Steps

### 1. Detect available models

Call `orchestrator_capabilities`, or `acp-mcp-call orchestrator_capabilities '{}'` where the T3 tools are not exposed. Its provider instances and their models are the dependable source. A target is valid only when its provider instance can run a child task and lists the model. Note each provider's own option IDs and values, such as `effort` on Claude, `reasoningEffort` on Codex and Grok, and `thought_level` on Antigravity. Never write a target you have not seen there. The aliases `inherit-parent` and `auto` are always valid.

### 2. Load current state

Read the machine sheet if it exists. Otherwise check `t3-pstack-models.md` in the host's config directory (`$CLAUDE_CONFIG_DIR` or `~/.claude` on Claude Code, `$CODEX_HOME` or `~/.codex` on Codex). If neither exists, start with the built-in medium profile in step 5. Read the current `# budget` as the starting choice. Offer `large` for a legacy `unlimited` budget.

### 3. Budget, map, and confirm

**(a) Ask for a budget.** Ask a structured multiple-choice question (`AskUserQuestion` on Claude Code, numbered options in plain text elsewhere). Name the current budget if recorded. With no sheet, offer `medium` as the built-in profile.

- `large - xhigh reasoning`
- `medium - high reasoning`
- `small - medium reasoning`

**(b) Build the candidate.** Save the provider catalog to a temp file as `{"providers": [...]}`. For each model the defaults or current sheet use, append the matching catalog entry from `orchestrator_capabilities` with `search` if the model was omitted. Include Gemini 4 Neon if a legacy panel uses Gemini 4 Carbon. Run the command below with the chosen budget. Omit `<current.md>` when there is no sheet. The command prints the candidate to stdout and reports migrations and unavailable targets on stderr.

```sh
node <plugin-root>/skills/setup-pstack/scripts/t3-sheet.mjs --candidate <large|medium|small> <catalog.json> [<current.md>]
```

The medium profile uses each seat's built-in options. Large raises each built-in reasoning level by one step and small lowers it by one step on the `low`, `medium`, `high`, `xhigh` ladder. The OpenCode variant stays fixed. For large and small, use the highest available level at or below the requested level if the provider lacks it. A budget change updates rows that match the previous OMS preset. A `# override: <role>` comment keeps an explicit choice when its value also matches the preset. Other role values stay as written, including `inherit-parent`, `auto`, and explicit provider options. The candidate migrates recognized old defaults and the Antigravity option rename when the catalog supports it. An existing Neon `thought_level=high` remains valid for medium.

**(c) Show the roles and confirm.** Show every role with its entry, marking any target not in the detected set as needing a choice. Include the changes the candidate command reports. Ask whether to accept as-is or change specific roles, offering the detected targets at `xhigh` or below plus `inherit-parent` and `auto` (both mean: this role runs on the parent chat's model) as the options. For panel roles (`arena runners`, `interrogate reviewers`) the value is a list, and one subagent runs per entry, alias entries included, so the list length sets the count. Each panel list, and the cross-judge pool, needs at least two model families among its targets. A model's family is the first segment of its ID's last `/` part, such as `claude`, `gpt`, or `gemini`, except that Fable (`claude-fable-*`) is its own family. `arena cross-judge pool` is also a list, but Arena runs one judge. It tries only values from a vendor other than the parent's, in list order, so order it by preference. Fable and the other Claude models are one vendor. An `inherit-parent` or `auto` value never judges. `swarm workers` is the default target for every worker unless a race or comparison assigns another per arm.

**(d) Ask about the session-start hook.** Keep the current `session hook` value, or use `on` for a fresh sheet. Ask the user whether to change it.

### 4. Validate

Write the candidate to a temp file. If the user selects a target omitted from the catalog, search for it and add its entry before validation. Run `node <plugin-root>/skills/setup-pstack/scripts/t3-sheet.mjs <candidate.md> <catalog.json>`. Resolve every reported problem before writing the sheet. A missing role line uses the built-in medium entry. If Node is unavailable, apply the rules in step 3 and check each effective target against the catalog by reading.

### 5. Write the sheet

Write the approved candidate to the machine sheet. Create its directory if needed and resolve its path with `realpath` if it is a symlink. Keep the candidate's `# defaults`, `# budget`, and `# override` comments. Link the host's legacy `t3-pstack-models.md` to the machine sheet if it is missing or the user approved moving that legacy sheet. Preserve a different legacy sheet and native model overrides. The generated medium example shows a fresh sheet.

```markdown
# pstack model configuration (T3). One line per role. Delete a line to fall back to the skill default.
# `inherit-parent` or `auto` as a value: the role runs on the parent chat's model (`delegate_task` omits `target`). Alias entries in a panel list still count toward its fan-out.
# defaults: 4
# budget: medium (high)
feature, refactoring: codex/gpt-6.2-sol reasoningEffort=high
bug-fix: codex/gpt-6.2-sol reasoningEffort=high
perf-issue: codex/gpt-6.2-sol reasoningEffort=high
hillclimb: codex/gpt-6.2-sol reasoningEffort=high
judgment and prose: codex/gpt-6.2-sol reasoningEffort=high
strongest judgment: codex/gpt-6.2-astra reasoningEffort=high
arena runners: codex/gpt-6.2-astra reasoningEffort=medium, claudeAgent/claude-opus-5-5 effort=medium, antigravity/gemini-4-neon thought_level=high
arena cross-judge pool: claudeAgent/claude-opus-5-5 effort=medium, antigravity/gemini-4-neon thought_level=high
swarm workers: opencode/opencode-go/deepseek-v4.1-flash variant=high
interrogate reviewers: codex/gpt-6.2-astra reasoningEffort=medium, claudeAgent/claude-opus-5-5 effort=medium, antigravity/gemini-4-neon thought_level=high
thermos reviewers: codex/gpt-6.2-sol reasoningEffort=high
no-comments reviewer: codex/gpt-6.2-sol reasoningEffort=high
session hook: on
```

### 6. Confirm

Tell the user the sheet was written and that it applies to new sessions. Re-running this skill updates it.

### 7. Offer a verification skill (optional)

Check whether the project has a way to drive the real app for proof (a `verify-*` skill, or an existing harness). If not, offer once: "want a project-local verification skill, so agents can drive the app the way a user does and prove changes work? I can generate one with /create-verification-skill." On yes, read [`../create-verification-skill/SKILL.md`](../../create-verification-skill/SKILL.md) from this file and follow it. Do not call the Skill tool for it, since that tool refuses a skill only the user may invoke. On no, move on without pushing.

### 8. Offer a formal verification skill (optional)

Check whether the project already has a formal verification skill (a project skill that runs a model checker, a proof, or another verifier against the code). If not, offer once: "want a formal verification skill, so agents can prove a key property of your code holds in every case in scope, not only the cases tests reach? I can generate one with /create-formal-verification-skill." On yes, read [`../create-formal-verification-skill/SKILL.md`](../../create-formal-verification-skill/SKILL.md) from this file and follow it. Do not call the Skill tool for it, since that tool refuses a skill only the user may invoke. On no, move on without pushing.
