この章では、次の6つの原則を扱います。

1. [Model the Domain](https://github.com/cursor/plugins/blob/main/pstack/skills/principle-model-the-domain/SKILL.md)
2. [Boundary Discipline](https://github.com/cursor/plugins/blob/main/pstack/skills/principle-boundary-discipline/SKILL.md)
3. [Type System Discipline](https://github.com/cursor/plugins/blob/main/pstack/skills/principle-type-system-discipline/SKILL.md)
4. [Make Operations Idempotent](https://github.com/cursor/plugins/blob/main/pstack/skills/principle-make-operations-idempotent/SKILL.md)
5. [Migrate Callers Then Delete Legacy APIs](https://github.com/cursor/plugins/blob/main/pstack/skills/principle-migrate-callers-then-delete-legacy-apis/SKILL.md)
6. [Separate Before Serializing Shared State](https://github.com/cursor/plugins/blob/main/pstack/skills/principle-separate-before-serializing-shared-state/SKILL.md)

6件はArchitecture（設計）のグループの原則で、どれも<strong>エージェントがコードをどんな形（状態の持ち方や、検証を置く場所など）に組み立てるか</strong>を決めます。同梱ガイドのページ [`docs/guide/08-principles.md`](https://github.com/cursor/plugins/blob/main/pstack/docs/guide/08-principles.md) は、6件を「状態、検証、互換性をどこに置くか」を決める原則とまとめています。

6件を使うと、エージェントは、次のように動作します。

- 状態を、いくつもの真偽値の組み合わせではなく、状態機械で持つ
- 外から受け取るデータの検証を、境界に集める
- 呼び出し元をすべて新しいAPIに移したら、その同じ変更の中で古いAPIを消す

<ul class="code-line" data-line="18">
<li class="code-line" data-line="18">
<strong>状態機械</strong>・・・ 取りうる状態と、状態から状態への移り方を、あらかじめ決めておく書き方。ある時点では、決められた状態のどれか一つだけを取る<br/>
たとえば、信号機は、青、黄、赤のどれか一つだけを示し、青→黄→赤の決まった順に移ります。「青と赤が同時につく」ことも、「青から赤へ飛ぶ」こともありません。状態機械は、このような決まりをコードで表します。</li>
<li class="code-line" data-line="20">

</ul>
</div></aside>

## 『Model the Domain』は、ドメインを条件分岐ではなく構造で表す

原則『<strong>Model the Domain</strong>』は、実際のドメインを、あちこちの条件分岐の中にばらばらに書くのではなく、データの構造で表すよう求めます。  
エージェントは、状態や分岐が増えそうなとき、<strong>条件分岐（if/else）を追加する前に、ドメインを表す構造を選びます</strong>。

### 散らばった真偽値、繰り返される前提、広がる分岐は、不要な複雑さである

原則は、次の3つを、本来は不要な複雑さと呼びます。

- 散らばった真偽値
- ファイルごとに繰り返される「このデータはこの形のはず」という前提
- ファイルをまたいで広がる分岐

<a id="3%E3%81%A4%E3%81%AE%E8%A4%87%E9%9B%91%E3%81%95%E3%82%92%E5%90%AB%E3%82%80%E3%82%B3%E3%83%BC%E3%83%89%E3%81%A7%E3%81%AF%E3%80%81%E3%81%82%E3%82%8A%E3%81%88%E3%81%AA%E3%81%84%E7%8A%B6%E6%85%8B%E3%81%8C%E6%9B%B8%E3%81%91%E3%81%A6%E3%81%97%E3%81%BE%E3%81%86"></a>


### 3つの複雑さを含むコードでは、ありえない状態が書けてしまう

たとえば、ネットショップの注文を、発送ラベルを作るファイルと、お知らせメールを作るファイルの2つで扱うケースを考えてみましょう。

3つの複雑さをすべて含むコードは、次のようになります。

```
// order.ts：注文の状態を、3つの真偽値で持つ（散らばった真偽値）
type Order = {
  address: string;
  isPaid: boolean;
  isShipped: boolean;
  isCanceled: boolean;
  trackingNo?: string;
};

// label.ts：発送ラベルを作る
function labelText(order: any): string {
  // 「注文には住所があるはず」という前提を、ここで確かめる
  if (!order.address) throw new Error("住所がありません");
  // 状態の分岐
  if (order.isCanceled) return "キャンセル済み";
  if (order.isShipped) return "発送済み";
  if (order.isPaid) return "発送待ち";
  return "支払い待ち";
}

// mail.ts：お知らせメールの件名を作る
function mailSubject(order: any): string {
  // 同じ前提を、別のファイルでもう一度確かめる
  if (!order.address) throw new Error("住所がありません");
  // 同じ分岐が、ファイルをまたいで繰り返される
  if (order.isCanceled) return "ご注文をキャンセルしました";
  if (order.isShipped) return "商品を発送しました";
  if (order.isPaid) return "お支払いを確認しました";
  return "お支払いをお待ちしています";
}
```

このコードでは、`isShipped` と `isCanceled` が同時に `true` という値も書けてしまいます。  
これが<strong>ありえない状態</strong>で、「発送済み」と「キャンセル済み」は、実際の注文では同時に成り立ちません。  
また、`isShipped` が `true` なのに `trackingNo`（追跡番号）がない値も書けてしまいます。

<a id="%E3%83%89%E3%83%A1%E3%82%A4%E3%83%B3%E3%82%92%E8%A1%A8%E3%81%99%E6%A7%8B%E9%80%A0%E3%82%92%E9%81%B8%E3%81%B6%E3%81%A8%E3%80%81%E3%81%82%E3%82%8A%E3%81%88%E3%81%AA%E3%81%84%E7%8A%B6%E6%85%8B%E3%81%8C%E6%9B%B8%E3%81%91%E3%81%AA%E3%81%8F%E3%81%AA%E3%82%8A%E3%80%81%E5%88%86%E5%B2%90%E3%82%82%E6%B8%9B%E3%82%8B"></a>


### ドメインを表す構造を選ぶと、ありえない状態が書けなくなり、分岐も減る

エージェントがドメインを表す構造を選ぶと、<strong>ありえない状態はそもそも書けなくなり、条件分岐も減ります</strong>。ドメインを表す構造には、状態機械や、項目を決めた型付きのオブジェクトなどがあります。

同じ注文を、ドメインを表す構造で書くと、次のようになります。

```
// order.ts：注文の形と、取りうる状態を一か所で決める
type OrderStatus =
  | { state: "unpaid" }
  | { state: "paid" }
  | { state: "shipped"; trackingNo: string }
  | { state: "canceled" };

type Order = { address: string; status: OrderStatus };

// 状態ごとの文言を、一つの表にまとめる
const LABEL_TEXT: Record<OrderStatus["state"], string> = {
  unpaid: "支払い待ち",
  paid: "発送待ち",
  shipped: "発送済み",
  canceled: "キャンセル済み",
};

// label.ts：状態ごとの文言を表にまとめ、型を信じて表を引くだけにする
function labelText(order: Order): string {
  return LABEL_TEXT[order.status.state];
}

// mail.ts：状態ごとの件名を表にまとめ、型を信じて表を引くだけにする
const MAIL_SUBJECT: Record<OrderStatus["state"], string> = {
  unpaid: "お支払いをお待ちしています",
  paid: "お支払いを確認しました",
  shipped: "商品を発送しました",
  canceled: "ご注文をキャンセルしました",
};

function mailSubject(order: Order): string {
  return MAIL_SUBJECT[order.status.state];
}
```

このコードでは、3つの複雑さが次のように消えます。

- <strong>散らばった真偽値</strong>・・・ 3つの真偽値の代わりに、`OrderStatus` が4つの状態のどれか一つだけを取ります。「発送済みかつキャンセル済み」は書けません。また、追跡番号は `shipped` のときだけ持ち、`shipped` なら必ず持ちます。
- <strong>繰り返される前提</strong>・・・ 「注文には住所がある」という前提は、`Order` 型に一度だけ書きます。各ファイルは型を信じるので、住所を確かめ直すことはしません。
- <strong>ファイルをまたぐ分岐</strong>・・・ 状態ごとの文言は、表を引くだけで決まります。状態を追加するときは、表に1行追加すれば済み、追加し忘れるとコンパイルの時点でエラーになります。

<a id="%E6%A7%8B%E9%80%A0%E3%81%AF%E3%80%81%E5%BE%8C%E3%81%8B%E3%82%89%E5%85%A5%E3%82%8C%E7%9B%B4%E3%81%99%E3%81%AE%E3%81%A7%E3%81%AF%E3%81%AA%E3%81%8F%E3%80%81%E3%82%B3%E3%83%BC%E3%83%89%E3%82%92%E6%9B%B8%E3%81%8F%E3%81%A8%E3%81%8D%E3%81%AB%E9%81%B8%E3%81%B6"></a>


### 構造は、後から入れ直すのではなく、コードを書くときに選ぶ

エージェントは、<strong>コードを書くときに構造を選びます</strong>。書くときなら、構造を選ぶ手間はほとんどかかりません。

一方、条件分岐で書き終えたコードに後から構造を入れ直す作業は、後回しにされがちです。

後回しにされるのは、入れ直してもコードの挙動は何も変わらず、入れ直す作業がリファクタリングに該当するからです。  
リファクタリングは、新しい機能と違って目に見える成果がないため、開発者もエージェントも、機能の追加を先に行い、リファクタリングを後に回しがちです。

たとえば、送料を決める条件分岐が3つのファイルに広がった後で、参照表に置き換えるケースでは、置き換えても、送料の金額も画面の表示も変わりません。そのため、この置き換えは「今すぐでなくてよい作業」として後に回され、その間にも、新しい機能のたびに条件分岐が増えていきます。

### ルール：散らばった書き方ごとに、代わりの構造が決まっている

この原則が挙げる代表的な置き換えは、次のとおりです。

<table class="code-line" data-line="207">
<thead class="code-line" data-line="207">
<tr class="code-line" data-line="207">
<th>散らばった書き方</th>
<th>代わりの構造</th>
</tr>
</thead>
<tbody class="code-line" data-line="209">
<tr class="code-line" data-line="209">
<td>状態を表す真偽値（<code>isLoading</code>、<code>isError</code> など）や、「今どの段階か」の確認が、コードのあちこちにある</td>
<td>状態機械（取りうる状態と移り方を定めた表し方）</td>
</tr>
<tr class="code-line" data-line="210">

#### 真偽値の代わりに、状態機械を使う

状態を真偽値で持つと、`running`（実行中）と `failed`（失敗）が同時に `true` という矛盾した状態も、コンパイルでエラーにならずに書けてしまいます。  
状態を状態機械で表せば、<strong>その組み合わせはそもそも書けません</strong>。

```
// 前：矛盾した組み合わせが表現できてしまう
type ExportJobFlags = { running: boolean; failed: boolean; retrying: boolean };

// 後：状態ごとに持てるデータが決まる
type ExportJob =
  | { state: "queued" }
  | { state: "running"; attempt: number }
  | { state: "failed"; attempt: number; error: string }
  | { state: "done"; rowCount: number };

// 移り方も決める：失敗したジョブだけが、次の試行として running に戻れる
function retry(job: ExportJob): ExportJob {
  if (job.state !== "failed") return job;
  return { state: "running", attempt: job.attempt + 1 };
}
```

<a id="%E3%81%B0%E3%82%89%E3%81%B0%E3%82%89%E3%81%AE%E5%BC%95%E6%95%B0%E3%81%AE%E4%BB%A3%E3%82%8F%E3%82%8A%E3%81%AB%E3%80%81%E5%9E%8B%E4%BB%98%E3%81%8D%E3%81%AE%E3%82%AA%E3%83%96%E3%82%B8%E3%82%A7%E3%82%AF%E3%83%88%E3%82%92%E4%BD%BF%E3%81%86"></a>


#### ばらばらの引数の代わりに、型付きのオブジェクトを使う

たとえば、会員の名前、メールアドレス、プランを、Welcomeメールを送る関数と請求書を作る関数に、それぞればらばらの引数で渡しているケースの場合、どちらの関数も「会員には名前、メールアドレス、プランがあるはず」という同じ前提を、それぞれの引数の並びで繰り返しています。

エージェントは、会員を表す `User` 型を一つ作り、2つの関数がどちらも `User` を受け取るように直します。  
こうすれば、会員に項目を追加するときも、直すのは `User` 型の一か所だけで済みます。また、名前とメールアドレスを逆の順番で渡してしまう間違いも起きません。

```
// 前：同じ3つの引数を、関数ごとに並べている
function sendWelcomeMail(name: string, email: string, plan: string) { /* ... */ }
function createInvoice(name: string, email: string, plan: string) { /* ... */ }
```

```
// 後：会員の形を User 型に一度だけ書き、2つの関数はこれを受け取る
type User = { name: string; email: string; plan: "free" | "paid" };

function sendWelcomeMail(user: User) { /* ... */ }
function createInvoice(user: User) { /* ... */ }
```

<a id="%E5%BA%83%E3%81%8C%E3%81%A3%E3%81%9F%E6%9D%A1%E4%BB%B6%E5%88%86%E5%B2%90%E3%81%AE%E4%BB%A3%E3%82%8F%E3%82%8A%E3%81%AB%E3%80%81%E5%8F%82%E7%85%A7%E8%A1%A8%E3%82%84-discriminated-union-%E3%82%92%E4%BD%BF%E3%81%86"></a>


#### 広がった条件分岐の代わりに、参照表や discriminated union を使う

たとえば、注文の種類ごとの送料を、画面、請求、メールの3つのファイルでそれぞれ、条件分岐で決めているケースの場合、エージェントは「種類から送料を引く参照表」を一つ作り、3つのファイルがどれもその表を引くように直します。

こうすれば、注文の種類が増えても、3つのファイルの条件分岐をそれぞれ直す必要はなく、表に1行追加するだけで済みます。

```
type OrderKind = "standard" | "express" | "pickup";
declare const order: { kind: OrderKind };

// 前：画面、請求、メールの3つのファイルに、同じ if/else がある
function shippingFee(kind: OrderKind): number {
  if (kind === "standard") return 500;
  if (kind === "express") return 1200;
  return 0;
}

// 後：種類から送料を引く参照表を一つだけ作り、3つのファイルはこれを引く
const SHIPPING_FEES: Record<OrderKind, number> = {
  standard: 500,
  express: 1200,
  pickup: 0,
};

const fee = SHIPPING_FEES[order.kind];
```

`Record<OrderKind, number>` と書いておくと、注文の種類を型（`OrderKind`）に追加したのに表（`SHIPPING_FEES`）へ行を追加し忘れた場合、コンパイルの時点でエラーになります。

参照表は、種類ごとに「値」が一つ決まるときに向いています。

一方、種類ごとに<strong>持つデータそのものが違う</strong>ときは、エージェントは <strong>discriminated union</strong> を使います。

たとえば、支払い方法が「カード」「銀行振込」「代金引換」の3種類あり、カードのときだけカード番号の下4桁を、銀行振込のときだけ振込先の口座番号を持つケースが、これに該当します。

種類を表す項目と、省略できる項目（optional型）で書くと、「カードなのに口座番号が入っている」という値も書けてしまいます。  
discriminated union で書けば、`kind` の値ごとに持てる項目が決まるので、そうした値は書けません。

```
// 前：どの支払い方法でも、すべての項目を持ててしまう
type PaymentLoose = { method: "card" | "bank" | "cod"; cardLast4?: string; bankAccount?: string };

// 後：kind の値ごとに、持てる項目が決まる
type Payment =
  | { kind: "card"; cardLast4: string }
  | { kind: "bank"; bankAccount: string }
  | { kind: "cod" };

function paymentLabel(p: Payment): string {
  switch (p.kind) {
    case "card":
      return `カード（末尾 ${p.cardLast4}）`;
    case "bank":
      return `銀行振込（口座 ${p.bankAccount}）`;
    case "cod":
      return "代金引換";
  }
}
```

<a id="%E3%81%9D%E3%81%AE%E5%A0%B4%E3%81%AE%E6%9B%B8%E3%81%8D%E6%8F%9B%E3%81%88%E3%81%AE%E4%BB%A3%E3%82%8F%E3%82%8A%E3%81%AB%E3%80%81reducer-%E3%82%92%E4%BD%BF%E3%81%86"></a>


#### その場の書き換えの代わりに、reducer を使う

たとえば、買い物かごの中身を、商品一覧の画面、商品の詳細画面、かごの画面の3か所で、それぞれ直接書き換えているケースでは <strong>reducer</strong> が向いています。  
この場合、かごの中身がどこで、どう変わったのかを知るには、3か所をすべて読む必要があります。

エージェントは、かごへの操作（追加、削除）を型で決め、「今のかごと操作から、次のかごを計算する」reducer を一つ作ります。3か所は、かごを直接書き換えず、操作を reducer に渡すだけにします。  
こうすれば、<strong>かごの中身の変わり方は、reducer の中だけを読めば分かります</strong>。

```
type CartItem = { id: string; price: number };
type Cart = { items: CartItem[] };
declare let cart: Cart;
declare const item: CartItem;
declare const id: string;

// 前：3つの画面で、それぞれ直接書き換えている
cart.items.push(item);
cart.items = cart.items.filter((i) => i.id !== id);

// 後：操作を型で決め、次のかごの計算は reducer の中だけで行う
type CartAction =
  | { type: "add"; item: CartItem }
  | { type: "remove"; id: string };

function cartReducer(cart: Cart, action: CartAction): Cart {
  switch (action.type) {
    case "add":
      return { items: [...cart.items, action.item] };
    case "remove":
      return { items: cart.items.filter((i) => i.id !== action.id) };
  }
}

cart = cartReducer(cart, { type: "add", item });
```

#### 無理に構造を入れない

ただし、原則は、無理に構造を入れることは求めていません。今のコードが分かりやすく、一か所にまとまっていて、これから増える見込みもないなら、エージェントは単純なコードのままにします。

また、エージェントは、<strong>呼び出しの間に1段挟むだけで何も減らさない、共通の関数や型を疑います</strong>。分岐も、重複したルールも、ありえない状態も減らさない共通の関数や型は、読み手が開いて確かめる場所を増やすだけだからです。

### 発火条件

- 状態を持つロジックを書くとき
- 分岐が多いとき
- 「このデータにはこの項目がある」という同じ前提が、複数のファイルで繰り返されるとき

次のようなことが起きていたら、この原則を飛ばした兆候です。

- エージェントが、新しい機能のために、既存の条件分岐の連なりに、分岐をもう一つ追加した
- エージェントが、既存の真偽値と常に値をそろえておく必要のある、2つ目の真偽値を追加した

たとえば、読み込み中を表す `isLoading` があるところに、エラーを表す `isError` を追加したケースの場合、読み込みが失敗したとき、コードは `isError` を `true` にし、同時に `isLoading` を `false` に戻す必要があります。

`isLoading` を戻し忘れると、`isLoading: true` と `isError: true` が同時に成り立ち、画面は「読み込み中なのにエラー」という食い違った状態になります。

このように、2つ目の真偽値を追加すると、どちらかの値を書き換えるたびに、もう一方の値もそろえる必要が生まれます。

`/poteto-mode` の『[Non-negotiables](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/SKILL.md#non-negotiables)』も、この原則を求めています（[第8章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/096f3d)）。

『Non-negotiables』は、どんなコードを書くときも、エージェントがまずデータの形を明らかにし、この原則に沿って構造を選ぶよう求めています。<strong>23件の原則のうち、『Non-negotiables』で名指しされているのは、この『Model the Domain』だけです</strong>。

<a id="%E3%80%8Eboundary-discipline%E3%80%8F%E3%81%AF%E3%80%81%E5%85%A5%E5%8A%9B%E3%81%AE%E6%A4%9C%E8%A8%BC%E3%82%92%E5%A4%96%E3%81%A8%E3%81%AE%E5%A2%83%E7%95%8C%E3%81%AB%E9%9B%86%E3%82%81%E3%80%81%E5%86%85%E5%81%B4%E3%81%AF%E5%9E%8B%E3%82%92%E4%BF%A1%E3%81%98%E3%82%8B"></a>


## 『Boundary Discipline』は、入力の検証を外との境界に集め、内側は型を信じる

原則『<strong>Boundary Discipline</strong>』は、<strong>入力の検証、型の絞り込み、エラー処理を、システムの境界に置く</strong>よう求めます。この原則は、境界の例として、CLI引数、設定ファイル、外部API、ネットワークを通して届くデータを挙げています。

境界で確かめた値には型が付いています。そのため、境界の内側のコードは、その型のとおりの値が来ると信頼して使い、同じ確認を繰り返しません。

原則が確認を境界に集めるのは、確認がコードのあちこちに散らばると、次の2つの問題が起きるからです。

- 同じ確認を、何か所にも書くことになる
- 開発者もエージェントも、「どこかで確かめているはずだ」と思い込む。どの確認がどこで行われているかを把握しない限り、確かめていない経路が残っても気づけない可能性がある

次のコードは、確認がコードのあちこちに散らばった例です。注文フォームから届く「数量」が1以上かどうかを、一部の関数だけが確かめています。

```
let stock = 10; // 在庫の数

// 値段を計算する：数量が1以上かを確かめる
function calcPrice(quantity: number): number {
  if (quantity < 1) throw new Error("数量は1以上にしてください");
  return quantity * 500;
}

// 在庫を減らす：「どこかで確かめているはず」として、何も確かめない
function reserveStock(quantity: number) {
  stock = stock - quantity;
}

// 注文画面：calcPrice を先に呼ぶので、確かめてから在庫を減らす
calcPrice(2);
reserveStock(2);

// 別の画面：reserveStock だけを直接呼ぶ
reserveStock(-3); // 在庫が 8 から 11 に増えてしまう
```

注文画面の経路では `calcPrice` が確かめていますが、`reserveStock` だけを呼ぶ経路には確認が1つもありません。  
そのため、`-3` がそのまま届き、在庫を減らすはずの処理で在庫が増えてしまいます。

同じ処理を原則どおりに書くと、次のようになります。

```
let stock = 10; // 在庫の数

// 境界：フォームから届いた値を、ここで一度だけ確かめる
function parseQuantity(input: string): number {
  const quantity = Number(input);
  if (!Number.isInteger(quantity) || quantity < 1) {
    throw new Error("数量は1以上の整数にしてください");
  }
  return quantity;
}

// 内側：確かめた値だけが届くので、確認を書かない
function calcPrice(quantity: number): number {
  return quantity * 500;
}

function reserveStock(quantity: number) {
  stock = stock - quantity;
}

// どの画面も、フォームの値を parseQuantity に通してから使う
const quantity = parseQuantity("-3"); // ここでエラーになり、先へ進まない
calcPrice(quantity);
reserveStock(quantity);
```

確認は `parseQuantity` の1か所だけになり、`calcPrice` の中の確認は要らなくなります。  
また、どの画面もフォームの値を `parseQuantity` に通してから使うので、`-3` のような値は、`calcPrice` にも `reserveStock` にも届きません。

また、原則は、ビジネスロジックを純粋関数として書き、シェルを、純粋関数を呼ぶだけの薄い作りにするよう求めます（詳細は[『シェルが呼ぶだけの純粋関数に切り出す』](#%E3%82%B7%E3%82%A7%E3%83%AB%E3%81%8C%E5%91%BC%E3%81%B6%E3%81%A0%E3%81%91%E3%81%AE%E7%B4%94%E7%B2%8B%E9%96%A2%E6%95%B0%E3%81%AB%E5%88%87%E3%82%8A%E5%87%BA%E3%81%99)を参照）。ロジックをフレームワークから切り離しておけば、<strong>フレームワークを動かさずにロジックだけをテストできる</strong>からです。

<a id="%E3%83%AB%E3%83%BC%E3%83%AB%EF%BC%9A%E5%A4%96%E3%81%8B%E3%82%89%E5%85%A5%E3%82%8B%E3%83%87%E3%83%BC%E3%82%BF%E3%82%92%E5%A2%83%E7%95%8C%E3%81%A7%E6%A4%9C%E8%A8%BC%E3%81%99%E3%82%8B"></a>


### ルール：外から入るデータを境界で検証する

エージェントは、検証をどこに置くかを、次の2つの問いで判断します。

<a id="%E5%A4%96%E3%81%8B%E3%82%89%E5%85%A5%E3%81%A3%E3%81%A6%E3%81%8D%E3%81%9F%E3%83%87%E3%83%BC%E3%82%BF%E3%81%A0%E3%81%91%E3%82%92%E7%A2%BA%E3%81%8B%E3%82%81%E3%82%8B"></a>


#### 外から入ってきたデータだけを確かめる

1つ目の問いは「このデータは今、システムの境界をまたいでいるか（外から入ってきたところか）」です。  
<strong>またいでいないなら、確認は余分です</strong>。境界のコードは、確かめた値を型の付いた値に変えて内側の関数に渡し、内側の関数はその型を信じます。

たとえば、設定ファイルを読み込む関数が、読み込み時に `batchSize` を正の数だと確かめたなら、`batchSize` を使う内側の関数で `batchSize > 0` を確かめ直す必要はありません。境界で一度確かめれば、内側のすべての関数でその値を安心して使えるからです。

```
type Config = { batchSize: number };

// 境界：設定ファイルを読み込むときに一度だけ確かめ、Config 型の値にする
function parseConfig(raw: { batchSize?: unknown }): Config {
  if (typeof raw.batchSize !== "number" || raw.batchSize <= 0) {
    throw new Error("batchSize は正の数にしてください");
  }
  return { batchSize: raw.batchSize };
}

// 内側：Config 型を信じ、batchSize > 0 を確かめ直さない
function splitIntoBatches(items: string[], config: Config): string[][] {
  const batches: string[][] = [];
  for (let i = 0; i < items.length; i += config.batchSize) {
    batches.push(items.slice(i, i + config.batchSize));
  }
  return batches;
}
```

<a id="%E3%82%B7%E3%82%A7%E3%83%AB%E3%81%8C%E5%91%BC%E3%81%B6%E3%81%A0%E3%81%91%E3%81%AE%E7%B4%94%E7%B2%8B%E9%96%A2%E6%95%B0%E3%81%AB%E5%88%87%E3%82%8A%E5%87%BA%E3%81%99"></a>


#### シェルが呼ぶだけの純粋関数に切り出す

2つ目の問いは「この処理は、シェルが呼ぶだけの純粋関数にできるか」です。  
できるなら、エージェントはその処理を純粋関数として切り出します。

<aside class="msg message"><span class="msg-symbol">!</span><div class="msg-content">
<ul class="code-line" data-line="493">
<li class="code-line" data-line="493">
<strong>純粋関数</strong>・・・ 同じ引数には常に同じ値を返し、画面やファイルの読み書きのような、プログラムの外とのやり取りをしない関数</li>
<li class="code-line" data-line="494">
<strong>シェル</strong>・・・ 画面、ファイル、ネットワーク、フレームワークなど、プログラムの外とのやり取りを受け持つ部分。外から値を受け取って純粋関数に渡し、返ってきた結果を外へ出す</li>
</ul>
</div></aside>

たとえば、エージェントは、注文の合計金額の計算を、ボタンを押したときの処理の中に直接書かず、`calcTotal(items)` という関数に切り出し、ボタンの処理からはそれを呼ぶだけにします。こうすれば、画面を動かさずに合計金額の計算だけをテストできるからです。

一方、シェルには計算がないので、シェルの中で間違える余地はほとんどありません。

```
type Item = { price: number; quantity: number };
declare const button: HTMLButtonElement;
declare const totalLabel: HTMLElement;
declare function readItemsFromCart(): Item[];

// 純粋関数：同じ items には、いつも同じ合計を返す。画面には触らない
function calcTotal(items: Item[]): number {
  return items.reduce((sum, item) => sum + item.price * item.quantity, 0);
}

// シェル：画面から値を読み、純粋関数を呼び、結果を画面に書くだけ
button.addEventListener("click", () => {
  const items = readItemsFromCart(); // 画面から読む
  const total = calcTotal(items); // 計算は純粋関数に任せる
  totalLabel.textContent = `${total}円`; // 画面に書く
});
```

### 発火条件

入力の検証やエラー処理を組み込むとき、またはフレームワークと自分のコードをつなぐ部分（アダプタ）を書くときです。

<a id="%E3%80%8Etype-system-discipline%E3%80%8F%E3%81%AF%E3%80%81%E5%9E%8B%E3%81%A7%E4%B8%8D%E6%AD%A3%E3%81%AA%E7%8A%B6%E6%85%8B%E3%82%92%E4%BD%9C%E3%82%8C%E3%81%AA%E3%81%8F%E3%81%99%E3%82%8B"></a>


## 『Type System Discipline』は、型で不正な状態を作れなくする

原則『<strong>Type System Discipline</strong>』は、型検査器を、「この値は必ずこの形だ」と証明してくれる道具（原文では proof assistant）として扱います。

エージェントは、型検査器を使って、矛盾した状態や、variant の扱い漏れを、<strong>動かしてから見つけるのではなく、コンパイルの時点でエラーとして止めます</strong>。型が見逃した扱い漏れは、コンパイラが止められたはずの、実行時のエラーになるからです。

<aside class="msg message"><span class="msg-symbol">!</span><div class="msg-content">
<ul class="code-line" data-line="531">
<li class="code-line" data-line="531">
<strong>型検査器</strong>・・・ プログラムを動かす前に型の間違いを見つける仕組み（TypeScriptのコンパイラなど）</li>
<li class="code-line" data-line="532">
<strong>variant</strong>・・・ 直和型を構成する、一つひとつの形（たとえば、<code>type Status = "success" | "error" | "pending";</code>では <code>success</code>・<code>error</code>といった1つ1つの値が variant と呼ばれる）</li>
<li class="code-line" data-line="533">
<strong>直和型</strong>・・・ いくつかの形のうち、どれか一つを取る値を表す型。TypeScriptのユニオン型（<code>type FooBar = 'foo' | 'bar'</code> は foo か bar のいずれか1つの値となる）</li>
</ul>
</div></aside>

<a id="%E3%83%AB%E3%83%BC%E3%83%AB%EF%BC%9A%E4%B8%8D%E6%AD%A3%E3%81%AA%E7%8A%B6%E6%85%8B%E3%82%92%E3%80%81%E5%9E%8B%E3%81%AE%E5%AE%9A%E7%BE%A9%E3%81%AE%E6%99%82%E7%82%B9%E3%81%A7%E6%9B%B8%E3%81%91%E3%81%AA%E3%81%8F%E3%81%99%E3%82%8B"></a>


### ルール：不正な状態を、型の定義の時点で書けなくする

主なパターンは次のとおりです。

<a id="%E3%81%82%E3%82%8A%E3%81%88%E3%81%AA%E3%81%84%E7%8A%B6%E6%85%8B%E3%82%92%E6%9B%B8%E3%81%91%E3%81%AA%E3%81%8F%E3%81%99%E3%82%8B"></a>


#### ありえない状態を書けなくする

タスクの型を `{ completed: boolean; completedAt?: Date }` にすると、「完了したのに完了日時がない」という意味のない組み合わせも書けてしまいます。

そこでエージェントは、`{ kind: "open" } | { kind: "done"; at: Date }` のような直和型にします。直和型なら、「完了」のときは必ず日時を持つ形しか書けません。

組み合わせが正しいかを後から確かめるより、<strong>ありえない組み合わせを最初から書けなくするほうが確実</strong>だからです。

<a id="%E6%84%8F%E5%91%B3%E3%81%AE%E9%81%95%E3%81%86%E5%80%A4%E3%81%AB%E5%8D%B0%E3%82%92%E4%BB%98%E3%81%91%E3%82%8B"></a>


#### 意味の違う値に印を付ける

エージェントは、`UserId` と `OrderId` をブランド型にして、中身がどちらも文字列でも、互いに取り替えて使えないようにします。

<aside class="msg message"><span class="msg-symbol">!</span><div class="msg-content">
<p class="code-line" data-line="553"><strong>ブランド型</strong>・・・ 文字列や数値のような基本的な値（プリミティブ）に、型の印を付けたもの（以下のコード例の UserId や OrderId がブランド型）</p>
</div></aside>

たとえば、ユーザーIDを渡すべき `getUser()` に注文IDを渡したら、コンパイルでエラーになるようにします。取り替えられると、意味の違う値を取り違えてもコンパイルが通ってしまうからです。

```
type UserId = string & { readonly __brand: "UserId" };
type OrderId = string & { readonly __brand: "OrderId" };
type User = { id: UserId; name: string };

declare function getUser(id: UserId): Promise<User>;
declare const orderId: OrderId;

// 中身はどちらも文字列だが、OrderId を渡すとコンパイルでエラーになる
await getUser(orderId);
```

<a id="%E5%9E%8B%E3%82%B7%E3%82%B9%E3%83%86%E3%83%A0%E3%81%AB%E5%98%98%E3%82%92%E3%81%A4%E3%81%8B%E3%81%AA%E3%81%84"></a>


#### 型システムに嘘をつかない

エージェントは、キャストやアサーションで、型の検査をすり抜けません。すり抜けた箇所は、実行中に落ちる危険を抱えたままになるからです。

<aside class="msg message"><span class="msg-symbol">!</span><div class="msg-content">
<ul class="code-line" data-line="575">
<li class="code-line" data-line="575">
<strong>キャスト</strong>・・・ 値の型を強制的に別の型とみなさせる書き方（たとえば、<code>value as unknown as User</code> のように、型の検査を通らない変換を強制するなど）</li>
<li class="code-line" data-line="576">
<strong>アサーション</strong>・・・ 「この値は必ずこの型だ」とコンパイラに言い切る書き方（TypeScriptで <code>as</code> 句で <code>as User</code>などとして記述される）</li>
</ul>
</div></aside>

たとえば、APIから受け取った値を確かめずに `as User` と書くと、コンパイルは通ります。  
しかし、実際の応答に `name` の項目が欠けていても、コードは `name` があるものとして読み進めるため、`user.name` を使うところで実行中に落ちます。

コンパイラが証明できない事実は、エージェントが、値を実際に確かめたり、条件分岐で型を絞り込んだりして、自分で証明します。

<a id="%E6%89%B1%E3%81%84%E6%BC%8F%E3%82%8C%E3%81%AE%E7%A2%BA%E8%AA%8D%E3%81%AF%E3%82%B3%E3%83%B3%E3%83%91%E3%82%A4%E3%83%A9%E3%81%AB%E4%BB%BB%E3%81%9B%E3%82%8B"></a>


#### 扱い漏れの確認はコンパイラに任せる

エージェントは、直和型に新しい variant が追加されたとき、それを扱っていない分岐でコンパイルがエラーになるように書きます。

たとえば、タスクの種類に「キャンセル済み」（`canceled`）を追加したとき、表示する文言を決める関数がそれを扱っていなければ、コンパイルがエラーになります。  
そのため、扱い漏れを人が探して回らずに済みます。

```
// タスクの種類に canceled を追加した
type Task = { kind: "open" } | { kind: "done" } | { kind: "canceled" };

// 前：扱っていない種類は、最後の return "" に流れる。コンパイルはエラーにならない
function labelLoose(task: Task): string {
  if (task.kind === "open") return "未完了";
  if (task.kind === "done") return "完了";
  return ""; // canceled のタスクは、文言が空のまま画面に出る
}

// 後：扱っていない種類があると、コンパイルがエラーになる
function label(task: Task): string {
  switch (task.kind) {
    case "open":
      return "未完了";
    case "done":
      return "完了";
    default: {
      // canceled を case で扱っていないので、この行でコンパイルがエラーになる
      const unhandled: never = task;
      return unhandled;
    }
  }
}
```

前の `labelLoose` は、`canceled` を扱い忘れてもコンパイルが通ります。そのため、画面に空の文言が出て初めて、扱い漏れに気づきます。

後の `label` の `never` は、「ここには、どの値も届かないはず」という意味の型です。

すべての種類を `case` で扱っていれば、`default` に届く値はないので、コンパイルは通ります。

一方、`canceled` を扱い忘れると、`canceled` のタスクが `default` に届くため、`never` の変数に代入する行でコンパイルがエラーになります。エラーの出た場所が、`canceled` の `case` を追加すべき場所です。

<a id="%E5%9E%8B%E3%82%92%E5%BC%B7%E3%82%81%E3%82%8B%E3%81%AE%E3%81%AF%E3%80%81%E5%BC%B1%E3%81%99%E3%81%8E%E3%82%8B%E3%81%A8%E5%88%86%E3%81%8B%E3%81%A3%E3%81%9F%E5%A0%B4%E6%89%80%E3%81%A0%E3%81%91%E3%81%AB%E3%81%99%E3%82%8B"></a>


#### 型を強めるのは、弱すぎると分かった場所だけにする

ただし、原則は、型をできるだけ細かく書くことを目的にしていません。原則によれば、型の役目は、データをできるだけ細かく表すことではなく、<strong>その型を使うそれぞれの場所が扱うべきケースを、漏れなく示すこと</strong>です。

そのため、エージェントは、型が弱すぎると分かった場所だけで型を強めます。その目印は、実行時のアサーションや、「起きるはずがない」としてエラーを投げる throw 文です。こうした確認を書いた場所は、型が防げたはずのケースを通してしまっている場所だからです。

たとえば、完了したタスクには必ず日時があるはずなのに、`if (!task.completedAt) throw new Error("起きるはずがない")` と書いている場所は、型が「完了なのに日時がない」値を許してしまっている場所です。

<a id="%E7%99%BA%E7%81%AB%E6%9D%A1%E4%BB%B6-2"></a>


### 発火条件

- 型を設計するとき
- 関数のシグネチャ（受け取る引数と返す値の型）をレビューするとき
- 静的型付き言語（TypeScriptのように、動かす前に型を検査する言語）でコードを書くとき

この原則が挙げる判定の問いの一つは、型を、次にこのコードを触るエージェントへの指示として扱っています。

> "If a new variant is added next month, will the compiler tell the next agent where to add a case?" If no, the match isn't exhaustive.
>
> 「来月新しい variant が追加されたとき、コンパイラは次のエージェントに、ケースを追加する場所を教えるか」。教えないなら、その分岐は網羅的ではない。

網羅的な分岐を書いておけば、コンパイラが次のエージェントに直す場所を教えます。そのため、人間が「新しい状態を追加したら、この3か所も直して」と文章で書いておく必要はありません。

`/typescript-best-practices` は、この原則をTypeScriptの具体的な書き方で示したSkillです（[第29章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/4f9a46)）。

<a id="%E3%80%8Emake-operations-idempotent%E3%80%8F%E3%81%AF%E3%80%81%E6%93%8D%E4%BD%9C%E3%82%92%E4%BD%95%E5%BA%A6%E5%AE%9F%E8%A1%8C%E3%81%97%E3%81%A6%E3%82%82%E5%90%8C%E3%81%98%E7%B5%90%E6%9E%9C%E3%81%AB%E3%81%AA%E3%82%8B%E3%82%88%E3%81%86%E3%81%AB%E4%BD%9C%E3%82%8B"></a>


## 『Make Operations Idempotent』は、操作を何度実行しても同じ結果になるように作る

原則『<strong>Make Operations Idempotent</strong>』は、状態を変える操作を、何回実行しても、途中から実行し直しても、<strong>最後には同じ正しい状態に落ち着く（収束する）ように作る</strong>よう求めます。

<aside class="msg message"><span class="msg-symbol">!</span><div class="msg-content">
<ul class="code-line" data-line="655">
<li class="code-line" data-line="655">
<strong>冪等（idempotent）</strong>・・・ 同じ操作を何度実行しても、1回だけ実行したときと同じ結果になる性質（例：設定値を5にする操作は、何度実行しても値が5のまま）</li>
</ul>
</div></aside>

原則がこれを求めるのは、<strong>操作は途中で止まるものとして作る必要がある</strong>からです。

コマンド、起動や終了などの手順、処理を繰り返すループは、クラッシュ、再起動、再試行によって、途中で止まったり、もう一度実行されたりすることがよくあります。

そのとき、前回の実行が途中で残したデータやファイルによって次の実行の結果が変わると、開発者は、再起動のたびに「なぜ今回は結果が違うのか」を調べることになります。

冪等性を担保して作っておけば、何回実行し直しても結果は同じなので、再起動のたびに調べる必要はありません。

<a id="%E3%83%AB%E3%83%BC%E3%83%AB%EF%BC%9A3%E3%81%A4%E3%81%AE%E5%95%8F%E3%81%84%E3%81%A7%E5%8F%8E%E6%9D%9F%E3%82%92%E7%A2%BA%E3%81%8B%E3%82%81%E3%82%8B"></a>


### ルール：3つの問いで収束を確かめる

エージェントは、操作が冪等かどうかを、次の3つの問いで確かめます。

1. 同じ操作を2回続けて実行したら、結果はどうなるか
2. 前の実行が途中で止まっていたら、次の実行の結果はどうなるか（止まった場所が最初でも、途中でも、終わる直前でも、同じ結果になるか）
3. 何度実行し直しても、最後は同じ状態になる（収束する）か

3つの問いのどれか一つでも、答えが「前回の実行が何を残したかで変わる」になるなら、その操作には<strong>照合（reconciliation）の手順</strong>が必要です。

たとえば、2つ目の問いについて見てみましょう。

1,000行を出力ファイルに書き出す処理で、次の実行が、前回のファイルを残したまま、その末尾に1行目から追加で書き込むケースです。

前回の実行が400行を書いて止まっていれば、ファイルには、前回書いた400行の後ろに、今回書いた1,000行が続きます。前回の400行は、今回の最初の400行と同じ内容なので、同じ行が重複した1,400行のファイルになります。前回の実行が1行も書かずに止まっていれば、ファイルは1,000行です。

このように、前回の実行がどこで止まったかで結果が変わるなら、照合が必要です。

<aside class="msg message"><span class="msg-symbol">!</span><div class="msg-content">
<ul class="code-line" data-line="685">
<li class="code-line" data-line="685">
<strong>照合</strong>・・・ 前の実行が残したものを確かめ、何が残っていても正しい状態へそろえる手順</li>
</ul>
<p class="code-line" data-line="687">たとえば、途中で止まった実行が、1,000行中400行目までしか書かれていない出力ファイルを残していても、<strong>次の実行がまずそのファイルを見つけて消してから書き出しを始めれば</strong>、前回がどこで止まっていても、結果は毎回同じ1,000行のファイルになります。</p>
</div></aside>

<a id="%E7%99%BA%E7%81%AB%E6%9D%A1%E4%BB%B6-3"></a>


### 発火条件

途中で止まったり再試行されたりすることがあるコマンド、起動や終了などの手順、処理を繰り返すループを設計するときです。

<a id="%E3%80%8Emigrate-callers-then-delete-legacy-apis%E3%80%8F%E3%81%AF%E3%80%81%E5%91%BC%E3%81%B3%E5%87%BA%E3%81%97%E5%85%83%E3%82%92%E3%81%99%E3%81%B9%E3%81%A6%E7%A7%BB%E3%81%97%E3%80%81%E3%81%9D%E3%81%AE%E5%A4%89%E6%9B%B4%E3%81%AE%E4%B8%AD%E3%81%A7%E5%8F%A4%E3%81%84api%E3%82%82%E6%B6%88%E3%81%99"></a>


## 『Migrate Callers Then Delete Legacy APIs』は、呼び出し元をすべて移し、その変更の中で古いAPIも消す

原則『<strong>Migrate Callers Then Delete Legacy APIs</strong>』は、新しい内部APIのほうが正しい設計だと決めたときに使います。

エージェントは、互換レイヤーを残さず、呼び出し元をすべて新しいAPIに移し、<strong>その同じ変更の中で古いAPIを消します</strong>。

新旧のAPIを両方残すと、同じことをする呼び出し方が2つになり、片付けが遅れ、コードが増えるばかりで減らないからです。

<aside class="msg message"><span class="msg-symbol">!</span><div class="msg-content">
<p class="code-line" data-line="703"><strong>互換レイヤー</strong>・・・ 古いAPIの呼び出し方を使えるように残しておく層</p>
</div></aside>

poteto氏は[講演](https://x.com/poteto/status/2102050467505430555)（[第4章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/dc9141)）で、推奨される実装方法を一つに絞る必要がある、と述べています。本書では、この原則を、APIの移行で実装方法を一つに戻す手順と読みます。

<a id="%E3%83%AB%E3%83%BC%E3%83%AB%EF%BC%9A%E5%91%BC%E3%81%B3%E5%87%BA%E3%81%97%E5%85%83%E3%82%92%E6%B4%97%E3%81%84%E5%87%BA%E3%81%97%E3%81%A6%E7%A7%BB%E3%81%97%E3%80%81%E5%8F%A4%E3%81%84api%E3%82%92%E3%81%99%E3%81%90%E6%B6%88%E3%81%99"></a>


### ルール：呼び出し元を洗い出して移し、古いAPIをすぐ消す

主なルールは次のとおりです。

<a id="%E5%91%BC%E3%81%B3%E5%87%BA%E3%81%97%E5%85%83%E3%81%8C%E6%AE%8B%E3%81%A3%E3%81%A6%E3%81%84%E3%82%8B%E3%81%93%E3%81%A8%E3%82%92%E3%80%81%E5%8F%A4%E3%81%84api%E3%82%92%E6%AE%8B%E3%81%99%E7%90%86%E7%94%B1%E3%81%AB%E3%81%97%E3%81%AA%E3%81%84"></a>


#### 呼び出し元が残っていることを、古いAPIを残す理由にしない

エージェントは、古いAPIの呼び出し元をすべて洗い出して新しいAPIへ移し、古いAPIをすぐに消します。

たとえば、`getUser(id)` を `fetchUser({ id })` に置き換えるなら、エージェントは、`getUser` を呼んでいる箇所をすべて検索して `fetchUser` に書き換え、同じ一連の変更の中で `getUser` を消します。

新旧の呼び方が並んでいると、読み手はどちらを使うべきか迷い、片付けも後回しになるからです。

<a id="%E4%B8%80%E6%99%82%E7%9A%84%E3%81%AA%E3%81%A4%E3%81%AA%E3%81%8E%E3%81%AE%E5%B1%A4%E3%81%AF%E4%BE%8B%E5%A4%96%E3%81%AB%E3%81%99%E3%82%8B"></a>


#### 一時的なつなぎの層は例外にする

古い呼び方を新しいAPIにつなぐ一時的な層（アダプタ）は、どうしても必要なときだけの例外とし、エージェントは、置くときにいつ消すかの期限を決めます。つなぎの層を当たり前に置くと、コードが増えるばかりで減らなくなるからです。

たとえば、古い `getUser(id)` を消さずに、中身を `return fetchUser({ id });` の1行だけにして残した関数が、アダプタです。

<a id="%E3%83%86%E3%82%B9%E3%83%88%E3%82%92%E6%96%B0%E3%81%97%E3%81%84api%E3%81%AB%E5%90%88%E3%82%8F%E3%81%9B%E3%82%8B"></a>


#### テストを新しいAPIに合わせる

エージェントは、テストを、新しいAPIが約束する挙動を確かめるように直し、古い実装の内部の作りを守るだけのテストは消します。

たとえば、「`fetchUser({ id })` が、そのIDのユーザーを返すか」を確かめるテストは残し、「古い `getUser` が内部で別の関数を何回呼んだか」だけを確かめるテストは消します。

古い作りを守るテストが残っていると、コードは、消したはずの古い実装の内部の作りに合わせ続けることになるからです。

<a id="%E7%99%BA%E7%81%AB%E6%9D%A1%E4%BB%B6-4"></a>


### 発火条件

古い呼び出し元が残っている状態で、新しい内部APIを導入するときです。

<strong>外部のユーザーがいる公開API（外部API）には、そのままでは、この原則は当てはまりません</strong>。この原則には、次の3つの前提があるからです。

1. 古いAPIを使っている外部のユーザーがいない
2. 古いAPIを消して動かなくなる呼び出し元を、プロジェクトの中で一度にまとめて直しきれる
3. 新しいAPIを入れる目的が、コードを単純にすることやリファクタリングである

<a id="%E3%80%8Eseparate-before-serializing-shared-state%E3%80%8F%E3%81%AF%E3%80%81%E6%9B%B8%E3%81%8D%E8%BE%BC%E3%81%BF%E5%85%88%E3%81%AE%E5%85%B1%E6%9C%89%E3%82%92%E3%81%AA%E3%81%8F%E3%81%99%E3%81%AE%E3%81%8C%E5%85%88%E3%81%A7%E3%80%81%E3%83%AD%E3%83%83%E3%82%AF%E3%81%AF%E6%9C%80%E5%BE%8C%E3%81%AE%E6%89%8B%E6%AE%B5"></a>


## 『Separate Before Serializing Shared State』は、書き込み先の共有をなくすのが先で、ロックは最後の手段

原則『<strong>Separate Before Serializing Shared State</strong>』は、複数の主体（エージェントやWorkerなど）が同じ書き込み先を共有するかもしれない場面で使います。

エージェントは、ロックを追加する前に、<strong>主体どうしが本当に同じ書き込み先を必要としているか</strong>を考え、必要でなければ、書き込み先を主体ごとに分けて共有をなくします。並行した書き込みが生む競合状態は、たまにしか起きず再現しにくいため、原因の調査に時間がかかるからです。

### ロックは共有をなくさないので、書き込みの直列化は最後の手段にする

この原則は、<strong>書き込みの直列化を、書き込み先を分けられないときの最後の手段としています</strong>。

最後の手段にしているのは、ロックが共有そのものをなくすわけではないからです。  
書き込み先を分ければ、同じ場所に書く主体がいなくなるので、競合状態はそもそも起きません。

一方、ロックを入れても、書き込み先は共有されたままです。すべての主体が、書き込むたびに必ずロックを取らなければならず、ロックを取らずに書き込む処理が1つでも残れば、競合状態がまた起きます。

また、ロックを持ったままの主体が途中で止まると、ロックが外れず、ほかの主体がいつまでも書き込めなくなることもあります。

そのため、<strong>原則は、「ロックが必要だ」と思ったら、すぐにロックを入れるのではなく、まず本当に書き込み先を分けられないのかを見直すよう求めます</strong>。

<a id="%E5%88%86%E3%81%91%E3%82%89%E3%82%8C%E3%81%AA%E3%81%84%E3%81%A8%E3%81%8D%E3%82%82%E3%80%81%E9%A0%86%E7%95%AA%E3%81%AF%E6%8C%87%E7%A4%BA%E3%81%A7%E3%81%AF%E3%81%AA%E3%81%8F%E4%BB%95%E7%B5%84%E3%81%BF%E3%81%A7%E5%AE%88%E3%82%89%E3%81%9B%E3%82%8B"></a>


### 分けられないときも、順番は指示ではなく仕組みで守らせる

<strong>書き込み先を本当に分けられないときも、原則は、順番を守らせる方法を人への指示に頼らず、ロックなどの仕組みで守らせるよう求めます</strong>。

この原則の最初の段落は、次の一文で終わります。

> Instructions and conventions are not concurrency control.
>
> 指示や慣習は並行性の制御ではない。

エージェントに当てはめると、人間が「同じファイルを触らないように」と依頼に書いても、それはエージェントどうしの並行した書き込みを防ぐ仕組みにはなりません。

<a id="%E3%83%AB%E3%83%BC%E3%83%AB%EF%BC%9A%E3%83%AD%E3%83%83%E3%82%AF%E3%81%AE%E5%89%8D%E3%81%AB%E6%9B%B8%E3%81%8D%E8%BE%BC%E3%81%BF%E5%85%88%E3%82%92%E5%88%86%E3%81%91%E3%82%8B"></a>


### ルール：ロックの前に書き込み先を分ける

手順は3つです。

<a id="1.-%E8%A4%87%E6%95%B0%E3%81%AE%E4%B8%BB%E4%BD%93%E3%81%8C%E6%9B%B8%E3%81%8D%E6%8F%9B%E3%81%88%E3%82%8B%E3%80%81%E5%85%B1%E6%9C%89%E3%81%AE%E5%A0%B4%E6%89%80%E3%82%92%E8%A6%8B%E3%81%A4%E3%81%91%E3%82%8B"></a>


#### 1. 複数の主体が書き換える、共有の場所を見つける

複数の主体が読み書きするファイルや、複数の主体がpushするブランチなどを見つけます。

<a id="2.-%E6%9B%B8%E3%81%8D%E8%BE%BC%E3%81%BF%E5%85%88%E3%81%AE%E5%85%B1%E6%9C%89%E3%82%92%E3%81%AA%E3%81%8F%E3%81%99"></a>


#### 2. 書き込み先の共有をなくす

エージェントは、書き込み先の共有をなくすことを、基本の対応とします。

まず、主体たちが一つの正式なデータを必要としているのか、それぞれ別々の事実を書き出しているだけなのかを考えます。

そのうえで、各主体に、自分だけが書き込むファイル、キー、ブランチを持たせ、結果は読むときや報告するときにまとめます。

たとえば、2つのWorkerが一つの `state.json` にそれぞれの項目を書くなら、書き込み先を共有しています。`indexer-state.json` と `metrics-state.json` に分ければ、共有ではなくなります。

書き込み先を分ける前と後を図にすると、次のようになります。

```
分ける前（書き込み先を共有している）
WorkerA ─┐
           ├─→ state.json
WorkerB ─┘

分けた後（書き込み先が主体ごとに分かれている）
WorkerA ──→ indexer-state.json
WorkerB ──→ metrics-state.json
```

<a id="3.-%E5%88%86%E3%81%91%E3%82%89%E3%82%8C%E3%81%AA%E3%81%84%E3%81%A8%E3%81%8D%E3%81%A0%E3%81%91%E3%80%81%E6%9B%B8%E3%81%8D%E8%BE%BC%E3%81%BF%E3%82%92%E7%9B%B4%E5%88%97%E5%8C%96%E3%81%99%E3%82%8B"></a>


#### 3. 分けられないときだけ、書き込みを直列化する

書き込み先を一つにしなければ正しく動かないときだけ、書き込みを一つずつ順番に行わせる仕組み（直列化）を入れます。

たとえば、在庫の残り数や座席の予約のように、すべての主体が同じ一つの値を読み書きしなければ正しくならないデータなどが該当します。

原則が挙げる仕組みは、次の4つです。

- <strong>ロックファイル</strong>・・・ 書き込む前に「書き込み中」を示すファイルを作り、書き終えたら消します。ほかの主体は、そのファイルがある間は書き込まずに待ちます。
- <strong>段階を分けて順番に実行する</strong>・・・ 書き込みを段階に分け、前の段階が終わってから次の段階を始めます（例：Aが書き終えてから、Bが書く）。
- <strong>書き込みを一つの主体だけに任せる</strong>・・・ 書き込める主体を1つだけにし、ほかの主体は、その主体に「この値を書いて」と頼みます。
- <strong>アトミックな比較交換</strong>・・・ 「値がまだ10なら11にする」のように、読んだときから値が変わっていないときだけ書き換えます。変わっていたら書き換えず、読み直してやり直します。値の確認と書き換えは、途中でほかの処理に割り込まれない一つの操作（アトミックな操作）として行います。

アトミックな比較交換を、先のカウンタの例に当てはめると、次のようになります。

並行して動く複数の主体が、同じファイル、ブランチ、キー、状態を持つオブジェクトに書き込むかもしれないときです。

## まとめ

- 『<strong>Model the Domain</strong>』は、散らばった分岐と真偽値を、状態機械や参照表にまとめます。エージェントは、コードを書くたびにこの原則を適用します。
- 『<strong>Boundary Discipline</strong>』は、検証を境界に集め、境界の内側のコードでは型を信じます。
- 『<strong>Type System Discipline</strong>』は、ありえない状態をコンパイルの時点で作れなくします。
- 『<strong>Make Operations Idempotent</strong>』は、3つの問いを使って、再試行や再起動があっても同じ最終状態に収束する操作を作るよう求めます。
- 『<strong>Migrate Callers Then Delete Legacy APIs</strong>』は、呼び出し元の移行と古いAPIの削除を同じ一連の変更で済ませます。本書では、これを、推奨される実装方法を一つに保つ原則だと読みます。
- 『<strong>Separate Before Serializing Shared State</strong>』は、ロックで直列化（書き込みを一つずつ順番に行わせること）する前に、書き込み先の共有そのものをなくします。
- 本書では、6件はどれも、構造そのものをエージェントへの説明書にする原則だと読みます。
