エージェントに仕事を任せるとき、信頼すべきなのはエージェントの報告ではなく、<strong>エージェントが作った成果物</strong>です。

これは、poteto氏が[講演](https://x.com/poteto/status/2102050467505430555)の最初のテーマ「信頼」で示した考えです。

この章では、成果物を信頼するとはどういうことか、そしてpstackがそれをどう形にしているかを解説します。

<a id="%E3%81%93%E3%81%AE%E7%AB%A0%E3%81%AE%E6%A7%8B%E6%88%90"></a>


## この章の構成

この章の構成は次のとおりです。

- なぜ報告ではなく成果物を信頼するのか
- 成果物を確かめるとは、何をどう確かめることなのか
- 返答の何を見れば、任せてよいと判断できるのか
- 安心して任せられる状態に、どう近づけばよいのか
- まとめ：信頼の置き場所を、報告から成果物へ移す

## なぜ報告ではなく成果物を信頼するのか

成果物を信頼するのは、<strong>報告は正しさの証明にならないから</strong>です。

エージェントの「直しました」「動くはずです」は、エージェントがそう判断した、という情報でしかありません。判断の材料がテストの合格なのか、コードを読んだ印象なのか、実際に動かした結果なのかは、報告だけでは分かりません。  
人間が正しさを確かめるには、結局、自分で差分を読み、アプリを触るしかなくなります。

この状態のまま仕事を増やすと、確かめていない変更が増えるだけです。講演でも、検証できないまま処理量だけを増やせば、<strong>増えるのは成果ではなく不具合</strong>だと述べられています。人間が隣で見張っている間しか品質を保てないなら、それは任せたことにはなりません。

反対に、成果物を確かめられる状態になっていれば、人間は報告を信じる必要も、自分で全部を確かめ直す必要もなくなります。

pstackではこれを、検証機構（仕組み）として提供しています。poteto氏は『The Complete Guide to pstack』[Part 1](https://x.com/poteto/status/2094457600259842065)で、検証（verification）を「<strong>エージェントが自分の仕事を確かめられること</strong>」と定義しています。

<a id="%E6%88%90%E6%9E%9C%E7%89%A9%E3%82%92%E7%A2%BA%E3%81%8B%E3%82%81%E3%82%8B%E3%81%A8%E3%81%AF%E3%80%81%E4%BD%95%E3%82%92%E3%81%A9%E3%81%86%E7%A2%BA%E3%81%8B%E3%82%81%E3%82%8B%E3%81%93%E3%81%A8%E3%81%AA%E3%81%AE%E3%81%8B"></a>


## 成果物を確かめるとは、何をどう確かめることなのか

成果物を確かめるとは、<strong>実物を、エージェント自身が、証拠が残る形で確かめること</strong>です。  
これを具体的に言い換えると、次の3つの条件になります。

1. <strong>実物を相手にする</strong>・・・ ビルドの成否やテストの件数ではなく、動いているアプリ、実際に書き込まれた値、実際に出力されたファイルを確かめる
2. <strong>エージェント自身が実行する</strong>・・・ 人間が手でアプリを触るのではなく、エージェントが操作し、観察する
3. <strong>証拠が残る</strong>・・・ スクリーンショット、動画、トレース、コマンドの出力など、あとから人間が見て判断できるものが残る

pstackのファイルでどう支えられているか、条件ごとに見ていきます。

<a id="%E5%AE%9F%E7%89%A9%E3%82%92%E7%9B%B8%E6%89%8B%E3%81%AB%E3%81%99%E3%82%8B"></a>


### 実物を相手にする

1つ目の条件は、原則『[<strong>Prove It Works</strong>](https://github.com/cursor/plugins/blob/main/pstack/skills/principle-prove-it-works/SKILL.md)』が定めています。冒頭は次の一文です。

> Verify every task output by checking the real thing directly. Do not infer from proxies, self-reports, or "it compiles."
>
> すべての作業結果を、実物を直接確かめて検証する。代わりの指標、自己申告、「コンパイルが通った」から推測しない。

この一文は、ビルドやテストを禁じてはいません。禁じているのは、「コンパイルが通った」ことを、動いている証拠として扱うことです。ビルドやテストに加えて、実物を動かして確かめる必要があります。

`SKILL.md` の `description` は、確かめ方の例として、以下の3つを挙げています。

1. 機能を実際に動かす
2. 実際の値を読む
3. 差分を見る

また、この原則は、避けるべき間接的な確かめ方の例として、キャッシュされたスクリーンショットを挙げています。スクリーンショットは成果物に見えますが、今回の変更を反映した画面かどうかが分からなければ、検証の根拠としては弱いということです。ここから、成果物を見るときは<strong>その成果物が今回の変更のあとに作られたものか</strong>まで確かめるのがよい、と読み取ることができます。

同じ考えは、エージェントがサブエージェントに仕事を任せる場面にも当てはめられています。[`/poteto-mode`](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/SKILL.md) では、主エージェントがサブエージェントの報告をそのまま渡さず、差分を見てから返答するので、<strong>人間が受け取る返答は、その時点ですでに一度、成果物で確かめられたもの</strong>になります（[第8章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/096f3d)）。

<a id="%E3%82%A8%E3%83%BC%E3%82%B8%E3%82%A7%E3%83%B3%E3%83%88%E8%87%AA%E8%BA%AB%E3%81%8C%E5%AE%9F%E8%A1%8C%E3%81%99%E3%82%8B"></a>


### エージェント自身が実行する

2つ目の条件は、不具合の修正に使う『<strong>Bug fix</strong>』Playbook（[`playbooks/bug-fix.md`](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/playbooks/bug-fix.md)）が支えています。このPlaybookでは、担当エージェントがアプリを操作する道具（Playbookは control系Skill と呼んでいます）を使い、不具合が起きたのと同じ環境で自分で再現し、修正も同じ環境で確かめます（[第11章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/6fcb42)）。

アプリを操作する道具は、pstack本体には含まれていません。ブラウザやElectron（デスクトップアプリを構築するためのフレームワーク）向けの `control-ui` と、CLIやTUI向けの `control-cli` は、別のプラグイン [`cursor-team-kit`](https://github.com/cursor/plugins/tree/main/cursor-team-kit) に入っています。自分のアプリ専用の道具を作る方法は、[第3章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/a88ea5)と[第36章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/7d7081)で扱います。

利用者に再現を頼めるのは、操作の手段が対象に届かない具体的な理由を述べ、しかも手段で行けるところまで操作したあとだけです。

たとえば、ログインの途中で実機の二要素認証が要り、道具ではその先に進めない場合なら、エージェントはそこまで操作したことと、止まった理由を添えて、利用者に再現を頼むことになります。

私は、この限定が大事だと考えます。人間に頼む道を残しつつ、頼むには理由が要る形にしているので、エージェントが手間を理由に確認を人間へ戻しにくくなります。

<a id="%E8%A8%BC%E6%8B%A0%E3%81%8C%E6%AE%8B%E3%82%8B"></a>


### 証拠が残る

3つ目の条件は、『<strong>Prove It Works</strong>』の節『[Script the check when you can](https://github.com/cursor/plugins/blob/main/pstack/skills/principle-prove-it-works/SKILL.md#script-the-check-when-you-can)』が支えています。

> The strongest proof is a deterministic script that re-runs the same comparison, not a one-time eyeball.
>
> 最も強い証拠は、一度きりの目視ではなく、同じ比較を再実行できる決定的なスクリプトである。

この節は、同じ比較を再実行できるスクリプトを作り、その実行結果を人間が見られる形に残すよう勧めています。再実行できるのはスクリプトで、人間が読むのは実行結果です。

証拠をリポジトリにコミットまでするのは、大規模な移植や移行のように、あとから履歴を監査する必要がある場合に限られます。確かめ方をスクリプトにする方法は[第3章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/a88ea5)で扱います。

私が一番見落とされやすいと感じるのは、この3つ目です。1つ目と2つ目の条件を満たしていても、証拠が残らなければ、人間の手元に届くのは「確かめました」という報告だけで、この章の出発点に戻ってしまいます。

実際に検証の仕組みを作るときは、エージェントが確かめられるかだけでなく、<strong>確かめた結果が人間の見られる場所に残るか</strong>まで決めておくのがよいと思います。

<a id="%E8%BF%94%E7%AD%94%E3%81%AE%E4%BD%95%E3%82%92%E8%A6%8B%E3%82%8C%E3%81%B0%E3%80%81%E4%BB%BB%E3%81%9B%E3%81%A6%E3%82%88%E3%81%84%E3%81%A8%E5%88%A4%E6%96%AD%E3%81%A7%E3%81%8D%E3%82%8B%E3%81%AE%E3%81%8B"></a>


## 返答の何を見れば、任せてよいと判断できるのか

返答を見るときは、<strong>「〜しました」という主張のそれぞれに、確かめた証拠が付いているか</strong>を見れば判断できます。

たとえば「不具合を直しました」とだけ書かれた返答は、正しいかどうか判断できません。直す前に不具合が出ていた出力と、直したあとに出なくなった出力が付いていれば、読む人が自分で判断できます。

<a id="pstack%E3%81%AF%E3%80%81%E4%B8%BB%E5%BC%B5%E3%81%94%E3%81%A8%E3%81%AB%E8%A8%BC%E6%8B%A0%E3%81%8B%E3%80%8C%E6%8E%A8%E6%B8%AC%E3%80%8D%E3%81%AE%E3%83%A9%E3%83%99%E3%83%AB%E3%82%92%E6%B1%82%E3%82%81%E3%82%8B"></a>


### pstackは、主張ごとに証拠か「推測」のラベルを求める

pstackでは、作業を始めるときに使う `/poteto-mode`（[`skills/poteto-mode/SKILL.md`](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/SKILL.md)）が、返答の書き方として次のルールを持っています。

> Every claim carries its evidence or its label in the same sentence. Measured, inferred, or guess.
>
> すべての主張は、同じ文の中に証拠か、種類のラベルを持つ。測定したのか、推論したのか、推測なのか。

エージェントは、証拠があれば証拠を付け、証拠がなければ「推論です」「推測です」と正直に書きます。pstackに同梱されているガイドの検証のページ（[`docs/guide/06-verify-and-ship.md`](https://github.com/cursor/plugins/blob/main/pstack/docs/guide/06-verify-and-ship.md)）も、同じ考えで返答の良し悪しを見分けています。

> If a check couldn't run, a good reply says "inconclusive", and you should treat a confident reply without evidence as a red flag.
>
> 確認を実行できなかったなら、良い返答は「結論が出ない」と言う。証拠のない自信満々の返答は、危険信号として扱うべきだ。

たとえば、テストを実行する環境がなかったのに「修正しました、問題ありません」と返ってきたら、それは危険信号です。

### 「テストが通りました」だけでは、不具合が直ったとは判断できない

間違えやすいのは、「テストが通りました」を右の列に入れてしまうことです。  
『<strong>Bug fix</strong>』Playbookの「修正を確かめる手順（手順4）」も、単体テストに合格しただけでは不具合が直ったとは判断できないとしています。テストで用意した条件で処理が動いても、報告された不具合が起きた操作で直ったかは、同じ操作を再現して確かめる必要があります。

<a id="%E3%83%86%E3%82%B9%E3%83%88%E3%81%8C%E6%8C%AF%E3%82%8B%E8%88%9E%E3%81%84%E3%82%92%E7%A2%BA%E3%81%8B%E3%82%81%E3%81%A6%E3%81%84%E3%82%8B%E3%81%8B%E3%81%AF%E3%80%81%E9%96%A2%E6%95%B0%E3%81%8C-undefined-%E3%82%92%E8%BF%94%E3%81%97%E3%81%A6%E3%82%82%E9%80%9A%E3%82%8B%E3%81%8B%E3%81%A7%E7%82%B9%E6%A4%9C%E3%81%99%E3%82%8B"></a>


### テストが振る舞いを確かめているかは、関数が `undefined` を返しても通るかで点検する

テストが<strong>コードの振る舞い</strong>、つまり、コードを使う人が実際に受け取る結果を確かめているかどうかは、原則『[<strong>Test Behavior, Not Implementation</strong>](https://github.com/cursor/plugins/blob/main/pstack/skills/principle-test-behavior-not-implementation/SKILL.md)』で確かめられます。

この原則は、<strong>テストとは、コードを使う人と同じ方法でコードを呼び出し、その人が受け取る結果を具体的な期待値と比べるもの</strong>だとしています。テストが実際にその結果を見ているかは、次の問いで点検されます。

> The check: before you keep a test, ask whether it would still pass if every function it imports returned `undefined`. If yes, it observes no behavior and cannot fail for a defect.
>
> 確認：テストを残す前に、テストが読み込む関数がすべて `undefined` を返しても、そのテストがまだ通るかを問う。通るなら、そのテストは何の振る舞いも観察しておらず、欠陥があっても落ちることがない。

たとえば、関数が呼ばれたかどうかだけを確かめるテストは、関数が `undefined` を返しても通ります。この原則は、こうしたテストを書き直すか消すよう求めています。

ただし、この問いに合格しても、分かるのは「コードが返す結果を確かめているテストだ」ということだけです。不具合がないことの証明にはなりません。

<a id="%E3%80%8Ebug-fix%E3%80%8Fplaybook%E3%81%AF%E3%80%81%E5%A4%B1%E6%95%97%E6%99%82%E3%81%A8%E6%88%90%E5%8A%9F%E6%99%82%E3%81%AE%E5%87%BA%E5%8A%9B%E3%82%92%E8%BF%94%E7%AD%94%E3%81%AB%E4%B8%A6%E3%81%B9%E3%81%95%E3%81%9B%E3%82%8B"></a>


### 『<strong>Bug fix</strong>』Playbookは、失敗時と成功時の出力を返答に並べさせる

最後に、返答に何が残るかを、不具合を直す『<strong>Bug fix</strong>』Playbookで確かめておきます。

同Playbookは、返答に書く内容を次のように定めています。ここでいう「再現」は、[前の節](#%E3%82%A8%E3%83%BC%E3%82%B8%E3%82%A7%E3%83%B3%E3%83%88%E8%87%AA%E8%BA%AB%E3%81%8C%E5%AE%9F%E8%A1%8C%E3%81%99%E3%82%8B)で見たとおり、不具合が起きる操作を実際に行い、同じ不具合が起きることを確認する作業です。

> <strong>Reply:</strong> what was broken, root cause, fix, how you verified. Paste failing-then-passing repro output verbatim.
>
> 返答：何が壊れていたか、根本原因、修正内容、どう確かめたか。再現が失敗していたときの出力と、通るようになったときの出力を、そのまま貼る。

<strong>不具合が出ていたときの出力と、出なくなったときの出力が、返答に並びます</strong>。

1つ目の「完了の条件」は、同梱ガイドの検証のページ（[`docs/guide/06-verify-and-ship.md`](https://github.com/cursor/plugins/blob/main/pstack/docs/guide/06-verify-and-ship.md)）が、『State the finish condition up front』で扱っています。

> Put what done means in the first prompt, in whatever words fit:
>
> 何をもって終わりとするかを、最初の依頼に、合う言葉で書く。

例として挙がっているのは次の依頼です。

```
/poteto-mode add json output to this command. text output stays byte-identical, the json parses, both run against the sample project. show me the evidence.
// このコマンドにJSON出力を加えて。テキスト出力は1バイトも変えない。JSONはパースできる。どちらもサンプルプロジェクトで実行する。証拠を見せて。
```

ガイドは、こう書くことで、<strong>エージェントは、満たしたかを感覚で決めるしかない目標ではなく、実行して確かめられる3つの確認を持つ</strong>ことになる、と説明しています。

完了の条件を書くと、2つ目以降の確認項目も一緒に決まります。「テキスト出力は1バイトも変えない」と書けば、変更前後の出力を比べる手順が要ります。「サンプルプロジェクトで実行する」と書けば、エージェントがそのプロジェクトを動かせる必要があります。

完了の条件を、実行して合否が出る形で書けないときは、仕様が決まっているか、合否を判定する手段があるかを見直すきっかけになります。

表の右の列にある仕組みの多くは、依頼文だけでは用意できません。アプリを動かす道具、証拠を残す手順、人間が席を外しても回る仕組みが要ります。これが[第3章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/a88ea5)以降のテーマです。

## まとめ：信頼の置き場所を、報告から成果物へ移す

- <strong>なぜ報告ではなく成果物を信頼するのか</strong>・・・ 報告は正しさの証明にならず、見張っている間しか品質を保てない状態では任せたことにならないからです。
- <strong>成果物を確かめるとは何か</strong>・・・ 実物を、エージェント自身が、証拠が残る形で確かめることです。pstackでは、原則『<strong>Prove It Works</strong>』、`/poteto-mode`、『<strong>Bug fix</strong>』Playbookがこの条件を支えています。見落とされやすいのは、証拠が残ることです。
- <strong>返答の何を見るか</strong>・・・ 「〜しました」という主張のそれぞれに、確かめた証拠が付いているかを見ます。テストの合格は、そのテストがコードの振る舞いを確かめているときの判断材料の一つにすぎず、不具合がないことの証明にはなりません。
- <strong>どう近づくか</strong>・・・ 5つの確認項目で足りないところを見つけ、それを一つずつ仕組みに移します。

『<strong>Prove It Works</strong>』をはじめとするVerificationグループの原則は、[第19章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/1fb019)で詳しく扱います。

信頼の対象がはっきりしたら、次は信頼を増やす方法です。一度だけ成果物を確かめても、次の変更で同じ確認ができなければ、信頼は積み上がりません。[第3章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/a88ea5)では、信頼を高める3つの方法と、訂正した教訓を仕組みに残す方法を解説します。
