この章では、次の4つのPlaybookを扱います。

1. [Feature](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/playbooks/feature.md)
2. [Refactoring](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/playbooks/refactoring.md)
3. [Prototype](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/playbooks/prototype.md)
4. [Visual parity](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/playbooks/visual-parity.md)

4つとも、コードに手を入れるPlaybookです。違いは、振る舞いの扱い方です。振る舞いとは、コマンドの出力や画面の表示のように、ユーザーが実際に受け取る結果のことです。

扱い方の違いは次のとおりです。

- 振る舞いを追加するか、変える
- 振る舞いを変えずに、構造だけを直す
- 振る舞いを試して設計を決め、コードは捨てる
- 見た目をピクセル単位でそろえる

どのPlaybookを使うときも、<strong>依頼には何を変えてはいけないかを書きます</strong>。同梱ガイドの実装のページ（[`docs/guide/05-build-and-clean.md`](https://github.com/cursor/plugins/blob/main/pstack/docs/guide/05-build-and-clean.md)）も、Featureの依頼には、振る舞いと、変えてはいけないものを書くよう勧めています。

この章では、4つの違い、それぞれの使い方、依頼の書き方を順に解説します。

<a id="%E3%81%93%E3%81%AE%E7%AB%A0%E3%81%AE%E6%A7%8B%E6%88%90"></a>


## この章の構成

この章の構成は次のとおりです。

- 4つのPlaybookは、振る舞いを追加するか、保つか、試すか、見た目をそろえるかで選ぶ
- 『Feature』は、データの形を決めてから、実装を任せてレビューする
- 『Refactoring』は、今の振る舞いを固定してから構造を動かす
- 『Prototype』は、捨てる前提のコードで設計を低コストで決める
- 『Visual parity』は、基準の見た目（ベースライン）を仕様として画像差分ゼロを目指す
- 依頼には「何を変えてはいけないか」を書く
- まとめ

## 4つのPlaybookは、振る舞いを追加するか、保つか、試すか、見た目をそろえるかで選ぶ

4つのPlaybookは、<strong>振る舞いをどう扱うか</strong>で分かれます。何を変えてはいけないか、何に責任を持つか、どう検証するかも、それに合わせて変わります。

4つの間には受け渡しもあります。『<strong>Prototype</strong>』は比較して決めた設計案を『<strong>Feature</strong>』に渡します。『<strong>Refactoring</strong>』は、途中で見つかった足りない機能や本物のバグを別の作業に切り出し、先に構造の変更を出します。設計ごと作り直す場合は、作り直しだと明示して『<strong>Feature</strong>』へ回します。

<a id="%E3%80%8Efeature%E3%80%8F%E3%81%AF%E3%80%81%E3%83%87%E3%83%BC%E3%82%BF%E3%81%AE%E5%BD%A2%E3%82%92%E6%B1%BA%E3%82%81%E3%81%A6%E3%81%8B%E3%82%89%E3%80%81%E5%AE%9F%E8%A3%85%E3%82%92%E4%BB%BB%E3%81%9B%E3%81%A6%E3%83%AC%E3%83%93%E3%83%A5%E3%83%BC%E3%81%99%E3%82%8B"></a>


## 『Feature』は、データの形を決めてから、実装を任せてレビューする

『<strong>Feature</strong>』は、新しい機能で扱うデータの形（データの項目や型）を先に決め、それをもとに機能を実装するPlaybookです。<strong>主エージェントは設計に責任を持ち</strong>、コードを書く作業は別のエージェントに任せます。

要点は2つです。

- <strong>書き始める前にデータの形を決める</strong>・・・ 原則『[<strong>Model the Domain</strong>](https://github.com/cursor/plugins/blob/main/pstack/skills/principle-model-the-domain/SKILL.md)』（[第18章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/cdc49b)）は、構造は書くときに選べば低コストで済むが、後から取り戻そうとするとリファクタリングに見えて先送りされがちだ、と説明しています。
- <strong>コードを書く人と、その差分をレビューする人を分ける</strong>・・・ コードを書く作業はサブエージェントに任せ、主エージェントはその差分をレビューします（手順4）。

<a id="%E6%89%8B%E9%A0%86%EF%BC%9A%E8%A8%AD%E8%A8%88%E3%82%92%E6%B1%BA%E3%82%81%E3%80%81%E5%AE%9F%E8%A3%85%E3%82%92%E4%BB%BB%E3%81%9B%E3%80%81%E6%A4%9C%E8%A8%BC%E3%81%97%E3%81%A6%E3%81%8B%E3%82%89pr%E3%82%92%E4%BD%9C%E3%82%8B"></a>


### 手順：設計を決め、実装を任せ、検証してからPRを作る

手順は8つです。

1. 影響するサブシステムに `/how`（コードの仕組みを説明するSkill、[第22章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/788746)）をかける
2. `/architect`（コードより先に設計を描くSkill、[第24章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/2ad346)）で、型やモジュール構成の案を並列に探る
3. スループット・チェックポイントを書く（以下の表を参照）
4. コードを書く作業をサブエージェントに任せる
5. 変更が現れる環境（画面ならブラウザ、コマンドならCLI）で検証する
6. 小さく順序立ったコミットにrebaseする（原則『[<strong>Sequence Work into Verifiable Units</strong>](https://github.com/cursor/plugins/blob/main/pstack/skills/principle-sequence-verifiable-units/SKILL.md)』、[第19章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/1fb019)）
7. 設計に異論があるなら、複数のモデルのレビュアーが変更を問いただす `/interrogate`（[第27章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/997880)）をかけてから進める
8. PRを作る手順を定めた『[<strong>Opening a PR</strong>](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/playbooks/opening-a-pr.md)』を実行する（[第14章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/45a56e)）

<aside class="msg message"><span class="msg-symbol">!</span><div class="msg-content">
<p class="code-line" data-line="67"><strong>rebase</strong>・・・ Gitの操作で、コミットを別の土台の上に積み直すこと。コミットの順序を並べ替えたり、複数のコミットを1つにまとめたりするのにも使う</p>
</div></aside>

手順3のスループット・チェックポイントは、<strong>作業を「どう並列に分けられるか」を検討した結果を、TODOリストに記録する際の4つの項目</strong>です。

4項目のうち、今回の作業に当てはまらないものも削らず、`n/a: <理由>` と理由を書きます。これで、検討した結果不要としたのか、項目を見落としたのかを区別できます。

手順4の実装では、ファイルのパス、データの形、成功の基準を指定して、feature用に設定したモデル（[第6章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/33f073)で触れた `/setup-pstack` で変えられます）のサブエージェントに任せます。実装に複数の妥当な形があり得るなら、同じ課題に複数の候補を並列に作らせて良いところを組み合わせる `/arena`（[第24章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/2ad346)）を通します。

<strong>この委任は必須</strong>で、`skip: <理由>` で省くことも、「最小の変更」を求める原則『[<strong>Laziness Protocol</strong>](https://github.com/cursor/plugins/blob/main/pstack/skills/principle-laziness-protocol/SKILL.md)』で覆すこともできません。得たいのは行数の節約ではなく、レビューの分離だからです。

実装を任されたサブエージェントが、さらに別のサブエージェントを起動できない場合は、その実装サブエージェントがコードを書きます。依頼元のエージェントが差分をレビューするため、実装とレビューの担当は分かれたままです。

### 依頼の書き方：振る舞いと、変えてはいけないものを書く

同梱ガイドの例は、次のとおりです。

```
/poteto-mode add a --json flag. text output stays byte-identical. verify both forms.
// --json フラグを足して。テキスト出力はバイト単位で同じまま。両方の形を確かめて。
```

<a id="%E3%80%8Erefactoring%E3%80%8F%E3%81%AF%E3%80%81%E4%BB%8A%E3%81%AE%E6%8C%AF%E3%82%8B%E8%88%9E%E3%81%84%E3%82%92%E5%9B%BA%E5%AE%9A%E3%81%97%E3%81%A6%E3%81%8B%E3%82%89%E6%A7%8B%E9%80%A0%E3%82%92%E5%8B%95%E3%81%8B%E3%81%99"></a>


## 『Refactoring』は、今の振る舞いを固定してから構造を動かす

『<strong>Refactoring</strong>』は、名前の変更、抽出、重複の除去、移動のように、<strong>振る舞いを保ったまま構造だけを変えるPlaybook</strong>です。

主エージェントが責任を持つのは「契約」、つまり今の振る舞いです。構造は変えても、今の振る舞いは変えません。

構造だけでなく設計ごと作り直すことも許容されますが、その場合は作り直しだと明示し『<strong>Feature</strong>』へ回します。

<a id="%E6%89%8B%E9%A0%86%EF%BC%9A%E6%8C%AF%E3%82%8B%E8%88%9E%E3%81%84%E3%82%92%E5%9B%BA%E5%AE%9A%E3%81%97%E3%80%81%E4%B8%8D%E8%A6%81%E3%81%AA%E3%82%B3%E3%83%BC%E3%83%89%E3%82%92%E6%B6%88%E3%81%97%E3%81%A6%E3%81%8B%E3%82%89%E5%8B%95%E3%81%8B%E3%81%97%E3%80%81%E5%90%8C%E7%AD%89%E6%80%A7%E3%82%92%E7%A2%BA%E3%81%8B%E3%82%81%E3%82%8B"></a>


### 手順：振る舞いを固定し、不要なコードを消してから動かし、同等性を確かめる

手順は8つです。

1. 振る舞いの契約を固定する
2. 欠けている構造に名前をつける
3. 目標の形に名前をつける
4. 追加する前に消す
5. 小さな歩幅で動かす
6. 振る舞いが変わっていないことを、本物の成果物で証明する
7. 残す価値があるかを確かめる
8. 小さく順序立ったコミットにrebaseする

ここからは、各手順を1つずつ見ていきます。

<aside class="msg message"><span class="msg-symbol">!</span><div class="msg-content">
<ul class="code-line" data-line="127">
<li class="code-line" data-line="127">
<strong>スナップショットテスト</strong>・・・ 出力を一度ファイルに保存しておき、以降の実行結果をそれと比べて変化を検出するテスト</li>
</ul>
</div></aside>

<a id="1.-%E6%8C%AF%E3%82%8B%E8%88%9E%E3%81%84%E3%81%AE%E5%A5%91%E7%B4%84%E3%82%92%E5%9B%BA%E5%AE%9A%E3%81%99%E3%82%8B"></a>


#### 1. 振る舞いの契約を固定する

構造を動かす前に、今の振る舞いを担保する特性テスト（今の出力をそのまま正解として記録するテスト）、スナップショットテスト、新旧の出力を比べる仕組みなどを書く。型チェックやlintが通るだけでは、振る舞いを固定したことにはならないためである。

<a id="2.-%E6%AC%A0%E3%81%91%E3%81%A6%E3%81%84%E3%82%8B%E6%A7%8B%E9%80%A0%E3%81%AB%E5%90%8D%E5%89%8D%E3%82%92%E3%81%A4%E3%81%91%E3%82%8B"></a>


#### 2. 欠けている構造に名前をつける

この手順は、原則『<strong>Model the Domain</strong>』（[第18章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/cdc49b)）に当たる。

<a id="3.-%E7%9B%AE%E6%A8%99%E3%81%AE%E5%BD%A2%E3%81%AB%E5%90%8D%E5%89%8D%E3%82%92%E3%81%A4%E3%81%91%E3%82%8B"></a>


#### 3. 目標の形に名前をつける

モジュールの分け方、データ型、関数同士の呼び出し関係を決める。目標の形が関数の境界をまたぐなら `/architect` で探る。

<a id="4.-%E8%BF%BD%E5%8A%A0%E3%81%99%E3%82%8B%E5%89%8D%E3%81%AB%E6%B6%88%E3%81%99"></a>


#### 4. 追加する前に消す

デッドコード（使われていないコード）や、呼び出し元が1か所しかない関数（Wrapper）は、その処理を呼び出し元にまとめるなどし、不要なコードを消してから、新しい構成を入れる（原則『[<strong>Subtract Before You Add</strong>](https://github.com/cursor/plugins/blob/main/pstack/skills/principle-subtract-before-you-add/SKILL.md)』）。

<a id="5.-%E5%B0%8F%E3%81%95%E3%81%AA%E6%AD%A9%E5%B9%85%E3%81%A7%E5%8B%95%E3%81%8B%E3%81%99"></a>


#### 5. 小さな歩幅で動かす

一つずつ、手順1で固定したテストや比較が通る状態を保つ。APIの形を変えるなら、APIの呼び出し元をすべて新しいAPIに移し、古いAPIを同じ一連の変更の中で消す（原則『[<strong>Migrate Callers Then Delete Legacy APIs</strong>](https://github.com/cursor/plugins/blob/main/pstack/skills/principle-migrate-callers-then-delete-legacy-apis/SKILL.md)』、[第18章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/cdc49b)）。

<a id="6.-%E6%8C%AF%E3%82%8B%E8%88%9E%E3%81%84%E3%81%8C%E5%A4%89%E3%82%8F%E3%81%A3%E3%81%A6%E3%81%84%E3%81%AA%E3%81%84%E3%81%93%E3%81%A8%E3%82%92%E3%80%81%E6%9C%AC%E7%89%A9%E3%81%AE%E6%88%90%E6%9E%9C%E7%89%A9%E3%81%A7%E8%A8%BC%E6%98%8E%E3%81%99%E3%82%8B"></a>


#### 6. 振る舞いが変わっていないことを、本物の成果物で証明する

コンパイルやbuildが通るだけでは、振る舞いが変わっていないことの証明にならない（原則『[<strong>Prove It Works</strong>](https://github.com/cursor/plugins/blob/main/pstack/skills/principle-prove-it-works/SKILL.md)』）。

<a id="7.-%E6%AE%8B%E3%81%99%E4%BE%A1%E5%80%A4%E3%81%8C%E3%81%82%E3%82%8B%E3%81%8B%E3%82%92%E7%A2%BA%E3%81%8B%E3%82%81%E3%82%8B"></a>


#### 7. 残す価値があるかを確かめる

差分が読み手の負荷を下げていなければ取り消す（原則『[<strong>Minimize Reader Load</strong>](https://github.com/cursor/plugins/blob/main/pstack/skills/principle-minimize-reader-load/SKILL.md)』、[第17章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/a8e80b)）。

<a id="8.-%E5%B0%8F%E3%81%95%E3%81%8F%E9%A0%86%E5%BA%8F%E7%AB%8B%E3%81%A3%E3%81%9F%E3%82%B3%E3%83%9F%E3%83%83%E3%83%88%E3%81%ABrebase%E3%81%99%E3%82%8B"></a>


#### 8. 小さく順序立ったコミットにrebaseする

コードを消す引き算の実装、構造の作り直し、後続のclean upの順にコミットし、『<strong>Opening a PR</strong>』を実行する。

<a id="%E4%BE%9D%E9%A0%BC%E3%81%AE%E6%9B%B8%E3%81%8D%E6%96%B9%EF%BC%9A%E6%A7%8B%E9%80%A0%E3%82%92%E5%8B%95%E3%81%8B%E3%81%99%E5%89%8D%E3%81%AB%E4%BB%8A%E3%81%AE%E5%87%BA%E5%8A%9B%E3%82%92%E8%A8%98%E9%8C%B2%E3%81%95%E3%81%9B%E3%82%8B"></a>


### 依頼の書き方：構造を動かす前に今の出力を記録させる

同梱ガイドの例は、次のとおりです。

```
/poteto-mode move parsing into one module, zero behavior change. record the current output first and prove it's unchanged after.
// パースを1つのモジュールに移して。振る舞いの変化はゼロ。先に今の出力を記録して、後で変わっていないことを証明して。
```

「先に今の出力を記録して」が手順1に、「後で変わっていないことを証明して」が手順6に該当します。

<a id="%E3%80%8Eprototype%E3%80%8F%E3%81%AF%E3%80%81%E6%8D%A8%E3%81%A6%E3%82%8B%E5%89%8D%E6%8F%90%E3%81%AE%E3%82%B3%E3%83%BC%E3%83%89%E3%81%A7%E8%A8%AD%E8%A8%88%E3%82%92%E4%BD%8E%E3%82%B3%E3%82%B9%E3%83%88%E3%81%A7%E6%B1%BA%E3%82%81%E3%82%8B"></a>


## 『Prototype』は、捨てる前提のコードで設計を低コストで決める

『<strong>Prototype</strong>』は、捨てる前提のプロトタイプを作り、<strong>観察した結果で設計の判断を下す</strong>Playbookです。

主エージェントが責任を持つのは設計判断で、コードではありません。本番の実装は『<strong>Feature</strong>』で行います。

捨てる前提なので、原則『Laziness Protocol』の「最小の変更」と、検証の基準の2つが<strong>逆転する唯一のPlaybook</strong>とされています。

磨くより速さを優先し、コードの品質は問わず、頼まれていない案も出します。<strong>検証の基準は「変更が正しい」ことの証明ではなく、「決めたいことを観察する」ことに変わります</strong>。

<a id="%E6%89%8B%E9%A0%86%EF%BC%9A%E4%BD%95%E3%82%92%E6%B1%BA%E3%82%81%E3%82%8B%E3%81%AE%E3%81%8B%E3%82%92%E3%81%AF%E3%81%A3%E3%81%8D%E3%82%8A%E3%81%95%E3%81%9B%E3%81%9F%E3%81%86%E3%81%88%E3%81%A7%E3%80%81%E3%83%97%E3%83%AD%E3%83%88%E3%82%BF%E3%82%A4%E3%83%97%E3%82%92%E4%BD%9C%E3%82%8A%E3%80%81%E6%AF%94%E8%BC%83%E3%81%99%E3%82%8B"></a>


### 手順：何を決めるのかをはっきりさせたうえで、プロトタイプを作り、比較する

手順は6つです。

1. プロトタイプで何を決めるのかをはっきりさせる
2. 方針がまだ決まっていないなら参考例を集める
3. 本番のソースから離れた作業用ディレクトリで作る
4. 代替案は同じ画面で切り替えて比べられるようにする
5. 各案を実際に動かして比べる
6. 比較結果として代替案、トレードオフ、推奨を示す

ここからは、各手順を1つずつ見ていきます。

<a id="1.-%E3%83%97%E3%83%AD%E3%83%88%E3%82%BF%E3%82%A4%E3%83%97%E3%81%A7%E4%BD%95%E3%82%92%E6%B1%BA%E3%82%81%E3%82%8B%E3%81%AE%E3%81%8B%E3%82%92%E3%81%AF%E3%81%A3%E3%81%8D%E3%82%8A%E3%81%95%E3%81%9B%E3%82%8B"></a>


#### 1. プロトタイプで何を決めるのかをはっきりさせる

決めるのは、見た目や操作なら「どのレイアウトにするか」「どの操作方法にするか」「画面の要素をどれくらい詰めて並べるか」、動かして観察すればどれが良いかがわかる選択なら「どの挙動にするか」「どのタイミングにするか」「どの方法にするか」だ。決めることがないならプロトタイプを作らず、『<strong>Feature</strong>』へ回す。

<a id="2.-%E6%96%B9%E9%87%9D%E3%81%8C%E3%81%BE%E3%81%A0%E6%B1%BA%E3%81%BE%E3%81%A3%E3%81%A6%E3%81%84%E3%81%AA%E3%81%84%E3%81%AA%E3%82%89%E5%8F%82%E8%80%83%E4%BE%8B%E3%82%92%E9%9B%86%E3%82%81%E3%82%8B"></a>


#### 2. 方針がまだ決まっていないなら参考例を集める

似た機能や画面の例を利用者に見せ、プロトタイプを作り始める前に、どんな見た目や操作にするか選んでもらう。すでに決まっていれば省略する。

<a id="3.-%E6%9C%AC%E7%95%AA%E3%81%AE%E3%82%BD%E3%83%BC%E3%82%B9%E3%81%8B%E3%82%89%E9%9B%A2%E3%82%8C%E3%81%9F%E4%BD%9C%E6%A5%AD%E7%94%A8%E3%83%87%E3%82%A3%E3%83%AC%E3%82%AF%E3%83%88%E3%83%AA%E3%81%A7%E4%BD%9C%E3%82%8B"></a>


#### 3. 本番のソースから離れた作業用ディレクトリで作る

本番用のフレームワーク、テスト、抽象化は持ち込まず、問いを確かめるための最小限のコードだけ用意する。

<a id="4.-%E4%BB%A3%E6%9B%BF%E6%A1%88%E3%81%AF%E5%90%8C%E3%81%98%E7%94%BB%E9%9D%A2%E3%81%A7%E5%88%87%E3%82%8A%E6%9B%BF%E3%81%88%E3%81%A6%E6%AF%94%E3%81%B9%E3%82%89%E3%82%8C%E3%82%8B%E3%82%88%E3%81%86%E3%81%AB%E3%81%99%E3%82%8B"></a>


#### 4. 代替案は同じ画面で切り替えて比べられるようにする

各案にラベルをつけ、ボタンやキー操作で切り替える（原則『[<strong>Exhaust the Design Space</strong>](https://github.com/cursor/plugins/blob/main/pstack/skills/principle-exhaust-the-design-space/SKILL.md)』、[第17章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/a8e80b)）。

<a id="5.-%E5%90%84%E6%A1%88%E3%82%92%E5%AE%9F%E9%9A%9B%E3%81%AB%E5%8B%95%E3%81%8B%E3%81%97%E3%81%A6%E6%AF%94%E3%81%B9%E3%82%8B"></a>


#### 5. 各案を実際に動かして比べる

画面の見た目ならスクリーンショット、処理時間なら計測値を記録し、手順1ではっきりさせたことを決めるための材料を集める。

<a id="6.-%E6%AF%94%E8%BC%83%E7%B5%90%E6%9E%9C%E3%81%A8%E3%81%97%E3%81%A6%E4%BB%A3%E6%9B%BF%E6%A1%88%E3%80%81%E3%83%88%E3%83%AC%E3%83%BC%E3%83%89%E3%82%AA%E3%83%95%E3%80%81%E6%8E%A8%E5%A5%A8%E3%82%92%E7%A4%BA%E3%81%99"></a>


#### 6. 比較結果として代替案、トレードオフ、推奨を示す

各案の違いと採用した場合の長所・短所を説明し、推奨案を伝える。採用する案が決まったら、その方針を『<strong>Feature</strong>』に引き継ぐ。

<a id="%E4%BE%9D%E9%A0%BC%E3%81%AE%E6%9B%B8%E3%81%8D%E6%96%B9%EF%BC%9A%E3%80%8C%E6%AF%94%E3%81%B9%E3%81%9F%E3%81%84%E3%81%AE%E3%81%A72%E3%81%A4%E4%BD%9C%E3%81%A3%E3%81%A6%E3%80%8D%E3%81%A8%E6%9B%B8%E3%81%8F"></a>


### 依頼の書き方：「比べたいので2つ作って」と書く

pstackの[README](https://github.com/cursor/plugins/blob/main/pstack/README.md)の例は、次のとおりです。

```
/poteto-mode build two prototypes of the markdown renderer so we can compare. spawn an agent for each.
// 比べられるように、markdownレンダラーのプロトタイプを2つ作って。それぞれにエージェントを立てて。
```

「モックを作って」「このレイアウトを試して」のような言い回しも、<strong>このPlaybookへの合図</strong>です。

<a id="%E3%80%8Evisual-parity%E3%80%8F%E3%81%AF%E3%80%81%E5%9F%BA%E6%BA%96%E3%81%AE%E8%A6%8B%E3%81%9F%E7%9B%AE%EF%BC%88%E3%83%99%E3%83%BC%E3%82%B9%E3%83%A9%E3%82%A4%E3%83%B3%EF%BC%89%E3%82%92%E4%BB%95%E6%A7%98%E3%81%A8%E3%81%97%E3%81%A6%E7%94%BB%E5%83%8F%E5%B7%AE%E5%88%86%E3%82%BC%E3%83%AD%E3%82%92%E7%9B%AE%E6%8C%87%E3%81%99"></a>


## 『Visual parity』は、基準の見た目（ベースライン）を仕様として画像差分ゼロを目指す

『<strong>Visual parity</strong>』は、2つの実装を一致させるときや、スタイリングの仕組みを移行するときに、<strong>UIの見た目をピクセル単位で同一に保つPlaybook</strong>です。

ベースラインには手を触れず、同一であることは画像差分で確かめます。

合否は目視ではなく、差分がゼロかどうかで決まります。ただし、ベースラインそのものがおかしく見えたときは、エージェントはベースラインを直さず、止まって利用者に聞きます（手順2）。

<a id="%E6%89%8B%E9%A0%86%EF%BC%9A%E9%83%A8%E5%93%81%E3%81%94%E3%81%A8%E3%81%AB%E7%94%BB%E5%83%8F%E5%B7%AE%E5%88%86%E3%82%BC%E3%83%AD%E3%81%BE%E3%81%A7%E5%9B%9E%E3%81%99"></a>


### 手順：部品ごとに画像差分ゼロまで回す

手順は5つです。

1. 移行の前に、比較基準（ベースライン）を作る
2. 差分を通すための近道を禁じる
3. 部品を1つずつ移す
4. 各部品をベースラインと画像差分で比べる
5. 部品ごと、または安全なまとまりごとに『Opening a PR』を実行する

ここからは、各手順を1つずつ見ていきます。

<aside class="msg message"><span class="msg-symbol">!</span><div class="msg-content">
<ul class="code-line" data-line="252">
<li class="code-line" data-line="252">
<strong>worktree</strong>・・・ Gitの機能で、1つのリポジトリから複数の作業ディレクトリを作り、別々のブランチを同時に扱えるようにするもの</li>
</ul>
</div></aside>

<a id="1.-%E7%A7%BB%E8%A1%8C%E3%81%AE%E5%89%8D%E3%81%AB%E3%80%81%E6%AF%94%E8%BC%83%E5%9F%BA%E6%BA%96%EF%BC%88%E3%83%99%E3%83%BC%E3%82%B9%E3%83%A9%E3%82%A4%E3%83%B3%EF%BC%89%E3%82%92%E4%BD%9C%E3%82%8B"></a>


#### 1. 移行の前に、比較基準（ベースライン）を作る

移行前の部品を、さまざまな状態（通常、ホバー、無効など）で自動的にスクリーンショットする仕組みを作る。このスクリーンショットが、移行後の見た目と比較する基準になる。

<a id="2.-%E5%B7%AE%E5%88%86%E3%82%92%E9%80%9A%E3%81%99%E3%81%9F%E3%82%81%E3%81%AE%E8%BF%91%E9%81%93%E3%82%92%E7%A6%81%E3%81%98%E3%82%8B"></a>


#### 2. 差分を通すための近道を禁じる

ハーネス（手順1のスクリーンショットを撮って比べる仕組み）を変えない、ベースラインを改ざんしない、差分を通すために部品の構造を組み替えない。ベースラインがおかしく見えたら、止まって利用者に聞く。

<a id="3.-%E9%83%A8%E5%93%81%E3%82%921%E3%81%A4%E3%81%9A%E3%81%A4%E7%A7%BB%E3%81%99"></a>


#### 3. 部品を1つずつ移す

部品を1つずつ新しい実装やスタイリング方式に置き換える。worktreeを分けて並列に進め、共有の基本部品は最初に移す。

<a id="4.-%E5%90%84%E9%83%A8%E5%93%81%E3%82%92%E3%83%99%E3%83%BC%E3%82%B9%E3%83%A9%E3%82%A4%E3%83%B3%E3%81%A8%E7%94%BB%E5%83%8F%E5%B7%AE%E5%88%86%E3%81%A7%E6%AF%94%E3%81%B9%E3%82%8B"></a>


#### 4. 各部品をベースラインと画像差分で比べる

比較差分がゼロになるまで `/loop`（エージェントを繰り返し起こし直すCursor組み込みのコマンド、[第15章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/7d7609)）で回す。

<a id="5.-%E9%83%A8%E5%93%81%E3%81%94%E3%81%A8%E3%80%81%E3%81%BE%E3%81%9F%E3%81%AF%E5%AE%89%E5%85%A8%E3%81%AA%E3%81%BE%E3%81%A8%E3%81%BE%E3%82%8A%E3%81%94%E3%81%A8%E3%81%AB%E3%80%8Eopening-a-pr%E3%80%8F%E3%82%92%E5%AE%9F%E8%A1%8C%E3%81%99%E3%82%8B"></a>


#### 5. 部品ごと、または安全なまとまりごとに『Opening a PR』を実行する

<a id="%E4%BE%9D%E9%A0%BC%E3%81%AE%E6%9B%B8%E3%81%8D%E6%96%B9%EF%BC%9A%E3%80%8C2%E6%9E%9A%E7%9B%AE%E3%81%AE%E7%94%BB%E5%83%8F%E3%81%8C%E6%AD%A3%E3%81%97%E3%81%84%E3%80%8D%E3%81%A8%E3%83%99%E3%83%BC%E3%82%B9%E3%83%A9%E3%82%A4%E3%83%B3%E3%82%92%E4%BC%9D%E3%81%88%E3%82%8B"></a>


### 依頼の書き方：「2枚目の画像が正しい」とベースラインを伝える

READMEの例は、次のとおりです。

```
/poteto-mode the row spacing is too tall when this flag is on. the second image is correct. repro and fix until it matches.
// このフラグがオンのとき、行間が高すぎる。2枚目の画像が正しい。再現して、一致するまで直して。
```

「2枚目の画像が正しい」が、<strong>どちらの見た目をベースラインにするか</strong>を伝える一文です。これがなければ、エージェントはどちらに合わせるかを推測するしかありません。

<a id="%E4%BE%9D%E9%A0%BC%E3%81%AB%E3%81%AF%E3%80%8C%E4%BD%95%E3%82%92%E5%A4%89%E3%81%88%E3%81%A6%E3%81%AF%E3%81%84%E3%81%91%E3%81%AA%E3%81%84%E3%81%8B%E3%80%8D%E3%82%92%E6%9B%B8%E3%81%8F"></a>


## 依頼には「何を変えてはいけないか」を書く

4つのどれに頼むときも、<strong>依頼には「何を変えてはいけないか」を書きます</strong>。

<table class="code-line" data-line="288">
<thead class="code-line" data-line="288">
<tr class="code-line" data-line="288">

</tr>

## まとめ

- <strong>4つの分かれ方</strong>・・・ 『<strong>Feature</strong>』は設計、『<strong>Refactoring</strong>』は契約、『<strong>Prototype</strong>』は設計判断、『<strong>Visual parity</strong>』はピクセル単位の同一性に責任を持ちます。
- <strong>Feature</strong>・・・ データの形を決め、スループット・チェックポイントを書き、実装は必ず別のエージェントに任せます。
- <strong>Refactoring</strong>・・・ 今の振る舞いをテストなどで固定し、不要なコードを消してから構造を動かし、本物の成果物で振る舞いが変わっていないことを証明します。
- <strong>Prototype</strong>・・・ 「最小の変更」と検証の基準が逆転します。案を低コストで作って観察で比べ、決まった方向を『<strong>Feature</strong>』に渡します。
- <strong>Visual parity</strong>・・・ ベースラインに手を触れず、部品ごとに画像差分がゼロになるまで回します。
- <strong>依頼の書き方</strong>・・・ 「何を変えてはいけないか」を書くと、それが完了の検査になります。

次の[第13章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/8263c0)では、Skillを書く『[<strong>Authoring or modifying a skill</strong>](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/playbooks/authoring-a-skill.md)』と、変更の効果を確かめる『[<strong>Eval</strong>](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/playbooks/eval.md)』を扱います。
