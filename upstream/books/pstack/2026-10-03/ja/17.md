この章では、次の2つのPlaybookを扱います。

1. [Authoring or modifying a skill](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/playbooks/authoring-a-skill.md)

2つとも、アプリのコードではなく、<strong>エージェントの働き方を決めるSkillについて扱います</strong>。

『Authoring or modifying a skill』は、Skill（`SKILL.md`）を書くときや直すときに、『Eval』は、そのSkillの変更に効果があったかを測定するときに使います。

この章では、2つの分担と、それぞれの使い方を順に解説します。

## 2つのPlaybookは、Skillを書く手順と効果を測る手順を分担する

同梱ガイドの「Make it yours」のページ（[`docs/guide/09-make-it-yours.md`](https://github.com/cursor/plugins/blob/main/pstack/docs/guide/09-make-it-yours.md)）は、Skillについて2つのことを求めています。

- <strong>エージェント向けの文章は、人間向けより基準を高くする</strong>・・・ 役に立たない一文も、将来どこかのエージェントが従う指示になるからです。
- <strong>Skillの編集は、実験としてテストする</strong>・・・ Skillの編集は、将来のすべてのセッションに影響するからです。

書くほうが『<strong>Authoring or modifying a skill</strong>』、効果を測定するほうが『<strong>Eval</strong>』です。

Authoring or modifying a skillの手順には、複数のエージェントを使う指示はありません。  
一方、Evalでの作業に必要なものは次の3つです。

- <strong>候補</strong>・・・ 変更を入れた環境で作業するエージェントです。
- <strong>審査員</strong>・・・ 候補の出力を採点する、候補とは別のエージェントです。
- <strong>手がかりを取り除いた作業環境</strong>・・・ 評価だと気づかれる手がかり（ディレクトリ名やファイル名など）を取り除いた作業環境です。

## 『Authoring or modifying a skill』は、決められた手順でSkillを書き、作業中の判断を変える指示だけ残す

『<strong>Authoring or modifying a skill</strong>』は、<strong>`SKILL.md` を新しく書く、または直すとき</strong>に通すPlaybookです。

同梱ガイドは、`SKILL.md` を自由に書き下ろすことをよくある失敗に挙げ、このPlaybookを通せば検証とレビューが行われる、としています。

### 4つの手順

手順は4つです。

1. create-skill を使う
2. Skillを検証する
3. Skillの構造を変えるならテストケースを用意する
4. 『[Opening a PR](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/playbooks/opening-a-pr.md)』でPRを作成（[第14章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/45a56e)）

ここからは、各手順を1つずつ見ていきます。

<a id="%E8%A6%81%E7%82%B9%E3%81%AF%E3%80%8C%E8%BF%B7%E3%81%A3%E3%81%9F%E3%82%89%E5%89%8A%E3%82%8B%E3%80%8D%E3%81%A8%E3%81%84%E3%81%86%E6%96%87%E7%AB%A0%E3%81%AE%E8%A6%8F%E5%BE%8B"></a>


### 要点は「迷ったら削る」という文章の規律

このPlaybookの要点は、手順の後に置かれた<strong>文章の規律</strong>です。

> When in doubt, delete. Keep only prose that changes a decision.
>
> 迷ったら削る。判断を変える文章だけを残す。

Skillを書くエージェントは、一文ごとに「この文でエージェントのどの判断が変わるか」を問い、答えられない文は消します。

主な規律は次のとおりです。

- <strong>理由の説明を省略する</strong>・・・ 指示は「何をするか」を中心に書き、理由がないと指示の意味や適用条件が分からない場合に限定して、理由を説明します。
- <strong>中身を写さず、情報源を指し示す</strong>・・・ 型、README、設定ファイルのような、コードベースに実在する情報源を示します（原則『[<strong>Encode Lessons in Structure</strong>](https://github.com/cursor/plugins/blob/main/pstack/skills/principle-encode-lessons-in-structure/SKILL.md)』、[第21章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/dd2d9f)）。
- <strong>他のSkillに委ねる</strong>・・・ 他のSkillの中身は書き写さず、そのSkillのパスを示して任せます。
- <strong>繰り返す作業をSkillにする</strong>・・・ 何度も同じ作業をしているなら、新しいSkillを提案します。

エージェントが作業の途中で壊れたSkillに気づいたら、作業は止めず、黙認して回避することもせず、<strong>そのSkillだけ修正し、PRを出します</strong>。

機能開発のPRに混ざったSkillの編集は、レビューで気づかれにくく、『Eval』で効果を測ることもできないためです。

## 『Eval』は、評価だと気づかせずに、変更がエージェントの行動に与える効果を測る

『<strong>Eval</strong>』は、Skill、構造、プロンプトの変更がエージェントの行動にどう影響するかを、<strong>採用する前にテストする</strong>Playbookです。

『Eval』を実行するエージェントは、実験を設計し、結果をまとめる役を担います。ここでいう実験とは、変更したSkillを別のエージェントに実際の作業で使わせ、その仕事ぶりを採点することです。

実験では、課題を解くエージェントを複数体起動します。このエージェントを<strong>候補</strong>と呼びます。

- <strong>候補ごとに作業用のディレクトリを分ける</strong>・・・ 各ディレクトリには、変更したSkillと、プロジェクトの骨組みを置いておきます。候補どうしが互いの作業に影響しないようにするためです。
- <strong>候補ごとに別のモデルを使う</strong>・・・ たとえば、1体目はOpus、2体目はGrokで動かします。モデルにはそれぞれ偏りがあり、1つのモデルだけで試すと、その偏りが結果に混ざるからです。
- <strong>全員に同じ依頼を与える</strong>・・・ 依頼が異なると、結果の違いが変更によるものか、依頼によるものか分からなくなるからです。

候補の作業が終わったら、候補とは別のモデルで動く<strong>審査員</strong>が、どの候補の出力かを知らない状態で採点します。

変更前と変更後の2つの版を比べることもできます。その場合は、1体の審査員が、どちらの版の出力かを知らないまま、両方を同じ基準で一度に採点します。

### 7つの手順

1. <strong>実験の枠組みを決める</strong>・・・ テストする変更と、成功とみなす行動を書く。審査員用の採点基準（ルーブリック）を3〜6項目で作り、候補には見せない
2. <strong>評価の手がかりを取り除いた環境を用意する</strong>・・・ 候補ごとに作業ディレクトリを用意し、テストする変更を入れておく。プロジェクトの骨組みや、候補が自然に読むSkillなど、本物のタスクならあるはずのコンテキストも置く
3. <strong>自然なプロンプトを一つ書く</strong>・・・ 利用者が与えそうな依頼にし、何を測っているかを漏らさない
4. <strong>N体の候補を並列に起動する</strong>・・・ [`/arena`](https://github.com/cursor/plugins/blob/main/pstack/skills/arena/SKILL.md) の手順に従い、候補ごとに異なるモデルを使う
5. <strong>盲検の審査員を1体起動する</strong>・・・ 候補とは別のモデルファミリーを使い、モデル名は見せない
6. <strong>指示をたどったかは、自己申告ではなく記録から確かめる</strong>・・・ 候補がSkillから指し示されたファイルを順にたどって従ったかは、会話の記録で実際に開いたファイルとコードの形から採点する
7. <strong>実験を設計したエージェントが、すべての出力を自分で読む</strong>・・・ 審査員の判定と比べ、食い違いはモデルの偏りかルーブリックのあいまいさの表れとみて、結論をまとめる

### 要点は、手順より先に置かれた盲検化のルール

同梱ガイドによれば、このPlaybookは、「評価されていると知ったエージェントの振る舞いが変わる」という失敗を中心に作られています。この失敗を<strong>観察者効果</strong>と呼びます。

盲検化のルールは、情報が漏れる経路ごとに3つに分けられます。

- <strong>候補が目にする文字列</strong>・・・ `eval`、`test`、`judge` などの語を、ディレクトリ名、ファイル名、プロンプトに入れません。名前は利用者が付けそうなものにし、プロンプトは普通の依頼に見せます。
- <strong>候補が答える内容</strong>・・・ どのSkillやファイルを使ったかを列挙させず、他の候補がいることも伝えません。
- <strong>審査員が目にする情報</strong>・・・ 出力には、どのモデルのものか分からないラベルを付けて見せ、モデル名は伏せます。2つの版を比べるときは、1体の審査員が両方を1回で、同じ尺度で採点します。

<a id="%E4%BE%9D%E9%A0%BC%E3%81%AE%E6%9B%B8%E3%81%8D%E6%96%B9%EF%BC%9A%E4%B8%A1%E6%96%B9%E3%81%AE%E7%89%88%E3%81%AB%E5%90%8C%E3%81%98%E3%82%BF%E3%82%B9%E3%82%AF%E3%82%92%E4%B8%8E%E3%81%88%E3%80%81%E5%80%99%E8%A3%9C%E3%82%92%E7%9B%B2%E6%A4%9C%E3%81%AE%E3%81%BE%E3%81%BE%E3%81%AB%E3%81%99%E3%82%8B%E3%82%88%E3%81%86%E6%9B%B8%E3%81%8F"></a>


### 依頼の書き方：両方の版に同じタスクを与え、候補を盲検のままにするよう書く

同梱ガイドの依頼例は、変更前と変更後の2つの版を比べる使い方で、両方の版に同じタスクを与えることと、候補を盲検のままにすることを伝えています。

```
/poteto-mode run the eval playbook on this skill change. same task for both variants, candidates stay blind.
// このSkillの変更に Eval Playbook を実行して。両方の版に同じタスクを与えて。候補は盲検のままにして。
```

## まとめ

- <strong>2つのPlaybookの分担</strong>・・・ Skillを作成・編集する『<strong>Authoring or modifying a skill</strong>』と、効果を測る『<strong>Eval</strong>』です。
- <strong>Authoring or modifying a skill</strong>・・・ `create-skill` で書き、機械的に検証してPRにします。要点は「迷ったら削る。判断を変える文章だけを残す」です。壊れたSkillは、そのSkillの修正だけを含む独立したPRで直します。
- <strong>Eval</strong>・・・ 変更を採用する前に、行動への効果を確かめます。候補は評価されていると知らず、審査員はモデル名を知りません。採点は候補の自己申告ではなく、実際に開いたファイルを示す会話の記録から行います。

次の[第14章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/45a56e)では、PRを作る『<strong>Opening a PR</strong>』、PRをマージできる状態まで運ぶ『[<strong>Babysit</strong>](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/playbooks/babysit.md)』、検証済みのものだけを本流のブランチ（trunk）へ取り込む『[<strong>Shipping</strong>](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/playbooks/shipping.md)』を見ていきます。
