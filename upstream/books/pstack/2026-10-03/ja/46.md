## 要点9：/architectで、複数の設計を比較・統合する

大きな変更では、人間はアーキテクチャの設計やデータ構造、システムどうしの連携を考えることに時間を使い、エージェントは実装の細部を埋めることに時間を使います。

ただし、エージェントは、いきなり実装を始めるのではなく、<strong>まず複数の設計案を比べて1つに統合し、それから実装します</strong>。

<a id="%E8%A8%98%E4%BA%8B%E3%81%AE%E8%80%83%E3%81%88%EF%BC%9Apoteto%E6%B0%8F%E3%81%AF%E3%82%A2%E3%83%BC%E3%82%AD%E3%83%86%E3%82%AF%E3%83%81%E3%83%A3%E3%81%AE%E8%A8%AD%E8%A8%88%E3%81%AB%E6%99%82%E9%96%93%E3%82%92%E4%BD%BF%E3%81%86"></a>


### 記事の考え：poteto氏はアーキテクチャの設計に時間を使う

節『Architecting bigger changes』で、poteto氏は、<strong>エージェントの時代のエンジニアとして、次のことに時間を使うのが、より大切だ</strong>と書いています。

- アーキテクチャの設計
- 適切なデータ構造の選択
- 自分が作るシステムどうしの連携

<strong>実装の細部は、自分のエージェントが埋める</strong>とも書いています。

設計を明確な段階に分けて進めるSkillとして記事が挙げているのが `/architect` で、依頼例は次の一行です。

```
/architect this new <feature request>
// この新しい<機能の要望>を設計して
```

記事は、[`/architect`](https://github.com/cursor/plugins/blob/main/pstack/skills/architect/SKILL.md) の流れを、次の5つの段階で説明しています。

1. 問題を調べる
2. 骨組みを描く
3. 評価し、統合する
4. 骨組みに沿って実装する
5. 設計が間違っていたら捨てる

流れを図にすると、次のようになります。

#### 1. 問題を調べる

エージェントは、新しいコードが関わる既存の仕組みを `/how` と `/why` で調べます。

<aside class="msg message"><span class="msg-symbol">!</span><div class="msg-content">
<ul class="code-line" data-line="107">
<li class="code-line" data-line="107">
<strong><code>/how</code></strong>・・・ コードが今どう動くかを調べるSkillです（<a href="https://zenn.dev/sc30gsw/books/080faba713547b/viewer/788746" target="_blank">第22章</a>）。</li>
<li class="code-line" data-line="108">
<strong><code>/why</code></strong>・・・ コードがなぜ今の形になったかを調べるSkillです（<a href="https://zenn.dev/sc30gsw/books/080faba713547b/viewer/788746" target="_blank">第22章</a>）。</li>
</ul>
</div></aside>

そして、どのモジュールが何を受け持つかという責任の分担と、既存の制約を正しく把握します。

#### 2. 骨組みを描く

エージェントは、互いの案を見せずに、複数のモデルに設計案を並列に作らせます（`/architect` の `SKILL.md` では `/arena` を使います）。  
モデルには、多くの場合、系統の異なるものを使います。

<aside class="msg message"><span class="msg-symbol">!</span><div class="msg-content">
<p class="code-line" data-line="119"><strong><code>/arena</code></strong>・・・ 同じ課題を複数のエージェントに別々に解かせるSkillです（<a href="https://zenn.dev/sc30gsw/books/080faba713547b/viewer/2ad346" target="_blank">第24章</a>）</p>
</div></aside>

各モデルが作る案は、次の4つをそろえた設計一式（原文では design package）です。

- <strong>呼び出し側の使い方</strong>・・・ 作るものを使う側のコードです（下の例のコードの1の部分）。
- <strong>中心になる型の定義</strong>・・・ 設計の中心になるデータの形です（下の例のコードの2の `RateLimiterOptions` と `RateLimiter`）。
- <strong>公開する関数のシグネチャ</strong>・・・ ほかのコードから呼べる関数の名前、引数、戻り値の型です（下の例のコードの2の `createRateLimiter` の1行目）。
- <strong>設計の理由を短く書いた文書</strong>・・・ なぜこの形にしたか、ほかにどんな形を考えて採らなかったかを、1ページ程度にまとめた文書です。これだけは、コードではなく文章で書きます（`/architect` の `references/rationale-template.md` が書き方を定めています）。

このうち、最初の3つは、多くの場合、骨組みのコードとして描かれます。

<aside class="msg message"><span class="msg-symbol">!</span><div class="msg-content">
<p class="code-line" data-line="132"><strong>骨組み</strong>・・・ 型と関数の形だけを書き、中身はまだ書かないコードです（<a href="https://zenn.dev/sc30gsw/books/080faba713547b/viewer/2ad346" target="_blank">第24章</a>）。</p>
</div></aside>

また、案を作る各モデルは、次の3つの観点でも自分の案を確かめます。

- <strong>インターフェースの深さ</strong>・・・ 使う側から見える関数や型は少なく、その裏で多くの処理を引き受けているか。（例：`tryAcquire` を1つ呼ぶだけで、件数を数えることも、1分ごとに数え直すことも、内側で済むか。）
- <strong>能力の低いモデルが扱うときに起きる失敗</strong>・・・ 後でその設計に沿ってコードを書く能力の低いモデルが、「設計を満たした実装ができるかどうか」を確かめる。
- <strong>4つの危険信号との照合</strong>・・・ `/architect` は、設計の危険信号を4つ並べた一覧（[`references/design-red-flags.md`](https://github.com/cursor/plugins/blob/main/pstack/skills/architect/references/design-red-flags.md)）を持っています（[第24章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/2ad346)）。浅いモジュール、情報の漏れ、順番による分割、素通しのメソッドの4つです。案がどれかに当てはまれば、直すか、退けます。

#### 3. 評価し、統合する

主エージェント（案を作るモデルを起動した元のエージェント）とは別のモデルの判定役が、厳しい採点基準で各案を評価します。

主エージェントは、各案とその評価を踏まえて、案を1つの設計に統合します。

同梱ガイドの [`docs/guide/04-design.md`](https://github.com/cursor/plugins/blob/main/pstack/docs/guide/04-design.md) は、統合するエージェントが各案を最後まで読み、土台にする案を1つ選び、ほかの案の良い部分を取り込んで、結果を検証すると説明しています。

<a id="4.-%E9%AA%A8%E7%B5%84%E3%81%BF%E3%81%AB%E6%B2%BF%E3%81%A3%E3%81%A6%E5%AE%9F%E8%A3%85%E3%81%99%E3%82%8B"></a>


#### 4. 骨組みに沿って実装する

エージェントは、骨組みの仮の本体（中身の代わりに置いた `throw new Error("not implemented")` のようなコード）を、実際のコードに置き換えます。

実装の途中で、関数に予想していなかった引数や状態が必要だと分かったら、エージェントは、その食い違いを黙って実装の中で片付けずに、表に出します。

そのうえで、原因が次のどれかを問い直します（`/architect` の `SKILL.md` の節『Phase D: Implement against the sketch』）。

- 骨組みが間違っていた
- 要件を見落としていた
- 実装が必要以上のことをしている

<a id="5.-%E8%A8%AD%E8%A8%88%E3%81%8C%E9%96%93%E9%81%95%E3%81%A3%E3%81%A6%E3%81%84%E3%81%9F%E3%82%89%E6%8D%A8%E3%81%A6%E3%82%8B"></a>


#### 5. 設計が間違っていたら捨てる

実装の途中で骨組みが間違っていたと分かったら、エージェントは、すべてを捨てて最初からやり直します（[要点10](#%E8%A6%81%E7%82%B910%EF%BC%9A%E5%AE%9F%E8%A3%85%E3%81%A7%E8%A8%AD%E8%A8%88%E3%81%AE%E8%AA%A4%E3%82%8A%E3%81%8C%E5%88%86%E3%81%8B%E3%81%A3%E3%81%9F%E3%82%89%E3%80%81%E8%A8%AD%E8%A8%88%E3%82%92%E8%A6%8B%E7%9B%B4%E3%81%99)）。

<a id="pstack%EF%BC%9A%2Farchitect-%E3%82%92%E4%BD%BF%E3%81%86%E3%81%AE%E3%81%AF%E3%80%81%E9%96%A2%E6%95%B0%E3%81%AE%E5%A2%83%E7%95%8C%E3%82%92%E3%81%BE%E3%81%9F%E3%81%90%E5%A4%89%E6%9B%B4%E3%81%A8%E3%80%81%E8%B2%AC%E4%BB%BB%E3%81%AE%E6%89%80%E5%9C%A8%E3%82%92%E7%A7%BB%E3%81%99%E5%A4%89%E6%9B%B4"></a>


### pstack：/architect を使うのは、関数の境界をまたぐ変更と、責任の所在を移す変更

同梱ガイドの [`docs/guide/04-design.md`](https://github.com/cursor/plugins/blob/main/pstack/docs/guide/04-design.md) は、ほとんどの変更には、複数の案を比べて統合するような設計作業は必要ないとしています。

そのうえで、<strong>関数の境界をまたぐ変更や、責任の所在（どのモジュールが責任を持つか）を移す変更</strong>を `/architect` の対象としています。

本書で例を挙げると、ある関数の引数や戻り値の形を変え、その関数を呼ぶ側のコードも合わせて直す必要がある変更は、関数の境界をまたぐ変更です。

たとえば、商品の金額を返す関数 `getPrice` の戻り値を、金額だけから「金額と通貨」に変えるとします。

```
// price.ts（変更前）：金額だけを返す
function getPrice(itemId: string): number {
  // ...
}

// price.ts（変更後）：金額と通貨を返す
function getPrice(itemId: string): { amount: number; currency: string } {
  // ...
}
```

戻り値の形が変わるので、`getPrice` を呼ぶ側のコードも、合わせて直す必要があります。

また、キャッシュを持つ役目を、画面のコードから、データを取得するモジュールへ移す変更は、責任の所在を移す変更です。

変更前は、画面のコードが、自分でキャッシュ（一度取得したデータを取っておく入れ物）を持っています。

```
// UserPage.ts（変更前）：画面のコードがキャッシュを持つ
const cache = new Map<string, User>();

async function showUser(id: string) {
  const user = cache.get(id) ?? (await fetchUser(id));
  cache.set(id, user);
  render(user);
}
```

変更後は、データを取得するモジュールがキャッシュを持ち、画面のコードは呼ぶだけになります。

```
// userApi.ts（変更後）：データを取得するモジュールがキャッシュを持つ
const cache = new Map<string, User>();

export async function fetchUser(id: string): Promise<User> {
  const cached = cache.get(id);
  if (cached) return cached;
  const user = await request(`/users/${id}`);
  cache.set(id, user);
  return user;
}

// UserPage.ts（変更後）：キャッシュを気にせず、呼ぶだけ
async function showUser(id: string) {
  render(await fetchUser(id));
}
```

キャッシュを持つ役目が、画面のコードから `userApi.ts` へ移っています。これが、責任の所在を移す変更です。

このように、変更が1つの関数の中で閉じず、ほかのコードとの約束（引数や戻り値の形）や役目の分担に及ぶなら、その変更は `/architect` で設計から入る対象になります。

`04-design.md` は、`/poteto-mode` が依頼を受けると、この基準を当てはめ、`/architect` を使うかを自分で決めると明示しています。

そのため、<strong>利用者が毎回、`/architect`の使用有無を判断する必要はありません</strong>。

利用者が `/architect` などのSkillを直接呼ぶのは、主に、`/poteto-mode` が既定で行うよりも念入りに、または手短に設計を確かめたいときです。

<a id="%E8%A6%81%E7%82%B910%EF%BC%9A%E5%AE%9F%E8%A3%85%E3%81%A7%E8%A8%AD%E8%A8%88%E3%81%AE%E8%AA%A4%E3%82%8A%E3%81%8C%E5%88%86%E3%81%8B%E3%81%A3%E3%81%9F%E3%82%89%E3%80%81%E8%A8%AD%E8%A8%88%E3%82%92%E8%A6%8B%E7%9B%B4%E3%81%99"></a>


## 要点10：実装で設計の誤りが分かったら、設計を見直す

実装の途中で、骨組みとの食い違いや、繰り返し現れる回避策（問題の原因を直さずに、その場しのぎで問題を避ける書き方）が見つかったら、エージェントは、それらを設計が間違っている証拠とみなして、<strong>設計を見直します。必要なら、エージェントは骨組みを捨てて、問題を調べる段階から設計をやり直します</strong>。

たとえば、実装してみると、骨組みにない引数が関数に必要になることがあります。これが、骨組みとの食い違いです。

また、エージェントが、データの型にない項目を読むために `as any`（値の型を決めつけ、型の検査を止める書き方）を同じ形であちこちに書くのは、繰り返し現れる回避策です。

<a id="%E8%A8%98%E4%BA%8B%E3%81%AE%E8%80%83%E3%81%88%EF%BC%9A%E7%84%A1%E9%96%A2%E4%BF%82%E3%81%AA%E7%AE%87%E6%89%80%E3%81%AB%E7%8F%BE%E3%82%8C%E3%82%8B%E5%90%8C%E3%81%98%E5%9B%9E%E9%81%BF%E7%AD%96%E3%82%84%E3%80%81%E5%9E%8B%E3%81%AE%E9%80%83%E3%81%92%E9%81%93%E3%81%AF%E3%80%81%E8%A8%AD%E8%A8%88%E3%81%8C%E9%96%93%E9%81%95%E3%81%A3%E3%81%A6%E3%81%84%E3%82%8B%E8%A8%BC%E6%8B%A0"></a>


### 記事の考え：無関係な箇所に現れる同じ回避策や、型の逃げ道は、設計が間違っている証拠

節『Architecting bigger changes』は、`/architect` の5つの段階を説明した後、設計を捨てるかどうかの目安を次の一文にまとめています。

> If the same workaround appears across unrelated call sites, or if the types require escape hatches like any or forced casts, that is empirical proof that the architecture is wrong.
>
> 無関係な呼び出し箇所に同じ回避策が現れるなら、あるいは、型が any や強制的なキャストのような逃げ道を必要とするなら、それは、アーキテクチャが間違っていることを、実際に確かめて示した証拠だ。

引用が挙げる兆候は、次の2つです。

- 無関係な呼び出し箇所に、同じ回避策が現れる
- 型が、`any` や強制的なキャスト（`as unknown as User` などの書き方）といった逃げ道を必要とする

本書の例で、2つの兆候がどう現れるかを示します。

骨組みで決めた `Order` 型には、通貨の項目がありません。  
ところが、エージェントが実装してみると、請求書、メール、管理画面という無関係な3つの箇所が、どれも通貨を必要としました。

```
// 骨組みで決めた型：通貨の項目がない
type Order = { id: string; total: number };

// 表示や送信の対象になる注文
declare const order: Order;

// invoice.ts：型の逃げ道（as any）で、型にない項目を読む
const invoiceCurrency = (order as any).currency ?? "JPY";

// mail.ts：同じ回避策を、無関係な別の箇所でも書く
const mailCurrency = (order as any).currency ?? "JPY";

// admin.ts：さらに別の箇所でも、同じ回避策を書く
const adminCurrency = (order as any).currency ?? "JPY";
```

エージェントが3つの箇所に同じ回避策を書くのは、<strong>それぞれの箇所の書き方が悪いからではなく、骨組みの `Order` 型に通貨の項目がないから</strong>です。

このように、無関係な箇所に同じ回避策や型の逃げ道が現れるなら、<strong>個々の箇所ではなく、設計そのものを見直す必要があります</strong>。

<a id="pstack%EF%BC%9A%E8%A8%AD%E8%A8%88%E3%82%92%E6%8D%A8%E3%81%A6%E3%82%8B%E3%81%8B%E3%81%AF%E3%80%81%E5%85%86%E5%80%99%E3%81%8C%E7%B9%B0%E3%82%8A%E8%BF%94%E3%81%97%E7%8F%BE%E3%82%8C%E3%82%8B%E3%81%8B%E3%81%A7%E5%88%A4%E6%96%AD%E3%81%99%E3%82%8B"></a>


### pstack：設計を捨てるかは、兆候が繰り返し現れるかで判断する

`/architect` の [`SKILL.md`](https://github.com/cursor/plugins/blob/main/pstack/skills/architect/SKILL.md) は、設計を捨てるかどうかを、<strong>兆候が1回だけ現れたかではなく、同じ形で繰り返し現れるかで判断する</strong>よう求めています。

同 `SKILL.md` は、<strong>兆候を見つけても、すぐに設計が間違っていると決めつけない</strong>よう求めています。エッジケース（まれな入力や状況）への対応がいくつか必要になるだけでは、設計が間違っているとは言えません。問題そのものが本当に複雑な場合もあるからです。

記事の引用は型の逃げ道を兆候として挙げていますが、同 `SKILL.md` に従えば、`any` が1か所に1回だけ現れても、それだけでは設計を捨てる理由になりません。

一方、請求書、メール、管理画面の例のように、無関係な3つの呼び出し箇所に同じ回避策を書き始めたら、その回避策を、骨組みを捨てるべき兆候とみなします。

また、同 `SKILL.md` の節『Phase E: Scrap when the architecture is wrong』は、設計を捨てるかどうかを判断する材料として、前述した2つの兆候（同じ回避策と型の逃げ道）に加えて、次の4つの兆候も挙げています。

1. 互いに無関係な複数のエッジケースが、どれも専用の分岐を必要とする
2. 骨組みでは状態を共有しないとしていたのに、実装の途中でエージェントが「ロック（同時に書き換えられないように守る仕組み）が必要だ」と考える
3. 呼び出し側が、モジュールの内部の決まりを知らないと使えない（例：先に初期化の関数を呼んでおく必要がある）
4. 実装の途中で見つかった骨組みとの食い違いのうち、同じ形のものが、互いに独立して2回以上現れる

## 要点11：小さく検証できる作業に分ける

設計が固まったら、エージェントは、計画用の『[<strong>Multi-phase or multi-PR plan</strong>](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/playbooks/multi-phase-plan.md)』Playbookを使い、<strong>作業を小さく、それぞれ検証できるPRに分けます</strong>。

そして、PRごとに、何が確かめられれば完了とするか（例：ログの行、スクリーンショット、テストの実行結果）を、計画書に書いておきます。

<a id="%E8%A8%98%E4%BA%8B%E3%81%AE%E8%80%83%E3%81%88%EF%BC%9A%E8%A8%88%E7%94%BB%E7%94%A8%E3%81%AEplaybook%E3%81%AF%E3%80%81%E3%81%9F%E3%81%84%E3%81%A6%E3%81%84%E8%A8%AD%E8%A8%88%E3%81%AE%E5%BE%8C%E3%81%AB%E4%BD%BF%E3%81%86"></a>


### 記事の考え：計画用のPlaybookは、たいてい設計の後に使う

poteto氏は、節『Okay but I really want a planning doc』で、pstackに計画用のSkillはないが、複数の段階に分けて計画するPlaybookはある、と書いています。

そのうえで、自分が納得できる設計をエージェントが出した後に、<strong>その設計を、実行の手順まで具体的に決めた計画にするため、たいていこの計画用のPlaybook（『Multi-phase or multi-PR plan』）を使う</strong>としています。  
（このPlaybookで作られる計画書の例は「[計画書の完成形の例](#%E8%A8%88%E7%94%BB%E6%9B%B8%E3%81%AE%E5%AE%8C%E6%88%90%E5%BD%A2%E3%81%AE%E4%BE%8B)」で後述します）

記事が挙げる依頼は、次の一行です。

```
/poteto-mode turn this design into a plan
// この設計を計画にして
```

このPlaybookを使うと、エージェントは、計画の各タスクを、完了を示す証拠と、その確かめ方（検証）を中心に組み立てます。

人間が計画を承認した後は、エージェントが項目ごとに実行します。  
計画の各PRは、<strong>小さく、それ1つで完結していて、レビューしやすい</strong>ものになります。

<a id="pstack%EF%BC%9A%E8%A8%88%E7%94%BB%E6%9B%B8%E3%81%AB%E3%81%AF%E3%80%81pr%E3%81%94%E3%81%A8%E3%81%AB%E5%AE%8C%E4%BA%86%E3%81%AE%E8%A8%BC%E6%8B%A0%E3%81%A8%E7%A2%BA%E3%81%8B%E3%82%81%E6%96%B9%E3%82%92%E6%9B%B8%E3%81%8F"></a>


### pstack：計画書には、PRごとに完了の証拠と確かめ方を書く

『[<strong>Multi-phase or multi-PR plan</strong>](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/playbooks/multi-phase-plan.md)』Playbookのファイル（`playbooks/multi-phase-plan.md`）が定める要点は、次の5つです。

- 計画が成果物で、実装はしない
- 書く前に、未解決の疑問をプロトタイプで決める
- 1つのPRに1つの変更と、その証拠
- テストだけでは検証済みにしない
- 利用者が開始を指示してから実行する

最後に、この5つに沿って書いた計画書の完成形の例を示します。

<a id="%E8%A8%88%E7%94%BB%E3%81%8C%E6%88%90%E6%9E%9C%E7%89%A9%E3%81%A7%E3%80%81%E5%AE%9F%E8%A3%85%E3%81%AF%E3%81%97%E3%81%AA%E3%81%84"></a>


#### 計画が成果物で、実装はしない

<strong>このPlaybookでエージェントが作るのは計画書だけで、コードは書きません</strong>。

計画の実行は、計画書の中で名前を挙げた実行用のPlaybookで行います。

実行用のPlaybookは、『<strong>Autopilot-full</strong>』か『<strong>Autopilot-stack</strong>』から選びます。何日も続く作業の全体（プログラム）を運用するときは『<strong>Orchestrate</strong>』を使います（いずれも[第16章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/8a8dd5)）。

<a id="%E6%9B%B8%E3%81%8F%E5%89%8D%E3%81%AB%E3%80%81%E6%9C%AA%E8%A7%A3%E6%B1%BA%E3%81%AE%E7%96%91%E5%95%8F%E3%82%92%E3%83%97%E3%83%AD%E3%83%88%E3%82%BF%E3%82%A4%E3%83%97%E3%81%A7%E6%B1%BA%E3%82%81%E3%82%8B"></a>


#### 書く前に、未解決の疑問をプロトタイプで決める

エージェントは、「どちらの方法が速いか」のような未解決の疑問ごとに『[<strong>Prototype</strong>](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/playbooks/prototype.md)』Playbook（[第12章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/f1e85b)）を実行します。

そして、プロトタイプで得た証拠（ブランチ、コミット、スクリーンショット）を計画書の付録に残します。

これは、[第38章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/7549a7)の要点8（疑問は、実験で確かめさせる）と同じ考え方です。第38章は、要点8を次のように書いています。

> 人間は、作って動かせば答えが出る疑問について、自分で答えたり、エージェントに人間の返事を待たせたりせず、<strong>エージェントに実験で確かめさせます</strong>。

<a id="1%E3%81%A4%E3%81%AEpr%E3%81%AB1%E3%81%A4%E3%81%AE%E5%A4%89%E6%9B%B4%E3%81%A8%E3%80%81%E3%81%9D%E3%81%AE%E8%A8%BC%E6%8B%A0"></a>


#### 1つのPRに1つの変更と、その証拠

計画書では、PRを1つずつ、見出し（`##`）で区切って書きます。たとえば、PRが2つある計画書は、次の形になります。

```
# webhook のレート制限の計画書

## 送り手ごとに件数を数える RateLimiter を作る（PR 1）
（PR 1 について、下の欄を書く）

## 送り手ごとのレート制限を追加する（PR 2）
（PR 2 について、同じ欄を書く）
```

どの見出しの下にも、次の欄を順に書きます。中身まで書いた完成形は、この節の最後に載せます。

- 依存するPR
- 変更するファイル
- 行う変更
- 観察できる結果（ログの行や画面の状態）
- 単体テスト
- ライブ確認（動くアプリを実際に操作して確かめること）
- 性能の確認
- 利用者のレビュー（[第16章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/8a8dd5)では「運用者」の確認と呼ぶ。利用者が行う操作の流れを変えるPRだけが対象で、それ以外のPRは「なし」と書く）
- マージ

たとえば、上の骨格の PR 2 の見出しの下に、これらの欄を書くと、次のようになります。

```
## 送り手ごとのレート制限を追加する（PR 2）

**依存するPR**：PR 1（送り手ごとに件数を数える RateLimiter を作る）

**変更するファイル**
- [ ] `src/webhooks/handleWebhook.ts` を編集する

**行う変更**
- [ ] `handleWebhook` で `limiter.tryAcquire(senderId)` を呼び、上限を超えたら 429 を返す

**観察できる結果**
- [ ] 同じ送り手から1分に61件送ると、61件目でログに `rate_limited sender=sender-a` が出る

**単体テスト**（テストだけでは検証済みにしない）
- [ ] `handleWebhook.test.ts` に「61件目は 429 を返す」ケースを足し、`npm test` を実行する

**ライブ確認**
- [ ] 動いているサーバーに webhook を61件送り、61件目が 429 になることを確かめる

**性能の確認**
- [ ] webhook 1件あたりの処理時間を、変更前と変更後で比べる

**利用者のレビュー**：なし（利用者の操作の流れは変わらない）

**マージ**
- [ ] 単体テスト、ライブ確認、性能の確認にすべてチェックが入ってから、マージする
```

<a id="%E3%83%86%E3%82%B9%E3%83%88%E3%81%A0%E3%81%91%E3%81%A7%E3%81%AF%E6%A4%9C%E8%A8%BC%E6%B8%88%E3%81%BF%E3%81%AB%E3%81%97%E3%81%AA%E3%81%84"></a>


#### テストだけでは検証済みにしない

Playbookは、次の2文を検証の決まりとしています。

> Tests alone are not sufficient verification. A PR is verified only when its unit, live, and perf boxes are all checked.
>
> テストだけでは、検証として十分ではない。単体テスト、ライブ確認、性能の確認の3つの欄すべてにチェックが入ったときだけ、そのPRを検証済みとする。

<a id="%E5%88%A9%E7%94%A8%E8%80%85%E3%81%8C%E9%96%8B%E5%A7%8B%E3%82%92%E6%8C%87%E7%A4%BA%E3%81%97%E3%81%A6%E3%81%8B%E3%82%89%E5%AE%9F%E8%A1%8C%E3%81%99%E3%82%8B"></a>


#### 利用者が開始を指示してから実行する

エージェントは、計画書の場所と、計画書の形式の検査（`check-plan.mjs`）の結果を利用者に渡して止まります。

利用者が開始を指示するまで、実行は始めません。

<a id="%E8%A8%88%E7%94%BB%E6%9B%B8%E3%81%AE%E5%AE%8C%E6%88%90%E5%BD%A2%E3%81%AE%E4%BE%8B"></a>

## 要点12：計画書は一時的なもの

計画書は、「作業を実行するとき」と、「大きな作業の進捗をほかのエージェントに知らせるとき」に使う、<strong>一時的な文書</strong>です。

<a id="%E8%A8%98%E4%BA%8B%E3%81%AE%E8%80%83%E3%81%88%EF%BC%9A%E8%A8%88%E7%94%BB%E6%9B%B8%E3%81%AF%E3%80%81%E7%B5%82%E3%82%8F%E3%81%A3%E3%81%9F%E3%82%89%E9%80%9A%E5%B8%B8%E3%81%AF%E6%B6%88%E3%81%99"></a>


### 記事の考え：計画書は、終わったら通常は消す

poteto氏は、1週間かかるような大きなプロジェクトでは、ほかのエージェントに進行中の作業を知らせるために、計画書をリポジトリに一時的にコミットすることがある、と書いています。

ただし、<strong>作業が終わったら、通常は計画書を削除します</strong>。コードベースに混乱を残さないためです。

計画書をずっと残しておくことに価値を感じない、とも書いています。

<a id="pstack%EF%BC%9A%E8%A8%88%E7%94%BB%E6%9B%B8%E3%81%AF%E3%80%81%E3%82%A8%E3%83%BC%E3%82%B8%E3%82%A7%E3%83%B3%E3%83%88%E3%81%AE%E3%82%B9%E3%83%88%E3%82%A2%E3%81%AE-docs%2F-%E3%81%AB%E7%BD%AE%E3%81%8F"></a>


### pstack：計画書は、エージェントのストアの docs/ に置く

『<strong>Multi-phase or multi-PR plan</strong>』Playbookは、利用者が場所を指定しない限り、<strong>計画書を、エージェントのストアの `docs/` に書く</strong>よう定めています。

<aside class="msg message"><span class="msg-symbol">!</span><div class="msg-content">
<p class="code-line" data-line="636"><strong>エージェントのストア</strong>（原文では agent store）・・・ エージェントが使う保存領域です。ストアの場所は、エージェントのシステムプロンプト（エージェントに最初に渡される指示文）に書かれています（『Orchestrate』Playbook の記述）。</p>
</div></aside>

<a id="%E8%A6%81%E7%82%B913%EF%BC%9A%2Fpoteto-mode%E3%81%AB%E4%BC%9D%E3%81%88%E3%82%8B%E3%81%93%E3%81%A8"></a>


## 要点13：/poteto-modeに伝えること

人間は、`/poteto-mode` に手順を並べず、<strong>目的、制約、確認したい結果、レビューのタイミング</strong>を伝えます。

<a id="%E8%A8%98%E4%BA%8B%E3%81%AE%E8%80%83%E3%81%88%EF%BC%9A%E3%81%9F%E3%81%84%E3%81%A6%E3%81%84%E3%81%AF-%2Fpoteto-mode-%E3%81%A0%E3%81%91%E3%81%A7%E3%82%88%E3%81%84"></a>


### 記事の考え：たいていは /poteto-mode だけでよい

記事は、紹介したSkillの多くを `/poteto-mode` が自動で使うため、<strong>人間は、たいてい `/poteto-mode` に依頼するだけで済む</strong>と書いています。

節『The workflow in practice』には、4つの場面それぞれについて、依頼の例が載っています。

<a id="%E4%BE%8B1%EF%BC%89%E5%8E%9F%E5%9B%A0%E3%81%AE%E5%88%86%E3%81%8B%E3%82%89%E3%81%AA%E3%81%84%E4%B8%8D%E5%85%B7%E5%90%88%E3%81%AE%E8%AA%BF%E6%9F%BB"></a>


#### 例1）原因の分からない不具合の調査

1つ目は、本番環境で起きた、原因のはっきりしない不具合の調査です。

```
/poteto-mode investigate why background workers periodically fail with timeout errors. give me a breakdown of what we know, what data you used, and your best hypotheses.
// バックグラウンドワーカーが定期的にタイムアウトエラーで失敗する理由を調べて。分かっていること、使ったデータ、有力な仮説を分けて示して。
```

この依頼は、目的に加えて、結果の形（分かっていること、使ったデータ、有力な仮説）を指定しています。

この依頼を受けたエージェントは、コードを調べ、メトリクス（処理にかかった時間やエラーの件数など、システムの状態を数値で記録したデータ）と過去のコミットを並列に確かめて、問題がどこにありそうかについて、有力な推測を返します。

<a id="%E4%BE%8B2%EF%BC%89%E8%A8%AD%E8%A8%88%E3%81%AE%E4%BE%9D%E9%A0%BC"></a>


#### 例2）設計の依頼

2つ目は、ほかのモジュールが依存する新しい仕組みを入れる場面です。

poteto氏は、外部から届く webhook に、レート制限（一定時間に受け付ける要求の数の上限）を設ける設計を頼んでいます。

```
/poteto-mode we need to add rate limiting for external webhooks. /architect this first, and answer any open questions with prototypes. let me review before proceeding.
// 外部の webhook にレート制限を追加する必要がある。まず /architect で設計して、未解決の疑問はプロトタイプで答えて。進める前に私にレビューさせて。
```

<aside class="msg message"><span class="msg-symbol">!</span><div class="msg-content">
<p class="code-line" data-line="674"><strong>webhook</strong>・・・ 指定したURLにHTTPリクエストを送って、別のシステムにイベントを知らせる仕組みです（<a href="https://zenn.dev/sc30gsw/books/080faba713547b/viewer/46bd1f" target="_blank">第25章</a>）。</p>
</div></aside>

この依頼は、設計の進め方に加えて、「進める前に私にレビューさせて」と止まる場所を指定しています。

この依頼を受けたエージェントは、今の webhook の仕組みを調べ、複数のモデルで設計案を競わせ、使い捨てのプロトタイプで性能を測って、整理された、検証済みのインターフェースを作ります。

<a id="%E4%BE%8B3%EF%BC%89%E7%A7%BB%E8%A1%8C%E3%81%AE%E8%A8%88%E7%94%BB"></a>


#### 例3）移行の計画

3つ目は、多くのファイルにまたがる移行の計画です。poteto氏は、UIライブラリ全体を[StyleX](https://stylexjs.com/)（JavaScriptのコードの中でスタイルを書くためのライブラリ）へ移す作業を、複数のPRに分けた計画にするよう頼んでいます。

```
/poteto-mode create a plan to migrate our entire UI library to StyleX. break the migration into small, verifiable PRs. each PR must have its visual regression tests and live verification steps. i want the final result to be 100% identical compared to the original - bugs included
// UIライブラリ全体をStyleXへ移す計画を作って。移行は、小さく検証できるPRに分けて。各PRには、見た目の回帰テストと、動くアプリで確かめる検証手順を必ず持たせて。最終結果は、不具合も含めて元と100%同じにしたい。
```

この依頼は、目的（UIライブラリ全体をStyleXへ移す）のほかに次の3つを指定していますが、どう移すかの手順は指定していません。

- <strong>移行の分け方</strong>・・・ 小さく検証できるPR
- <strong>各PRが持つべき検証</strong>・・・ 見た目の回帰テスト（変更の前後で画面の見た目が変わっていないかを確かめるテスト）と、動くアプリで確かめる手順
- <strong>最終結果の条件（制約）</strong>・・・ 不具合も含めて元と同じ

この依頼を受けたエージェントは、作業を互いに独立した段階に分け、点検できるチェックリストを書き、各段階を、ビルド、検証、マージまで安全に進められるように準備します。

<a id="%E4%BE%8B4%EF%BC%89slack%E3%81%A7%E5%A0%B1%E5%91%8A%E3%81%95%E3%82%8C%E3%81%9F%E4%B8%8D%E5%85%B7%E5%90%88%E3%81%AE%E4%BF%AE%E6%AD%A3"></a>


#### 例4）Slackで報告された不具合の修正

4つ目は、Slackで報告された不具合の修正です。

この場面の依頼は2つあります。

1つ目の依頼は、Slackのスレッドにすでに十分なコンテキストがあるときのものです。

```
# thread already has sufficient context
/poteto-mode do it
// （スレッドには十分なコンテキストがすでにある）これをやって。
```

2つ目の依頼は、再現の手段と証拠を指定するものです。

```
/poteto-mode repro this with /control-app. if it repros on main, fix it and show me a video as proof
// /control-app でこれを再現して。main で再現したら、直して、証拠として動画を見せて。
```

<aside class="msg message"><span class="msg-symbol">!</span><div class="msg-content">
<p class="code-line" data-line="720"><strong>検証スキル</strong>・・・ エージェントがアプリを起動・操作して証拠を取るための、プロジェクト専用のSkillです。<br/>
利用者が <code>/create-verification-skill</code> を実行すると、エージェントが作ります。</p>
</div></aside>

`/control-app` は、『The Complete Guide to pstack』[Part 1](https://x.com/poteto/status/2094457600259842065)で作った検証スキルを指す、記事での呼び名です（[第36章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/7d7081)）。

<a id="4%E3%81%A4%E3%81%AE%E4%BE%8B%E3%81%AB%E5%85%B1%E9%80%9A%E3%81%99%E3%82%8B%E3%81%93%E3%81%A8"></a>


#### 4つの例に共通すること

このように、4つの場面の依頼はどれも、<strong>細かな手順は `/poteto-mode` に任せ、目的と、必要に応じて次のことを伝えています</strong>。

- 制約
- 確認したい結果（結果の形）
- レビューのタイミング（止まる場所）

ただし、[例2](#%E4%BE%8B2%EF%BC%89%E8%A8%AD%E8%A8%88%E3%81%AE%E4%BE%9D%E9%A0%BC)の `/architect` や[例4](#%E4%BE%8B4%EF%BC%89slack%E3%81%A7%E5%A0%B1%E5%91%8A%E3%81%95%E3%82%8C%E3%81%9F%E4%B8%8D%E5%85%B7%E5%90%88%E3%81%AE%E4%BF%AE%E6%AD%A3)の `/control-app` のように、依頼の中で使う手段を指定することもあります。

また、[例4](#%E4%BE%8B4%EF%BC%89slack%E3%81%A7%E5%A0%B1%E5%91%8A%E3%81%95%E3%82%8C%E3%81%9F%E4%B8%8D%E5%85%B7%E5%90%88%E3%81%AE%E4%BF%AE%E6%AD%A3)の `do it` では、目的やコンテキストは依頼ではなく、Slackのスレッドに書かれています。

<a id="pstack%EF%BC%9Askill%E3%81%AE%E5%90%8D%E5%89%8D%E3%81%AF%E3%80%81%E9%81%B8%E6%8A%9E%E3%82%92%E4%B8%8A%E6%9B%B8%E3%81%8D%E3%81%97%E3%81%9F%E3%81%84%E3%81%A8%E3%81%8D%E3%81%A0%E3%81%91%E6%9B%B8%E3%81%8F"></a>


### pstack：Skillの名前は、選択を上書きしたいときだけ書く

同梱ガイドの [`docs/guide/02-poteto-mode.md`](https://github.com/cursor/plugins/blob/main/pstack/docs/guide/02-poteto-mode.md) は、`/poteto-mode` が依頼の種類を見てPlaybookを選び、Playbookの手順の中で必要なSkillを呼ぶと説明しています。

そのため、<strong>利用者は、どのSkillをどの順で使うかを依頼に書かずに済みます</strong>。

同ページは、Skillの名前を書くのは次の場合だけにするよう勧めています（[第7章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/4fda7d)）。

> Name a skill only when you want to override a specific choice.
>
> Skillの名前を書くのは、特定の選択を上書きしたいときだけにする。

ただし、[例2](#%E4%BE%8B2%EF%BC%89%E8%A8%AD%E8%A8%88%E3%81%AE%E4%BE%9D%E9%A0%BC)のように、ほかのモジュールが依存する新しい仕組みを入れる変更では、`/poteto-mode` も、[要点9](#%E8%A6%81%E7%82%B99%EF%BC%9A%2Farchitect%E3%81%A7%E3%80%81%E8%A4%87%E6%95%B0%E3%81%AE%E8%A8%AD%E8%A8%88%E3%82%92%E6%AF%94%E8%BC%83%E3%83%BB%E7%B5%B1%E5%90%88%E3%81%99%E3%82%8B)（`/architect`で、複数の設計を比較・統合する）で見た、次の基準を当てはめて、自分で `/architect` を選ぶことがあります。

> そのうえで、<strong>関数の境界をまたぐ変更や、責任の所在（どのモジュールが責任を持つか）を移す変更</strong>を `/architect` の対象としています。

本書では、[例2](#%E4%BE%8B2%EF%BC%89%E8%A8%AD%E8%A8%88%E3%81%AE%E4%BE%9D%E9%A0%BC)の依頼が `/architect` と書いているのは、`/architect` を使うかどうかを `/poteto-mode` の判断に任せず、実装より先に必ず設計させるためだと考えます。

<a id="13%E3%81%AE%E8%A6%81%E7%82%B9%E3%82%92%E3%80%81%E4%B8%80%E3%81%A4%E3%81%AE%E6%B5%81%E3%82%8C%E3%81%A8%E3%81%97%E3%81%A6%E8%AA%AD%E3%82%80"></a>


## 13の要点を、一つの流れとして読む

13の要点を並べると、[第6部](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/b22889)の「[この部の章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/b22889#%E3%81%93%E3%81%AE%E9%83%A8%E3%81%AE%E7%AB%A0)」の表で示した、3つの段階の流れになります。

1. <strong>問題を理解する</strong>（要点1〜4、[第37章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/b4b9a1)）・・・ 人間が、エージェントに問題を自分と同じように理解させ、過去の作業のコンテキストを引き継がせる
2. <strong>解決策を試す</strong>（要点5〜8、[第38章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/7549a7)）・・・ エージェントが、使い方を書いた文書とプロトタイプで解決策を試し、人間が設計案を選ぶ
3. <strong>解決策を固めて、実行できる計画に変える</strong>（要点9〜13、この章）・・・ エージェントが、複数の案を比べて設計を固め、実装で得た証拠をもとに設計を見直し、検証できる計画に変える。計画書は一時的な文書で、poteto氏は、作業が終われば通常は消す、としている。人間は、入口の `/poteto-mode` に、手順ではなく、目的、制約、確認したい結果、レビューのタイミングを伝える

3つの段階に共通するのは、<strong>判断の根拠を、文章だけの計画ではなく、調べて得た証拠や動かした結果に置くこと</strong>だと、本書では考えます。

具体的には、判断の根拠にするのは、次の2種類の証拠です。

- コードや履歴を調べて得た証拠（[要点3：/how・/why・/teachで、仕組みと理由を知る](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/b4b9a1#%E8%A6%81%E7%82%B93%EF%BC%9A%2Fhow%E3%83%BB%2Fwhy%E3%83%BB%2Fteach%E3%81%A7%E3%80%81%E4%BB%95%E7%B5%84%E3%81%BF%E3%81%A8%E7%90%86%E7%94%B1%E3%82%92%E7%9F%A5%E3%82%8B)／[要点4：/recallで、過去の作業を新しい会話へ引き継ぐ](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/b4b9a1#%E8%A6%81%E7%82%B94%EF%BC%9A%2Frecall%E3%81%A7%E3%80%81%E9%81%8E%E5%8E%BB%E3%81%AE%E4%BD%9C%E6%A5%AD%E3%82%92%E6%96%B0%E3%81%97%E3%81%84%E4%BC%9A%E8%A9%B1%E3%81%B8%E5%BC%95%E3%81%8D%E7%B6%99%E3%81%90)）
- プロトタイプを操作した結果や測定値、実装したときに無関係な箇所に現れた同じ回避策のような、実際に作って動かして得た証拠（[要点7：複数案のプロトタイプで比べる](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/7549a7#%E8%A6%81%E7%82%B97%EF%BC%9A%E8%A4%87%E6%95%B0%E6%A1%88%E3%81%AE%E3%83%97%E3%83%AD%E3%83%88%E3%82%BF%E3%82%A4%E3%83%97%E3%81%A7%E6%AF%94%E3%81%B9%E3%82%8B)／[要点8：疑問は、実験で確かめさせる](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/7549a7#%E8%A6%81%E7%82%B98%EF%BC%9A%E7%96%91%E5%95%8F%E3%81%AF%E3%80%81%E5%AE%9F%E9%A8%93%E3%81%A7%E7%A2%BA%E3%81%8B%E3%82%81%E3%81%95%E3%81%9B%E3%82%8B)／[要点10：実装で設計の誤りが分かったら、設計を見直す](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/166acb#%E8%A6%81%E7%82%B910%EF%BC%9A%E5%AE%9F%E8%A3%85%E3%81%A7%E8%A8%AD%E8%A8%88%E3%81%AE%E8%AA%A4%E3%82%8A%E3%81%8C%E5%88%86%E3%81%8B%E3%81%A3%E3%81%9F%E3%82%89%E3%80%81%E8%A8%AD%E8%A8%88%E3%82%92%E8%A6%8B%E7%9B%B4%E3%81%99)）

記事も、最後の節『The art of planning』で、<strong>抽象的な計画（まだコードで形にしていない、文章だけの計画）は、作業が進んでいるという錯覚を人間に与えるだけだ</strong>と書いています。

長い計画書は、人間とエージェントがよく働いたように見せるものの、おそらく中身が伴っていない、とも書いています。

そのうえで、pstackは、<strong>次の3つを組み合わせるための道具になる</strong>と述べています。

- 徹底した調査
- 実際に試して得た証拠
- 厳密な検証

そして、この節を次の文で締めくくっています。

> When you plan this way, engineering with agents stops feeling like a gamble. It becomes predictable and repeatable.
>
> このように計画すれば、エージェントとのエンジニアリングは賭けのようには感じられなくなる。予測でき、繰り返せるものになる。

## まとめ

- <strong>要点9：/architectで、複数の設計を比較・統合する</strong>・・・ 大きな変更では、人間はアーキテクチャやデータ構造、システムどうしの連携を考えることに時間を使い、エージェントは実装の細部を埋めることに時間を使います。エージェントは、`/architect` で、まず複数の設計案を比べて1つに統合し、それから実装します。
- <strong>要点10：実装で設計の誤りが分かったら、設計を見直す</strong>・・・ エージェントは、骨組みとの食い違いが見つかったり、無関係な箇所に同じ回避策や型の逃げ道が繰り返し現れたりしたら、それらを設計が間違っている証拠とみなして設計を見直します。必要なら、骨組みを捨てて、問題を調べる段階から設計をやり直します。
- <strong>要点11：小さく検証できる作業に分ける</strong>・・・ エージェントは、計画用のPlaybookで、作業を小さく検証できるPRに分け、PRごとに、テストだけでなく実際に動かして確かめた結果を完了の証拠として定めます。計画は、利用者が開始を指示してから実行されます。
- <strong>要点12：計画書は一時的なもの</strong>・・・ 計画書は、作業を実行するときと、大きな作業の進み具合をほかのエージェントに知らせるときに使う一時的な文書で、poteto氏は、作業が終わったら通常は削除します。
- <strong>要点13：/poteto-modeに伝えること</strong>・・・ 人間は、`/poteto-mode` に、手順ではなく、目的、制約、確認したい結果、レビューのタイミングを伝えます。
- <strong>13の要点の流れ</strong>・・・ どの段階にも共通するのは、判断の根拠を文章だけの計画ではなく、調べて得た証拠や動かした結果に置くことだと、本書では考えます。
