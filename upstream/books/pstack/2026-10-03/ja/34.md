この章では、[`/show-me-your-work`](https://github.com/cursor/plugins/blob/main/pstack/skills/show-me-your-work/SKILL.md) を扱います。

`/show-me-your-work` は、エージェントが何を決めたか（例：サブエージェントの成果を捨てた）と、その根拠（例：スクリーンショットが真っ白だった）を、1行に1つずつファイルに記録するSkillです。記録は、作業をしたモデルとは別系統のモデルが点検します。エージェントは、点検で見つかった注意すべき点を、返答の最後の「Attention」欄にまとめます。

[第26章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/03ebca)の検証スキルは、アプリが実際に動くことを、証拠で示すためのものです。一方、`/show-me-your-work` は、エージェントがなぜそう判断したかを、利用者が後から証拠をたどって確かめられるようにします。

`/show-me-your-work` の `SKILL.md` は、`disable-model-invocation: true` の設定を持っています（[第25章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/46bd1f)）。この設定があるSkillを、エージェントが会話の内容から自分で選んで動かすことはありません。そのため、このSkillが動くのは、利用者が名前で呼んだときか、`/poteto-mode`、Playbook、ほかのSkillが手順の中で名前を指定して呼んだときだけです。

この章では、`/show-me-your-work` を、役割、使いどき、手順、依頼の書き方の4つの観点で解説します。

<a id="%E3%81%93%E3%81%AE%E7%AB%A0%E3%81%AE%E6%A7%8B%E6%88%90"></a>


## この章の構成

この章の構成は次のとおりです。

- 役割：後から点検できる判断の記録を、一つだけ残す
- 使いどき：長時間の作業、自律的な作業、後で確かめる作業
- 手順：判断を記録し、トランスクリプト（エージェントとの会話の記録）と突き合わせ、別のモデルに点検させる
- 依頼の書き方：記録を始めさせる
- まとめ

## 役割：後から点検できる判断の記録を、一つだけ残す

`/show-me-your-work` は、長時間の作業や、利用者が席を外している間に進む作業について、後から点検できる判断の記録を、1つのファイルにまとめて残すSkillです。

同梱ガイドの [`docs/guide/07-overnight.md`](https://github.com/cursor/plugins/blob/main/pstack/docs/guide/07-overnight.md) は、エージェントに長時間の作業を任せて席を外すには、うまくいくと期待するだけでは足りず、次の3つが必要だと述べています。

- 確かめられる完了条件
- ほかの作業と衝突しない、専用の worktree（[第18章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/cdc49b)）
- 後から点検する判断の記録

このSkillは、3つ目の「後から点検する判断の記録」を受け持ちます。

判断の記録が必要なのは、<strong>コードの差分には、最後まで残った変更しか載らない</strong>からです。途中で捨てたやり方や、サブエージェントの成果を取り消した判断は、差分には現れません。

利用者が席を外している間に長時間進んだ作業では、戻った利用者の手元には差分しかありません。そこで、エージェントは判断とその根拠を記録に残し、利用者が後から、なぜそうなったのかを点検できるようにします。

<a id="%E4%BD%BF%E3%81%84%E3%81%A9%E3%81%8D%EF%BC%9A%E9%95%B7%E6%99%82%E9%96%93%E3%81%AE%E4%BD%9C%E6%A5%AD%E3%80%81%E8%87%AA%E5%BE%8B%E7%9A%84%E3%81%AA%E4%BD%9C%E6%A5%AD%E3%80%81%E5%BE%8C%E3%81%A7%E7%A2%BA%E3%81%8B%E3%82%81%E3%82%8B%E4%BD%9C%E6%A5%AD"></a>


## 使いどき：長時間の作業、自律的な作業、後で確かめる作業

`/poteto-mode` の節『[Non-negotiables](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/SKILL.md#non-negotiables)』（[第8章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/096f3d)）は、長時間の作業、自律的な作業、複数フェーズの作業、利用者が席を離れて後で確かめる作業で、この記録を求めています。

<a id="%2Fshow-me-your-work-%E3%81%AF%E3%80%81playbook%E3%82%84%E3%81%BB%E3%81%8B%E3%81%AEskill%E3%81%8B%E3%82%89%E3%82%82%E5%91%BC%E3%81%B0%E3%82%8C%E3%82%8B"></a>


### `/show-me-your-work` は、PlaybookやほかのSkillからも呼ばれる

長時間の作業を受け持つPlaybookやSkillも、このSkillで記録を残します。

このSkillの `SKILL.md` は、他のSkillが判断を記録するときの決まりを定めています。  
他のSkillは、自分で記録の形式を作らず、このSkillを名前で呼び、記録の形式をこのSkillに任せます。

そのため、どのPlaybookやSkillから呼ばれても、記録は同じ形式になり、利用者は同じ見方で記録を点検できます。

代表的な呼ぶ側と、それぞれが記録を残す理由は、次のとおりです。

<a id="%E3%80%8Eautonomous-run%E3%80%8F%EF%BC%9A%E5%8F%8D%E5%BE%A9%E3%81%AE%E3%81%9F%E3%81%B3%E3%81%AB%E3%80%81%E4%BD%95%E3%82%92%E5%A4%89%E3%81%88%E3%80%81%E5%AE%8C%E4%BA%86%E6%9D%A1%E4%BB%B6%E3%81%AB%E8%BF%91%E3%81%A5%E3%81%84%E3%81%9F%E3%81%8B%E3%82%92%E6%AE%8B%E3%81%99"></a>


#### 『Autonomous run』：反復のたびに、何を変え、完了条件に近づいたかを残す

『[<strong>Autonomous run</strong>](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/playbooks/autonomous-run.md)』は、完了条件を決めて、途中で止まらずに最後まで作業を進めるPlaybookです（[第15章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/7d7609)）。

このPlaybookは、手順5で、反復のたびに、このSkillで1行、記録するよう定めています。行に書くのは、その反復で何を変えたかと、完了条件に近づいたかどうかです。

<a id="%E3%80%8Eorchestrate%E3%80%8F%EF%BC%9A%E4%BD%95%E6%97%A5%E3%82%82%E7%B6%9A%E3%81%8F%E3%83%97%E3%83%AD%E3%82%B8%E3%82%A7%E3%82%AF%E3%83%88%E3%81%AE%E5%88%A4%E6%96%AD%E3%82%92%E3%80%811%E3%81%A4%E3%81%AE%E8%A8%98%E9%8C%B2%E3%81%AB%E3%81%BE%E3%81%A8%E3%82%81%E3%82%8B"></a>


#### 『Orchestrate』：何日も続くプロジェクトの判断を、1つの記録にまとめる

『[<strong>Orchestrate</strong>](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/playbooks/orchestrate.md)』は、コードを書かない1体のコーディネーターエージェントが、何日も続く多数のPRの作業を管理するPlaybookです（[第16章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/8a8dd5)）。

このPlaybookは、プロジェクトの記録を置くディレクトリの `decisions.tsv` を、このSkillの記録にすると定めています。

コーディネーターエージェントは、サブエージェントを起動し始める前の準備の手順（Install the runtime）でこの記録を始め、最後の手順（Close）で、このSkillの決まりどおりに記録を確かめ、別系統のモデルにも点検させます。

このPlaybookは、利用者が5分ごとに様子を見るのではなく、1日に2回ほど様子を見る前提で作られています。また、Close の手順では、記録を含むディレクトリを消さずに残し、振り返りの資料（postmortem）として使うよう定めています。

<a id="%2Ffigure-it-out%EF%BC%9A%E8%A8%98%E9%8C%B2%E3%81%A8%E5%B7%AE%E5%88%86%E3%81%8C%E3%81%9D%E3%82%8D%E3%81%A3%E3%81%A6%E3%80%81%E5%88%A9%E7%94%A8%E8%80%85%E3%81%AF%E4%BD%9C%E6%A5%AD%E3%82%92%E4%BF%A1%E9%A0%BC%E3%81%A7%E3%81%8D%E3%82%8B"></a>


#### `/figure-it-out`：記録と差分がそろって、利用者は作業を信頼できる

`/figure-it-out` は、利用者の依頼に合致するPlaybookがない大きな作業のために、Playbookそのものを設計するSkillです（[第23章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/3ce2b2)）。

`/figure-it-out` は、作業の記録を残す段階（Phase D）で、このSkillで作業を記録します。`/figure-it-out` が扱う作業はたいてい大きいので、エージェントは記録をコミットし、レビューする人がPRの中で読めるようにします。<strong>記録と差分がそろって初めて、利用者は作業を信頼できる</strong>からです。

<a id="%E6%89%8B%E9%A0%86%EF%BC%9A%E5%88%A4%E6%96%AD%E3%82%92%E8%A8%98%E9%8C%B2%E3%81%97%E3%80%81%E3%83%88%E3%83%A9%E3%83%B3%E3%82%B9%E3%82%AF%E3%83%AA%E3%83%97%E3%83%88%EF%BC%88%E3%82%A8%E3%83%BC%E3%82%B8%E3%82%A7%E3%83%B3%E3%83%88%E3%81%A8%E3%81%AE%E4%BC%9A%E8%A9%B1%E3%81%AE%E8%A8%98%E9%8C%B2%EF%BC%89%E3%81%A8%E7%AA%81%E3%81%8D%E5%90%88%E3%82%8F%E3%81%9B%E3%80%81%E5%88%A5%E3%81%AE%E3%83%A2%E3%83%87%E3%83%AB%E3%81%AB%E7%82%B9%E6%A4%9C%E3%81%95%E3%81%9B%E3%82%8B"></a>


## 手順：判断を記録し、トランスクリプト（エージェントとの会話の記録）と突き合わせ、別のモデルに点検させる

<a id="%E5%BD%A2%E5%BC%8F%EF%BC%9A%E5%88%A4%E6%96%AD%E3%82%921%E8%A1%8C%E3%81%AB1%E3%81%A4%E3%81%9A%E3%81%A4%E3%80%816%E5%88%97%E3%81%AEtsv%E3%81%A7%E6%9B%B8%E3%81%8F"></a>


### 形式：判断を1行に1つずつ、6列のTSVで書く

このSkillは、判断の記録を、TSV（列をタブで区切ったテキストの表）で残します。点検する人が記録を上から順に読み、証拠をたどって確かめられるようにするためです。  
※ TSVの例は後述します。

<strong>1行に1つの判断を書き、証拠は文章で書かず、証拠の在りかを指すポインタ（コミットやファイルなど、証拠のある場所を示す手がかり）にします</strong>。証拠を文章で書くと、点検する人は実物を見られず、その文章を信じるしかなくなります。ポインタなら、たどって実物を確かめられます。

列は次の6つです。いつ、どの段階で、何を、なぜ決め、何がその裏づけで、どうなったか、という順になっています。

`SKILL.md` に載っている例から、見出しの行と2行を抜き出すと、TSVは次のようになります（列の間はタブです）。

```
ts	phase	decision	why	evidence	result
2026-05-24T11:15:00Z	widget	moved the widget styles over without changing how it looks	keep the change small and the result identical	commit 7c21e0a, pixel-diff 0	looks identical, tests pass
2026-05-24T12:30:00Z	widget	threw out a helper's work because its screenshots were blank	checked the real files instead of trusting its summary	worktree reset	reverted, tightened the instructions for next time
```

1行目は、「見た目を変えずに、ウィジェットのスタイルを移した」という判断です。証拠は、コミット `7c21e0a` と、画素の差が0だったこと（`pixel-diff 0`）です。点検する人は、このコミットを開けば、実物を確かめられます。

2行目は、「サブエージェントの成果を捨てた。スクリーンショットが真っ白だったから」という判断です。エージェントは、サブエージェントの「できました」という要約を信じず、実際のファイルを確かめてから捨てています。

エージェントが記録するのは、すべての行動ではなく、判断の分かれ目です。当たり前のことや、些細な行動は記録しません。

エージェントが1行を記録するタイミング例は次のとおりです。

- 2つのやり方のどちらかを選んだとき
- 作業の一区切りを終えて確認の結果が出たとき
- 方針を変えたり変更を取り消したりしたとき
- 先へ進めない問題にぶつかったとき

エージェントは、各行を、平易な言葉で書きます。AIらしい言い回しを削る `/unslop`（[第32章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/44857b)）の決まりも、ログの文に当てはめます。

### 追記と置き場所：log.sh で判断の行を追記する

<a id="%E3%82%A8%E3%83%BC%E3%82%B8%E3%82%A7%E3%83%B3%E3%83%88%E3%81%AF%E3%80%81log.sh-%E3%81%A71%E8%A1%8C%E3%81%9A%E3%81%A4%E8%BF%BD%E8%A8%98%E3%81%99%E3%82%8B"></a>


#### エージェントは、log.sh で1行ずつ追記する

エージェントは、行の追加に [`scripts/log.sh`](https://github.com/cursor/plugins/blob/main/pstack/skills/show-me-your-work/scripts/log.sh) を使います。

```
scripts/log.sh <logfile> <phase> <decision> <why> <evidence> <result>
```

スクリプトは、タイムスタンプを自動で入れたり、セル内のタブや改行を空白に置き換えたりして、行をTSVの形式に整えます。

<a id="%E3%83%AD%E3%82%B0%E3%81%AF%E4%BD%9C%E6%A5%AD%E3%83%87%E3%82%A3%E3%83%AC%E3%82%AF%E3%83%88%E3%83%AA%E3%81%AB%E7%BD%AE%E3%81%8D%E3%80%81%E5%A4%A7%E3%81%8D%E3%81%AA%E4%BD%9C%E6%A5%AD%E3%81%AE%E3%81%A8%E3%81%8D%E3%81%A0%E3%81%91%E3%82%B3%E3%83%9F%E3%83%83%E3%83%88%E3%81%99%E3%82%8B"></a>


#### ログは作業ディレクトリに置き、大きな作業のときだけコミットする

エージェントは、ログを作業ディレクトリの `decisions.tsv` に置き、既定ではコミットしません。エージェントがログをコミットするのは、点検する人が結果を信じるのに、判断の記録まで必要になるくらい、大きな作業のときだけです。

たとえば、「約100個のコンポーネントのスタイルを、見た目を変えずに移した」というような、作業の場合が、該当します。

コードを読めば、何が変わったかは分かりますが、見た目が本当に変わっていないことを何で確かめたか、途中でどのやり方を捨てたかは、コードには残りません。

したがって、作業が大きいほど、こうした判断は増えるので、点検する人は、コミットされたログで判断と証拠をたどって、報告された成果を確かめます。

<a id="%E9%96%93%E9%81%95%E3%81%A3%E3%81%9F%E5%88%A4%E6%96%AD%E3%81%AF%E3%80%81%E8%A1%8C%E3%82%92%E6%9B%B8%E3%81%8D%E6%8F%9B%E3%81%88%E3%81%9A%E3%81%AB%E3%80%81%E8%A8%82%E6%AD%A3%E3%81%99%E3%82%8B%E8%A1%8C%E3%82%92%E8%BF%BD%E5%8A%A0%E3%81%97%E3%81%A6%E7%9B%B4%E3%81%99"></a>


#### 間違った判断は、行を書き換えずに、訂正する行を追加して直す

<strong>ログは追記のみで、間違った判断は、それを訂正する新しい行を追加して直します</strong>。行を書き換えたり消したりすると、途中で判断を改めた経緯が記録から見えなくなるからです。

<a id="%E6%96%B0%E3%81%97%E3%81%84%E5%AE%9F%E8%A1%8C%E3%81%AF%E3%80%81%E6%9C%80%E5%88%9D%E3%81%AB-start-%E3%81%AE%E8%A1%8C%E3%82%92%E6%9B%B8%E3%81%8D%E3%80%81%E5%89%8D%E3%81%AE%E5%AE%9F%E8%A1%8C%E3%81%AE%E8%A1%8C%E3%81%A8%E5%8C%BA%E5%88%87%E3%82%8B"></a>


#### 新しい実行は、最初に start の行を書き、前の実行の行と区切る

このSkillは、1つのエージェントとの1つの会話を、1回の<strong>実行</strong>（run）と数えます。同じ会話の中で、利用者が後から追加の依頼を送り、エージェントが続けて作業した分も、同じ実行に含めます。会話が長くなって要約された後に続けた分も同じく、同一の実行に含まれます。

一方、別のエージェントが作業を引き継いだときや、新しいチャットを始めたときは、新しい実行になります。

長時間の作業は、1回の実行で終わるとは限りません。途中で別のエージェントが作業を引き継いだり、利用者が新しいチャットで続きを頼んだりすることがあります。このSkillは、1つの作業の記録を1つのログ（作業ディレクトリの `decisions.tsv`）にまとめるよう定めているので、新しい実行も、前の実行が書いたログに続きを書き足します。

こうして、1つのログに、複数の実行が書いた行が並びます。どの行をどの実行が書いたかが分からないと、点検する人は、新しい実行の判断だけを取り出して読めません。

そこで、すでに行のあるログに書き足す実行のエージェントは、最初に、`phase` 列で `start` の行を1行書きます。

この `start` の行が、ここから下は新しい実行が書いた行だ、という区切りになります。`start` の行には、それより上の、自分が書いていない行のタイムスタンプの範囲と、自分の実行を示すもの（エージェントのIDなど）を書きます。

たとえば、前のチャットの実行が書いたログに、新しいチャットの実行が書き足すと、次のようになります。

```
ts	phase	decision	why	evidence	result
2026-05-24T11:15:00Z	widget	moved the widget styles over without changing how it looks	keep the change small and the result identical	commit 7c21e0a, pixel-diff 0	looks identical, tests pass
2026-05-24T12:30:00Z	widget	threw out a helper's work because its screenshots were blank	checked the real files instead of trusting its summary	worktree reset	reverted, tightened the instructions for next time
2026-05-25T09:00:00Z	start	rows 2026-05-24T11:15:00Z to 12:30:00Z were written by another run	picking up yesterday's log	agent a1b2c3	open
2026-05-25T09:40:00Z	widget	moved the button styles over	same approach as the widget	commit 9d4e2f1, pixel-diff 0	looks identical, tests pass
```

タイムスタンプが `2026-05-25T09:00:00Z` の行が、今日の実行が最初に書いた `start` の行です。点検する人は、この行より下だけを読めば、今日の実行の判断を確かめられます。

この後の[『突き合わせ：利用者に手渡す前に、ログをトランスクリプト（エージェントとの会話の記録）と照合する』](#%E7%AA%81%E3%81%8D%E5%90%88%E3%82%8F%E3%81%9B%EF%BC%9A%E5%88%A9%E7%94%A8%E8%80%85%E3%81%AB%E6%89%8B%E6%B8%A1%E3%81%99%E5%89%8D%E3%81%AB%E3%80%81%E3%83%AD%E3%82%B0%E3%82%92%E3%83%88%E3%83%A9%E3%83%B3%E3%82%B9%E3%82%AF%E3%83%AA%E3%83%97%E3%83%88%EF%BC%88%E3%82%A8%E3%83%BC%E3%82%B8%E3%82%A7%E3%83%B3%E3%83%88%E3%81%A8%E3%81%AE%E4%BC%9A%E8%A9%B1%E3%81%AE%E8%A8%98%E9%8C%B2%EF%BC%89%E3%81%A8%E7%85%A7%E5%90%88%E3%81%99%E3%82%8B)でも、エージェントは、自分の実行が書いた行だけを、自分の実行のトランスクリプトと照らし合わせます。どこから下が自分の書いた行かは、この `start` の行で見分けます。

<a id="%E7%AA%81%E3%81%8D%E5%90%88%E3%82%8F%E3%81%9B%EF%BC%9A%E5%88%A9%E7%94%A8%E8%80%85%E3%81%AB%E6%89%8B%E6%B8%A1%E3%81%99%E5%89%8D%E3%81%AB%E3%80%81%E3%83%AD%E3%82%B0%E3%82%92%E3%83%88%E3%83%A9%E3%83%B3%E3%82%B9%E3%82%AF%E3%83%AA%E3%83%97%E3%83%88%EF%BC%88%E3%82%A8%E3%83%BC%E3%82%B8%E3%82%A7%E3%83%B3%E3%83%88%E3%81%A8%E3%81%AE%E4%BC%9A%E8%A9%B1%E3%81%AE%E8%A8%98%E9%8C%B2%EF%BC%89%E3%81%A8%E7%85%A7%E5%90%88%E3%81%99%E3%82%8B"></a>


### 突き合わせ：利用者に手渡す前に、ログをトランスクリプト（エージェントとの会話の記録）と照合する

作業したエージェントは、結果を返す前に、記録が事実どおりかを確かめます。具体的には、エージェントは、この実行で書いた行を、この実行のトランスクリプトと照合します。確かめる点は次のとおりです。

- どの行も実際の判断に対応しているか
- 証拠が実在し、行に書いたとおりのことを示しているか
- 作業の形を決めた重要な分岐が、記録から欠けていないか

> Correct the log, not the story. The audit never edits or removes a row, even an invented one.
>
> 直すのはログの誤りであり、起きたことの経緯を書き換えるのではない。突き合わせでは、事実でないことを書いた行であっても、行を編集したり消したりしない

突き合わせで事実と異なる行を見つけても、エージェントは、その行を消したり書き換えたりしません。代わりに、実際に起きたことを書いた、訂正の行を追加します。この章の前の方の[『間違った判断は、行を書き換えずに、訂正する行を追加して直す』](#%E9%96%93%E9%81%95%E3%81%A3%E3%81%9F%E5%88%A4%E6%96%AD%E3%81%AF%E3%80%81%E8%A1%8C%E3%82%92%E6%9B%B8%E3%81%8D%E6%8F%9B%E3%81%88%E3%81%9A%E3%81%AB%E3%80%81%E8%A8%82%E6%AD%A3%E3%81%99%E3%82%8B%E8%A1%8C%E3%82%92%E8%BF%BD%E5%8A%A0%E3%81%97%E3%81%A6%E7%9B%B4%E3%81%99)と同じ決まりです。

たとえば、存在しないコミットを証拠に書いた行を、突き合わせで見つけたケースで見てみましょう。1行目が事実と異なる行で、2行目が、エージェントが追加した訂正の行です。

```
ts	phase	decision	why	evidence	result
2026-05-24T13:00:00Z	widget	ボタンの色を直した	見た目の崩れを直すため	commit 9d4e2b1	tests green
2026-05-24T15:20:00Z	widget	13:00の行を訂正する。ボタンの色は直しておらず、commit 9d4e2b1 は存在しない	トランスクリプトと突き合わせて、行が事実と違うと分かった	agent-transcripts/ の、この実行の記録	open
```

1行目は消さずに残るので、点検する人は、記録がどこで事実とずれ、いつ訂正されたかをたどれます。

<a id="%E7%82%B9%E6%A4%9C%EF%BC%9A%E5%88%A5%E7%B3%BB%E7%B5%B1%E3%81%AE%E3%83%A2%E3%83%87%E3%83%AB%E3%81%8C%E8%A8%98%E9%8C%B2%E3%82%92%E8%AA%AD%E3%82%80"></a>


### 点検：別系統のモデルが記録を読む

作業したエージェントは、<strong>作業をしたモデルとは別系統のモデル</strong>でサブエージェントを起動し、記録とトランスクリプトを読ませます。この<strong>点検役</strong>のサブエージェントは、作業をやり直すのではなく、利用者が注意すべき点を探し、次のようなものを拾います。

- 根拠が弱い、または根拠のない判断
- 飛ばした検証や、トランスクリプトに証拠がないのに済ませたと書いた検証
- 後から見ると危うい選択。たとえば、次のようなものです。
  - 早すぎる判断
  - 作業の範囲の広げすぎ
  - 症状（エラーや画面の崩れなど、表に現れた不具合）が見えなくなるだけで、根本原因は残ったままの修正
- 利用者が記録を斜め読みしただけでは気づかない問題

作業をしたモデルに、自分の記録を見直させるだけでは、この点検の代わりにはなりません。<strong>作業をしたモデルは、作業中に見落としたことを、再度見直したとしても、同じように見落としやすい</strong>からです。

同梱ガイドの [`docs/guide/04-design.md`](https://github.com/cursor/plugins/blob/main/pstack/docs/guide/04-design.md) も、複数のモデルに差分の弱点を探させる `/interrogate`（[第27章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/997880)）について、同じ理由を挙げています。

エージェントは、記録を残した作業の返答の最後に、必ず「Attention」欄を付けます。「Attention」欄は、点検役が見つけた、利用者が注意すべき点の一覧です。たとえば、点検役が、この章の例に出てきた次の2つの行を点検した場合を考えます。

ウィジェットのスタイルを移した判断の行<sup class="footnote-ref"><a href="#fn-e542-1" id="fnref-e542-1">[1]</a></sup>は、次のとおりです。

```
2026-05-24T11:15:00Z	widget	moved the widget styles over without changing how it looks	keep the change small and the result identical	commit 7c21e0a, pixel-diff 0	looks identical, tests pass
```

存在しないコミットを証拠に書いた行<sup class="footnote-ref"><a href="#fn-e542-2" id="fnref-e542-2">[2]</a></sup>は、次のとおりです。

```
2026-05-24T13:00:00Z	widget	ボタンの色を直した	見た目の崩れを直すため	commit 9d4e2b1	tests green
```

このとき、「Attention」欄は次のようになります（原文にない例です）。

```
Attention
reviewed by grok-4.7-xhigh-fast

- decisions.tsv の 11:15 の行：pixel-diff 0 の根拠は、トップページのスクリーンショット1枚だけ。ウィジェットを使うほかの画面は確かめていない。
- decisions.tsv の 13:00 の行：存在しない commit 9d4e2b1 を証拠にしていた。15:20 の行で訂正済みだが、ボタンの色はまだ直っていない。
```

最初の行の `reviewed by grok-4.7-xhigh-fast` は、どのモデルが点検したかを示します。その下に、点検役の指摘を1つずつ並べます。各指摘には、`decisions.tsv` のどの行（またはトランスクリプトのどの場面）についての指摘かを書きます。利用者は、指摘からその行をたどり、証拠を確かめられます。

指摘が1つもなければ、一覧の代わりに「No flags」（指摘なし）と書きます。`reviewed by` の行だけを書いて、指摘も「No flags」も書かない、ということはしません。また、「No flags」の場合も、`reviewed by` の行は省略できません。

```
Attention
reviewed by grok-4.7-xhigh-fast

No flags
```

<strong>`reviewed by` の行がなければ、利用者は、作業をしたモデル自身ではなく、別系統のモデルが本当に点検したのかを確かめられない</strong>からです。

<a id="%E4%BE%9D%E9%A0%BC%E3%81%AE%E6%9B%B8%E3%81%8D%E6%96%B9%EF%BC%9A%E8%A8%98%E9%8C%B2%E3%82%92%E5%A7%8B%E3%82%81%E3%81%95%E3%81%9B%E3%82%8B"></a>


## 依頼の書き方：記録を始めさせる

記録を始める依頼は、[README](https://github.com/cursor/plugins/blob/main/pstack/README.md) に例があります。

```
/show-me-your-work keep a decision trail i can review when i'm back.
// 戻ったときに見直せるよう、判断の記録を残して。
```

戻った利用者は、`docs/guide/07-overnight.md` にある次の依頼で、昨夜の作業の報告を受け取れます。報告の最後には「Attention」欄が付きます。

```
/show-me-your-work catch me up on what you did last night
// 昨夜やったことを教えて。
```

利用者は、返答の「Attention」欄を先に読み、次にその欄が指すログの行を読みます。「Attention」欄には、点検役が見つけた注意すべき判断だけが並ぶので、利用者は、長時間任せた作業をすべて読み直さずに済みます。

<a id="%E3%81%BE%E3%81%A8%E3%82%81"></a>


## まとめ

- <strong>役割</strong>・・・ 長時間の作業や、利用者が席を外している間に進む作業について、後から点検できる判断の記録を、1つのファイルにまとめて残します。コードの差分には、最後まで残った変更しか載らないからです。
- <strong>記録の形式</strong>・・・ 判断を6列のTSVに1行ずつ、追記のみで残します。間違った行は消さず、訂正の行を追加します。
- <strong>突き合わせ</strong>・・・ 利用者に結果を返す前に、ログをトランスクリプト（エージェントとの会話の記録）と照らし、事実と異なる行には訂正の行を追加します。
- <strong>点検と「Attention」欄</strong>・・・ 別系統のモデルが記録とトランスクリプトを読み、エージェントは、点検したモデルの名前と指摘を並べた「Attention」欄で返答を終えます。指摘がなくても、モデル名は省略しません。

次の[第29章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/4f9a46)から[第31章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/8960d3)までの3章では、コードの品質を保つ3つのSkillを1つずつ扱います。[第29章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/4f9a46)で扱うのは、TypeScriptの規則をまとめた [`/typescript-best-practices`](https://github.com/cursor/plugins/blob/main/pstack/skills/typescript-best-practices/SKILL.md) です。
