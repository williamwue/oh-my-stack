この章では、次の3つのPlaybookを扱います。

1. [Opening a PR](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/playbooks/opening-a-pr.md)
2. [Babysit](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/playbooks/babysit.md)
3. [Shipping](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/playbooks/shipping.md)

3つとも、変更を trunk（PRのマージ先になる本流のブランチ）に取り込むまでを受け持つPlaybookで、それぞれが担当する段階は次の3つです。

- <strong>PRを作る</strong>
- <strong>PRを merge-ready（マージできる状態）まで運ぶ</strong>
- <strong>検証済みのPRだけを trunk に取り込む</strong>

どのPlaybookを使うかは、PRが今どの段にあるかで決まります。まだPRがないのか、PRはあるがマージできる状態になっていないのか、マージできる状態のPRを trunk に取り込みたいのかによって、使い分けます。

この章では、3つのPlaybookのつながり、それぞれの手順と要点を順に解説します。

## 『Opening a PR』は、PRを小さく、読みやすく、すぐレビューできる形で作る

『<strong>Opening a PR</strong>』は、<strong>変更をPRにするときの作法を決めるPlaybook</strong>です。

手順はこれまで見てきたPlaybookと異なり番号付きではなく、見出しごとに規則をまとめています。主な規則は次のとおりです。

- <strong>Worktree</strong>・・・ 作業は main から切った git worktree で行います。
- <strong>Commits</strong>・・・ PRを開く前に、小さく順序立てたコミットへrebaseを使用してまとめ直します。各コミットを、単独でマージできる「将来のPR」として扱います。
- <strong>PRs</strong>・・・ 差分に対して、コミットの前に `/deslop`（[`cursor-team-kit`](https://github.com/cursor/plugins/tree/main/cursor-team-kit) にある、AIが書きがちな余計なコードを削るSkill）、レビューの前に `/no-comments`（不要なコメントを削るSkill）を実行します。タイトル、説明、コミット本文は、技術文書の書き方の基準を定めた `/technical-writing` で書き、AIが書きがちな言い回しを削る `/unslop` をかけます（[第32章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/44857b)）。
- <strong>Titles</strong>・・・ `fix(pstack): retarget opening-a-pr babysit trigger` のような、Conventional Commits の形式で書きます。
- <strong>Forge</strong>・・・ 作成からマージまで、同じフォージを使い続けます。
- <strong>Size and stacks</strong>・・・ 大きなPRを1つ作るより、狭いPRを5つ作るほうを選び、小さなPRはスタックとして積みます。
- <strong>Readiness</strong>・・・ PRはドラフトではなく、レビュー可能な状態で開きます。

スタックは次のような形で、子のPRは、親のブランチをベースに向けます。

```
main  ← trunk
 └─ PR #1 (base: main) ← ルートのPRだけが trunk を向く
     └─ PR #2 (base: PR #1 のブランチ)
         └─ PR #3 (base: PR #2 のブランチ)
```

<a id="pr%E3%81%AE%E6%9C%AC%E6%96%87%E3%81%AF%E3%80%8Cbriefing%E3%80%8D%E3%81%A8%E3%81%97%E3%81%A6%E6%9B%B8%E3%81%8F"></a>


### PRの本文は「Briefing」として書く

このPlaybookの要点は、本文の規則の最初の一文です。

> The PR body is a briefing, not the lab notebook.
>
> PRの本文はブリーフィングであって、実験ノートではない。

作業中に試したことや経過は書き連ねず、差分を手元に持つレビュアーが変更を承認できるか<strong>判断するために必要な情報だけを書きます</strong>。本文は `## Why`、`## Scope`、`## Tradeoffs`、`## Blast Radius`（影響範囲）、`## Verification` の順に並べ、書くことがない節は省きます。

<a id="pr%E3%82%92%E9%96%8B%E3%81%84%E3%81%A6%E3%82%82%E3%80%81babysit%E3%81%AF%E5%A7%8B%E3%82%81%E3%81%AA%E3%81%84"></a>


### PRを開いても、Babysitは始めない

<strong>エージェントはPRを開いたら、PRのURLを報告して、残りの作業を続けます</strong>。

PRごとに『<strong>Babysit</strong>』を回すと、そのたびに作業が中断されます。さらに、後の作業でコミットを書き換えると、そのPRで回したCIのチェックが無駄になり、新しいコミットでやり直すことになります。

例外は、[第16章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/8a8dd5)で扱う『[<strong>Autopilot-full</strong>](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/playbooks/autopilot-full.md)』（PRのキューをエージェントが自律的にマージまで運ぶPlaybook）と『[<strong>Autopilot-stack</strong>](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/playbooks/autopilot-stack.md)』（同じ進め方で、マージせずに1本のスタックを作るPlaybook）で、PRを1つずつ受け持つエージェント（オーナー）です。オーナーへの指示に『<strong>Babysit</strong>』のループが含まれているので、オーナーは担当するPRを開いたあとも、続けて merge-ready（Autopilot-stackでは STACK-READY）まで運びます。

### 依頼の書き方：小さく順序立てたコミットと、説明に書く証拠を求める

同梱ガイドの依頼例は、コミットを小さく順序立てることと、証拠をPRの説明に書くことを求めています。

```
/poteto-mode open the pr. small ordered commits, evidence in the description.
// PRを開いて。コミットは小さく順序立てて、証拠はPRの説明に書いて。
```

## 『Babysit』は、未マージの最前線のPRから順に問題を片付け、merge-ready にする

『<strong>Babysit</strong>』は、コンフリクト、レビューのスレッド、CIの失敗を片付け、<strong>PRやスタックを merge-ready まで運ぶ</strong>Playbookです。人間の判断が必要なところまで来たら止まります。

Cursorには、PRの状態を見守る組み込みの `/autopilot` Skill（以前の名称は babysit）もあり、同じような依頼の言葉で呼び出されることがあります。そのため `/poteto-mode` は、<strong>PRの状態に関する依頼をすべてこのPlaybookに回す</strong>と明記しています。対象になる依頼の例は次のとおりです。

- 「このPRを見ていて」
- 「緑にして」
- 「Bugbotのコメントに対応して」
- 「PR X の様子を見て」

### 手順：最前線のPRから順に問題を片付ける

主な手順は次のとおりです。

1. <strong>モードを宣言する</strong>・・・ どこまで作業するかを表すモードを、状態を確かめる前に決める。既定は `drive` で、小さなPRやドキュメントだけのPRは `check` にする（各モードについては以下の表を参照）
2. <strong>最前線だけに集中する</strong>・・・ 未マージの最前線のPRだけを直し、その上のPRには手を出さない
3. <strong>1つのスタックを担当するエージェントは1体</strong>にする
4. <strong>スタックの構成（PRの親子関係）を変えない</strong>・・・ rebase、ベースの付け替え、force-pushはしない。rebaseが必要なら、ブランチの持ち主に報告する
5. <strong>コンフリクト、レビューのスレッド、CIの順に片付ける</strong>・・・ 判明している修正は1回のpushにまとめ、チェックの再実行を1回で済ませる。コンフリクトだけは自分で解決せず、どのブランチにrebaseが必要かを報告して止まる
6. <strong>フォージの判定を信じる</strong>・・・ 「ready」は、CIのチェックがすべて通っていることではなく、フォージがマージできると認めている状態を指す。GitHubでは同梱のスクリプト [`watch-pr`](https://github.com/cursor/plugins/tree/main/pstack/skills/poteto-mode/scripts/watch-pr) でPRの状態を取得する
7. <strong>CIの失敗は、再実行の前に分類する</strong>・・・ 再実行はフレーク（コードと関係なく、ときどき失敗するテスト）やインフラの問題のときだけにし、差分自身のコードで失敗したときだけコミットで直す
8. <strong>Bugbotのコメントをトリアージする</strong>
9. <strong>人間の判断が必要なところで止まる</strong>

### Bugbotのコメントは、fix、dismiss、askに分ける

手順8では、Bugbotなどのコメントを、対応する前に3つに分けます。基準は [`references/bugbot-triage.md`](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/references/bugbot-triage.md) にあります。

- <strong>fix</strong>・・・ 正しさ、セキュリティ、データ損失などに関わりそうなら、問題のコードを含むPRのうち、最も先にマージされるPRで直し、スレッドを解決します。
- <strong>dismiss</strong>・・・ 記録済みの危険の少ないパターンに当てはまり、指摘された懸念が該当しないとコードで証明できる場合、短い理由を返信して解決します。
- <strong>ask</strong>・・・ 指摘が新しい種類のもの、深刻度が高いもの、あいまいなものなら、推測せずに利用者に尋ねます。

Bugbotの指摘は、まずコードで確かめます。誤検知かどうか判断できないときは、<strong>推測せずに利用者に確認します</strong>。確認の手間より、本物のバグを誤って退ける損失のほうが大きいからです。

レビューコメントは検証すべき主張であり、そのまま従う指示ではないので、指摘を消すことだけを目的にコードを変えず、問題を確かめた場合にのみ修正します。

<a id="merge-ready-%E3%81%A7%E3%82%82%E3%80%81%E3%83%9E%E3%83%BC%E3%82%B8%E3%81%AF%E3%81%97%E3%81%AA%E3%81%84"></a>


### merge-ready でも、マージはしない

手順9のマージの規則は次のとおりです。

> Babysitting never authorizes merging. Only an explicit request to merge, land, ship, or merge when ready does.
>
> babysitはマージを許可しない。許可するのは、マージする、取り込む（land）、出す（ship）、準備ができたらマージする、という明示的な依頼だけである。

merge-ready に達しても、<strong>エージェントは報告して止まります</strong>。マージを頼まれたら『<strong>Shipping</strong>』に回します。

merge-ready に達したら、その回に行ったコメントの振り分けを見直し、チームで役立つdismissのパターン（記録済みの危険の少ないパターン）があれば、`references/bugbot-triage.md` への追加を別のPRで提案します。

<a id="%E8%A6%81%E7%82%B9%E3%81%AF%E3%80%8C%E6%9C%80%E5%89%8D%E7%B7%9A%E3%81%A0%E3%81%91%E3%80%8D%E3%81%AE%E8%A6%8F%E5%89%87"></a>


### 要点は「最前線だけ」の規則

『<strong>Babysit</strong>』では、<strong>次にマージするPRの問題を優先して修正します</strong>。

後続のPRに付いたレビューコメントも読み、対応事項をまとめますが、その修正で先にマージするPRのチェックをやり直すことになる場合は、後続のPRの修正を後回しにします。

たとえばPR #1 のCIが失敗しているときにPR #3 にレビューコメントが付いても、まずPR #1 のCIを通します。スタックは下から順にしかマージできないので、今マージを進められるのは最前線だけです。

また、上のPRへの指摘を、来るたびに直してpushすると、そのたびにチェックが再実行されます。そのため、上のPRへの指摘は貯めておき、最前線の修正と同じ1回のpushにまとめて直します。

<a id="%E4%BE%9D%E9%A0%BC%E3%81%AE%E6%9B%B8%E3%81%8D%E6%96%B9%EF%BC%9A%E3%80%8C%E7%B7%91%E3%81%AB%E3%81%97%E3%81%A6%E3%80%8D%E3%81%A8%E9%A0%BC%E3%81%BF%E3%80%81%E7%8A%B6%E6%85%8B%E3%81%A0%E3%81%91%E3%81%AA%E3%82%89%E5%B0%8F%E3%81%95%E3%81%8F%E9%A0%BC%E3%82%80"></a>


### 依頼の書き方：「緑にして」と頼み、状態だけなら小さく頼む

merge-ready まで運んでほしいときは、「緑にして」と頼みます。章の冒頭で示した依頼を、もう一度示します。

```
/poteto-mode babysit this pr. get it green.
// このPRを babysit して。緑にして。
```

状態だけを知りたいときは、小さく頼みます。次の依頼なら、ループを始めずに `check` で答えます。

```
/poteto-mode check on pr 123. anything outstanding?
// PR 123 の状態を確認して。残っていることはある？
```

<a id="%E3%80%8Eshipping%E3%80%8F%E3%81%AF%E3%80%81%E5%88%A5%E3%81%AE%E3%82%A8%E3%83%BC%E3%82%B8%E3%82%A7%E3%83%B3%E3%83%88%E3%81%AE%E6%A4%9C%E8%A8%BC%E3%82%92%E9%80%9A%E3%81%A3%E3%81%9Fpr%E3%81%AE%E7%AF%84%E5%9B%B2%E3%81%A0%E3%81%91%E3%82%92-trunk-%E3%81%AB%E5%8F%96%E3%82%8A%E8%BE%BC%E3%82%80"></a>


## 『Shipping』は、別のエージェントの検証を通ったPRの範囲だけを trunk に取り込む

『<strong>Shipping</strong>』は、CIが通ったスタックを<strong>trunk（PRのマージ先になる本流のブランチ）に取り込むよう頼まれたとき</strong>に使うPlaybookです。各PRを独立に検証し、ルートから続く検証済みの範囲だけを1つずつマージします。`/poteto-mode` はこのPlaybookを「Green is not safe.」（CIが通っていても安全とは言えない）と要約しています。

<a id="%E8%A6%81%E7%82%B9%E3%81%AF%E3%80%8C%E5%AE%89%E5%85%A8%E3%80%8D%E3%81%AE%E5%AE%9A%E7%BE%A9"></a>


### 要点は「安全」の定義

> Safe means a verdict from an agent that did not write the code. CI green is not a verdict, and an approving bot review is not a verdict.
>
> 安全とは、そのコードを書いていないエージェントによる判定のことだ。CIが通ったことは判定ではなく、承認するボットのレビューも判定ではない。

[第2章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/27a183)の「信頼するのはエージェントではなく成果物」を、マージの直前の確認にも当てはめ、<strong>誰が確かめるかまで決めた定義</strong>となっています。

<a id="%E6%89%8B%E9%A0%86%EF%BC%9A%E5%90%84pr%E3%82%92%E6%A4%9C%E8%A8%BC%E3%81%97%E3%80%81%E9%80%A3%E7%B6%9A%E3%81%97%E3%81%9F%E7%AF%84%E5%9B%B2%E3%82%92%E6%B1%BA%E3%82%81%E3%80%811%E3%81%A4%E3%81%9A%E3%81%A4-trunk-%E3%81%AB%E5%8F%96%E3%82%8A%E8%BE%BC%E3%82%80"></a>


### 手順：各PRを検証し、連続した範囲を決め、1つずつ trunk に取り込む

手順は6つです。

1. すべてのPRを独立に検証する
2. ルートから続く、連続した検証済みの範囲だけを取り込む
3. 判定が今もそのパッチ（変更差分）を表しているか確かめる
4. 最前線のPRだけを準備し、1つずつマージする
5. マージのたびに計算し直し、最前線がマージされるまで状態を監視する
6. 上限で止まる

ここからは、各手順を1つずつ見ていきます。

<strong><code>git patch-id</code></strong>・・・ コミットの差分の中身から識別子を計算するgitのコマンド。コミットのIDが変わっても、差分が同じなら同じ値になる</li>
</ul>

<a id="1.-%E3%81%99%E3%81%B9%E3%81%A6%E3%81%AEpr%E3%82%92%E7%8B%AC%E7%AB%8B%E3%81%AB%E6%A4%9C%E8%A8%BC%E3%81%99%E3%82%8B"></a>


#### 1. すべてのPRを独立に検証する

PRごとにサブエージェントを1体ずつ割り当て、親のブランチとPRの最新のコミットを実際の画面やコマンドで比べさせる。結果は `PASS`、`PASS+NOTES`（注記つきの合格）、`FAIL` のいずれか。

<a id="2.-%E3%83%AB%E3%83%BC%E3%83%88%E3%81%8B%E3%82%89%E7%B6%9A%E3%81%8F%E3%80%81%E9%80%A3%E7%B6%9A%E3%81%97%E3%81%9F%E6%A4%9C%E8%A8%BC%E6%B8%88%E3%81%BF%E3%81%AE%E7%AF%84%E5%9B%B2%E3%81%A0%E3%81%91%E3%82%92%E5%8F%96%E3%82%8A%E8%BE%BC%E3%82%80"></a>


#### 2. ルートから続く、連続した検証済みの範囲だけを取り込む

手順2の「連続した範囲」は、次のように決まります。

```
PR #4  PASS      ← 検証済みだが、下に未検証がある
PR #3  (未検証)  ← ここで連続が切れる
PR #2  PASS
PR #1  PASS      ← 最前線
main
```

つまり、<strong>取り込んでよいのは PR #1 と #2 だけです</strong>。

PR #4をマージするには、前提となる未検証のPR #3を検証してからマージする必要があり、#3の検証を飛ばすと、未検証の変更まで trunk に入ってしまうことになります。

<a id="3.-%E5%88%A4%E5%AE%9A%E3%81%8C%E4%BB%8A%E3%82%82%E3%81%9D%E3%81%AE%E3%83%91%E3%83%83%E3%83%81%EF%BC%88%E5%A4%89%E6%9B%B4%E5%B7%AE%E5%88%86%EF%BC%89%E3%82%92%E8%A1%A8%E3%81%97%E3%81%A6%E3%81%84%E3%82%8B%E3%81%8B%E7%A2%BA%E3%81%8B%E3%82%81%E3%82%8B"></a>


#### 3. 判定が今もそのパッチ（変更差分）を表しているか確かめる

rebaseでコミットのID（SHA）が変わっても、差分の中身が同じかを `git patch-id` で比べる。中身が変わっていれば検証し直す。

<a id="4.-%E6%9C%80%E5%89%8D%E7%B7%9A%E3%81%AEpr%E3%81%A0%E3%81%91%E3%82%92%E6%BA%96%E5%82%99%E3%81%97%E3%80%811%E3%81%A4%E3%81%9A%E3%81%A4%E3%83%9E%E3%83%BC%E3%82%B8%E3%81%99%E3%82%8B"></a>


#### 4. 最前線のPRだけを準備し、1つずつマージする

準備は、必要なら最前線のPRを最新の trunk にrebaseし、そのPRのベースを trunk に付け替えることを指す。1つマージされてから次を準備する。

<a id="5.-%E3%83%9E%E3%83%BC%E3%82%B8%E3%81%AE%E3%81%9F%E3%81%B3%E3%81%AB%E8%A8%88%E7%AE%97%E3%81%97%E7%9B%B4%E3%81%97%E3%80%81%E6%9C%80%E5%89%8D%E7%B7%9A%E3%81%8C%E3%83%9E%E3%83%BC%E3%82%B8%E3%81%95%E3%82%8C%E3%82%8B%E3%81%BE%E3%81%A7%E7%8A%B6%E6%85%8B%E3%82%92%E7%9B%A3%E8%A6%96%E3%81%99%E3%82%8B"></a>


#### 5. マージのたびに計算し直し、最前線がマージされるまで状態を監視する

1つマージされるたびに、新しく最前線になったPRのベース、チェック、patch-idを調べ直す。自動マージを予約していても、それをスタックが安全である証拠とは見なさない。

<a id="6.-%E4%B8%8A%E9%99%90%E3%81%A7%E6%AD%A2%E3%81%BE%E3%82%8B"></a>


#### 6. 上限で止まる

上限は、検証済みの連続したPRの一番上のPR（手順2の図ではPR #2）。そこまでマージしたら、何が取り込まれたか、次の未検証のPRはどれかを報告して終わる。

<a id="%E4%BE%9D%E9%A0%BC%E3%81%AE%E6%9B%B8%E3%81%8D%E6%96%B9%EF%BC%9A%E3%80%8C%E3%82%B9%E3%82%BF%E3%83%83%E3%82%AF%E3%82%92%E5%8F%96%E3%82%8A%E8%BE%BC%E3%82%93%E3%81%A7%E3%80%8D%E3%81%A8%E9%A0%BC%E3%82%80"></a>


### 依頼の書き方：「スタックを取り込んで」と頼む

章の冒頭で示した依頼を、もう一度示します。

```
/poteto-mode land the stack.
// スタックを trunk に取り込んで。
```

## まとめ

- <strong>3つのPlaybookのつながり</strong>・・・ 『<strong>Opening a PR</strong>』はPRを作成し、『<strong>Babysit</strong>』はマージ可能な状態まで整え、『<strong>Shipping</strong>』は検証を通ったPRを trunk（PRのマージ先になる本流のブランチ）へマージします。
- <strong>Opening a PR</strong>・・・ 小さく順序立てたコミットと差分を絞ったPRを作り、本文は「ブリーフィング」として短く書きます。PRを開いても『<strong>Babysit</strong>』は始めません。
- <strong>Babysit</strong>・・・ モードを宣言し、最前線だけを見て merge-ready まで運びます。Bugbotのコメントは fix、dismiss、ask に分けます。
- <strong>Shipping</strong>・・・ 「安全」をコードを書いていないエージェントの判定と定義し、ルートから連続した検証済みの範囲だけを1つずつマージします。
- <strong>BabysitとShippingの違い</strong>・・・ 2つのうち、マージするのは明示的な依頼を受けた『<strong>Shipping</strong>』だけです（『Autopilot-full』など[第16章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/8a8dd5)のPlaybookには別の決まりがあります）。

次の[第15章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/7d7609)では、1つの長い作業を人が席を外している間も続け、止め、再開し、片付ける4つのPlaybookを見ていきます。
