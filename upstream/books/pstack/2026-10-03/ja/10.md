`/poteto-mode` は、pstackの入口です。<strong>依頼を読み、23件のPlaybookから1冊を選び、その手順に沿って作業を進めます</strong>。

利用者は、どのPlaybookを使うかも、どのSkillをどの順で呼ぶかも指定しなくて済みます。利用者がするのは、<strong>ゴールとそれを確かめる方法を、自分の言葉で渡すことだけ</strong>です。

この章では、`/poteto-mode` の呼び出し方、呼び出したときに起きること、依頼をPlaybookに振り分ける規則、良い依頼の書き方を解説していきます。

## `/poteto-mode` は、依頼の先頭に付けて呼び出す

`/poteto-mode` は、<strong>作業の依頼の先頭に付けて呼び出します</strong>。

一度呼び出すと、同じ会話の後のターンでは、`/poteto-mode` を付けなくても有効となります（[後の項](#%E4%B8%80%E5%BA%A6%E5%91%BC%E3%81%B3%E5%87%BA%E3%81%99%E3%81%A8%E3%80%81%E5%90%8C%E3%81%98%E4%BC%9A%E8%A9%B1%E3%81%AE%E4%B8%AD%E3%81%A7%E3%81%AF%E6%9C%89%E5%8A%B9%E3%81%AA%E3%81%BE%E3%81%BE)）。会話を始めるたびに付けるのが手間なら、`/poteto-mode` を[Custom Mode](https://cursor.com/ja/changelog/0-48-x)（毎ターン同じSkillを使うようにする、Cursorのモード）として固定することもできます。

<a id="%E5%9F%BA%E6%9C%AC%E3%81%AF%E3%80%81%E4%BE%9D%E9%A0%BC%E6%96%87%E3%81%AE%E9%A0%AD%E3%81%AB%E4%BB%98%E3%81%91%E3%82%8B%E3%81%A0%E3%81%91"></a>


### 基本は、依頼文の頭に付けるだけ

pstackの[README](https://github.com/cursor/plugins/blob/main/pstack/README.md)は、`/poteto-mode` を自明でない作業に対する、すべての既定の入口と位置づけ、次のような例を挙げています。

```
/poteto-mode this pr has a subtle bug where the scroll drifts every 750ms even when idle. repro first, then fix and verify.
// このPRには気づきにくいバグがある。アイドル中でも750msごとにスクロールがずれる。まず再現して、それから直して、確かめて。
```

この依頼には、どのPlaybookやSkillを使うかは書かれていません。書かれているのは、起きている症状（アイドル中でも750msごとにスクロールがずれる）と、してほしい作業（まず再現し、直し、確かめる）だけです。

どのPlaybookやSkillを使うかは `/poteto-mode` が依頼の内容から選ぶので、<strong>利用者は、症状と、してほしい作業を書けばよいだけです</strong>。

`/poteto-mode` を適用するかどうかは、[次の項](#cursor%E3%81%A7%E3%81%AF%E3%80%81custom-mode%E3%81%A8%E3%81%97%E3%81%A6%E5%9B%BA%E5%AE%9A%E3%81%A7%E3%81%8D%E3%82%8B)で見る `reminder` が決めています。`reminder` は、新しいタスクで、Playbookに当てはまるときや厳密さが必要なときだけ `/poteto-mode` を適用し、雑談などの軽い依頼や質問には適用しないと定めています。

そのため、`/poteto-mode` を付けるか迷ったときは、付けておくと良いと私は考えています。軽い依頼や質問なら、エージェントはPlaybookの手順を踏まずに答えます。

<a id="cursor%E3%81%A7%E3%81%AF%E3%80%81custom-mode%E3%81%A8%E3%81%97%E3%81%A6%E5%9B%BA%E5%AE%9A%E3%81%A7%E3%81%8D%E3%82%8B"></a>


### Cursorでは、Custom Modeとして固定できる

依頼のたびに `/poteto-mode` を打つのが手間なら、`/poteto-mode` を[Custom Mode](https://cursor.com/ja/changelog/0-48-x)として固定できます。方法は『The Complete Guide to pstack』[Part 1](https://x.com/poteto/status/2094457600259842065)で紹介されています。

`/poteto-mode` を補完するときに、Enterではなく `Opt + Enter` を押すと、Skillが[Custom Mode](https://cursor.com/ja/changelog/0-48-x)として追加され、新しいターンのたびに、このSkillを使うようにというリマインダーがエージェントに入ります。

リマインダーの文面は、[`/poteto-mode`](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/SKILL.md) の frontmatter に `reminder` として書かれています。

```
mode: true
reminder: New task? Playbook match or rigor needed -> apply /poteto-mode. Casual turn or user opts out -> don't.
# 新しいタスクで、Playbookに当てはまるか厳密さが必要なら /poteto-mode を適用する。雑談のターンや、利用者がやめると言った場合は適用しない。
```

<strong>この1行があるので、[Custom Mode](https://cursor.com/ja/changelog/0-48-x)で固定したままでも、雑談などの軽い依頼・質問のターンや、利用者がモードをやめると言った場合には、エージェントはPlaybookの手順を踏みません</strong>。

<a id="%E4%B8%80%E5%BA%A6%E5%91%BC%E3%81%B3%E5%87%BA%E3%81%99%E3%81%A8%E3%80%81%E5%90%8C%E3%81%98%E4%BC%9A%E8%A9%B1%E3%81%AE%E4%B8%AD%E3%81%A7%E3%81%AF%E6%9C%89%E5%8A%B9%E3%81%AA%E3%81%BE%E3%81%BE"></a>


### 一度呼び出すと、同じ会話の中では有効なまま

READMEは、`/poteto-mode` を持続するモード（原文では sticky mode）と呼んでいます。一度 `/poteto-mode` を付けて依頼すると、同じ会話の後のターンでは、`/poteto-mode` を付けなくても有効なままになる、という意味です。

つまり、利用者は同じ会話で一度、`/poteto-mode`を実行するだけで、次ターン以降の会話では`/poteto-mode`を明示的に付ける必要がないということです。

有効な間も、`/poteto-mode` がPlaybookの手順で進めるのは、依頼がPlaybookに当てはまるときや、厳密さが必要な作業のときだけです。それ以外の依頼（雑談など）では、Playbookの手順を踏みません。やめたいときは、そう伝えれば止まります。

そのため、同じ会話の中で作業を続けるときは、依頼が短くても構いません。同梱ガイドの[`02-poteto-mode.md`](https://github.com/cursor/plugins/blob/main/pstack/docs/guide/02-poteto-mode.md)には、次のような例が並んでいます。

```
/poteto-mode do it
// それで進めて
```

```
continue
// 続けて
```

```
keep going until done
// 終わるまで続けて
```

同じページは、短い依頼で足りるのは、モードが持続していて、作業の組み立て（手順）をPlaybookが持っているからだと説明しています。<strong>利用者の言葉は何をしたいか（意図）を伝え、手順どおりに厳密に進める役目はSkillが受け持ちます</strong>。

ただし、`/poteto-mode` が持続するので、同じ会話で別の話題に移ると、前のタスクの続きとして扱われることがあります。話題を変えるときの頼み方は、この章の「[話題を変えるときは『新しいタスク』と言う](#%E8%A9%B1%E9%A1%8C%E3%82%92%E5%A4%89%E3%81%88%E3%82%8B%E3%81%A8%E3%81%8D%E3%81%AF%E3%80%8C%E6%96%B0%E3%81%97%E3%81%84%E3%82%BF%E3%82%B9%E3%82%AF%E3%80%8D%E3%81%A8%E8%A8%80%E3%81%86)」で扱います。

<a id="%E5%91%BC%E3%81%B3%E5%87%BA%E3%81%99%E3%81%A8%E3%80%813%E3%81%A4%E3%81%AE%E3%81%93%E3%81%A8%E3%81%8C%E8%B5%B7%E3%81%8D%E3%82%8B"></a>


## 呼び出すと、3つのことが起きる

`/poteto-mode` を呼び出すと、<strong>Playbookの手順をTODOリストに写し、手順に応じてほかのSkillを呼び、決まった書き方で返答する</strong>、という3つのことが起きます。

<aside class="msg message"><span class="msg-symbol">!</span><div class="msg-content">
<p class="code-line" data-line="89"><strong>TODOリスト</strong>・・・ エージェントが作業の始めに作る、その作業でやることの一覧（計画）です。Cursorでは、チャットの画面に表示されます。利用者は、この一覧を見て、エージェントがどの手順を進め、どの手順を飛ばしたか（<code>skip: &lt;理由&gt;</code>）を確かめられます<br/>
（同梱ガイド <a href="https://github.com/cursor/plugins/blob/main/pstack/docs/guide/01-setup.md" rel="nofollow noopener noreferrer" target="_blank"><code>01-setup.md</code></a>）。</p>
</div></aside>

READMEは、3つを次のように説明しています。

1. 依頼をPlaybookに照らし合わせ、TODOリストを開く。最初の項目は、そのPlaybookの手順を一字一句写したものになる
2. 手順が進むにつれて、必要なほかのSkillへ振り分ける
3. 利用者に向けて、AIらしさを取り除いた返答を書く

<a id="1.-playbook%E3%81%AE%E6%89%8B%E9%A0%86%E3%82%92%E3%80%81%E3%81%9D%E3%81%AE%E3%81%BE%E3%81%BEtodo%E3%83%AA%E3%82%B9%E3%83%88%E3%81%AB%E5%86%99%E3%81%99"></a>


### 1. Playbookの手順を、そのままTODOリストに写す

`/poteto-mode` の中心にある規則です。`/poteto-mode` の節『[Playbooks](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/SKILL.md#playbooks)』は、最初にこう定めています。

> Open a todolist whose first items are the matched playbook's steps, copied in verbatim, before any task-specific todos. A step you choose not to do stays in the list with a one-line `skip: <reason>`.
>
> TODOリストを開き、その最初の項目には、選んだPlaybookの手順を一字一句写す。タスク固有のTODOはその後ろに置く。やらないと決めた手順もリストに残し、`skip: <理由>` を1行添える。

エージェントは、<strong>Playbookの手順を要約せずにそのまま作業の一覧にし、やらない手順も理由を添えて残します</strong>。

この規則には、以下の2つの効き目があります。

- <strong>Playbookの順序が、そのまま作業の骨組みになること</strong>・・・ エージェントが自分の判断で手順を要約したり、組み立て直したりする余地が小さくなります。
- <strong>飛ばした手順が見えること</strong>・・・ やらない手順も `skip: <理由>` として残るので、人間は結果だけでなく、途中のエージェントの判断も点検できます。同梱ガイドの[`01-setup.md`](https://github.com/cursor/plugins/blob/main/pstack/docs/guide/01-setup.md)も、TODOリストを見れば、エージェントが何をやらないと決めたかが分かると書いています。

<a id="2.-%E6%89%8B%E9%A0%86%E3%81%8C%E6%B1%82%E3%82%81%E3%82%8B%E3%81%A8%E3%81%8D%E3%81%AB%E3%80%81%E3%81%BB%E3%81%8B%E3%81%AEskill%E3%82%92%E5%91%BC%E3%81%B6"></a>


### 2. 手順が求めるときに、ほかのSkillを呼ぶ

Playbookの各手順には、どこでどのSkillを使うかが書かれています。`/how` や `/architect` は、起動時にまとめて呼ばれるのではなく、手順がその場面に来たときに呼ばれます。この仕組みは[第8章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/096f3d)と[第9章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/6b7496)で扱います。

<a id="3.-%E8%BF%94%E7%AD%94%E3%81%AF%E3%80%81%E6%B1%BA%E3%81%BE%E3%81%A3%E3%81%9F%E6%9B%B8%E3%81%8D%E6%96%B9%E3%81%A7%E6%9B%B8%E3%81%8F"></a>


### 3. 返答は、決まった書き方で書く

返答の書き方は、`/poteto-mode` の節『[Writing the reply](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/SKILL.md#writing-the-reply)』が定めています。たとえば以下のような規則です。

- 一文一義の短い断定文にする
- 誰のための作業で何が変わるかを先に書く
- 主張には証拠か「測定した・推論した・推測」のラベルを付ける

すべてのPlaybookはこの書き方の返答で終わり、各Playbookの末尾にある「Reply」行には、そのPlaybookで報告する内容が書かれています。規則の全体は[第35章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/4f8911)で扱います。

<a id="%E4%BE%9D%E9%A0%BC%E3%81%AF%E3%80%81%E6%B1%BA%E3%81%BE%E3%81%A3%E3%81%9F%E8%A6%8F%E5%89%87%E3%81%A7playbook%E3%81%AB%E6%8C%AF%E3%82%8A%E5%88%86%E3%81%91%E3%82%89%E3%82%8C%E3%82%8B"></a>


## 依頼は、決まった規則でPlaybookに振り分けられる

振り分けの基本は、<strong>依頼の種類（調べるだけの質問、不具合、新しい振る舞いなど）を見て、合うPlaybookを1冊選ぶこと</strong>です。

ただし、<strong>作業が大きいときは、依頼の種類より作業の大きさで振り分け先が決まります</strong>。『[<strong>Feature</strong>](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/playbooks/feature.md)』などのPlaybookに当てはまる依頼でも、`/figure-it-out` や『[<strong>Orchestrate</strong>](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/playbooks/orchestrate.md)』へ回ります。

### 大きな作業は `/figure-it-out` へ、プロジェクト規模の作業は『Orchestrate』へ回る

作業が大きいときは、個別のPlaybookより優先して、`/figure-it-out` か『<strong>Orchestrate</strong>』Playbookへ回ります。`/poteto-mode` の『Playbooks』にある2つの規則で、どちらも作業の大きさで振り分け先を変えるものです。

1つ目は `/figure-it-out` です。規則の原文は次のとおりです。

> A large or cross-cutting effort (a migration across many call sites, an ambitious multi-part change), or work the user steps away from to trust later, routes to the <strong>figure-it-out</strong> skill even when a narrower playbook like Feature fits.
>
> 大きく横断的な作業（多くの呼び出し箇所にまたがる移行、野心的な複数部分からなる変更）や、利用者が席を外してあとで信頼したい作業は、『Feature』のような狭いPlaybookが当てはまっても、figure-it-out のSkillへ回る。

エージェントは、<strong>依頼の言葉より作業の大きさを優先して、振り分け先を決めます</strong>。

どのPlaybookにも当てはまらない作業も `/figure-it-out` へ回ります。

`/figure-it-out` は、そのタスクのための厳密で監査可能なPlaybookを設計するSkillです。

2つ目は『<strong>Orchestrate</strong>』です。対象は、何日も続くプロジェクト規模の作業で、積み重なった多数のPRを、1体のコーディネーターエージェントと多数のサブエージェントで進めるものです。

2つの違いは、`/figure-it-out` がその作業1回分の進め方（Playbook）を設計するのに対し、『<strong>Orchestrate</strong>』は何日も続く作業全体を運営する点です。

ただし『<strong>Orchestrate</strong>』の説明には、1体のエージェントがセッションの予算内で終えられる作業は『[<strong>Autonomous run</strong>](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/playbooks/autonomous-run.md)』へ回すよう、明示されています。

## 良い依頼は、目的と完了条件を自分の言葉で書く

同梱ガイド（[`docs/guide/`](https://github.com/cursor/plugins/blob/main/pstack/docs/guide/README.md)）の勧めをまとめると、良い依頼の書き方は以下の4つです。

1. <strong>ゴールと確かめ方を書く</strong>
2. <strong>Skillを列挙しない</strong>
3. <strong>作業時間を完了条件にしない</strong>
4. <strong>話題を変えるときは「新しいタスク」と言う</strong>

<a id="%E6%89%8B%E9%A0%86%E3%81%A7%E3%81%AF%E3%81%AA%E3%81%8F%E3%80%81%E3%82%B4%E3%83%BC%E3%83%AB%E3%82%92%E6%9B%B8%E3%81%8F"></a>


### 手順ではなく、ゴールを書く

同梱ガイドの`02-poteto-mode.md`は、依頼に詳しい仕様書は必要ないと説明しています。何がおかしいか、何を実現したいか、そしてすでに分かっていることで作業の助けになる情報を伝えれば足ります。

ガイドには、次の不具合の依頼例があります。

```
/poteto-mode users get two notifications after a retry. repro first, then fix and verify.
// 再試行の後、ユーザーに通知が2回届く。まず再現して、それから直して、確かめて。
```

ガイドは、この「まず再現して」を丁寧さの飾りではなく、<strong>Playbookが守る本物の制約</strong>として扱うと説明しています。実際、この依頼は『[<strong>Bug fix</strong>](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/playbooks/bug-fix.md)』Playbookに振り分けられ、TODOリストは再現の手順から始まります。

同梱ガイドの目次も、覚えておくことを一つだけ挙げるなら、<strong>ゴールとそれを確かめる方法を自分の言葉で渡すこと</strong>だ、とまとめています。

確かめ方の書き方は、[第2章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/27a183)で見た同梱ガイドの例（「テキスト出力は1バイトも変えない。JSONはパースできる」）が参考になります。どちらも、エージェント自身が実行して合否を判定できる形になっています。

依頼に書くとよいものは、確かめ方だけではありません。『The Complete Guide to pstack』[Part 2](https://x.com/poteto/status/2097732320606507506)の依頼例には、受け取りたい結果の形（分かっていること、使ったデータ、有力な仮説を分けて示す）や、レビューのタイミング（進める前に確認させて）まで書かれたものがあります。

<a id="skill%E3%82%92%E5%88%97%E6%8C%99%E3%81%97%E3%81%AA%E3%81%84"></a>


### Skillを列挙しない

同梱ガイドの`02-poteto-mode.md`は、依頼でSkillを列挙することを落とし穴に挙げています。

> <strong>Pitfall:</strong> don't enumerate skills in your prompt ("use /how, then /architect, then /arena..."). The playbook already sequences them, and a hand-written sequence usually reorders or drops steps the playbook would have kept. Name a skill only when you want to override a specific choice.
>
> <strong>落とし穴：</strong> 依頼でSkillを列挙しない（「/howを使って、次に/architect、次に/arena……」）。順番はPlaybookがすでに決めていて、手書きの順番は、Playbookなら残したはずの手順を入れ替えたり落としたりしがちだ。Skillの名前を書くのは、特定の選択を上書きしたいときだけにする。

たとえば、不具合の依頼に「/howで調べて、/architectで設計して」と書くと、『<strong>Bug fix</strong>』Playbookが最初に置いている「自分で再現する」手順が、手書きの順番から抜け落ちるおそれがあります。ガイドの目次も冒頭で、<strong>pstackはエージェントを細かく管理するのをやめたときに最もよく働く</strong>、と書いています。

[前の項](#%E6%89%8B%E9%A0%86%E3%81%A7%E3%81%AF%E3%81%AA%E3%81%8F%E3%80%81%E3%82%B4%E3%83%BC%E3%83%AB%E3%82%92%E6%9B%B8%E3%81%8F)で見た「まず再現して」のような言葉は、Playbookが守る制約として扱われます。<strong>制約は依頼に書き、どう進めるかという手順はPlaybookに任せる</strong>、という分担です。

<a id="%E3%80%8C%E4%BD%95%E6%99%82%E9%96%93%E7%B6%9A%E3%81%91%E3%82%8B%E3%81%8B%E3%80%8D%E3%81%AF%E3%80%81%E5%AE%8C%E4%BA%86%E6%9D%A1%E4%BB%B6%E3%81%AB%E3%81%AA%E3%82%89%E3%81%AA%E3%81%84"></a>


### 「何時間続けるか」は、完了条件にならない

席を外すときは、「完了条件」を書いてから離れます。同梱ガイドの`02-poteto-mode.md`には、次の例があります。

```
/poteto-mode im stepping away. keep going until the migration check reports zero old callers. log your decisions.
// 席を外す。移行チェックが古い呼び出し元ゼロを報告するまで続けて。判断を記録して。
```

同梱ガイドの夜間実行のページ（[`07-overnight.md`](https://github.com/cursor/plugins/blob/main/pstack/docs/guide/07-overnight.md)）は、<strong>時間を完了条件にすることを落とし穴に挙げています</strong>。

「4時間これに取り組んで」はエージェントに確かめるものを何も与えず、朝には結果ではなく4時間分の動きが残るだけだからです。夜間の実行は[第15章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/7d7609)で取り上げます。

上の例のゴール「移行チェックが古い呼び出し元ゼロを報告する」は、エージェント自身が実行して合否を出せる判定です。このように、<strong>完了条件には、時間の代わりに、実行して合否が出る判定を書きます</strong>。

<a id="%E8%A9%B1%E9%A1%8C%E3%82%92%E5%A4%89%E3%81%88%E3%82%8B%E3%81%A8%E3%81%8D%E3%81%AF%E3%80%8C%E6%96%B0%E3%81%97%E3%81%84%E3%82%BF%E3%82%B9%E3%82%AF%E3%80%8D%E3%81%A8%E8%A8%80%E3%81%86"></a>


### 話題を変えるときは「新しいタスク」と言う

`/poteto-mode` は同じ会話の中で持続するので、長い会話には前のタスクのコンテキストがたまります。そのため同梱ガイドの`02-poteto-mode.md`は、話題を変えるときに「新しいタスク」と言うよう勧めています。

```
/poteto-mode new task. figure out why the cache entry survives logout. don't change any code yet.
// 新しいタスク。ログアウト後もキャッシュのエントリが残る理由を突き止めて。まだコードは変えないで。
```

つまり、<strong>「新しいタスク」はPlaybookを選び直させる合図</strong>です。

これを言わずに話題を変えると、進行中のPlaybookが新しい質問を前の作業の続きとして扱うことがあります。

## まとめ

- <strong>呼び出し方</strong>・・・ `/poteto-mode` は、依頼の先頭に付けて呼ぶpstackの入口で、自明でない作業すべての既定の入口です。一度呼び出すと、同じ会話の中では有効なままです。Cursorでは `Opt + Enter` で[Custom Mode](https://cursor.com/ja/changelog/0-48-x)として固定することもできます。
- <strong>呼び出したときに起きること</strong>・・・ Playbookを選んでその手順をTODOリストに一字一句写し、手順に応じてSkillを呼び、決まった書き方で返答します。飛ばした手順は `skip: <理由>` として残るので、途中で点検できます。
- <strong>振り分けの規則</strong>・・・ 基本は依頼の種類で1冊を選びます。大きな作業は `/figure-it-out`、継続的なプロジェクト規模の作業は『<strong>Orchestrate</strong>』へ回ります。
- <strong>良い依頼の書き方</strong>・・・ ゴールと確かめ方を自分の言葉で書き、Skillを列挙せず、作業時間を完了条件にせず、話題を変えるときは「新しいタスク」と言います。

次の[第8章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/096f3d)では、`/poteto-mode` の中で働く3つの部品、Playbook、Skill、Principleを扱います。3つの役割の違いを解説し、本書の実例の依頼を例に、『<strong>Bug fix</strong>』Playbookの各手順でSkillとPrincipleがどこで働くかをたどります。
