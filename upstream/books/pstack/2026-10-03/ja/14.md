この章では、次の3つのPlaybookを扱います。

1. [Investigation](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/playbooks/investigation.md)
2. [Runtime forensics](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/playbooks/runtime-forensics.md)
3. [Trace forensics](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/playbooks/trace-forensics.md)

3つとも、調べて答えを出すためのPlaybookで、コードは変えません。<strong>成果物は修正ではなく、根拠を示した答えか診断</strong>です。

どのPlaybookを使うかは、調査に使える情報や証拠で決まります。ソースコードと履歴を読めば答えられるのか、動いているプロセスを計測できるのか、取得されたプロファイルやダンプ（実行中の状態を記録したファイル）を調べるのかによって、使い分けます。

この章では、3つに共通する決まりと、それぞれの使い方を順に解説します。

<a id="%E3%81%93%E3%81%AE%E7%AB%A0%E3%81%AE%E6%A7%8B%E6%88%90"></a>


## この章の構成

この章の構成は次のとおりです。

- 3つのPlaybookはコードを変えず、調査に使える情報や証拠で選ぶ
- 『Investigation』は、コードや履歴を読んで答えられる質問に、引用つきで答える
- 『Runtime forensics』は、ソースからの推測をやめて生きたプロセスを計測する
- 『Trace forensics』は、プログラムを再実行せず、渡された成果物を問い合わせできる形にして読む
- まとめ

## 3つのPlaybookはコードを変えず、調査に使える情報や証拠で選ぶ

冒頭で述べたように、3つのPlaybookは、<strong>調査に使える情報や証拠で使い分けます</strong>。

選び方は次のとおりです。

- <strong>コードや履歴を読めば答えられる質問がある</strong>・・・ 『<strong>Investigation</strong>』
- <strong>不具合や遅延などが今も起きていて、動いているプロセスを自分で計測できる</strong>・・・ 『<strong>Runtime forensics</strong>』
- <strong>事後に渡されたプロファイルやダンプ（実行中の状態を記録したファイル）だけがある</strong>・・・ 『<strong>Trace forensics</strong>』

同じ「遅い」という相談でも、生きたプロセスを測れるのか、受け取ったファイルしかないのかで、選ぶPlaybookが異なります。また、証拠の種類ごとに「やってよいこと」も異なります。

『<strong>Runtime forensics</strong>』では、動いているプロセスにログや計測のコードを差し込んで確かめることが許容されています。一方『<strong>Trace forensics</strong>』では、受け取ったプロファイルやダンプを読むだけで、<strong>プログラムを再実行して取り直すことは禁じられています</strong>。

## 『Investigation』は、コードや履歴を読んで答えられる質問に、引用つきで答える

<a id="%E5%BD%B9%E5%89%B2%EF%BC%9A%E3%82%B3%E3%83%BC%E3%83%89%E3%82%84%E5%B1%A5%E6%AD%B4%E3%82%92%E8%AA%AD%E3%82%93%E3%81%A7%E7%AD%94%E3%81%88%E3%81%8C%E5%87%BA%E3%82%8B%E8%B3%AA%E5%95%8F%E3%81%AB%E7%AD%94%E3%81%88%E3%82%8B"></a>


### 役割：コードや履歴を読んで答えが出る質問に答える

『<strong>Investigation</strong>』は、「Xはどう動くか」「Yはなぜこう作られたか」「Zは本当に大丈夫か」「XとYのどちらにすべきか」のような、<strong>ソースコードや変更の履歴を読むだけで答えが出る質問に答えるPlaybook</strong>です。

成果物は引用つきの説明か推奨です。PRを作らず、PRをマージできる状態まで見守る作業（『[<strong>Babysit</strong>](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/playbooks/babysit.md)』。[第14章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/45a56e)）もしません。途中でコード変更が必要だと分かったら、自分で直し始めずに利用者に戻します。

<a id="%E6%89%8B%E9%A0%86%EF%BC%9A%E5%87%BA%E5%8A%9B%E3%81%AE%E5%BD%A2%E3%81%BE%E3%81%A7%E6%B1%BA%E3%82%81%E3%82%8B4%E3%81%A4%E3%81%AE%E6%89%8B%E9%A0%86"></a>


### 手順：出力の形まで決める4つの手順

1. 質問を `/how`（コードの仕組みや置き場所を説明するSkill）に通す。「なぜ」を問う質問なら、設計の理由や経緯を引用つきで調べる `/why` にも通す（どちらも[第22章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/788746)）
2. スループット・チェックポイントは「該当なし」の1行にする
3. `/how` と同じ5つの見出し（概要、主要な概念、仕組み、場所、注意点）で書く。選択肢の比較なら、トレードオフの表をつけた推奨を書く
4. 返答に `/unslop`（AIが書きがちな言い回しを削るSkill）をかける（[第32章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/44857b)）

### 依頼の書き方：「新しいタスク」「まだコードは変えないで」と書く

依頼に「新しいタスク」と「まだコードは変えないで」を書くと、Playbookが選び直され、コードを変えない制約がかかります。同梱ガイド（[docs/guide/02-poteto-mode.md](https://github.com/cursor/plugins/blob/main/pstack/docs/guide/02-poteto-mode.md)）の例は、次のとおりです。

```
/poteto-mode new task. figure out why the cache entry survives logout. don't change any code yet.
// 新しいタスク。ログアウト後もキャッシュのエントリが残る理由を突き止めて。まだコードは変えないで。
```

返答の形を依頼の側で指定しておく手もあります。『The Complete Guide to pstack』[Part 2](https://x.com/poteto/status/2097732320606507506)では、次の例が記載されています。

```
/poteto-mode investigate why background workers periodically fail with timeout errors. give me a breakdown of what we know, what data you used, and your best hypotheses.
// バックグラウンドのワーカーがときどきタイムアウトのエラーで失敗する理由を調べて。分かっていること、使ったデータ、有力な仮説を分けて示して。
```

この頼み方は、`/poteto-mode` の節『[Writing the reply](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/SKILL.md#writing-the-reply)』の規定と同じ区別を求めています。<strong>すべての主張に、証拠か、測定した・推論した・推測のどれかのラベルを同じ文の中で添える</strong>、という規定です。依頼の側でもこの区別を求めておくと、返答のどの文が確かめた事実で、どの文が推測なのかを見分けられます。

## 『Runtime forensics』は、ソースからの推測をやめて生きたプロセスを計測する

<a id="%E5%BD%B9%E5%89%B2%EF%BC%9A%E5%AE%9F%E8%A1%8C%E6%99%82%E3%81%AE%E7%97%87%E7%8A%B6%E3%82%92%E3%80%81%E7%94%9F%E3%81%8D%E3%81%9F%E3%83%97%E3%83%AD%E3%82%BB%E3%82%B9%E3%81%AE%E8%A8%88%E6%B8%AC%E3%81%8B%E3%82%89%E8%A8%BA%E6%96%AD%E3%81%99%E3%82%8B"></a>


### 役割：実行時の症状を、生きたプロセスの計測から診断する

『<strong>Runtime forensics</strong>』は、メモリリーク、アイドル中のCPU空転、表示の乱れといった実行時の症状を、ソースからの推測ではなく、<strong>動いているプロセスの計測から診断する</strong>Playbookです。

ソースを読めば、原因と考えられる経路は分かります。しかし実行時の症状では、どの経路が実際に走っているかが問題になります。実際に走っている経路は、動いているプロセスを計測して確かめます。

<a id="%E6%89%8B%E9%A0%86%EF%BC%9A%E4%BF%A1%E5%8F%B7%E3%82%92%E5%8F%96%E3%82%8B%E3%80%81%E8%A8%BC%E6%8B%A0%E3%81%B8%E7%B5%9E%E3%82%8B%E3%80%81%E4%BB%95%E7%B5%84%E3%81%BF%E3%82%92%E8%A8%BC%E6%98%8E%E3%81%99%E3%82%8B%E3%80%81%E3%82%BD%E3%83%BC%E3%82%B9%E3%81%AB%E5%AF%BE%E5%BF%9C%E3%81%A5%E3%81%91%E3%82%8B"></a>


### 手順：信号を取る、証拠へ絞る、仕組みを証明する、ソースに対応づける

1. <strong>ライブの信号を取る</strong>
   - 症状に合ったcontrol系Skillを使い、CPUプロファイル、ヒープスナップショット、CDP（Chrome DevTools Protocol）のトレースを取得する
   - control系Skillはpstackに同梱されておらず、[`cursor-team-kit`](https://github.com/cursor/plugins/tree/main/cursor-team-kit) の `control-ui` と `control-cli` を指す
2. <strong>決定的な証拠まで絞り込む</strong>
   - ホットパス（実行時間の大半を使っている経路）上の関数、リークしたオブジェクトの保持チェーン、入力がないのに回り続けるループを探す
   - 大きな成果物はサブエージェントに解析させる（原則『[<strong>Guard the Context Window</strong>](https://github.com/cursor/plugins/blob/main/pstack/skills/principle-guard-the-context-window/SKILL.md)』、[第20章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/c155cc)）
3. <strong>信じる前に仕組みを証明する</strong>
   - 仮説が示す、症状を起こしている仕組みを確かめる
   - 確かめ方は、実行中のプロセスに計測のコードを差し込むか、再起動せずに動いているコードを直接書き換える（ホットフィックス）
4. <strong>ソースに対応づける</strong>
   - 原因の箇所を、ソースコードのファイル、シンボル（関数名などの名前）、該当する行までたどる

頼まれない限り修正は加えず、原因が分かったら『<strong>Bug fix</strong>』か『<strong>Perf issue</strong>』に渡します。

## 『Trace forensics』は、プログラムを再実行せず、渡された成果物を問い合わせできる形にして読む

<a id="%E5%BD%B9%E5%89%B2%EF%BC%9A%E5%8F%96%E5%BE%97%E6%B8%88%E3%81%BF%E3%81%AE%E6%88%90%E6%9E%9C%E7%89%A9%E3%82%92%E8%AA%AD%E3%82%80%E3%81%93%E3%81%A8%E3%81%AB%E5%BE%B9%E3%81%99%E3%82%8B"></a>


### 役割：取得済みの成果物を読むことに徹する

『<strong>Trace forensics</strong>』は、利用者の環境で取られたCPUプロファイル、spindump、ヒープスナップショットなど、事後に渡された成果物を、<strong>再実行せずに読んで原因を診断する</strong>Playbookです。

<aside class="msg message"><span class="msg-symbol">!</span><div class="msg-content">
<ul class="code-line" data-line="127">
<li class="code-line" data-line="127">
<strong>spindump</strong>・・・ 応答しなくなったアプリの処理状態を調べる、macOSの診断レポート</li>
</ul>
</div></aside>

『<strong>Runtime forensics</strong>』との違いは、取得がすでに済んでいることです。成果物は固定されたデータなので、読むことに徹します。ツールも、Playbookをどの環境でも使えるように、DevToolsやtrace解析ツール（パーサー）のような汎用的なものに限定します。

<a id="%E6%89%8B%E9%A0%86%EF%BC%9A%E6%88%90%E6%9E%9C%E7%89%A9%E3%82%92%E8%AA%AD%E3%81%BF%E8%BE%BC%E3%82%80%E3%80%81%E5%BD%A2%E3%82%92%E6%95%B4%E3%81%88%E3%82%8B%E3%80%81%E5%8E%9F%E5%9B%A0%E3%81%B8%E7%B5%9E%E3%82%8B%E3%80%81%E3%82%BD%E3%83%BC%E3%82%B9%E3%82%B3%E3%83%BC%E3%83%89%E3%81%AE%E4%BD%8D%E7%BD%AE%E3%82%92%E7%89%B9%E5%AE%9A%E3%81%99%E3%82%8B"></a>


### 手順：成果物を読み込む、形を整える、原因へ絞る、ソースコードの位置を特定する

1. <strong>形式を見分けて読み込む</strong>
   - 大きな成果物はサブエージェントで解析する
2. <strong>問い合わせできる形に変換する</strong>
   - traceやヒープスナップショットをsqliteに流し込み、読む前に問い合わせできる形にする
3. <strong>原因へ絞り込む</strong>
   - 最も時間を使っているフレーム、リークの保持チェーン、止まっているスレッドを探す
4. <strong>ソースコードの位置を特定する</strong>
   - 最も時間を使っているフレームが、ソースコードのどのファイルの、どの関数の、何行目に当たるかを、成果物に含まれるシンボル情報を手がかりに特定する
   - この位置が分からない間は、どのコードが原因かを言えないので、診断はまだ終わっていないものとして扱う
   - 位置が分からないときは、シンボル情報を解決するか、成果物にシンボル情報が含まれていないことを明示する
5. <strong>対になる取得があれば突き合わせる</strong>
   - 修正の前と後のように、比べられる2つの成果物があれば差分を取る
   - 比較がなければ、所見を「成果物が支持する最も強い仮説」と書き、確定した原因とはしない
6. <strong>引用つきの診断を返す</strong>
   - 頼まれない限り修正はせず、『<strong>Bug fix</strong>』か『<strong>Perf issue</strong>』に渡す

## まとめ

- <strong>共通点と選び方</strong>・・・ 3つのPlaybookは、どれもコードを変えずに答えや診断を返します。コードや履歴を読めば答えられる質問か、今も動いているプロセスを計測できるか、取得された成果物しかないか、の3つで選びます。
- <strong>Investigation</strong>・・・ `/how` と `/why` で答え、5つの見出しか比較表つきの推奨で返します。コード変更が必要なら利用者に戻します。
- <strong>Runtime forensics</strong>・・・ ソースからの推測をやめ、生きたプロセスを計測し、仕組みを証明してからソース位置を示します。
- <strong>Trace forensics</strong>・・・ プログラムを再実行せず、渡された成果物を問い合わせできる形にして、原因のあるソースコードの位置まで特定します。比較できる成果物がなければ「最も強い仮説」を書きます。

次の[第11章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/6fcb42)では、診断を受け取って実際に直す側の3つのPlaybook、『<strong>Bug fix</strong>』、『<strong>Perf issue</strong>』、『[<strong>Hillclimb</strong>](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/playbooks/hillclimb.md)』を、「何を直したいか」という観点から見ていきます。
