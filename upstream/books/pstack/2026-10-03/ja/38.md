この章では、次の3つのSkillを扱います。

1. [`/unslop`](https://github.com/cursor/plugins/blob/main/pstack/skills/unslop/SKILL.md)
2. [`/bro`](https://github.com/cursor/plugins/blob/main/pstack/skills/bro/SKILL.md)
3. [`/technical-writing`](https://github.com/cursor/plugins/blob/main/pstack/skills/technical-writing/SKILL.md)

3つとも、エージェントが書いた文章の品質を保つためのSkillです。3つは、それぞれ次の仕事を受け持ちます。

- <strong>`/unslop`</strong>・・・ エージェントが、自分の書いた文章から、「I hope this helps!（お役に立てば幸いです）」のような決まり文句など、AIらしい癖を取り除きます。
- <strong>`/bro`</strong>・・・ エージェントが、直前の返答を、専門用語を使わずに短く言い直します。
- <strong>`/technical-writing`</strong>・・・ エージェントが、文書の種類（チュートリアルかリファレンスかなど）を先に決めてから、技術文書を書きます。

この章では、まず3つのSkillの対象、誰が直すか、何をきっかけに動くかの違いを確かめます。そのうえで、1つずつ、役割、使いどき、規則や手順、依頼の書き方の4つの観点で解説します。

### 3つは、名前で呼ばれたときだけ動く

3つの `SKILL.md` は、どれも `disable-model-invocation: true` の設定を持っています（[第25章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/46bd1f)）。この設定があるSkillを、エージェントが会話の内容から自分で選んで動かすことはありません。そのため、3つが動くのは、利用者が名前で呼んだときか、`/poteto-mode`、Playbook、ほかのSkillが手順の中で名前を指定して呼んだときだけです。

`/poteto-mode` の節『[Non-negotiables](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/SKILL.md#non-negotiables)』（[第8章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/096f3d)）は、このうち2つのSkillを呼ぶ場面を決めています。あらゆる文章を書くときは `/unslop`、ドキュメント、RFC（設計を提案する文書）、README、PR説明、コミットメッセージを書くときは `/technical-writing` を呼びます。

そのため、`/poteto-mode` で作業していれば、利用者がこの2つを名前で呼ばなくても、エージェントが『Non-negotiables』の規則に従って、この2つを呼びます。

## `/unslop` は、AIらしい文章の癖を番号付きの規則で取り除く

<a id="%E5%BD%B9%E5%89%B2%EF%BC%9Aai%E3%82%89%E3%81%97%E3%81%84%E6%96%87%E7%AB%A0%E3%81%AE%E7%99%96%E3%82%92%E8%A6%8F%E5%89%87%E3%81%A7%E5%8F%96%E3%82%8A%E9%99%A4%E3%81%8F"></a>


### 役割：AIらしい文章の癖を規則で取り除く

`/unslop` は、<strong>エージェントが、自分の書いた文章から、AIらしい癖を、規則に沿って削るSkill</strong>です。

AIらしい癖とは、AIが書いた文章によく現れ、読み手に「機械が書いた」と気づかせる言い回しや書式のことです。

原文は、この癖を AI tells や AI patterns と呼びます。たとえば、返答の最後に付く決まり文句や、em dash（英文で使う長いダッシュ記号 `—`）の多用などが該当します。

規則とその例は、どれも英語の文章を対象に書かれていますが、言語に関係なく、共通して文章に適用してほしい規則が大半なので、日本語では使えない、ということはないです。

もちろん、英語で最も効果を発揮するので、やはり英語は "The hottest programming language is English" と言えるでしょう。

<a id="%E4%BD%BF%E3%81%84%E3%81%A9%E3%81%8D%EF%BC%9A%E3%81%A9%E3%82%93%E3%81%AA%E6%96%87%E7%AB%A0%E3%81%AB%E3%82%82%E5%B8%B8%E3%81%AB%E9%81%A9%E7%94%A8%E3%81%99%E3%82%8B"></a>


### 使いどき：どんな文章にも常に適用する

`/poteto-mode` の『Non-negotiables』は、<strong>エージェントの返答を含むあらゆる文章</strong>にこのSkillを適用するよう定めています。

`SKILL.md` の説明（description）も、「Must always apply（常に適用すること）」と書いています。ただし、`/unslop` は `disable-model-invocation: true` の設定を持つので、エージェントがこの説明を読んで、自分で `/unslop` を呼ぶことはありません。常に適用されるのは、『Non-negotiables』の規則と、次に見るほかのSkillやPlaybookの手順が、`/unslop` を呼ぶからです。

呼ぶ側ごとの詳細は、次のとおりです。

##### `/technical-writing`：AIらしい癖の一覧を、`/unslop` に任せる

`/technical-writing` は、AIらしい語彙や埋め草（意味のない語句）などの癖の一覧を自分では持たず、`/unslop` に任せています。そのため、自分が書いたりレビューしたりするすべての文書に `/unslop` を適用します。

##### 『Opening a PR』『Multi-phase or multi-PR plan』Playbook：`/technical-writing` で書いた後に、`/unslop` を適用する

PRを作る『[<strong>Opening a PR</strong>](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/playbooks/opening-a-pr.md)』Playbook（[第14章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/45a56e)）は、PRのタイトル、PR説明、コミットの本文を `/technical-writing` で書いた後に、`/unslop` を適用するよう定めています。

複数のフェーズやPRにまたがる計画書を書く『[<strong>Multi-phase or multi-PR plan</strong>](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/playbooks/multi-phase-plan.md)』Playbook（[第16章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/8a8dd5)）も、計画書を `/technical-writing` で書いた後に、`/unslop` を適用するよう定めています。

##### `/teach`、`/show-me-your-work`：同僚に話すような言葉で書く

`/teach`（[第22章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/788746)）は、作業の内容を、人が本当に理解できるよう平易に説明するSkillです。`/teach` は、すべての返答を、同僚に説明するときのような平易な話し言葉で書くよう定め、その返答に `/unslop` を適用します。

`/show-me-your-work`（[第28章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/724887)）は、エージェントの判断とその根拠を、1行に1つずつファイルに記録するSkillです。`/show-me-your-work` は、判断の記録の各行を、自分のしたことをチームメイトに話すように、AIらしい言い回しや抽象的な専門用語を使わずに書くよう定めています。そのうえで、判断の記録の文にも `/unslop` を適用するとしています。

##### `/recall`、`/blast-radius`：利用者に渡す報告を書く

`/recall`（[第22章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/788746)）は、チャットの履歴などから、利用者の最近の作業の状況を組み立て直すSkillです。`/blast-radius`（[第27章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/997880)）は、変更がほかの場所で壊しうるものを、リリース前に探すSkillです。

2つとも、利用者に渡す報告を、`/unslop` を通して書きます。`/recall` の報告は、作業が今どこまで進み、次に何をするかを伝えます。`/blast-radius` の報告は、変更が壊しうるものと、マージの前に何を確かめるかを伝えます。

##### `/automate-me`：利用者専用のSkillの文章を、`/unslop` で直す

`/automate-me`（[第25章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/46bd1f)）は、利用者の最近のトランスクリプト（エージェントとの会話の記録）から作業の好みを読み取り、利用者専用のSkill（`<利用者の名前>-mode`）の下書きを作るSkillです。`/automate-me` は、その下書きの各行に、`/unslop` を適用します。

##### 『Investigation』Playbook：調べた結果の返答が、そのまま成果物になる

『[<strong>Investigation</strong>](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/playbooks/investigation.md)』（[第10章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/ea525d)）は、コードを変えずに、問いを調べて答えるPlaybookです。このPlaybookは、コードの変更ではなく、出典付きの説明か推奨を返し、<strong>その返答を調査の成果物と定めています</strong>。

このPlaybookは、手順の最後で、その返答に `/unslop` を適用します。

### 規則：AIらしい癖を、7つの分類と固定の番号で示す

`SKILL.md` の手順は、次の2つだけです。残りの大半は、規則が占めています。

1. 規則に当てはまる箇所を探す
2. 意味を保ち、書き手が意図した調子（文調）に合わせて書き直す

規則には番号が付いていて、その番号は、ほかのSkillが規則を指すときに使う固定のIDです。たとえば、`/poteto-mode` は、「文の途中のつなぎにコロンを使わない」という規則を、「unslop rule 14」のように番号で指しています。

`SKILL.md` は、規則を消したら、その番号を空けたままにすると定めています。pstack version `0.15.5`の `SKILL.md` では、1、2、4、6、21の番号が空いています。

### 依頼の書き方：直す文章と追加の規則を添えて呼ぶ

同梱ガイドの [`docs/guide/05-build-and-clean.md`](https://github.com/cursor/plugins/blob/main/pstack/docs/guide/05-build-and-clean.md) は、直す文章と、追加の規則を添えて呼ぶ次の例を挙げています。

```
/unslop the readme changes, no emdashes
// READMEの変更を unslop して。em dash は使わないで
```

この依頼では、「the readme changes」が直す文章で、「no emdashes」が追加の規則です。

同じページは、次のような短い依頼でも、エージェントは依頼の意図を読み取り、このSkillで文章を直せると説明しています。

```
unslop that, tighten it
// それを unslop して、引き締めて
```

「that」は、直前に書いた文章を指します。

<a id="%2Fbro-%E3%81%AF%E3%80%81%E5%88%86%E3%81%8B%E3%82%8A%E3%81%AB%E3%81%8F%E3%81%84%E8%BF%94%E7%AD%94%E3%82%92%E3%80%81%E5%B0%82%E9%96%80%E7%94%A8%E8%AA%9E%E3%81%AA%E3%81%97%E3%81%A7%E8%A8%80%E3%81%84%E7%9B%B4%E3%81%99"></a>


## `/bro` は、分かりにくい返答を、専門用語なしで言い直す

<a id="%E5%BD%B9%E5%89%B2%EF%BC%9A%E7%9B%B4%E5%89%8D%E3%81%AE%E8%BF%94%E7%AD%94%E3%82%92%E3%80%81%E5%B0%82%E9%96%80%E7%94%A8%E8%AA%9E%E3%81%AA%E3%81%97%E3%81%A7%E8%A8%80%E3%81%84%E7%9B%B4%E3%81%99"></a>


### 役割：直前の返答を、専門用語なしで言い直す

`/bro` は、<strong>エージェントが直前の返答を専門用語なしで言い直すためのSkill</strong>です。本文は3文だけで、pstack で最も短いSkillです。

`/unslop` との違いは、直す単位です。`/unslop` は、決まり文句のような、規則に当てはまる箇所だけを直します。一方、`/bro` は、規則を使わず、直前の返答全体を、平易な言葉で言い直します。

`/unslop` や `/technical-writing` と異なり、`/poteto-mode` も、Playbookも、他のSkillも、手順の中で `/bro` を呼びません。そのため、`/bro` は、利用者が名前で呼んだときだけ動きます。

<a id="%E4%BD%BF%E3%81%84%E3%81%A9%E3%81%8D%EF%BC%9A%E8%BF%94%E7%AD%94%E3%81%8C%E8%A9%B3%E3%81%97%E3%81%84%E3%81%AE%E3%81%AB%E3%80%81%E4%BD%95%E3%82%92%E8%A8%80%E3%81%A3%E3%81%A6%E3%81%84%E3%82%8B%E3%81%AE%E3%81%8B%E5%88%86%E3%81%8B%E3%82%89%E3%81%AA%E3%81%84%E3%81%A8%E3%81%8D"></a>


### 使いどき：返答が詳しいのに、何を言っているのか分からないとき

利用者は、エージェントの返答が技術的には詳しく書かれているのに、何を言っているのか分からないときに、このSkillを使います。

<a id="%E6%89%8B%E9%A0%86%EF%BC%9A%E6%9C%AC%E6%96%87%E3%81%AE3%E6%96%87%E3%81%8C%E3%80%81%E3%81%9D%E3%81%AE%E3%81%BE%E3%81%BE%E6%8C%87%E7%A4%BA%E3%81%AB%E3%81%AA%E3%82%8B"></a>


### 手順：本文の3文が、そのまま指示になる

`/bro` の本文は、次の3文だけです。

> Restate your last message. Stop using jargon and speak coherently. State it more simply and concisely, like one human talking to another.
>
> 直前のメッセージを言い直せ。専門用語を使うのをやめ、筋の通った話し方をせよ。人が人に話すように、もっと簡単に、短く言え。

`SKILL.md` には手順の節がなく、エージェントは、この3文をそのまま指示として受け取ります。

<a id="%E4%BE%9D%E9%A0%BC%E3%81%AE%E6%9B%B8%E3%81%8D%E6%96%B9%EF%BC%9A%E3%80%8C%2Fbro%E3%80%8D%E3%81%A0%E3%81%91%E3%81%A7%E8%B6%B3%E3%82%8A%E3%82%8B"></a>


### 依頼の書き方：「/bro」だけで足りる

同梱ガイドの [`10-recipes-and-pitfalls.md`](https://github.com/cursor/plugins/blob/main/pstack/docs/guide/10-recipes-and-pitfalls.md) は、次の一語だけをプロンプトとして載せています。

```
/bro
```

本文の3文がそのまま指示になるので、利用者が言い直し方を書き添える必要はありません。

<a id="%2Ftechnical-writing-%E3%81%AF%E3%80%81%E6%96%87%E6%9B%B8%E3%81%AE%E7%A8%AE%E9%A1%9E%E3%82%92%E5%85%88%E3%81%AB%E6%B1%BA%E3%82%81%E3%81%A6%E3%81%8B%E3%82%89%E6%9B%B8%E3%81%8B%E3%81%9B%E3%82%8B"></a>


## `/technical-writing` は、文書の種類を先に決めてから書かせる

<a id="%E5%BD%B9%E5%89%B2%EF%BC%9A%E6%8A%80%E8%A1%93%E6%96%87%E6%9B%B8%E3%82%92%E3%80%81%E5%B1%A4%E3%81%AB%E5%88%86%E3%81%91%E3%81%9F%E8%A6%8F%E7%AF%84%E3%81%A7%E3%82%A8%E3%83%BC%E3%82%B8%E3%82%A7%E3%83%B3%E3%83%88%E3%81%AB%E6%9B%B8%E3%81%8B%E3%81%9B%E3%82%8B"></a>


### 役割：技術文書を、層に分けた規範でエージェントに書かせる

`/technical-writing` は、エージェントが技術文書を書くときに従う規範を、文書全体の種類から一文の書き方までの4つの層に分けて示すSkillです。<strong>目標は、疲れたエンジニアが一度読んで理解できる文章です</strong>。

poteto氏は『The Complete Guide to pstack』[Part 2](https://x.com/poteto/status/2097732320606507506)で、このSkillを作ったきっかけを説明しています。

きっかけは、Cursor社内のデスクトップアプリ用フレームワーク Dune のREADMEを、このSkillなしでエージェントに書かせたことでした。できたREADMEは、チュートリアル、ハウツー、設計の解説、APIリファレンスが一つに混ざり、AIらしい癖のある凝った文章で書かれていて、読みにくいものだったそうです。

<a id="%E4%BD%BF%E3%81%84%E3%81%A9%E3%81%8D%EF%BC%9A%E6%96%87%E6%9B%B8%E3%82%92%E6%9B%B8%E3%81%8F%E3%81%A8%E3%81%8D%E3%81%A8%E3%83%AC%E3%83%93%E3%83%A5%E3%83%BC%E3%81%99%E3%82%8B%E3%81%A8%E3%81%8D"></a>


### 使いどき：文書を書くときとレビューするとき

`SKILL.md` の説明（description）は、ドキュメント、RFC（設計を提案する文書）、README、PR説明、コミットメッセージを書くときと、それらをレビューするときを、使いどきとして挙げています。

ただし、`/technical-writing` も `disable-model-invocation: true` の設定を持つので、エージェントがこの説明を読んで、自分で `/technical-writing` を呼ぶことはありません。こうした場面でこのSkillが使われるのは、『Non-negotiables』の規則が、こうした文書を書くときにはこのSkillを使うよう定めているからです。

Playbookでは、PRを作る『Opening a PR』が、PRのタイトル、PR説明、コミットの本文をこのSkillで書くよう定めています。計画書を作る『Multi-phase or multi-PR plan』も、計画書をこのSkillで書くよう定めています。

<a id="%E8%A6%8F%E5%89%87%EF%BC%9A4%E3%81%A4%E3%81%AE%E5%B1%A4%E3%81%A8%E3%80%81%E5%B1%A4%E3%81%AE%E5%A4%96%E3%81%AE%E8%A6%8F%E5%89%87"></a>


### 規則：4つの層と、層の外の規則

`SKILL.md` は、4つの層の規範のほかに、層の外の規則も定めています。先に層の外の規則を見てから、4つの層を1つずつ見ていきます。

<a id="4%E3%81%A4%E3%81%AE%E5%B1%A4%E3%82%88%E3%82%8A%E5%84%AA%E5%85%88%E3%81%99%E3%82%8B3%E3%81%A4%E3%81%AE%E8%A6%8F%E5%89%87"></a>


#### 4つの層より優先する3つの規則

エージェントは、4つの層とは別に、どの層よりも優先して、次の3つの規則を守ります。

- 取り除いても文の意味が変わらない語は、すべて削ります。たとえば、「In order to」は「to」にします。
- 短く日常的な語を使います。たとえば、「utilize」ではなく「use」と書きます。
- 規則を守ると文が悪くなるなら、別の方法で直すか、そのままにします。規則は読み手のためにあり、規則をすべて守っても機械が書いたように読める文は失敗だからです。

<a id="%E5%90%8D%E5%89%8D%E3%81%AF%E3%80%81%E3%82%B3%E3%83%BC%E3%83%89%E3%83%99%E3%83%BC%E3%82%B9%E3%81%AE%E5%90%8D%E5%89%8D%E3%82%92%E3%81%9D%E3%81%AE%E3%81%BE%E3%81%BE%E4%BD%BF%E3%81%84%E3%80%81%E6%96%B0%E3%81%97%E3%81%84%E5%B0%82%E9%96%80%E7%94%A8%E8%AA%9E%E3%82%92%E4%BD%9C%E3%82%89%E3%81%AA%E3%81%84"></a>


#### 名前は、コードベースの名前をそのまま使い、新しい専門用語を作らない

エージェントは、コードベースに実在するシンボル（関数名、型名、変数名など、コードの中で名前を付けたもの）、ファイル、フラグ、コマンドの名前を、言い換えずにそのまま書きます。

また、エージェントは、新しい専門用語も作らず、開発者が口語で使う言葉を使います。たとえば、コードを別の場所に移すことを、「evacuate（避難させる）」ではなく「move（移す）」と書きます。

一方で、「Strangler Fig パターン」のように、決まった設計や進め方に付いていて、すでに広く使われている名前は、エージェントもその名前で書きます。

ただし、エージェントは、その名前が文書で最初に出てきたところに、意味を書き添えます。たとえば、「Strangler Fig パターン（古い仕組みを、少しずつ新しい仕組みに置き換えていく進め方）で移行する」と書きます。

evacuate のような言い換えるべき語は、`/unslop` の規則26（抽象的な比喩の名詞）が一覧にしています。一覧にない語を見つけたら、エージェントは、`/unslop` を自分で書き換えず、「その一覧にない語」と「言い換えた語」を一覧に追加する案を、差分つきで返答に書きます。

<a id="%E6%96%87%E3%81%AE%E9%95%B7%E3%81%95%E3%82%92%E6%B7%B7%E3%81%9C%E3%80%81%E5%85%B7%E4%BD%93%E7%9A%84%E3%81%AB%E6%9B%B8%E3%81%8F"></a>


#### 文の長さを混ぜ、具体的に書く

このSkillは、文の長さと具体性について、次の4つを求めています。

- <strong>文の長さを意図的に混ぜる</strong>・・・ 短い文で要点を示し、長い文で事実をその条件や結果とともに書きます。
- <strong>文を分けるかどうかは、長さではなく、伝えたいことの数で決める</strong>・・・ 「一文に一つのこと」は、「どの文も短くする」という意味ではありません。伝えたいことが二つある文は分けますが、一つだけの文は、長くてもそのまま残します。
- <strong>解説では、書き手の評価も書く</strong>・・・ explanation（解説）では、長所と短所を並べるだけで終わらせず、書き手がそれをどう評価するかも書きます。一方、reference（リファレンス）には評価を書かず、事実だけを書きます。
- <strong>ぼかさず、具体的に書く</strong>・・・ 「スキーマの変更は問題を起こしうる」のような当たり障りのない書き方ではなく、「列の名前を変えると、ビルドが失敗する」のように、何が起きるかを書きます。

<strong>4つの層の規範をすべて守っても、短く切った文ばかりが並び、具体的なことが何も書かれていなければ、機械が書いたように読める</strong>からです。

<a id="pr%E8%AA%AC%E6%98%8E%E3%81%AF%E3%80%811%E5%88%86%E4%BB%A5%E5%86%85%E3%81%AB%E8%AA%AD%E3%82%81%E3%82%8B%E9%95%B7%E3%81%95%E3%81%AB%E3%81%99%E3%82%8B"></a>


#### PR説明は、1分以内に読める長さにする

エージェントは、PR説明を、レビューする人が1分以内に読める長さにします。そのため、`/swarm`（[第24章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/2ad346)）の実行ログ、コミットのSHA（コミットごとに付く、コミットを一意に指す識別子）の一覧、指標の表は、本文に貼らずにリンクします。

#### Diátaxis：文書の種類を先に決める

<strong>最初の層（Diátaxis）で、文書の種類を先に決めます</strong>。種類が混ざった文書は、この章の[『役割：技術文書を、層に分けた規範でエージェントに書かせる』](#%E5%BD%B9%E5%89%B2%EF%BC%9A%E6%8A%80%E8%A1%93%E6%96%87%E6%9B%B8%E3%82%92%E3%80%81%E5%B1%A4%E3%81%AB%E5%88%86%E3%81%91%E3%81%9F%E8%A6%8F%E7%AF%84%E3%81%A7%E3%82%A8%E3%83%BC%E3%82%B8%E3%82%A7%E3%83%B3%E3%83%88%E3%81%AB%E6%9B%B8%E3%81%8B%E3%81%9B%E3%82%8B)で見た Dune のREADMEのように読みにくくなるからです。

種類は、「行動のための文書か、理解のための文書か」と「学習のための文書か、仕事のための文書か」の2つの問いで決まります。

`SKILL.md` は、4つの種類を次のように説明しています。

- <strong>tutorial（チュートリアル）</strong>・・・ 初めて使う人が、ハンズオン（手を動かして）で、実際に何かを作りながら覚えるための文書です。最初に完成するものを示し、手順ごとに、「画面や出力に何が表示されるはずか」を書きます。
- <strong>how-to（ハウツー）</strong>・・・ すでに使い慣れた人が、目の前の問題を解決するための手順書です。基本の説明は省き、やることだけを順に書きます。
- <strong>reference（リファレンス）</strong>・・・ 必要なときに引いて、正確な事実を確かめるための文書です。仕様や設定項目を並べ、手順や書き手の意見は入れません。
- <strong>explanation（解説）</strong>・・・ 仕組みや設計が「なぜそうなっているのか」を理解するための文書です。設計の判断、経緯、制約、他の案を書きます。書き手の意見を書くのは、この文書だけです。

Dune のREADMEのように4つの種類を一つに混ぜた文書なら、エージェントは4つの文書に分け、互いにリンクします。

ただし、PR説明とコミットメッセージには、エージェントはこの層を適用せず、残りの3つの層だけを適用します。

#### Google developer style：読み手に語りかける

エージェントは、読み手を「you」と呼び、指示は「Click Submit.」のような命令形で書きます。

また、エージェントは、条件を指示の前に置き、「To delete the document, click Delete.」（ドキュメントを削除するには、Delete をクリックする）のように書きます。条件が先にあれば、読み手は自分に関係のない指示を読み飛ばせるからです。

さらに、エージェントは、見出しに、「何についての節か」だけでなく、「その節の要点」まで書きます。

たとえば、「Modes（モード）」のように「何についての節か」だけを示す見出しではなく、「Pick the mode first（最初にモードを選ぶ）」のように、読み手が「何をすればよいか」まで分かる見出しにします。  
ここでのモードは、Diátaxis の文書の種類のことです。

<a id="ste%EF%BC%9A%E4%B8%80%E6%96%87%E3%81%AB%E3%81%AF%E3%80%81%E4%BC%9D%E3%81%88%E3%81%9F%E3%81%84%E3%81%93%E3%81%A8%E3%82%92%E4%B8%80%E3%81%A4%E3%81%A0%E3%81%91%E6%9B%B8%E3%81%8F"></a>


#### STE：一文には、伝えたいことを一つだけ書く

エージェントは、一文に一つの指示だけを書きます。ここでの指示とは、「Install the component.（部品をインストールする）」のように、読み手に何かをさせる文です。

また、エージェントは、長い文を2つに分けます。目安は、指示なら約20語、それ以外の文なら約25語です。この語の数は、英語の単語の数です。

文章を書く時、エージェントは、英語の冠詞「the」や「a」を省きません。たとえば、「Remove backup file」は二通りに読めますが、「Remove the backup file（そのバックアップファイルを消す）」なら一通りにしか読めません。

<aside class="msg message"><span class="msg-symbol">!</span><div class="msg-content">
<ul class="code-line" data-line="389">
<li class="code-line" data-line="389">
<strong>冠詞</strong>・・・ 英語で、名詞の前に付ける「the」「a」などの語。日本語にはない</li>
<li class="code-line" data-line="390">
<strong>「Remove backup file」が二通りに読める理由</strong>・・・ 原文は、どの二通りかまでは書いていない。本書では、次のように読めると考える。冠詞がないと、「backup file」を1つの名詞（バックアップファイル）として読み、「バックアップファイルを消す」と取ることも、backup（バックアップ）と file を切り離し、file を動詞（保管する）として「バックアップを消して、保管する」と取ることもできる。「the」があれば、「the backup file」がひとまとまりの名詞だと決まる</li>
</ul>
</div></aside>

さらに、エージェントは、同じ動作を、文書の中でずっと同じ語で書きます。ある箇所で「start（始める）」と書いたなら、別の箇所で「initiate（開始する）」と言い換えません。

<a id="global-english%EF%BC%9A%E4%BA%8C%E9%80%9A%E3%82%8A%E3%81%AB%E8%AA%AD%E3%82%81%E3%82%8B%E6%96%87%E3%82%92%E3%81%AA%E3%81%8F%E3%81%99"></a>


#### Global English：二通りに読める文をなくす

エージェントは、「only」や「not」を、それが修飾する語のすぐ隣に置きます。「only fails on growth（増えたときに、失敗するだけ）」と「fails only on growth（増えたときだけ、失敗する）」のように、置く場所で意味が変わるからです。

また、エージェントは、一つのものを、どこでも一つの名前で呼びます。一つの仕組みを「the gate」「the ratchet」「the budget check」と呼び分ける文書は、読み手に3つのものがあると思わせてしまいます。

<a id="%E4%BE%8B%EF%BC%891%E6%AE%B5%E8%90%BD%E3%82%92%E3%80%81%E8%A6%8F%E5%89%87%E3%81%AB%E6%B2%BF%E3%81%A3%E3%81%A6%E6%9B%B8%E3%81%8D%E7%9B%B4%E3%81%99"></a>


#### 例）1段落を、規則に沿って書き直す

`SKILL.md` は、書き直しの例を1つ載せています。直す前の段落は、次のとおりです。

> Configuration of the proto import ratchet budget script parameters is performed via budget.json. Note that it's important to remember that running with --write, which updates the committed budget to reflect the current count, should only be done when lowering it. If exceeded, CI fails.
>
> proto import ratchet budget script のパラメータの設定は、budget.json を介して行われる。--write を付けて実行すること（コミットされた予算を現在の数に合わせて更新する）は、予算を下げるときにだけ行うべきだと覚えておくことが重要である点に注意。超えると、CI が失敗する。

直した後の段落は、次のとおりです。

> `budget.mjs` reads the committed budget from `budget.json` and counts the files that import protos. If the count exceeds the budget, CI fails. Run `budget.mjs --write` only to lower the budget.
>
> `budget.mjs` は、コミットされた予算を `budget.json` から読み、protoをインポートしているファイルを数える。数が予算を超えると、CI が失敗する。`budget.mjs --write` は、予算を下げるときにだけ実行する。

2つの段落を比べると、次の点が変わっています。

- 「proto import ratchet budget script」という名詞の連なりをやめ、実在するファイル名 `budget.mjs` と `budget.json` で書いている
- 「is performed via」という受け身をやめ、`budget.mjs` を主語にして、何をするかを書いている
- 「Note that it's important to remember that」のような、意味のない語句を削っている
- 比喩の「ratchet」を使っていない。ratchet は一方向にしか回らない歯車のことで、ここでは「減ることしかない上限」の比喩として使われていた
- 「should only be done」という受け身の注意を、「Run `budget.mjs --write` only to lower the budget.」という命令形の指示にしている

## まとめ

- <strong>3つの違い</strong>・・・ `/unslop` と `/technical-writing` は書いたエージェント自身が規則で直し、`/bro` は利用者が呼んだときにエージェントが言い直します。
- <strong>`/unslop`</strong>・・・ 番号を変えない28の規則で、あらゆる文章からAIらしい癖を取り除きます。
- <strong>`/bro`</strong>・・・ 直前の返答を、専門用語なしで、短く言い直します。
- <strong>`/technical-writing`</strong>・・・ 文書の種類を先に1つに決め、疲れたエンジニアが一度読んで理解できる文書にします。

次の[第33章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/f70847)では、作業の学びを振り返り、既存のSkillに反映する [`/reflect`](https://github.com/cursor/plugins/blob/main/pstack/skills/reflect/SKILL.md) を扱います。
