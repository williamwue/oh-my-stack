## pstackを導入する

pstackの導入は、コマンド1つと短い会話で終わります。

1. Cursor のチャットで、次のコマンドを実行します。

   ```
   /add-plugin pstack
   ```
2. 続けて、次のコマンドで `/setup-pstack` を実行し、`/setup-pstack` の質問に答えます。何を聞かれ、何が決まるかは、この章の次の節から解説します。

   ```
   /setup-pstack
   ```
3. `/setup-pstack` が終わったら、新しいチャットを始めます。<strong>`/setup-pstack` が書き出すモデルのルールは、新しいチャットから適用される</strong>からです。

## 全体の流れ

`/setup-pstack` は、推論の予算と役割ごとのモデルを尋ね、その答えを `~/.cursor/rules/pstack-models.mdc` という<strong>常に適用されるルールに書き出すSkill</strong>です。

<aside class="msg message"><span class="msg-symbol">!</span><div class="msg-content">
<ul class="code-line" data-line="81">
<li class="code-line" data-line="81">
<strong>推論の予算</strong>・・・ 原文では budget。役割のモデルの推論の強さを、一度に決める設定</li>
<li class="code-line" data-line="82">
<strong>スラッグ</strong>・・・ <code>claude-opus-5-5-max</code> のような、モデルを指定する識別子
<ul class="code-line" data-line="83">
<li class="code-line" data-line="83">例：<code>claude-opus-5-5-max</code> は、Claude Opus 5.5 をEffort Level <code>max</code> で動かす指定</li>
</ul>
</li>
<li class="code-line" data-line="84">
<strong>推論の強さ（Effort Level）</strong>・・・ モデルが推論にかける手間の段階。スラッグの中の <code>max</code>、<code>xhigh</code>、<code>high</code>、<code>medium</code>、<code>low</code> の語で表し、左ほど強い</li>
</ul>
</div></aside>

## 使えるモデルを検出する

最初に、`/setup-pstack` は、利用者が使えるモデルのスラッグを調べます。調べ方は、次のとおりです。

- <strong>基本の調べ方</strong>・・・ 今のチャットで、サブエージェントに渡せるスラッグを調べます。原文は、これを確実な方法としています。
- <strong>APIやCLIがある場合</strong>・・・ Cursor が、利用者の使えるモデルを一覧にするAPIやCLIを用意していれば、漏れがないよう、そちらを優先します。
- <strong>何も見つからない場合</strong>・・・ 利用者に、自分が使えるスラッグをチャットに貼ってもらうよう頼みます。

ここで見つかったスラッグを、この章では「使えるモデル」と呼びます。

<a id="%E5%89%8D%E5%9B%9E%E3%81%AE%E3%83%AB%E3%83%BC%E3%83%AB%E3%83%95%E3%82%A1%E3%82%A4%E3%83%AB%E3%82%92%E8%AA%AD%E3%82%80"></a>


## 前回のルールファイルを読む

過去に、`/setup-pstack` を実行していれば、そのとき書き出したルールファイル（`~/.cursor/rules/pstack-models.mdc`）がすでにあります。その場合、`/setup-pstack` は、そのファイルの `# budget` の行（前回選んだ予算）と各役割の値を読み、今回の選び直しの出発点にします。

ただし、前回のルールファイルには、すでに廃止された役割の行（たとえば `how critics` の行）が残っていることがあります。廃止された役割とは、今の pstack が書き出すファイルに並んでいない役割です（書き出すファイルの中身は、この章の[『書き出すファイル』](#%E6%9B%B8%E3%81%8D%E5%87%BA%E3%81%99%E3%83%95%E3%82%A1%E3%82%A4%E3%83%AB)で示します）。

`/setup-pstack` は、こうした行を捨てます。どの行を捨てたかは、`/setup-pstack` が、役割とモデルの一覧を示すときに利用者に伝えます。

<a id="%E6%8E%A8%E8%AB%96%E3%81%AE%E4%BA%88%E7%AE%97%E3%82%92%E9%81%B8%E3%81%B6"></a>


## 推論の予算を選ぶ

推論の予算は、<strong>すべての役割のモデルを、どの推論の強さで動かすか</strong>を一度に決める設定です。スラッグの中の `max`、`xhigh`、`high`、`medium`、`low` の語で表します。`max` が最も強く、`low` が最も弱い段階です。

利用者は、予算を次の4つから選びます。  
予算ごとに、そろえる推論の強さ（以下、目標の強さ）が決まっています。

<table class="code-line" data-line="145">
<thead class="code-line" data-line="145">
<tr class="code-line" data-line="145">
<th>予算</th>

### スラッグの強さの語を、目標の強さに置き換える

`large`、`medium`、`small` のどれかを選ぶと、`/setup-pstack` は、すべての役割のスラッグについて、強さの語だけを目標の強さに置き換えます。強さの語は、スラッグの末尾にあります。末尾が `fast` なら、その直前です。

たとえば、`small`（目標の強さは `medium`）を選ぶと、次のように変わります。

- `claude-opus-5-5-max` → `claude-opus-5-5-medium`
- `grok-4.7-xhigh-fast` → `grok-4.7-medium-fast`

`arena runners: claude-opus-5-5-max, gpt-5.6-sol-max, grok-4.7-xhigh-fast` のように、1つの役割に複数のモデルを並べた行では、並んだスラッグをすべて置き換えます。こうした役割は、この章の[『パネルの役割』](#%E3%83%91%E3%83%8D%E3%83%AB%E3%81%AE%E5%BD%B9%E5%89%B2)で説明します。

`inherit-parent` と `auto` はスラッグではないので、置き換えません。

<a id="%E7%BD%AE%E3%81%8D%E6%8F%9B%E3%81%88%E3%81%9F%E3%83%A2%E3%83%87%E3%83%AB%E3%81%8C%E4%BD%BF%E3%81%88%E3%81%AA%E3%81%84%E3%81%A8%E3%81%8D%E3%81%AF%E3%80%81%E5%90%8C%E3%81%98%E7%B3%BB%E7%B5%B1%E3%81%AE%E4%B8%AD%E3%81%A7%E4%BB%A3%E3%82%8F%E3%82%8A%E3%82%92%E9%81%B8%E3%81%B6"></a>


### 置き換えたモデルが使えないときは、同じ系統の中で代わりを選ぶ

置き換えた後のスラッグが、検出でき、かつ使用可能なモデルの中にないこともあります。たとえば、`claude-opus-5-5-medium` が使えないことがあります。

その場合、`/setup-pstack` は、次の順に代わりのモデルを決めます。

1. 同じ系統（原文では family）の、使えるモデルを探す
2. そのうち、目標の強さと同じか、それより弱いものの中で、最も強いものを使う
3. 1つも見つからなければ、その役割を、利用者が選び直す役割として示す

たとえば、`small`（目標の強さは `medium`）を選び、使える Claude のモデルが `claude-opus-5-5-high` と `claude-opus-5-5-low` だけだったとします。

- `high` は、目標の `medium` より強いので、使いません。
- `low` は、目標の `medium` より弱いので、使えます。

そのため、`/setup-pstack` は `claude-opus-5-5-low` を使います。

このように、代わりのモデルは同じ系統の中からしか選ばないので、<strong>予算を下げても、モデルの系統は変わりません</strong>。たとえば、Claude で動いていた役割が、予算を下げたことで Grok に変わることはありません。

<a id="%E6%9C%80%E5%BE%8C%E3%81%AB%E3%80%81%E5%BD%B9%E5%89%B2%E3%81%A8%E3%83%A2%E3%83%87%E3%83%AB%E3%81%AE%E4%B8%80%E8%A6%A7%E3%82%92%E7%A2%BA%E3%81%8B%E3%82%81%E3%82%8B"></a>


### 最後に、役割とモデルの一覧を確かめる

置き換えが終わると、`/setup-pstack` は、すべての役割と、それぞれに割り当てたモデルの一覧を見せます。選び直す必要がある役割には、その印が付いています。

利用者は、そのまま受け入れるか、特定の役割のモデルを変えるかを選びます。モデルを変えるときは、使えるモデル、`inherit-parent`、`auto` のどれかを選びます。

<a id="inherit-parent-%E3%81%A8-auto"></a>


## inherit-parent と auto

`inherit-parent` と `auto` は、どちらも、<strong>その役割のサブエージェントを、親のチャットと同じモデルで動かす指定</strong>です。親のチャットとは、サブエージェントを起動した元のチャットです。

この2つを書いた役割では、各Skillは、サブエージェントを起動するときにモデルを指定しません。モデルを指定されなかったサブエージェントは、親のチャットと同じモデルで動きます。

そのため、Auto（Cursor がモデルを自動で選ぶ設定）でチャットを使っている利用者は、役割に `inherit-parent` か `auto` を書けば、サブエージェントも Auto で動かせます。

<a id="%E6%9B%B8%E3%81%8D%E5%87%BA%E3%81%99%E5%89%8D%E3%81%AB%E3%80%81%E4%BD%BF%E3%81%88%E3%82%8B%E3%83%A2%E3%83%87%E3%83%AB%E3%81%8B%E3%82%92%E7%A2%BA%E3%81%8B%E3%82%81%E3%82%8B"></a>


## 書き出す前に、使えるモデルかを確かめる

利用者が一覧を確かめ終えると、`/setup-pstack` は、ルールファイルを書き出す前に、書き出すスラッグが、この章の[『使えるモデルを検出する』](#%E4%BD%BF%E3%81%88%E3%82%8B%E3%83%A2%E3%83%87%E3%83%AB%E3%82%92%E6%A4%9C%E5%87%BA%E3%81%99%E3%82%8B)で検出した使えるモデルに含まれているかを確かめます。

含まれていないスラッグが1つでもあれば、`/setup-pstack` は書き出さずに止まり、利用者にその役割のモデルを選び直してもらいます。<strong>`/setup-pstack` は、使えると確認していないスラッグを、ルールファイルに書きません</strong>。

ルールファイルに書いたスラッグは、各Skillがサブエージェントを起動するときに、そのままモデルの指定として渡されるからです。

`inherit-parent` と `auto` は、モデルのスラッグではないので、この確認の対象になりません。いつでもルールファイルに書けます。

<a id="%E3%83%91%E3%83%8D%E3%83%AB%E3%81%AE%E5%BD%B9%E5%89%B2"></a>


## パネルの役割

どのフロンティアモデル（各社の最先端のモデル）にも強みと弱みがあります。そこで、pstackの多くのSkillは、複数のモデルを組み合わせて、それぞれのモデルの強みを活かします（[README](https://github.com/cursor/plugins/blob/main/pstack/README.md)）。

そのために複数のモデルを並べる役割を、`/setup-pstack` は、パネルの役割（原文では panel roles）と呼びます。パネルとは、同じ問いを複数のモデルに解かせて比べる仕組みです（[第6章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/33f073)）。

パネルの役割は、次の3つです。

- <strong>`arena runners`</strong>・・・ `/arena` が、同じ課題を解かせる候補のサブエージェント
- <strong>`architect runners`</strong>・・・ `/architect` が、コードを書く前に設計案を作らせるサブエージェント
- <strong>`interrogate reviewers`</strong>・・・ `/interrogate` が、差分の弱点を探させるレビュアーのサブエージェント

<a id="%E4%B8%A6%E3%81%B9%E3%81%9F%E3%83%A2%E3%83%87%E3%83%AB%E3%81%AE%E6%95%B0%E3%81%A0%E3%81%91%E3%80%81%E3%82%B5%E3%83%96%E3%82%A8%E3%83%BC%E3%82%B8%E3%82%A7%E3%83%B3%E3%83%88%E3%81%8C%E8%B5%B7%E5%8B%95%E3%81%99%E3%82%8B"></a>


### 並べたモデルの数だけ、サブエージェントが起動する

パネルの役割の値には、モデルを `,` で区切って並べます。<strong>並べたモデルの数だけ、サブエージェントが起動します</strong>。

たとえば、`arena runners: claude-opus-5-5-max, gpt-5.6-sol-max, grok-4.7-xhigh-fast` なら、`/arena` は、3つのモデルで1体ずつ、合わせて3体のサブエージェントを起動します。

リストに `inherit-parent` や `auto` を書いたときも、1項目につき1体のサブエージェントが起動します。そのサブエージェントは、親のチャットのモデルで動きます。

<a id="%E3%83%A2%E3%83%87%E3%83%AB%E3%82%92%E4%B8%A6%E3%81%B9%E3%81%A6%E3%82%82%E3%80%81%E3%83%91%E3%83%8D%E3%83%AB%E3%81%AE%E5%BD%B9%E5%89%B2%E3%81%A7%E3%81%AF%E3%81%AA%E3%81%84%E3%82%82%E3%81%AE"></a>


### モデルを並べても、パネルの役割ではないもの

ルールファイルには、パネルの役割ではないのに、値にモデルを並べる行が1つあります。`arena cross-judge pool` です。

`arena cross-judge pool` は、`/arena` の判定役（候補の成果物を採点するエージェント。[第24章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/2ad346)）のモデルの候補を並べた行です。`/arena` は、候補がすべて書き終えた後、`arena cross-judge pool` の行に並んだモデルの中から1つのモデルを選び、判定役として起動します。選ぶときは、できるだけ親のチャットと系統の異なるモデルを選びます。

また、`swarm workers` も、パネルの役割ではありません。`swarm workers` は、`/swarm` が起動するすべてのWorkerが使う既定のモデルで、値に書くモデルは1つです。

例外は、モデルの競争（原文では model race）です。モデルの競争とは、同じ課題を、別々のモデルで動くWorkerに解かせ、どのモデルが最もよい結果を出すかを比べる使い方です。

この場合、`/swarm` は、Workerを起動する前に、Workerごとに使うモデルを決めます。そのWorkerは、`swarm workers` のモデルではなく、決められたモデルで動きます。

<a id="%E6%9B%B8%E3%81%8D%E5%87%BA%E3%81%99%E3%83%95%E3%82%A1%E3%82%A4%E3%83%AB"></a>


## 書き出すファイル

`/setup-pstack` は、実行するたびに、ルールファイルを丸ごと新しく書き直します。前回のファイルに、行を書き足したり、一部の行だけを書き換えたりはしません。

予算に `unlimited` を選び、すべての役割を既定値のまま受け入れたときに `/setup-pstack` が書き出すファイルは、次のとおりです（pstack version `0.15.5` 時点）。

```
---

hardest tasks: claude-opus-5-5-max
```

READMEによれば、pstackは、既定で、コードを書く役割（`feature, refactoring`、`bug-fix`、`perf-issue`、`hillclimb`）に `grok-4.7-xhigh-fast` を、最も難しい変更を受け持つ `hardest tasks` と、文章と判断を受け持つ `judgment and prose` に `claude-opus-5-5-max` を割り当てています。

## 再実行したときに残る行

`/setup-pstack` を再実行すると、各役割のモデルは、前回のルールファイルを見て、次のように決まります。

- <strong>前回、既定のモデルのままだった役割</strong>・・・ 既定のモデルから、改めて決めます。
- <strong>前回、利用者が既定とは別のモデルに変えていた役割</strong>・・・ 利用者が変えたモデルを、そのまま引き継ぎます。

たとえば、前回の実行で、`bug-fix` だけを既定の `grok-4.7-xhigh-fast` から `claude-opus-5-5-max` に変えていたとします。再実行すると、`bug-fix` は `claude-opus-5-5-max` のまま引き継がれ、ほかの役割は既定のモデルから決め直されます。

<strong>利用者は、自分で変えた役割を、再実行のたびに選び直さずに済みます</strong>。

<a id="pstack-version-0.15.3-%E3%82%88%E3%82%8A%E5%89%8D%E3%81%AE%E3%83%AB%E3%83%BC%E3%83%AB%E3%83%95%E3%82%A1%E3%82%A4%E3%83%AB%E3%81%AF%E3%80%81%E5%8F%A4%E3%81%84%E3%83%A2%E3%83%87%E3%83%AB%E3%81%AE%E3%81%BE%E3%81%BE%E6%AE%8B%E3%82%8B"></a>


### pstack version `0.15.3` より前のルールファイルは、古いモデルのまま残る

この仕組みには、注意点があります。

pstack version `0.15.3` より前に書き出したルールファイルには、その当時の既定のモデルが書かれていますが、pstackの既定のモデルは、その後に変更されています。つまり、当時の既定のモデルは、今の既定とは異なるモデルになっています。

そのため、再実行しても、`/setup-pstack` は、その行を「既定と異なるモデルが書かれた行」として残します。その役割は、古い既定のモデルのまま動き続けます。

pstack version `0.15.3` より前に `/setup-pstack` を実行したことがあるなら、次のどちらかをしてから、`/setup-pstack` を再実行します（[README](https://github.com/cursor/plugins/blob/main/pstack/README.md) と同梱ガイド）。

- 当時の既定のモデルが書かれた役割の行を消す
- ルールファイル（`~/.cursor/rules/pstack-models.mdc`）を丸ごと消す

## 検証スキルの作成の提案

`/setup-pstack` は、最後に、エージェントがプロジェクトのアプリを実際に動かして、変更が動くことを確かめられるかを調べます。調べるのは、次の2つがプロジェクトにあるかです。

- <strong>検証スキル</strong>・・・ エージェントがアプリを起動し、操作し、証拠を取るための、プロジェクト専用のSkill（[第3章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/a88ea5)）。`/create-verification-skill` で作ると、`verify-<アプリ名>` という名前になります。
- <strong>既存のハーネス</strong>・・・ アプリを外から動かすために、リポジトリにすでにある仕組み（例：Playwright のテスト）

どちらもなければ、`/setup-pstack` は、`/create-verification-skill` で検証スキルを作ることを、一度だけ提案します。

`/setup-pstack` は、提案の文面で、検証スキルを作る目的を「<strong>エージェントがユーザーと同じようにアプリを操作して、変更が動くことを証明できるようにするため</strong>」と伝えます。

- <strong>利用者が受け入れた場合</strong>・・・ `/setup-pstack` は `/create-verification-skill` を呼びます。
- <strong>利用者が断った場合</strong>・・・ `/setup-pstack` は、`/create-verification-skill`を勧めずに終了します。

`/create-verification-skill` が検証スキルを作る手順は[第26章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/03ebca)で、検証スキルを作って自分のアプリで使い始める流れは[第36章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/7d7081)で扱います。

<a id="%E3%81%BE%E3%81%A8%E3%82%81"></a>


## まとめ

- <strong>書き出すもの</strong>・・・ `/setup-pstack` は、役割ごとのモデルを、使えると確認したスラッグだけを使用し、1つのルールファイルに書き出します。
- <strong>推論の予算</strong>・・・ 予算を下げても、モデルの系統は変えずに、推論の強さだけを下げます。
- <strong>適用の時点</strong>・・・ ルールは新しいチャットから適用されるので、実行後は新しいチャットを始める必要があります。
