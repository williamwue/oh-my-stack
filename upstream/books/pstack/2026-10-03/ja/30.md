この章では、次の3つのSkillを扱います。

1. [`/architect`](https://github.com/cursor/plugins/blob/main/pstack/skills/architect/SKILL.md)
2. [`/arena`](https://github.com/cursor/plugins/blob/main/pstack/skills/arena/SKILL.md)
3. [`/swarm`](https://github.com/cursor/plugins/blob/main/pstack/skills/swarm/SKILL.md)

3つは、どれも複数のサブエージェントを並列に動かします。3つが異なるのは、<strong>並列に動かして何を得たいか</strong>です。

3つの違いは次のとおりです。

- <strong>`/architect`</strong>・・・ エージェントが、実装の前に、型とモジュールの境界（例：インポートの処理を、1つの関数として公開するか、読み込み、検証、保存の3つの関数として公開するか）を決めます。そのために、複数のモデルに設計案を作らせて比べます。得たいのは、実装が従う一つの設計です。
- <strong>`/arena`</strong>・・・ エージェントが、同じ課題（例：キャッシュキーの形式を決める）を複数のサブエージェントに別々に解かせ、最も良い案を土台にして、ほかの案の良いところを組み込みます。得たいのは、一つの最良の成果物です。
- <strong>`/swarm`</strong>・・・ エージェントが、仕事（例：`packages/` 以下の全パッケージのチェック）を複数のエージェントに分担させるか、同じ課題で競わせ、結果を一つの報告にまとめます。得たいのは、漏れのない確認か、速い答えです。

この章では、3つのSkillを誰が呼ぶのかを確かめたうえで、1つずつ、役割、使いどき、手順の3つの観点で解説します。原文に依頼例があるSkillには依頼例も示します。

最後に、並列の3つのSkillの使い分けを整理します。

## `/architect` は、呼び出し側の使い方から型を決め、骨組みが間違っていたら捨てる

<a id="%E5%BD%B9%E5%89%B2%EF%BC%9A%E8%A8%AD%E8%A8%88%E3%82%92%E3%80%81%E6%96%87%E7%AB%A0%E3%81%A7%E3%81%AF%E3%81%AA%E3%81%8F%E3%82%B3%E3%83%BC%E3%83%89%E3%81%AE%E9%AA%A8%E7%B5%84%E3%81%BF%E3%81%A7%E6%B1%BA%E3%82%81%E3%82%8B"></a>


### 役割：設計を、文章ではなくコードの骨組みで決める

`/architect` は、<strong>関数の境界をまたぐコードを書く前に、型、関数のシグネチャ（関数の名前、引数、戻り値の型）、モジュールの境界を、関数の中身を書かない骨組み（`not implemented`）で描くSkill</strong>です。

エージェントが骨組みを先に作るのは、<strong>骨組みが、実装が守るべき「契約」（実装は骨組みの型とシグネチャのとおりに書く、という約束）になる</strong>からです。

骨組みがあれば、実装が型から外れたことや、型の検査をすり抜ける逃げ道（`any` や、[第18章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/cdc49b)で見たキャスト（`as User` のように、値の型を決めつける書き方））が必要になったことが、骨組みとの<strong>差分として目に見えます</strong>。

たとえば、骨組みでは `importRows(file, options)` だったのに、実装の途中で3つ目の引数が必要になれば、シグネチャの変更が差分に現れます。

エージェントは、こうしたずれを、実装の中で黙って整合させて片付けずに表に出し、骨組みが間違っていたのか、要件を見落としていたのか、実装が必要以上のことをしているのかを問い直します。このような<strong>ずれは、設計か要件か実装のどこかに誤りがあることを示している</strong>からです。

`/architect` は、骨組みを1つの案で決めず、複数のモデルに作らせた案を統合して決めます。そのうえで骨組みに沿って中身を埋め、骨組みが間違っていると分かったら、骨組みを捨てて設計し直します。

poteto氏は『The Complete Guide to pstack』[Part 2](https://x.com/poteto/status/2097732320606507506)で、計画はコードで行うほうがはるかに効果的だと書き、その手段として、`/poteto-mode` でのプロトタイプ作りと `/architect` を挙げています。

### 使いどき：関数の境界をまたぐコードを書く前

`/poteto-mode` の節『[Non-negotiables](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/SKILL.md#non-negotiables)』（[第8章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/096f3d)）は、関数の境界をまたぐコードには `/architect` を使うと定めています。

Playbookも、この決まりに沿って `/architect` を手順に組み込んでいます。『[<strong>Feature</strong>](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/playbooks/feature.md)』（機能の追加）は、手順2で必ず `/architect` を呼びます。『[<strong>Bug fix</strong>](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/playbooks/bug-fix.md)』（不具合の修正）、『[<strong>Refactoring</strong>](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/playbooks/refactoring.md)』（リファクタリング）、『[<strong>Perf issue</strong>](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/playbooks/perf-issue.md)』（性能の改善）は、変更が関数の境界をまたぐときに `/architect` を呼びます。

たとえば、新しい関数を作り、それを別のファイルの関数から呼ぶ変更は、関数の境界をまたぎます。一方、1つの関数の中の計算を直すだけの変更のように、1つの関数の中で閉じる変更には、`/architect` は必要ありません。

また、ほかのSkillでは、`/figure-it-out`（[第23章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/3ce2b2)）が、後戻りできない設計の判断で `/architect` を呼びます。`/no-comments`（[第31章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/8960d3)）も、コメントの指摘を直すのにコードの新しい形が必要なときに、`/architect` を一度だけ呼びます。

#### Phase B：構造の異なる案を2つ以上比べる

エージェントは、最初の案で十分に見えても、<strong>構造の異なる設計を少なくとも2つ作らせてから統合します</strong>。難しい設計を1回だけ作らせると、その設計は、モデルが最初に思いついた形に固まってしまうからです（同梱ガイドの [`04-design.md`](https://github.com/cursor/plugins/blob/main/pstack/docs/guide/04-design.md)）。

エージェントが比べるのは、1つの形の中の部分的な手直しではなく、形そのものが異なる案です。

たとえば、`importRows` の引数の名前だけを変えた案は、同じ形の手直しにすぎません。1つの関数だけを公開する案と、読み込み、検証、保存を別々の関数として公開する案なら、形そのものが異なります。

Phase B のこのやり方は、[第17章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/a8e80b)の原則『[<strong>Exhaust the Design Space</strong>](https://github.com/cursor/plugins/blob/main/pstack/skills/principle-exhaust-the-design-space/SKILL.md)』を具体化したものです。

`/arena` が起動する各候補（設計案を1つずつ作るサブエージェント）は、10項目の指示に従って設計案を作ります。ここでは、そのうち主な5つを紹介します。

##### 1. 呼び出し側の使い方を先に書き、そこから型を決める

候補は、型を書く前に、その型を使う呼び出し箇所のコードを先に書きます。<strong>呼び出し側がどう使いたいかが、設計が満たすべき仕様</strong>だからです。

使い方と型が食い違ったら、候補は、型のほうを直して使い方に合わせます。

たとえば、骨組みの例で使用したコードでは、先に `onImportClick` の中で `importRows(file, { onError: "skip" })` という呼び出しを書き、その書き方に合わせて `ImportOptions` と `ImportResult` の型を決めました。

```
// 呼び出し側の使い方：これを先に書き、ここから型を決める
async function onImportClick(file: File) {
  const result = await importRows(file, { onError: "skip" });
  console.log(`${result.imported}件を取り込み、${result.skipped}件を飛ばしました`);
}

// 骨組み：型とシグネチャだけを書き、中身は書かない
// onError は、不正な行があったときに、その行を飛ばすか（skip）、取り込みを止めるか（stop）
type ImportOptions = { onError: "skip" | "stop" };
type ImportResult = { imported: number; skipped: number };

export async function importRows(file: File, options: ImportOptions): Promise<ImportResult> {
  throw new Error("not implemented");
}
```

##### 2. よく行う読み書きに合うデータ構造を先に決める

候補は、ロジックを書く前に、よく行う読み書き（例：IDでユーザーを1人引く）に合うデータ構造を決めます。

候補は、その読み書きを、決めたデータ構造でどう処理するかを1つずつたどって確かめます。たどった結果、「後で索引やキャッシュを追加すればよい」という答えになるなら、そのデータ構造は間違っています。

たとえば、IDでユーザーを引く処理が多いのに、ユーザーを配列で持つケースを見てみましょう。

配列で持つと、IDで引くたびに配列を先頭から探すことになります。IDで引く処理をこの構造でたどると、「後でIDからの索引を追加すればよい」という答えになるので、配列という構造は間違っています。そこで、候補は最初から、IDをキーにした表（マップ）で持つ構造を選びます。

```
type User = { id: string; name: string };
// 探したいユーザーのID
declare const id: string;

// 前：IDで引くたびに、配列を先頭から探す
const userList: User[] = [];
const found = userList.find((u) => u.id === id);

// 後：IDをキーにした表で持ち、IDから直接引く
const usersById = new Map<string, User>();
const user = usersById.get(id);
```

このように、向いているデータ構造はよく行う読み書きで変わるので、候補は、実装の前に、その読み書きに合った構造を選びます。

##### 3. 公開する関数を少なくし、処理はその裏に隠す

候補は、外に公開する関数や型（公開インターフェース）を少なく小さくし、多くの処理をその裏に隠します。こうすることで、<strong>呼び出し側が知る必要のあることが減る</strong>からです。

公開するものが少ないのに、裏に多くの処理を隠しているインターフェースを、「<strong>深いインターフェース</strong>」と呼びます。

たとえば、インポートの処理の公開インターフェースを2通りに書くと、次のようになります。

```
// 深い：公開するのは1つの関数だけで、読み込み、検証、保存はその裏に隠す
type DeepImporter = {
  importRows(file: File, options: ImportOptions): Promise<ImportResult>;
};

// 浅い：3つの関数を公開し、呼び出し側がそれらを正しい順番で呼ぶ必要がある
type ShallowImporter = {
  loadRows(file: File): string[][];
  validateRows(rows: string[][]): string[][];
  saveRows(rows: string[][]): Promise<void>;
};
```

`DeepImporter` なら、呼び出し側は `importRows` を1回呼ぶだけで取り込めます。`ShallowImporter` では、呼び出し側が3つの関数を正しい順番で呼ばなければなりません。

##### 4. 常に成り立つべき条件は、できるだけ型で表す

候補は、不変条件を、まず型で表します。型で表せないときは実行時のチェックで表し、それもできないときだけコメントで書きます。

たとえば、「発送済みの注文は、必ず追跡番号を持つ」という不変条件を3通りで書くと、次のようになります。

```
// 型で表す：shipped の注文は、trackingNo を持つ形しか書けない
type Order =
  | { state: "paid" }
  | { state: "shipped"; trackingNo: string };

// 実行時のチェック：型では防げず、動かしたときに初めて見つかる
type LooseOrder = { state: "paid" | "shipped"; trackingNo?: string };

function assertTrackingNo(order: LooseOrder): void {
  if (order.state === "shipped" && !order.trackingNo) {
    throw new Error("発送済みなのに追跡番号がありません");
  }
}

// コメント：守られるかどうかは、コメントを読んだ人次第
type CommentedOrder = {
  state: "paid" | "shipped";
  // state が "shipped" のときは、必ず trackingNo を入れること
  trackingNo?: string;
};
```

型で表せば、不変条件を破るコードを書いた時点でコンパイラが知らせてくれます。そのため、候補は、不変条件をできるだけ型で表します。

##### 5. 外から入る値は入口で一度だけ検証し、内側では確かめ直さない

候補は、外から値が入る場所（境界。例：ファイルやAPIのレスポンスを受け取る関数）で、値を一度だけ検証し、検証した値に型を付けます。内側のコードは、型の付いた値を確かめ直さずに使います。<strong>入口で一度確かめておけば、内側で同じ確認を何度も書かずに済む</strong>からです。

たとえば、インポートの処理なら、`importRows` がファイルの各行を読んだ直後に、IDが空でないかを確かめます。内側の保存の処理は、確かめ終えた行だけを受け取るので、IDが空かどうかを確かめ直しません。

この指示は、[第18章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/cdc49b)の原則『[<strong>Boundary Discipline</strong>](https://github.com/cursor/plugins/blob/main/pstack/skills/principle-boundary-discipline/SKILL.md)』に従ったものです。

##### 設計に理由書を付け、退けた別案とその理由を書く

各候補は、設計に1ページの理由書を付けます。理由書では、呼び出し側から見た使い方（Usage）を型より先に書き、退けた別案とその理由を必ず書きます。

候補は、別案を比べるときに、実装が簡単かどうかだけでなく、呼び出し側に見せる複雑さと、内側に隠す複雑さで比べます。たとえば、`DeepImporter` と `ShallowImporter` なら、呼び出し側が知る必要のある関数は1つと3つなので、`DeepImporter` のほうが、呼び出し側に見せる複雑さが小さくなります。

##### 統合する前に、4つの危険信号で点検する

エージェントは、候補を統合する前に、すべての候補を4つの危険信号で点検します。危険信号とは、エージェントが見つけたら、その設計を直すか、退ける理由になる構造上の特徴です。

4つの危険信号は次のとおりです。

- <strong>浅いモジュール</strong>・・・ 公開する関数や型が多いのに、その裏に隠す処理が少ないモジュールです。
- <strong>情報の漏れ</strong>・・・ 本来は1つのモジュールの中だけで決めておけばよいこと（例：データをどんな形で持つか）を、ほかのモジュールも前提にして書かれている状態です。その決めごとを変えると、前提にしているモジュールをすべて一緒に直す必要があります。
- <strong>順番による分割</strong>・・・ 処理を実行する順番（読み込む→検証する→保存する）どおりに、モジュールを分けた構造です。順番どおりに分けると、どのモジュールも同じデータの形を受け渡しするので、その形を前提にするモジュールが増えます。原文は、同じデータを扱う処理は、実行するタイミングが異なっても1つのモジュールにまとめるよう勧めています。
- <strong>素通しのメソッド</strong>・・・ 受け取った引数を、同じ形のまま別のメソッドへ渡すだけのメソッドです。

たとえば、インポートの処理で、4つの危険信号をすべて含む骨組みは、次のようになります。

```
// load.ts：CSVを読み、各行を文字列の配列にする（浅いモジュール）
export function loadRows(file: File): string[][] {
  throw new Error("not implemented");
}

// validate.ts：0列目がIDであることを前提に、IDが空の行を除く（浅いモジュール・情報の漏れ）
export function validateRows(rows: string[][]): string[][] {
  throw new Error("not implemented");
}

// save.ts：0列目がIDであることを前提に、IDをキーにして保存する（浅いモジュール・情報の漏れ）
export function saveRows(rows: string[][]): Promise<void> {
  throw new Error("not implemented");
}

// importer.ts
export class Importer {
  // 受け取った rows を、同じ形のまま saveRows へ渡すだけ（素通しのメソッド）
  save(rows: string[][]): Promise<void> {
    return saveRows(rows);
  }
}

// 呼び出し側：3つを正しい順番で呼ばないと取り込めない（順番による分割）
async function onImportClick(file: File) {
  const rows = validateRows(loadRows(file));
  await new Importer().save(rows);
}
```

このコードでは、4つの危険信号が次のように現れています。

- <strong>浅いモジュール</strong>・・・ 3つのファイル（`load.ts`・`validate.ts`・`save.ts`）は関数を1つずつ公開していますが、どの関数も、読むだけ、行を除くだけ、保存するだけという小さな作業しかしていません。公開している関数の数に比べて、裏に隠している処理が少ないので、浅いモジュールです。その結果、1回の取り込みを終えるには、呼び出し側が3つの関数を自分で組み合わせて呼ぶ必要があります。原文も、1つの操作のために呼び出し側が複数の関数を組み合わせることを、浅いモジュールの兆候に挙げています。
- <strong>情報の漏れ</strong>・・・ `validate.ts` と `save.ts` は、どちらも「各行は文字列の配列で、0列目（配列の先頭の要素）がID」という前提で書かれています。たとえば、CSVの列の並びが変わり、IDが2列目に移ったとします。すると、`validate.ts` と `save.ts` の両方を同時に直さなければなりません。
- <strong>順番による分割</strong>・・・ ファイルを、処理の順番どおりに「読み込む」（`load.ts`）、「検証する」（`validate.ts`）、「保存する」（`save.ts`）の3つに分けています。3つのファイルは、行のデータを順に手渡ししていくので、3つとも「各行は文字列の配列」という同じ形を知っていなければなりません。そのため、行の形を変えると、3つのファイルすべてを直すことになります。
- <strong>素通しのメソッド</strong>・・・ `Importer.save` は、受け取った `rows` を同じ形のまま `saveRows` へ渡すだけで、何も隠していません。

このように、決めごとが複数のモジュールに散らばると、変えるたびに直す場所が増えるので、決めごとは1つのモジュールの内側に閉じ込める必要があります。

前に示した `importRows(file, options)` の骨組みなら、呼び出し側は1つの関数を呼ぶだけで済みます。行の表し方や、どの列がIDかという決めごとは、`importRows` のモジュールの内側に閉じ込められます。

<a id="phase-c%EF%BC%9A%E6%97%A2%E5%AE%9A%E3%81%A7%E3%81%AF%E4%BA%BA%E3%81%AE%E7%A2%BA%E8%AA%8D%E3%82%92%E6%8C%9F%E3%81%BE%E3%81%9A%E3%81%AB%E5%AE%9F%E8%A3%85%E3%81%B8%E9%80%B2%E3%82%80"></a>


#### Phase C：既定では人の確認を挟まずに実装へ進む

<strong>既定では、エージェントは人の確認を挟まずに実装へ進みます</strong>。

エージェントが人の返事を待たずに進め、人が後から方針を修正するのは、原則『[<strong>Never Block on the Human</strong>](https://github.com/cursor/plugins/blob/main/pstack/skills/principle-never-block-on-the-human/SKILL.md)』（[第20章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/c155cc)）と同じ考え方です。

人が設計の形に異議を唱えたら、エージェントはその異議を Phase A の新しい材料として扱い、調べ直して Phase B をやり直します。

実装の前に設計の弱点を厳しく問いただしたいときは、エージェントは、統合した骨組みに[第27章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/997880)の `/interrogate` をかけます。

<a id="phase-e%EF%BC%9A%E9%AA%A8%E7%B5%84%E3%81%BF%E3%82%92%E6%8D%A8%E3%81%A6%E3%82%8B%E5%88%A4%E6%96%AD"></a>


#### Phase E：骨組みを捨てる判断

<strong>エージェントは、骨組みを捨てるかどうかを、1回きりの出来事ではなく、繰り返し現れるパターンで判断します</strong>。

兆候は、たとえば次のようなものです。

1. 同じ形の回避策が、無関係なコードに繰り返し現れる（例：`importRows` を呼ぶ別々の画面が、どれも呼ぶ前に同じ前処理を自分で書いている）
2. コンパイルを通すために、`any` やキャストのような逃げ道が必要になる
3. 呼び出し側が、共通の関数や型の内部の決まりを知らないと、それを使えない（例：`importRows` を呼ぶ前に、呼び出し側が必ず別の初期化の関数を呼んでおかなければならない）
4. 骨組みからの同じ形の逸脱が、別々の箇所で2回以上起きる（例：骨組みにない引数の追加が、2つの関数で別々に必要になる）

たとえば、4つの兆候をすべて含む実装は、次のようになります。

```
type Row = { id: string; name: string };

// 取り込みに使うデータベースの接続を、先に作っておく関数
declare function initImporter(): Promise<void>;

// 骨組みでは parseRows(text: string): Row[] だった
// 兆候4：実装で、骨組みになかった tenantId（どの契約者のデータか）の引数が必要になった
declare function parseRows(text: string, tenantId: string): Row[];

// 骨組みでは saveRows(rows: Row[]): Promise<void> だった
// 兆候4：実装で、骨組みになかった tenantId（どの契約者のデータか）の引数が必要になった
declare function saveRows(rows: Row[], tenantId: string): Promise<void>;

// 設定画面
async function onUploadFromSettings(file: File) {
  // 兆候3：これを先に呼ばないと、importRows が失敗する。この決まりは、importRows の型からは読み取れない
  await initImporter();

  // 兆候1：importRows を呼ぶ前に、CSVの1行目（見出しの行）を自分で取り除いている
  const lines = (await file.text()).split("\n");
  const body = new File([lines.slice(1).join("\n")], file.name);

  // 兆候2：骨組みの ImportResult にない reasons（飛ばした行の理由）を読むために、any にしている
  const result = (await importRows(body, { onError: "skip" })) as any;
  console.log(result.reasons);
}

// ダッシュボード：設定画面とは無関係の画面なのに、兆候1の前処理と、兆候3の初期化を同じように書いている
async function onUploadFromDashboard(file: File) {
  // 兆候3の初期化
  await initImporter();
  // 兆候1の前処理
  const lines = (await file.text()).split("\n");
  const body = new File([lines.slice(1).join("\n")], file.name);
  await importRows(body, { onError: "stop" });
}
```

まれな入力や状況（エッジケース）への対応がいくつか必要になるだけでは、設計全体を否定する理由になりません。また、扱うデータそのものが入り組んでいるせいで分岐が増えるのも、骨組みを捨てる理由になりません。

たとえば、国ごとに住所の書き方が異なるせいで分岐が増えるのは、データが入り組んでいるからで、設計が間違っているからではありません。

骨組みを捨てるとき、エージェントは、それまでに作ったものに `/how` をかけ直して仕組みを調べ直します。そのうえで、古い骨組みに修正を継ぎ足すのではなく、実装で分かった新しい制約を最初からの前提として、Phase B から設計し直します。

また、エージェントは、新しい骨組みに何かを追加する前に、まず不要なもの（例：使われなくなった関数や、重複した検証）を削ります。不要なものを先に削る手順は、原則『[<strong>Subtract Before You Add</strong>](https://github.com/cursor/plugins/blob/main/pstack/skills/principle-subtract-before-you-add/SKILL.md)』（[第17章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/a8e80b)）に従ったものです。そのため、新しい骨組みは、機能を追加し始める前の時点で、古い骨組みより小さくなります。

## `/arena` は、一つの最良の成果物のために複数の候補を競わせる

<a id="%E5%BD%B9%E5%89%B2%EF%BC%9A%E5%90%8C%E3%81%98%E8%AA%B2%E9%A1%8C%E3%82%92n%E5%80%8B%E3%81%AE%E5%80%99%E8%A3%9C%E3%81%AB%E8%A7%A3%E3%81%8B%E3%81%9B%E3%82%8B"></a>


### 役割：同じ課題をN個の候補に解かせる

<strong>候補</strong>とは設計案を1つずつ作るサブエージェントのことです。  
`/arena`は、複数の候補に課題を解かせ、<strong>最良の成果物を選び、ほかの成果物の良い考えを最良のものに取り込むSkill</strong>です。

<a id="%E4%BD%BF%E3%81%84%E3%81%A9%E3%81%8D%EF%BC%9A%E5%BE%8C%E3%81%8B%E3%82%89%E7%9B%B4%E3%81%99%E3%81%A8%E9%AB%98%E3%81%8F%E3%81%A4%E3%81%8F%E6%88%90%E6%9E%9C%E7%89%A9"></a>


### 使いどき：後から直すと高くつく成果物

利用者やエージェントは、キャッシュキーの形式のように、1回だけ作らせると最初に思いついた形に決まってしまいそうで、しかも後から変えると高くつく成果物に `/arena` を使います。

`/poteto-mode` の作業の中で `/arena` を呼ぶ場面は、主に2つです。

1つは、`/architect` が Phase B で複数の設計案を作らせるときです。  
もう1つは、『<strong>Feature</strong>』Playbookの手順4で、実装に複数の妥当な形がありうるとき（たとえば、エラーの扱い方やテストの構成に、複数の妥当な書き方があるとき）に、主エージェントがコーディングを `/arena` の候補に任せるときです。

<a id="%2Farena-%E3%81%AF%E3%80%81playbook%E3%82%84%E3%81%BB%E3%81%8B%E3%81%AEskill%E3%81%8B%E3%82%89%E3%82%82%E5%91%BC%E3%81%B0%E3%82%8C%E3%82%8B"></a>


#### `/arena` は、PlaybookやほかのSkillからも呼ばれる

`/arena` を呼ぶPlaybookとSkillは、どれも、<strong>1つのモデルに1回だけ作らせた答えでは偏りや見落としが残る場面</strong>で `/arena` を使います。呼ぶ側ごとの場面と理由は、次のとおりです。

##### `/architect`：設計案を1つだけで決めない

`/architect` は、Phase B で `/arena` を呼び、複数のモデルに設計案を作らせます。難しい設計を1回だけ作らせると、その設計は、モデルが最初に思いついた形に固まってしまうからです（この章の[『Phase B：構造の異なる案を2つ以上比べる』](#phase-b%EF%BC%9A%E6%A7%8B%E9%80%A0%E3%81%AE%E7%95%B0%E3%81%AA%E3%82%8B%E6%A1%88%E3%82%922%E3%81%A4%E4%BB%A5%E4%B8%8A%E6%AF%94%E3%81%B9%E3%82%8B)）。

##### 『Eval』Playbook：Skillの変更の効果を、複数のモデルと目隠しの採点で測る

『[<strong>Eval</strong>](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/playbooks/eval.md)』は、Skillやプロンプトの変更が、エージェントの行動をどう変えるかを測るPlaybookです（[第13章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/8263c0)）。

『Eval』では`/arena`を直接、呼び出すわけではありませんが、`/arena`の手順どおりに作業を進めるように定義されています。

『Eval』では、変更を入れた環境で、同じ依頼を複数のモデルに別々に解かせます。そのうえで、どのモデルの出力かを伏せたまま、別のモデルに採点させます。  
つまり、複数の候補に同じ課題を解かせ、別のモデルに採点させる進め方は、`/arena` と同じということです。

##### 『Orchestrate』Playbook：後戻りできない判断を、作業を動かし始める前に比べる

『[<strong>Orchestrate</strong>](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/playbooks/orchestrate.md)』は、何日も続き、多数のPRとサブエージェントが動くプロジェクトを管理するPlaybookです（[第16章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/8a8dd5)）。

『Orchestrate』は、最初の手順（Frame）で、意見の分かれる作業の分け方や、後戻りできない判断を、最初の作業単位を試しに動かす前に `/arena` にかけます。<strong>後戻りできない判断は、プロジェクトが動き出した後では直せない</strong>からです。

##### `/blast-radius`：大きな変更の影響を、複数のモデルに調べさせる

`/blast-radius`（[第27章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/997880)）は、大きな変更や影響の広い変更を調べるときに、`/arena` で複数のモデルに同じ問いを投げ、その答えを統合します。`/blast-radius` の `SKILL.md` によれば、<strong>モデルが異なれば、見つける不具合も異なる</strong>からです。

<a id="%E6%89%8B%E9%A0%86%EF%BC%9Aframe-%E3%81%8B%E3%82%89-verify-%E3%81%BE%E3%81%A7%E3%80%816%E3%81%A4%E3%81%AE-phase-%E3%81%A7%E9%80%B2%E3%82%80"></a>

<a id="%E5%88%A4%E5%AE%9A%E5%BD%B9%E3%81%AF%E3%80%81%E5%85%A8%E5%80%99%E8%A3%9C%E3%81%8C%E6%9B%B8%E3%81%8D%E7%B5%82%E3%81%88%E3%81%A6%E3%81%8B%E3%82%89%E8%B5%B7%E5%8B%95%E3%81%99%E3%82%8B"></a>


#### 判定役は、全候補が書き終えてから起動する

判定役の採点と、主エージェントが全候補を読む作業は、全候補が書き終えてから並行して進みます。主エージェントは、候補がまだ書いている途中で判定役を起動しません。

<a id="%E5%80%99%E8%A3%9C%E3%81%AB%E3%81%AF%E3%80%81%E4%BD%9C%E3%82%8B%E6%88%90%E6%9E%9C%E7%89%A9%E3%82%92%E6%98%8E%E8%A8%98%E3%81%97%E3%81%9F%E5%90%8C%E3%81%98%E3%83%97%E3%83%AD%E3%83%B3%E3%83%97%E3%83%88%E3%82%92%E6%B8%A1%E3%81%97%E3%80%81%E6%8E%A1%E7%82%B9%E5%9F%BA%E6%BA%96%E3%81%AF%E8%A6%8B%E3%81%9B%E3%81%AA%E3%81%84"></a>


#### 候補には、作る成果物を明記した同じプロンプトを渡し、採点基準は見せない

全候補は同じプロンプトを受け取るので、<strong>各候補が何を作るかは、プロンプトに書いた内容だけで決まります</strong>。そのため、主エージェントは Phase A で、各候補が作る成果物（例：キャッシュキーの形式の案と、その理由）をプロンプトに明記します。

採点基準は、主エージェントが Phase D で土台を選ぶときに使うものなので、主エージェントは候補に採点基準を見せず、課題だけを見せます。

<a id="%E5%9C%9F%E5%8F%B0%E3%81%AB%E3%81%AF%E3%80%81%E6%9C%80%E3%82%82%E6%A9%9F%E8%83%BD%E3%82%92%E8%BF%BD%E5%8A%A0%E3%81%97%E3%82%84%E3%81%99%E3%81%84%E5%80%99%E8%A3%9C%E3%82%92%E9%81%B8%E3%81%B6"></a>


#### 土台には、最も機能を追加しやすい候補を選ぶ

主エージェントは、将来の保守担当者が、不変条件を壊さずに最も機能を追加しやすい候補を、土台に選びます。

全候補が同じ形にたどり着いたら、主エージェントは、別々に解いた候補の答えが一致したことを強い裏づけとみなし、移植をせずにその形を採ります。

<a id="%E5%80%99%E8%A3%9C%E3%81%AE%E5%BD%A2%E3%81%8C%E5%A4%A7%E3%81%8D%E3%81%8F%E9%A3%9F%E3%81%84%E9%81%95%E3%81%A3%E3%81%9F%E3%82%89%E3%80%81%E8%AA%B2%E9%A1%8C%E3%82%92%E5%AE%9A%E3%82%81%E7%9B%B4%E3%81%99"></a>


#### 候補の形が大きく食い違ったら、課題を定め直す

候補の形が大きく食い違ったら、主エージェントは、課題の定め方が足りなかったと判断し、Phase A に戻って課題を定め直してやり直します。

たとえば、3つの候補のキャッシュキーの形式がすべて異なるとき、主エージェントは、3つから少しずつ取った中間の形式を作ることはしません。<strong>中間の形式は、どの候補の考え方とも一貫しない形になる</strong>からです。

<a id="%E6%9C%80%E5%BE%8C%E3%81%AB%E3%80%81%E7%B5%B1%E5%90%88%E3%81%97%E3%81%9F%E6%88%90%E6%9E%9C%E7%89%A9%E3%81%A8%E7%B5%B1%E5%90%88%E3%83%A1%E3%83%A2%E3%82%92%E8%BF%94%E3%81%99"></a>


#### 最後に、統合した成果物と統合メモを返す

主エージェントが最後に返すのは、統合した成果物1つと、短い統合メモです。統合メモに書く内容は次のとおりです。

- 土台に選んだ候補と、選んだ理由（判定役の結論を含む）
- ほかの候補から取り込んだ部分と、それぞれがどの候補から来たか
- 検討したが取り込まなかった部分と、その理由
- 成果物を出せずに途中で抜けた候補（あれば）。主エージェントは、抜けた候補を除いた残りの候補で統合を進め、抜けたことをメモに残します
- 統合した成果物を、Phase F（Verify）で実際に動かして確かめた結果

<a id="%E4%BE%9D%E9%A0%BC%E3%81%AE%E6%9B%B8%E3%81%8D%E6%96%B9%EF%BC%9A%E5%80%99%E8%A3%9C%E3%81%AE%E6%95%B0%E3%82%92%E6%8C%87%E5%AE%9A%E3%81%99%E3%82%8B"></a>


### 依頼の書き方：候補の数を指定する

`04-design.md` には、候補数を指定する例があります。

```
/arena this, 5 candidates. the cache key format is expensive to change later.
// これを候補5つで。キャッシュキーの形式は後から変えると高くつく。
```

同梱ガイドの [`10-recipes-and-pitfalls.md`](https://github.com/cursor/plugins/blob/main/pstack/docs/guide/10-recipes-and-pitfalls.md) は、後から変えると高くつく決定の前に、今の設計についてセカンドオピニオンを頼む使い方も挙げています。

この使い方では、主エージェントは、利用者とエージェントが今進めている設計を候補の一つとして、ほかの候補と比べます。

```
ask /arena for a second opinion on this thread and our approach
// このスレッドと、私たちの進め方について、/arena でセカンドオピニオンを出して
```

<a id="%2Fswarm-%E3%81%AF%E3%80%81%E7%B6%B2%E7%BE%85%E3%81%A8%E7%AB%B6%E4%BA%89%E3%81%AE%E3%81%9F%E3%82%81%E3%81%AB%E4%BB%95%E4%BA%8B%E3%82%92workers%E3%81%AB%E5%88%86%E3%81%91%E3%80%81%E7%B5%90%E6%9E%9C%E3%82%92%E4%B8%80%E3%81%A4%E3%81%AE%E5%A0%B1%E5%91%8A%E3%81%AB%E3%81%99%E3%82%8B"></a>


## `/swarm` は、網羅と競争のために仕事をWorkersに分け、結果を一つの報告にする

<a id="%E5%BD%B9%E5%89%B2%EF%BC%9Acloud-agents%E3%82%92%E4%B8%A6%E5%88%97%E3%81%AB%E5%8B%95%E3%81%8B%E3%81%99"></a>


### 役割：Cloud Agentsを並列に動かす

`/swarm` は、クラウド上でN体のエージェント（Workers）を同時に動かし、<strong>結果を集めて一つの報告を返すSkill</strong>です。`/arena` が「一つの最良の答え」を作るのに対し、`/swarm` は「漏れのない確認」か「速い答え」を作ります。

poteto氏は『The Complete Guide to pstack』[Part 1](https://x.com/poteto/status/2094457600259842065)で、多数の Cloud Agents（Cursorのクラウド上で動くエージェント）で検証スキルを実行し、十分なサンプル数で性能の改善を確かめたり、アプリをファジングしたりする使い方を挙げています。

<aside class="msg message"><span class="msg-symbol">!</span><div class="msg-content">
<p class="code-line" data-line="518"><strong>ファジング</strong>・・・ ランダムな入力や壊れた入力を大量に与えて、不具合を探すテスト</p>
</div></aside>

<a id="%E4%BD%BF%E3%81%84%E3%81%A9%E3%81%8D%EF%BC%9A%E7%B6%B2%E7%BE%85%E3%80%81%E7%AB%B6%E4%BA%89%E3%80%81%E9%96%A2%E9%96%80%E3%80%81%E6%8E%A2%E7%B4%A2%E3%81%AE%E5%88%86%E5%89%B2"></a>


### 使いどき：網羅、競争、関門、探索の分割

使いどきは次のとおりです。

- <strong>網羅</strong>・・・ 主エージェントが、複数の範囲をWorkersに割り振り、漏れなく確かめます（例：`packages/` 以下のすべてのパッケージを確かめる）。
- <strong>競争</strong>・・・ 主エージェントが、同じ課題を複数のWorkersに競わせます（例：同じ不具合の再現を複数のWorkersで試す）。
- <strong>gauntlet</strong>（関門）・・・ 主エージェントが、1つの変更に検証を何本も並べ、変更がすべての検証に通ることを求めます（例は次の囲みで示します）。
- <strong>探索の分割</strong>・・・ 主エージェントが、探す場所を複数に分け、各Workersに1か所ずつ調べさせます（例：不具合の原因を探すとき、疑わしいモジュール1つ1つに対して1体ずつWorkerを割り振って調べさせる）。

<aside class="msg message"><span class="msg-symbol">!</span><div class="msg-content">
<p class="code-line" data-line="531"><strong>gauntlet</strong>（関門）は、pstackのファイルに定義のある言葉ではありません。英語の gauntlet は、次々と課される試練をくぐり抜けることを指します。</p>
<p class="code-line" data-line="533">pstackでの使われ方は、同梱ガイドの <code>04-design.md</code> にある「gauntlet lanes」（関門の担当）という書き方と、<code>/swarm</code> を使うPlaybookから読み取れます。</p>
<p class="code-line" data-line="535">たとえば、Playbook『<a href="https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/playbooks/multi-phase-plan.md" rel="nofollow noopener noreferrer" target="_blank"><strong>Multi-phase or multi-PR plan</strong></a>』（<a href="https://zenn.dev/sc30gsw/books/080faba713547b/viewer/8a8dd5" target="_blank">第16章</a>）が作る計画書では、PRがレビューに出せる状態になったときと、その後に変更をpushするたびに、その時点のPRの最新のコミットに対して、次の担当を <code>/swarm</code> で並列に走らせ、<strong>すべてが PASS のときだけ合格</strong>とします。</p>
<ul class="code-line" data-line="537">
<li class="code-line" data-line="537">テストやlintなどのチェックを、その最新のコミットで実行し直す担当1つ</li>
<li class="code-line" data-line="538">実際の画面やCLIで確かめる担当10個</li>
<li class="code-line" data-line="539">性能を測る担当1つ</li>
<li class="code-line" data-line="540">差分と実行の記録を読み、PRの説明を疑って点検する担当2つ以上</li>
</ul>
</div></aside>

`/poteto-mode` は、節『Non-negotiables』で、仕事を並列に分ける場面（網羅、競争、関門、探索の分割）では `/swarm` を使うと定めています。特に、[第16章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/8a8dd5)で見た、多数のPRを検証しながら進めるPlaybookは、PRをマージしてよいかの判定に `/swarm` を使います。

たとえば『[<strong>Autopilot-full</strong>](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/playbooks/autopilot-full.md)』（PRごとの担当者が、作るところからマージまでを受け持つ手順書）では、コーディネーターエージェント（作業全体を管理するエージェント）が、独立した検証者を `/swarm` で並列に動かし、その結果を一つの判定にまとめます。各PRの担当者は、問題なしの判定が出るまで、PRをマージしません。

<a id="%E6%89%8B%E9%A0%86%EF%BC%9Aframe-%E3%81%8B%E3%82%89-report-%E3%81%BE%E3%81%A7%E3%80%814%E3%81%A4%E3%81%AE-phase-%E3%81%A7%E9%80%B2%E3%82%80"></a>


### 手順：Frame から Report まで、4つの Phase で進む

`/swarm` は、次の4つの Phase で進みます。

1. <strong>Frame</strong>・・・ 主エージェントが、終了条件（何が成り立てば完了かを、確かめられる形で書いた条件）と、返すべき報告を定めます。形（次の表の分担、競争、混合）とWorkersの数も決めます。Workersの数は、利用者が依頼で指定すればその数にし、指定がなければ形から決めます。
2. <strong>Fan out</strong>・・・ 主エージェントが、全Workersをクラウドで同時に起動します。Workersはそれぞれ `PASS`（合格）、`ISSUES`（問題あり）、`BLOCKED`（確かめられなかった）のどれかを、証拠（例：確かめたコミットのSHA（コミットを識別する値）と、チェックの出力）付きで報告します。
3. <strong>Aggregate</strong>・・・ 主エージェントが結果を集めます。競争なら、Frame で宣言しておいた選び方の規則を当てはめて、結果を選びます。
4. <strong>Report</strong>・・・ 主エージェントが、結果の表、証拠付きの問題、結果が得られなかった範囲（空白）と途中で抜けたWorkers（脱落）を、一つの報告にまとめます。

Frame で選ぶ形は、次の3つです。

<table class="code-line" data-line="558">
<thead class="code-line" data-line="558">
<tr class="code-line" data-line="558">
<th>形</th>
<th>内容</th>
</tr>
</thead>
<tbody class="code-line" data-line="560">
<tr class="code-line" data-line="560">
<td>分担（partition）</td>
<td>仕事を重ならない範囲に分け、Workersがそれぞれ1つを受け持つ（例：パッケージごとに1体）</td>
</tr>
<tr class="code-line" data-line="561">
<td>競争（race）</td>
<td>N体のWorkersに同じ指示を与えて競わせる（例：同じ不具合の再現を複数のWorkersで試す）</td>
</tr>
<tr class="code-line" data-line="562">
<td>混合</td>
<td>分担と競争を組み合わせる（範囲ごとに複数のWorkersを競わせる）</td>
</tr>
</tbody>
</table>

競争と混合の形では、主エージェントが、「最初に合格したものを採る」（first pass）、「全員を順位付けする」（rank all）、「最も良いものを採る」（best-of）のどれを選び方の規則にするかを、起動する前に宣言します。

主エージェントは、指示で求めた記録（確かめたコミットのSHAや、何回測るかなどの計測の方法）がない結果は捨て、その結果を出したWorkerを一度だけ再実行します。<strong>どのコミットをどう確かめたかが分からない結果は、今のコードに当てはまるかを判断できない</strong>からです。

2回目も記録が欠けたら、主エージェントはその範囲を空白として記録します。<strong>空白は合格と数えません</strong>。

たとえば10体のうち9体が `PASS` で1体が欠ければ、報告は「9件合格」ではなく「9件合格、1件空白」になります。

### 依頼の書き方：確かめ方、形と数、返すものを一文ずつ書く

[README](https://github.com/cursor/plugins/blob/main/pstack/README.md)と同梱ガイドには、次の依頼例があります。

```
/swarm check every package under packages/ against its check.sh. one worker per package. one report.
// packages/ 以下の全パッケージを、それぞれの check.sh で確かめて。1パッケージに1体。報告は1つ。
```

この依頼は、確かめ方（`check.sh`）、形と数（1パッケージに1体）、返すもの（報告は1つ）を、<strong>一文ずつ書いています</strong>。この3つは、主エージェントが Frame で決める内容に該当するので、依頼に書いておけば、主エージェントはその指定に沿って Frame を組み立てます。

<a id="%E4%B8%A6%E5%88%97%E3%81%AE3%E3%81%A4%E3%81%AEskill%E3%81%AF%E3%80%81%E5%BE%97%E3%81%9F%E3%81%84%E3%82%82%E3%81%AE%E3%81%A8%E3%80%81%E5%A4%89%E6%9B%B4%E3%81%AE%E5%A4%A7%E3%81%8D%E3%81%95%E3%82%84%E6%88%BB%E3%81%97%E3%81%AB%E3%81%8F%E3%81%95%E3%81%A7%E4%BD%BF%E3%81%84%E5%88%86%E3%81%91%E3%82%8B"></a>


## 並列の3つのSkillは、得たいものと、変更の大きさや戻しにくさで使い分ける

使い分けは次のとおりです。

- <strong>関数の境界をまたぐ変更を設計したい（例：新しい関数を作り、別のファイルの関数から呼ぶ）</strong>・・・ 内部で `/arena` を使う `/architect`
- <strong>最後に一つの成果物がほしい（例：キャッシュキーの形式を1つに決める）</strong>・・・ `/arena`
- <strong>多くの範囲を確かめた結果を、一つの表にまとめたい（例：`packages/` 以下の全パッケージのチェック結果）</strong>・・・ `/swarm`

<strong>利用者が網羅のために `/arena` を使うのは、よくある取り違えです</strong>（`10-recipes-and-pitfalls.md`）。`/arena` は全候補に同じ課題を与えるので、別々の範囲を確かめることにはならないからです。

網羅には、利用者は、範囲を分けて結果を一つの報告にまとめる `/swarm` を使います。`/swarm` は、`/arena` のように土台を選んで移植する手順を踏みません。

## まとめ

- <strong>3つのSkillの分担</strong>・・・ `/architect`、`/arena`、`/swarm` は、`/poteto-mode` が『Non-negotiables』の規則やPlaybookの手順に従って呼びます。
- <strong>`/architect`</strong>・・・ 関数の境界をまたぐコードの前に、呼び出し側の使い方から型を導き、関数の中身を書かない骨組みを作ります。同じ形の回避策や型の逃げ道（`any` やキャスト）が繰り返し出たら、骨組みを捨てて設計し直します。
- <strong>`/arena`</strong>・・・ 後から直すと高くつく成果物（例：キャッシュキーの形式）を複数のモデルに解かせ、最も良い候補を土台に選び、ほかの候補の良い部分を土台の設計に合わせて書き直して移植します。
- <strong>`/swarm`</strong>・・・ 網羅（例：全パッケージのチェック）や競争のためにWorkersを並列に動かし、一つの報告にまとめます。確かめたコミットなどの記録が、1回再実行しても欠けた範囲は、合格と数えず空白として報告します。
- <strong>並列の3つの使い分け</strong>・・・ 関数の境界をまたぐ変更なら `/architect`、一つの成果物なら `/arena`、網羅した結果の表なら `/swarm` です。
