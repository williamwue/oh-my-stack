## 本書の結論：任せられる範囲は、確かめられる環境の広さで決まる

いよいよ、pstackの旅も終着点です。

ここまで本書は、poteto氏の講演と記事を手がかりに、pstackのPlaybook、Principle、Skillを1つずつ読み解いてきました。その旅で本書がたどり着いた結論は、次の一文です。

「<strong>エージェントに任せられる範囲は、エージェントの賢さではなく、エージェントが自分の仕事を確かめられる環境の広さで決まる</strong>」

<strong>エージェントが自分でアプリを起動し、操作し、結果を証拠として残せる範囲が広いほど、利用者が自分で動かして確かめなくても、任せられる仕事が増える</strong>、ということを結論としたいと思います。

この結論の出発点は、poteto氏の[講演](https://x.com/poteto/status/2102050467505430555)（[第1章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/74ae41)）と『The Complete Guide to pstack』[Part 1](https://x.com/poteto/status/2094457600259842065)です。<strong>どちらも、検証を土台に置くという考えで一貫していました</strong>。

講演は、<strong>信頼する対象はエージェントではなく成果物であり、その成果物を検証できることが信頼の前提になる</strong>としました。Part 1は、節『Verification is all you need』で、<strong>質の高い検証スキルを、最も重要なスキル</strong>として取り上げました。

<a id="%E6%9C%80%E5%88%9D%E3%81%AE%E4%B8%80%E6%AD%A9%E3%81%AF%E3%80%81%E5%B0%8F%E3%81%95%E3%81%AA%E4%BB%95%E4%BA%8B%E3%81%A7%E6%A4%9C%E8%A8%BC%E3%81%AE%E3%83%AB%E3%83%BC%E3%83%97%E3%82%92%E4%B8%80%E5%91%A8%E3%81%95%E3%81%9B%E3%82%8B%E3%81%93%E3%81%A8"></a>


## 最初の一歩は、小さな仕事で検証のループを一周させること

pstackには23件のPlaybook、23件のPrinciple、24件のSkillがありますが、<strong>明日からすべてを使いこなす必要はありません</strong>。

最初は、<strong>小さな仕事で検証のループを一周させるだけで十分です</strong>。

<li class="code-line" data-line="21">
<strong>検証スキル</strong>・・・ エージェントがアプリを起動・操作して証拠を取るための、プロジェクト専用のSkillです。</li>
<li class="code-line" data-line="22">
<strong>検証のループ</strong>・・・ 利用者が、合否が出る完了の条件を決めて依頼し、エージェントが本物のアプリで確かめ、条件を満たすまで直して、証拠を返すまでの一連の流れを指す、ループ処理です。</li>

ここからは、読み終えた後の最初の一歩として、1週間でできる4つのステップと、そこから任せる範囲を広げる順番を書きます。

1週間という区切りと4つのステップの組み立ては、本書の提案です。

## 1週間でできる4つのステップ

<a id="1.-%E5%A4%B1%E6%95%97%E3%81%97%E3%81%A6%E3%82%82%E5%9B%B0%E3%82%89%E3%81%AA%E3%81%84%E3%80%81%E6%9C%AC%E7%89%A9%E3%81%AE%E4%BB%95%E4%BA%8B%E3%82%921%E3%81%A4%E9%81%B8%E3%81%B6"></a>


### 1. 失敗しても困らない、本物の仕事を1つ選ぶ

最初に選ぶタスクは、「小さく、失敗しても困らないが、実際に必要な仕事」です。

表示の小さな不具合の修正、CLIのオプションの追加、設定値の読み込みの修正などが向いています。どれも変更が小さく、動かせば結果が合っているかをすぐに確かめられるからです。

<strong>練習用の課題は避け、本物の仕事を選んでください</strong>。この1週間の目的が、検証のループが本物のアプリで回るかを確かめることだからです。

<a id="2.-%E5%AE%8C%E4%BA%86%E3%81%AE%E6%9D%A1%E4%BB%B6%E3%82%92%E3%80%81%E5%90%88%E5%90%A6%E3%81%8C%E5%87%BA%E3%82%8B%E5%BD%A2%E3%81%A7%E6%9B%B8%E3%81%8F"></a>


### 2. 完了の条件を、合否が出る形で書く

利用者は、依頼を書く前に、「何が確認できたら終わりか」（完了の条件）を決めます。

<strong>完了の条件は、「いい感じにして」ではなく、実行して合否が出る形にします</strong>。

同梱ガイドの [`06-verify-and-ship.md`](https://github.com/cursor/plugins/blob/main/pstack/docs/guide/06-verify-and-ship.md) の節『State the finish condition up front』は、CLIにJSON出力を足す仕事を例に、完了の条件を次のように依頼に書いています。

```
/poteto-mode add json output to this command. text output stays byte-identical, the json parses, both run against the sample project. show me the evidence.
// このコマンドにJSON出力を足して。テキスト出力は1バイトも変えない。JSONはパースできる。両方をサンプルプロジェクトで実行する。証拠を見せて。
```

この依頼の3つの条件は、どれも実行して合否が出ます。

pstackを使っているなら、このように条件をそのまま、pstackの入口である [`/poteto-mode`](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/SKILL.md)（[第7章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/4fda7d)）への依頼に入れます。

pstackを使っていなくても、どのエージェントへの依頼にも同じ書き方ができます。

<a id="3.-%E3%82%A8%E3%83%BC%E3%82%B8%E3%82%A7%E3%83%B3%E3%83%88%E8%87%AA%E8%BA%AB%E3%81%8C%E6%9C%AC%E7%89%A9%E3%81%AE%E3%82%A2%E3%83%97%E3%83%AA%E3%81%A7%E7%A2%BA%E3%81%8B%E3%82%81%E3%82%8B%E3%82%88%E3%81%86%E3%80%81%E4%BE%9D%E9%A0%BC%E3%81%99%E3%82%8B"></a>


### 3. エージェント自身が本物のアプリで確かめるよう、依頼する

ここが一番大事なステップです。

利用者は、テストが通ったかどうかを報告させるのではなく、エージェントに、実際にアプリを起動し、変更した機能を動かして、<strong>結果を証拠として見せる</strong>よう求めます。テストが通っても、実際の画面や出力が正しいとは限らないからです。

たとえば、『The Complete Guide to pstack』[Part 1](https://x.com/poteto/status/2094457600259842065)は、機能を作る依頼を次のように書いています（[第36章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/7d7081)）。

```
/poteto-mode build <description of feature, any useful context>. use /control-app to verify your changes and show me a video and screenshots as proof
// <機能の説明と、役に立つコンテキスト>を作って。/control-app で変更を確かめて。証拠として動画とスクリーンショットを見せて。
```

`/control-app` は、[`/create-verification-skill`](https://github.com/cursor/plugins/blob/main/pstack/skills/create-verification-skill/SKILL.md) で作った検証スキルを指す、記事での検証スキル名です。

この依頼は、作る機能の説明に、どの検証スキルで確かめるか（`/control-app`）と、証拠の形式（動画とスクリーンショット）を添えています。

証拠には、次のようなものがあります。

- コマンドの出力
- 画面のスクリーンショット
- 保存された値を読み戻した結果

エージェントが自分で確かめられない場合は、利用者が<strong>その原因を最初に取り除きます</strong>。確かめられないままでは、結果を利用者が確かめるしかなく、任せられる範囲が広がらないからです。

本書では、<strong>エージェントが確かめられずに止まる原因として、次の3つ</strong>を挙げます。

- アプリの起動方法が分からない
- 操作する手段がない
- テスト用のユーザーやデータがない

<strong>利用者が、エージェントがこの3つのどれで止まったかを書き留めておくと、次に何を整えればよいかがはっきりします</strong>。

このうち、アプリの起動と、テスト用のユーザーやデータの2つは、Part 1の節『Make it Reproducible』にも出てきます。

Part 1はこの節で、アプリの開発体験（原文では dev experience）として、次の3つを考え始めておくよう勧めています。

> seeding a dev database  
> how to handle auth, test users, API calls against a test/staging environment  
> installing and bringing up your dev environment in a consistent way
>
> 開発用データベースにシードデータ（開発やテストのために最初から入れておくデータ）を入れること  
> 認証、テストユーザー、テスト環境やステージング環境へのAPIの呼び出しを、どう扱うか  
> 開発環境を、いつも同じ手順でインストールし、立ち上げること

検証スキル（[第26章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/03ebca)、[第36章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/7d7081)）は、エージェントが自分で確かめられない状態をなくすためのものです。検証スキルを用意する理由を、第26章では次のように書きました。

> 利用者が検証スキルを最初に用意するのは、<strong>エージェントが自分の仕事を確かめられないと、どれだけ多くの仕事をエージェントに任せても、最後は人間が1つずつ確かめることになり、人間が作業の流れを止める存在（ボトルネック）になる</strong>からです。

pstackを使っているなら、検証スキルを作る [`/create-verification-skill`](https://github.com/cursor/plugins/blob/main/pstack/skills/create-verification-skill/SKILL.md) を一度実行してみてください。

<a id="4.-%E5%90%8C%E3%81%98%E6%B3%A8%E6%84%8F%E3%82%922%E5%9B%9E%E3%81%97%E3%81%9F%E3%82%89%E3%80%81%E3%81%9D%E3%81%AE%E6%B3%A8%E6%84%8F%E3%82%92%E6%96%87%E7%AB%A0%E3%81%A7%E3%81%AF%E3%81%AA%E3%81%8F%E4%BB%95%E7%B5%84%E3%81%BF%E3%81%AB%E6%AE%8B%E3%81%99"></a>


### 4. 同じ注意を2回したら、その注意を文章ではなく仕組みに残す

<strong>利用者は、1週間のうちに同じ注意を2回したら、注意した間違いを自動で検出できないかを考え、できるなら仕組みにします</strong>。

この考え方は、本書がpstackの原則から借りたものです。

原則『[<strong>Encode Lessons in Structure</strong>](https://github.com/cursor/plugins/blob/main/pstack/skills/principle-encode-lessons-in-structure/SKILL.md)』（[第21章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/dd2d9f)）は、エージェントが同じ指示を2回書いていると気づいたときの対応を定めています。

エージェントは、その指示を、次のどれかにできないかを考え、できるなら仕組みにして、元の指示を消します。

- lint（コードの書き方を自動で検査する道具）のルール
- メタデータのフラグ（ファイルの設定欄に置く値）
- 実行時チェック（プログラムの実行中に、値や状態が条件を満たすかを確かめる処理）
- スクリプト

原則がこう定めるのは、<strong>文章の指示は、読み手が気づき、覚え、従わなければ効かない</strong>からです。

原則の本文は、次のように書いています。

> Textual instructions are easy to miss. They require the reader to notice, remember, and comply.
>
> 文章の指示は見落とされやすい。読み手が気づき、覚え、従う必要がある。

利用者の側では、lintのルールやCIのチェック、スクリプトなどが、文章の指示に代わる仕組みに当たります。

たとえば、`any` を使わないよう2回注意したなら、`any` を禁止するlintのルールを追加します。

eslint.config.js

```
// any を書くと、lint がエラーにする（typescript-eslint を導入済みの前提）
import tseslint from "typescript-eslint";

export default [
  {
    files: ["src/**/*.ts"],
    languageOptions: { parser: tseslint.parser },
    plugins: { "@typescript-eslint": tseslint.plugin },
    rules: {
      "@typescript-eslint/no-explicit-any": "error",
    },
  },
];
```

注意の内容をlintやCIのチェックにすれば、<strong>次の週からは、利用者が注意しなくても、エージェントが覚えていなくても、同じ間違いは自動で止まります</strong>。

## 任せる範囲は、段階的に広げる

利用者が[1週間でできる4つのステップ](#1%E9%80%B1%E9%96%93%E3%81%A7%E3%81%A7%E3%81%8D%E3%82%8B4%E3%81%A4%E3%81%AE%E3%82%B9%E3%83%86%E3%83%83%E3%83%97)を一通り終えると、「この種類の仕事なら、差分と動作を毎回自分で確かめなくても、エージェントが出した証拠を読めばよい」という範囲が1つできます。

<strong>この範囲を、仕事の種類ごとに一つずつ増やしていきます</strong>。

あわせて、1つの種類の仕事の中でも、任せる範囲はフェーズを追って広げます。

本書では、そのフェーズを次の4つに分けて扱います。

<tr class="code-line" data-line="166">
<th>任せるフェーズ</th>

</tr>
</thead>
<tbody class="code-line" data-line="168">
<tr class="code-line" data-line="168">
<td>1</td>
<td>毎回の差分と動作を自分で確かめる</td>
<td>コードを書く</td>
</tr>
<tr class="code-line" data-line="169">
<td>2</td>
<td>エージェントが出した証拠を読む</td>
<td>コードを書き、自分で動かして証拠を出す</td>
</tr>
<tr class="code-line" data-line="170">
<td>3</td>
<td>完了の条件を決めて依頼し、できあがったPRと証拠だけを見る</td>
<td>仕事の種類ごとに決まった手順（pstackならPlaybook）で調べ、直し、確かめ、PRを作る</td>
</tr>
<tr class="code-line" data-line="171">
<td>4</td>
<td>方針を決め、取り消せない操作（デプロイ、データの削除など）を承認する</td>

[4つのステップ](#1%E9%80%B1%E9%96%93%E3%81%A7%E3%81%A7%E3%81%8D%E3%82%8B4%E3%81%A4%E3%81%AE%E3%82%B9%E3%83%86%E3%83%83%E3%83%97)を一通り終えた種類の仕事は、この表のフェーズ2（エージェントが出した証拠を読む）まで来ています。

<strong>フェーズは飛ばさず、1から順に上がります</strong>。

フェーズ2でエージェントが出す証拠を信頼できないままフェーズ4へ進むと、確かめようのない変更が並列に増えるだけです。

講演の「月2,500件のPR」も、成果物の検証から順に環境を整えた先に出た数字です。[第1章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/74ae41)では、次のように書きました。

> つまり、まず成果物を検証できる状態を作り、そこで得た知識をコードベースに残し、その土台の上で自動化を進める、という順番が守られる必要があります。
>
> 月2,500件という数字は、この4つを順に整えた結果です。

引用は、講演の4つのテーマ（信頼、信頼を高める方法、コードベースを記憶として扱うこと、自動化）でもあります。

## 最後に

pstackは今も更新が続いています。

本書が対象にしたのは、2026年9月時点の pstack version `0.15.5` です。

Playbook・Principle・Skillの名前や数、既定のモデル（利用者が指定しないときに使われるモデル）は、これからも変わっていきます。

それでも本書では、<strong>「エージェントが自分の仕事を確かめられる環境を先に作る」という方針の価値は、モデルが賢くなっても下がらない</strong>と考えます。<strong>モデルが賢くなるほど任せる仕事は大きくなり、その分、確かめる仕組みが必要になる</strong>からです。

加えて、賢いモデルでも確かめずに、自信を持って、言い切ることもあります。

『The Complete Guide to pstack』[Part 2](https://x.com/poteto/status/2097732320606507506)は、節『Building up a mental model』で、最新のモデルについて次のように書いていました。

> Even with the latest frontier models, (this also depends on the quality of the harness), in general I find that they still often state things confidently without backing it up with data or actually reading the code needed to build up a mental model of how it works.
>
> 最新の最先端モデルでも（エージェントを動かすツールの質にもよるが）、概して、データで裏づけたり、仕組みを理解するのに必要なコードを実際に読んだりせずに、自信を持って言い切ることがまだ多いと感じている。

まずは1つ、小さな仕事で検証のループを一周させてみてください。

そこから、任せられる範囲が少しずつ広がっていきます。

最後まで読んでいただき、ありがとうございました。  
本書が読者のみなさまにとって、少しでも参考になり、開発ライフをより良くできるものになっていると感じていただけたら幸いです。

では、よい pstack lifeを！
