pstackの中身は、<strong>Playbook、Skill、Principleの3種類の部品</strong>でできています。

Playbookは作業の順序を決めます。Skillは手順の中で使う能力を提供します。Principleは、特定の状況で作業中の判断を導くルールです。変更を小さくする、根本原因を直す、完了を報告する前に実物を確かめる、といった判断に使います。

この章では、3つの部品の違いと、それぞれの担うものを中心に解説し、部品をつなぐ`Non-negotiables`と2つのサブエージェント、実例の依頼で部品が働く場所を、この順に見ていきます。

<a id="%E3%81%93%E3%81%AE%E7%AB%A0%E3%81%AE%E6%A7%8B%E6%88%90"></a>


## この章の構成

この章の構成は次のとおりです。

- 3つの部品は、「順序」「能力」「判断」を分担している
- Playbookは、作業の種類ごとの手順と順番を決める
- Skillは、手順の中で呼び出す能力
- Principleは、手順や能力ではなく、作業途中の判断の基準
- Non-negotiablesが、3つの部品をつなぐ
- 2つのサブエージェントは、作業を分担する相手
- SkillとPrincipleが働く場所をたどる
- まとめ

## 3つの部品は、「順序」「能力」「判断」を分担している

冒頭で記述したように3つの部品は担当領域が異なります。<strong>Playbookは「何を、どの順でやるか」といった仕事の進め方の型を、Skillは「この手順をどうやるか」といった能力を、Principleは「この一手を採るか。まだ終わりではないか」といった判断を</strong>、それぞれ担当します。

3つの部品は、`/poteto-mode` の中で次のようにつながっています。

1. `/poteto-mode` が依頼の種類を見て、Playbookを1冊選ぶ（[`/poteto-mode`](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/SKILL.md) の節『[Playbooks](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/SKILL.md#playbooks)』）
2. Playbookには、不具合なら「再現→原因→修正→確認」のように、その作業の手順と順番が書かれている
3. Playbookの各手順には、どこでどのSkillを使うかが書かれている。`/how`（現状把握）や `/arena`（複数案の比較）は、起動時ではなく、その手順に来たときに呼ばれる

## Playbookは、作業の種類ごとの手順と順番を決める

Playbookは、<strong>作業の種類ごとに「何を、どの順でやるか」を書いた手順書</strong>です。

`/poteto-mode` が依頼に合う1冊を選んで開くものです。

<a id="%E6%8B%85%E3%81%86%E3%82%82%E3%81%AE%EF%BC%9A%E6%89%8B%E9%A0%86%E3%81%A8%E9%A0%86%E7%95%AA%E3%82%92%E3%80%81%E5%89%8D%E7%BD%AE%E3%81%8D%E3%83%BB%E6%89%8B%E9%A0%86%E3%83%BB%E5%A0%B1%E5%91%8A%E3%81%AE3%E9%83%A8%E3%81%A7%E6%9B%B8%E3%81%8F"></a>


### 担うもの：手順と順番を、前置き・手順・報告の3部で書く

Playbookのファイルは、おおむね同じ形をしています。

1. <strong>前置き</strong>・・・ Playbook全体で守る基本ルールが書かれています。
2. <strong>番号付きの手順</strong>・・・ TODOリストに一字一句写される部分です。各手順の中に、どこでどのSkillを使うか、どのPrincipleに該当するかが書かれています。
3. <strong>Reply行</strong>・・・ 各Playbookの末尾にあり、作業後の返答に何を書くかを指定します。

## Skillは、手順の中で呼び出す能力

Skillは、<strong>特定の仕事をするための能力や手順のまとまり</strong>です。

大半は手順を必要とするときに `/poteto-mode` が呼び、残りは利用者が直接呼びます。

<a id="%E6%8B%85%E3%81%86%E3%82%82%E3%81%AE%EF%BC%9A1%E3%81%A4%E3%81%AEskill%E3%81%8C1%E7%A8%AE%E9%A1%9E%E3%81%AE%E4%BB%95%E4%BA%8B%E3%82%92%E6%8B%85%E3%81%86"></a>


### 担うもの：1つのSkillが1種類の仕事を担う

調査なら `/how` と `/why`、設計なら `/architect`、複数案の比較なら `/arena` というように、一つのSkillが一つの種類の仕事を担います。

### 利用者の使い方：各Skillは明示して呼び出せるし、Playbookから呼ばれない10件は利用者が呼ぶ

Skillは、Playbookと異なり単独で呼び出せます。調べものだけしたいときは、直接呼ぶほうが速いこともあります。

```
/how do we cancel runs? do we have an n+1 when we look up every run to cancel?
// 実行のキャンセルはどうやっている？キャンセルする実行を1件ずつ引くとき、n+1になっていない？
```

<strong>利用者が呼ぶ10件は、Playbookの手順には組み込まれていません</strong>。

## Principleは、手順や能力ではなく、作業途中の判断の基準

Principleは、手順でも能力でもなく、<strong>作業の途中で下す判断の基準</strong>です。

開始時には索引だけが読まれ、適用するときに本文が読まれます。

<a id="%E6%8B%85%E3%81%86%E3%82%82%E3%81%AE%EF%BC%9A%E4%BD%9C%E6%A5%AD%E9%80%94%E4%B8%AD%E3%81%AE%E5%88%A4%E6%96%AD%E3%82%92%E4%B8%8B%E3%81%99%E5%9F%BA%E6%BA%96"></a>


### 担うもの：作業途中の判断を下す基準

Principleは、<strong>今の一手を採るかと、まだ完了ではないか</strong>といった、<strong>作業途中の判断を下す基準</strong>を提供します。たとえば原則『[<strong>Laziness Protocol</strong>](https://github.com/cursor/plugins/blob/main/pstack/skills/principle-laziness-protocol/SKILL.md)』は、抽象やレイヤーを追加したくなったときに、削除と最小の変更を優先させます。原則『<strong>Prove It Works</strong>』は、完了を宣言する前に、本物の成果物で確かめたかを問いかけます。

Principleは1件ずつ独立したファイルになっていて、PlaybookやSkillから名前で参照されます。

Principle23件の詳細は[第4部](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/4b3166)（第17〜21章）で扱います。

## 2つのサブエージェントは、作業を分担する相手

pstackのサブエージェントは、<strong>`/poteto-mode` の流儀で作業する `poteto-agent` と、コメントを審査するComment Sickoの2つ</strong>です。

<a id="poteto-agent-%E3%81%AF%E3%80%81%2Fpoteto-mode-%E3%81%AE%E6%B5%81%E5%84%80%E3%81%A7%E5%83%8D%E3%81%8F%E3%82%B5%E3%83%96%E3%82%A8%E3%83%BC%E3%82%B8%E3%82%A7%E3%83%B3%E3%83%88"></a>


### `poteto-agent` は、`/poteto-mode` の流儀で働くサブエージェント

`poteto-agent`（[`agents/poteto-agent.md`](https://github.com/cursor/plugins/blob/main/pstack/agents/poteto-agent.md)）は、`/poteto-mode` のルールを読んでから作業を始めるサブエージェントです。Playbookの手順の中でサブエージェントを起動するときは、原則としてこれを使います。

### Comment Sickoは、コメントを消し、直すべきコードを報告する役

Comment Sicko（[`agents/comment-sicko.md`](https://github.com/cursor/plugins/blob/main/pstack/agents/comment-sicko.md)）は、コードのコメントを審査して、残す理由のないコメントを自分で消すサブエージェントです。アプリのコードそのものは書き換えません。その代わりに、コメントがなくても意味が通るように形を直すべきコード（関数や変数など）を、報告の中で `MUST KILL` として挙げます。その報告を受けて、コードを直すのは `/no-comments` です。直接は呼ばず、`/no-comments` を通して使います。詳しくは[第31章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/8960d3)で扱います。

<a id="%E3%82%B5%E3%83%96%E3%82%A8%E3%83%BC%E3%82%B8%E3%82%A7%E3%83%B3%E3%83%88%E3%81%AE%E4%BB%95%E4%BA%8B%E3%81%AF%E3%80%81%E4%B8%BB%E3%82%A8%E3%83%BC%E3%82%B8%E3%82%A7%E3%83%B3%E3%83%88%E3%81%8C%E8%B2%AC%E4%BB%BB%E3%82%92%E6%8C%81%E3%81%A4"></a>


### サブエージェントの仕事は、主エージェントが責任を持つ

<strong>サブエージェントに任せても、責任は主エージェントに残ります</strong>。

`/poteto-mode` は、サブエージェントの「終わりました」をそのまま利用者に渡さず、主エージェントが差分を見てから自分の言葉で報告するよう求めています。

[第2章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/27a183)で見た「信頼するのは、エージェントではなく成果物」という考えを、サブエージェントにも当てはめた規則です。

## SkillとPrincipleが働く場所をたどる

<strong>Skillは再現、調査、設計、コミットといった「作業をする」場面に、Principleは再現の仕方、修正の形と大きさ、完了の判定、コミットの並べ方といった判断して何かを「決める」場面に現れます</strong>。

本書の実例は、次の依頼です。

```
/poteto-mode the export writes duplicate rows when a retry lands mid-run. repro first, then fix and verify.
// 再試行が実行の途中に入ると、エクスポートが重複した行を書き出す。まず再現して、それから直して、確かめて。
```

この依頼は『<strong>Bug fix</strong>』Playbookに振り分けられ、TODOリストは、その6つの手順で始まります（手順6は『[<strong>Opening a PR</strong>](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/playbooks/opening-a-pr.md)』を実行してPRを開く手順なので、下の表では省きます）。ここでは、各手順のどこでSkillが呼ばれ、どこでPrincipleが効くかをたどります。

次の表は、`playbooks/bug-fix.md` と、`/poteto-mode` のNon-negotiablesとPrinciple索引に書かれた条件を、この依頼に当てはめたものです。実際の作業でどのPrincipleが選ばれるかは、エージェントがその場で索引の条件を判定して決まります。

### 条件に該当しないSkillは呼ばれない

たとえば `/show-me-your-work` は、長い作業や席を外す作業で判断の記録を残すSkillです。今回の依頼は席を外すとは書いていないので、条件に該当しません。長い作業や席を外す作業であれば条件に該当しますが、その場合は、[第7章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/4fda7d)で見た規則により `/figure-it-out` へ回る可能性もあります。

同じ『<strong>Bug fix</strong>』でも、依頼の内容と途中で起きる状況によって、呼ばれるSkillと効くPrincipleは変わります。条件に該当したものだけを読むこの設計が、次の[第9章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/6b7496)の主題です。

## まとめ

- <strong>3つの部品の違い</strong>・・・ Playbookは作業の順序を、Skillは手順の中で使う能力を、Principleは今の一手を採るか、まだ完了ではないかの判断を担います。
- <strong>Playbook</strong>・・・ 前置き、手順、Reply行の3部でできています。
- <strong>Skill</strong>・・・ 1つのSkillが1種類の仕事を担います。大半は `/poteto-mode` が手順に応じて呼び、利用者が呼ぶ10件は、Playbookの手順には組み込まれていません。
- <strong>Principle</strong>・・・ 手順や能力ではなく、今の一手と完了かどうか、といった判断基準を定義します。詳細は[第4部](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/4b3166)で扱います。
- <strong>Non-negotiables</strong>・・・ 作業の中で起きる状況に反応して、PlaybookをまたいでSkillを呼ぶつなぎ役です。
- <strong>サブエージェント</strong>・・・ `poteto-agent` は `/poteto-mode` の流儀で働くサブエージェント、Comment Sickoはコメントを消し、直すべきコードを報告する役です。任せた仕事の責任は主エージェントに残ります。
- <strong>実例の依頼</strong>・・・ 『<strong>Bug fix</strong>』の手順ごとに、再現と調査にcontrol系Skillと `/how`・`/why`、修正に `/architect`、コミットに `/tdd` が呼ばれ、『<strong>Fix Root Causes</strong>』や『<strong>Prove It Works</strong>』などの原則が判断に効きます。

次の[第9章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/6b7496)では、これらの部品がいつ読み込まれるかを扱います。必要なものを必要なときだけ読む仕組みと、その元にある考え方、利点と弱点を解説します。
