- <strong>1〜3</strong>・・・ コードを減らす原則
- <strong>4〜7</strong>・・・ 設計の置き方（設計の土台と、見直すタイミング）を決める原則

この章では、10原則をこの順に、1件ずつ次の観点で解説します。

- <strong>ルール</strong>・・・ その原則が求めること
- <strong>発火条件</strong>・・・ その原則が当てはまる場面

## Principleを読む前に押さえる3つの前提

Principleの仕組みは[第8章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/096f3d)と[第9章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/6b7496)でも扱いましたが、本章を読むうえでは、次の3つだけ押さえておけば十分です。

1. <strong>Principleは今の変更を入れるか、まだ完了ではないかを決める</strong>  
   <strong>Principle自体は手順や能力ではなく、判断の基準</strong>です。ただし『Build the Lever』や『[<strong>Prove It Works</strong>](https://github.com/cursor/plugins/blob/main/pstack/skills/principle-prove-it-works/SKILL.md)』のように、適用するとスクリプトを書くことを求めるものもあります。
2. <strong>発火条件は、`/poteto-mode` のPrinciple一覧と、各Principleの冒頭に書かれている</strong>  
   原則が当てはまる場面を、本書では発火条件と呼びます。本章の発火条件は、`/poteto-mode` の『[Principles](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/SKILL.md#principles)』の各項目にある「いつ当てはまるか」と、各Principleの `SKILL.md` の冒頭（description）にある適用の場面をもとにした訳です。
3. <strong>原則の名前は、依頼に書かなくても使われる</strong>  
   エージェントは、<strong>作業が発火条件に当てはまれば、原則を自分で読んで適用します</strong>。ただし、<strong>エージェントが一覧（索引）を読むのは手順が複数ある作業の始めで、当てはまるかどうかの判断もエージェントに任されている</strong>ため、当てはまる場面を見落とすことがあります。  
   エージェントが原則の適用を見落とした（見送った）場合、人間が<strong>原則名を依頼に明示すれば</strong>、エージェントはその原則を適用し、作業の方向を修正します。

## 『Laziness Protocol』は、最小の変更で最大の結果を得る

原則『<strong>Laziness Protocol</strong>』は、<strong>最小のコードと複雑さで最大の結果を得る</strong>ことを求めます。この原則が解決策の良し悪しを判定する基準は、人間の開発者が<strong>そのコードの保守に疲れ果てるかどうか</strong>という一点です。原文では「<strong>そのコードの保守に疲れ果てるなら悪い解決策</strong>」と明示されています。

<a id="%E3%83%AB%E3%83%BC%E3%83%AB%EF%BC%9A%E3%82%B3%E3%83%BC%E3%83%89%E3%82%92%E6%B6%88%E3%81%97%E3%80%81%E5%91%BC%E3%81%B3%E5%87%BA%E3%81%97%E3%81%AE%E9%9A%8E%E5%B1%A4%E3%82%92%E6%B5%85%E3%81%8F%E3%81%97%E3%80%81%E5%88%A4%E6%96%AD%E3%82%92%E4%B8%80%E3%81%8B%E6%89%80%E3%81%A7%E6%B1%BA%E3%82%81%E3%82%8B"></a>


### ルール：コードを消し、呼び出しの階層を浅くし、判断を一か所で決める

主なルールは次のとおりです。

<a id="%E6%B6%88%E3%81%9B%E3%82%8B%E3%82%82%E3%81%AE%E3%82%92%E5%85%88%E3%81%AB%E6%8E%A2%E3%81%99"></a>


#### 消せるものを先に探す

改善を頼まれたら、コードを追加する前に、消せるものを探します。

<a id="%E5%91%BC%E3%81%B3%E5%87%BA%E3%81%97%E3%81%AE%E9%9A%8E%E5%B1%A4%E3%82%92%E6%B5%85%E3%81%8F%E3%81%99%E3%82%8B"></a>


#### 呼び出しの階層を浅くする

コード上で目的のものを探すために、4つ以上のファイルをたどるか、処理を4層以上たどる必要があるなら、間の層をなくして階層を浅くします。何層もたどらないと答えが出ないコードは、保守する人を疲れさせるためです。

<a id="%E5%88%A4%E6%96%AD%E3%82%92%E4%B8%80%E3%81%8B%E6%89%80%E3%81%AB%E3%81%BE%E3%81%A8%E3%82%81%E3%82%8B"></a>


#### 判断を一か所にまとめる

同じ条件を複数の場所で判定せず、一か所で判定します。  
たとえば、入力欄が空かどうかを一度判定し、その結果を「ボタンの活性・非活性制御」や「案内の表示」といった複数箇所で使います。条件を変えるときも、判定箇所を一か所直せば済みます。同じ判断が何か所にもあると、それらをそろえ続ける手間がいつまでも残るからです。

<a id="%E5%B7%AE%E5%88%86%E3%82%92%E6%9C%80%E5%B0%8F%E3%81%AB%E3%81%99%E3%82%8B"></a>


#### 差分を最小にする

凝った定型コードより、行数が少ないほうが良いと判断します。

<a id="%E6%96%B0%E3%81%97%E3%81%84%E5%80%A4%E3%82%92%E5%B1%A4%E3%81%AB%E9%80%9A%E3%81%99%E5%89%8D%E3%81%AB%E6%AD%A2%E3%81%BE%E3%82%8B"></a>


#### 新しい値を層に通す前に止まる

新しい値を型、スキーマ、パイプラインと何層にも通す依頼が来たら、一旦止まり、より直接的な選択肢を探します。

たとえば、有料会員にだけボタンを表示する機能を追加するときに、「有料会員かどうか」という新しい値を、APIの型、変換処理、親から子へ渡す値と何層にも追加していくのではなく、ボタンの近くですでに使えるユーザー情報から直接判定できないかを先に探します。

<a id="%E7%99%BA%E7%81%AB%E6%9D%A1%E4%BB%B6"></a>


### 発火条件

- リファクタリングや差分の見積もりをするとき
- 抽象化や層を追加したくなったとき
- 新しい値を何層にもまたいで受け渡したくなったとき

<a id="%E3%80%8Esubtract-before-you-add%E3%80%8F%E3%81%AF%E3%80%81%E6%A9%9F%E8%83%BD%E3%82%92%E8%BF%BD%E5%8A%A0%E3%81%99%E3%82%8B%E5%89%8D%E3%81%AB%E8%A4%87%E9%9B%91%E3%81%95%E3%82%92%E5%89%8A%E3%82%8B"></a>


## 『Subtract Before You Add』は、機能を追加する前に複雑さを削る

原則『<strong>Subtract Before You Add</strong>』は、<strong>システムを育てるときは先に複雑さを取り除き、それから作る</strong>ことを求めます。複雑なシステムに機能を追加すると、複雑さが積み重なるからです。先に複雑さを削れば、コードが減り、システムの本質的な構造が見えて、次にどう設計すればよいかも大抵、明確になります。

<a id="%E3%83%AB%E3%83%BC%E3%83%AB%EF%BC%9A%E4%BD%9C%E3%82%8B%E5%89%8D%E3%81%AB%E8%A4%87%E9%9B%91%E3%81%95%E3%82%92%E5%8F%96%E3%82%8A%E9%99%A4%E3%81%8F"></a>


### ルール：作る前に複雑さを取り除く

- 作る前に複雑さを取り除き、品質を磨く前に最小限まで削る
- 必要性がまだ確かめられていない例外（エッジケース）への対応を増やさず、実際に確認できた使われ方に合わせて設計する
- 検証器やガードは仕様が求める範囲にとどめ、推測で追加しない
- プロンプトやSkillの文章でも、重複した指示を消す

<a id="%E7%99%BA%E7%81%AB%E6%9D%A1%E4%BB%B6-1"></a>


### 発火条件

機能や処理の追加、リファクタリング、書き直しを、どの順番で進めるかを決めるときです。

<a id="%E4%BE%9D%E9%A0%BC%E3%81%AE%E4%BE%8B%EF%BC%9A%E5%8F%A4%E3%81%84%E3%82%A2%E3%83%80%E3%83%97%E3%82%BF%E3%82%92%E6%B6%88%E3%81%97%E3%81%A6%E3%81%8B%E3%82%89%E8%A8%AD%E8%A8%88%E3%81%95%E3%81%9B%E3%82%8B"></a>


### 依頼の例：古いアダプタを消してから設計させる

次の依頼例は、エージェントが、すでにある3つのアダプタに4つ目を追加しようとしている場面で、同梱ガイドが挙げているものです。

```

// subtract before you add を使って。まず古くなったアダプタを消して。それから残ったものを設計して。
```

## 『Minimize Reader Load』は、読み手がたどる間接参照の層と、覚えておく必要があるコードの状態を減らす

原則『<strong>Minimize Reader Load</strong>』は、保守しやすさを「<strong>読み手がコードを理解するためにする仕事の量</strong>」と定義します。コードは、書かれるよりも読まれるほうがはるかに多いからです。

この原則は、読み手の負担を「たどる層」と「抱える状態」の2つの軸で測ります。

「たどる層」とは、読み手が疑問を持ってから答えにたどり着くまでに、関数やファイルを何段たどるかという段数のことです。

「抱える状態」とは、読み手がコードの挙動を理解するために頭の中に覚えておく必要がある、隠れた状態や書き換えられる値のことで、「どの値」が「どこ」で「変わるか」をどれだけ追い続ける必要があるか、といった「コードを追跡する際の負荷」を指します。

2つの軸は、それぞれ異なる種類の読みにくさを生みます。

たとえば、関数を何段もたどらずに済む1つのファイルでも、どこからでも書き換えられる変数（グローバル変数）が50個あれば、読み手が、ある値がいつ、どこで変わるかを追うのは難しくなります。逆に、変数が少なくても、答えにたどり着くまでに6層のアダプタ（変換を受け持つ層）をたどる必要があれば、それも読みにくいコードです。

そのため、この原則は、片方だけでなく両方を減らすよう求めます。

『<strong>Minimize Reader Load</strong>』は、[第20章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/c155cc)の『[<strong>Guard the Context Window</strong>](https://github.com/cursor/plugins/blob/main/pstack/skills/principle-guard-the-context-window/SKILL.md)』（エージェントのコンテキストウィンドウを大量の出力で埋めないための原則）の人間版に該当します。一度に覚えておける量（作業記憶）に限りがあるのは、エージェントだけでなく、コードを読む人間も同じだからです。

### ルール：層と状態を減らす

<a id="%E5%8F%97%E3%81%91%E6%B8%A1%E3%81%99%E3%81%A0%E3%81%91%E3%81%AE%E5%B1%A4%E3%82%92%E3%81%AA%E3%81%8F%E3%81%99"></a>


#### 受け渡すだけの層をなくす

内部で別の関数を呼ぶだけの関数が1か所からしか使われていないなら、その関数をなくし、呼び出し元から、その関数を直接呼びます。  
たとえば、`saveUser()` が `db.save()` を呼ぶだけなら、`db.save()` を直接呼びます。

```
type User = { name: string };
declare const db: { save(user: User): Promise<void> };
declare const user: User;

// 前：saveUser は db.save を呼ぶだけで、使われているのはここ1か所
function saveUser(user: User) {
  return db.save(user);
}
await saveUser(user);

// 後：saveUser をなくし、db.save を直接呼ぶ
await db.save(user);
```

また、呼び出し元と実際の処理の間に挟んだ層も、取り替え先が1つもないなら、同じようになくします。将来の拡張性などを考えて挟んだ層も、これに含まれます。

たとえば、決済サービスを1社しか使っていないのに、`PaymentGateway` のような取り替え用の窓口を挟んでいる場合です。こうした層は、読み手に「開いて中を確かめる」手間を増やすだけだからです。

```
declare const aPayClient: { charge(amount: number): Promise<void> };

// 前：取り替え用の窓口を挟んでいるが、実装は A社用の1つしかない
interface PaymentGateway {
  pay(amount: number): Promise<void>;
}

class APayPaymentGateway implements PaymentGateway {
  pay(amount: number) {
    return aPayClient.charge(amount);
  }
}

const gateway: PaymentGateway = new APayPaymentGateway();
await gateway.pay(1000);

// 後：窓口をなくし、A社の決済を直接呼ぶ
await aPayClient.charge(1000);
```

#### 状態の範囲を狭める

値を書き換えられる範囲を狭くします。たとえば、どこからでも書き換えられる変数（グローバル変数）より、1つの関数の中だけで使う変数（ローカル変数）を選びます。

また、ほかの値から計算できる値を、別の変数として持ちません。  
たとえば、商品の一覧とは別に「商品の件数」という変数を持つと、一覧を変えるたびに件数も更新する必要があります。3件の一覧に商品を1つ追加したのに件数の更新を忘れると、一覧には4件あるのに件数は3のままになります。件数は、必要なときに一覧から数えます。

状態の範囲が狭いほど、読み手が覚えておく必要があるコード上の状態が減るからです。

#### 不変条件は、境界で一度だけ確かめて名前を付ける

不変条件とは、「金額は0以上」のように、プログラムが動いている間、常に守られていなければならない条件のことです。原則は、不変条件を、利用側のすべてではなく境界で一度だけ確かめるよう求めます。

#### 30秒テストで判定する

<strong>この原則は、層や状態が多すぎるかどうかを「30秒テスト」で判定します</strong>。新しい読み手が「Xはどこから来るか」「何がXを変えうるか」に30秒以内に答えられなければ、層か状態を削ります。

### 発火条件

処理を追いにくいコードをレビューするとき、またはそうしたコードを書いたり、構成を組み直したりするときです。

## 『Foundational Thinking』は、ロジックの前にデータ構造と土台を決める

原則『<strong>Foundational Thinking</strong>』は、<strong>ロジックを書く前にデータの形を決める</strong>ことを求めます。

この原則は、判断を以下の2種類に分けています。

1. 構造の判断（データの形や作業の順番を決めること）
2. コードの書き方の判断

構造の判断は、将来の選択肢を守ります。ここでいう、構造の判断とは「データの形や作業の順番を決めること」で、将来の選択肢は「後から別の道を選べる余地のこと」です。  
コードの書き方の判断は、コードの単純さを守ります。データ構造を正しく選べば、その後に書くコードで何を書けばよいかは自然に決まります。

poteto氏は『The Complete Guide to pstack』[Part 2](https://x.com/poteto/status/2097732320606507506)で、<strong>エージェントの時代のエンジニアはアーキテクチャやデータ構造の選択に時間を使い、実装の詳細はエージェントが埋める</strong>、という分担を示しています。この原則は、データ構造を選ぶ判断を、エージェントの作業の最初に置いています。

<a id="%E3%83%AB%E3%83%BC%E3%83%AB%EF%BC%9A%E3%83%87%E3%83%BC%E3%82%BF%E6%A7%8B%E9%80%A0%E3%82%92%E6%B1%BA%E3%82%81%E3%80%81%E4%B8%A6%E8%A1%8C%E3%81%99%E3%82%8B%E7%8A%B6%E6%85%8B%E3%82%92%E5%88%86%E3%81%91%E3%80%81%E5%9C%9F%E5%8F%B0%E3%82%92%E4%BD%9C%E3%81%A3%E3%81%A6%E3%81%8B%E3%82%89%E4%BB%95%E7%B5%84%E3%81%BF%E3%82%92%E7%A9%8D%E3%82%80"></a>


### ルール：データ構造を決め、並行する状態を分け、土台を作ってから仕組みを積む

<a id="%E3%83%87%E3%83%BC%E3%82%BF%E6%A7%8B%E9%80%A0%E3%82%92%E5%85%88%E3%81%AB%E6%B1%BA%E3%82%81%E3%82%8B"></a>


#### データ構造を先に決める

ロジックを書く前に、中心になるデータの型を決めます。そのうえで、そのデータをどこでどう読み書きするかを一通り洗い出し、最もよく使われる処理に合う形を選びます。

たとえば、商品一覧の機能なら、先に「商品は名前、価格、在庫数を持つ」という形を決め、画面への表示やカートへの追加をどう書くかはその後に考えます。データの形が決まれば、それを使う処理は迷わずに書けるからです。

```
// 先に決める：商品は名前、価格、在庫数を持つ
type Product = {
  name: string;
  price: number;
  stock: number;
};

// 形が決まっているので、表示やカートへの追加は迷わずに書ける
function formatProduct(product: Product): string {
  return `${product.name}　${product.price}円（在庫 ${product.stock}）`;
}

function canAddToCart(product: Product): boolean {
  return product.stock > 0;
}
```

<a id="%E3%82%B3%E3%83%BC%E3%83%89%E3%81%A7%E3%81%AF%E3%80%81%E8%A1%8C%E3%81%AE%E9%87%8D%E8%A4%87%E3%82%88%E3%82%8A%E6%A7%8B%E9%80%A0%E3%81%AE%E9%87%8D%E8%A4%87%E3%82%92%E3%81%AA%E3%81%8F%E3%81%99"></a>


#### コードでは、行の重複より構造の重複をなくす

似た行があるたびに共通の関数へまとめるのではなく、データの形のような構造の重複をなくします。

この原則は、似た文が3つ並ぶ程度なら、急いで共通化するより、そのまま書いたほうが良いとします。また、凝った書き方より、見れば分かる書き方を選びます。凝った書き方とは、短く書けるが、読む人が一度では意味を取れない書き方のことです。たとえば、数が奇数かどうかを `n & 1` のようなビット演算で判定するより、`n % 2 === 1` と書きます。

<strong>早すぎる共通化や凝った書き方は、コードを単純に保つという目的に反する</strong>からです。

<a id="%E5%90%8C%E6%99%82%E3%81%AB%E6%9B%B8%E3%81%8D%E6%8F%9B%E3%81%88%E3%82%89%E3%82%8C%E3%82%8B%E5%80%A4%E3%81%AF%E3%80%81%E5%85%B1%E6%9C%89%E3%81%9B%E3%81%9A%E5%88%86%E3%81%91%E3%82%8B"></a>


#### 同時に書き換えられる値は、共有せず分ける

複数の主体（同時に動くWorkerやエージェント）で1つの値を共有する前に、「<strong>ほかの主体が同じ値を同時に書き換えたら、何が起きるか</strong>」を考えます。何か問題が起きるなら、値を共有せず、主体ごとに自分専用の値を持たせます。

たとえば、2つのWorkerA・Bが、共有の「処理済み件数」をそれぞれ1ずつ増やすとします。件数が10のときにAとBがほぼ同時に動くと、次の流れになります。

2つのWorkerが1件ずつ処理したので本当は12になるはずが、Bは、Aが書き込む前の10をもとに11を書き込むため、件数は11になり、1件分が消えてしまいます。

そこで、Workerごとに自分の件数を持たせ、全体の件数が必要なときだけ合計します。主体ごとに値が分かれていれば、ほかの主体に書き換えられる心配そのものがなくなるからです。

```
type Job = { id: string };
declare const store: {
  get(key: string): Promise<number>;
  set(key: string, value: number): Promise<void>;
};
declare function processJob(job: Job): Promise<void>;
declare const jobsForA: Job[];
declare const jobsForB: Job[];

// 前：全Workerで1つの「処理済み件数」を共有し、読んでから書き込む
async function countUp() {
  // A と B がほぼ同時に 10 を読む
  const current = await store.get("processedCount"); 
  // どちらも 11 を書き込み、1件分が消える
  await store.set("processedCount", current + 1);
}

// 後：Workerごとに自分の件数を持たせ、全体が必要なときだけ合計する
async function runWorker(jobs: Job[]): Promise<number> {
  let processedCount = 0; // このWorker専用の値

  for (const job of jobs) {
    await processJob(job);
    processedCount += 1;
  }

  return processedCount;
}

const counts = await Promise.all([runWorker(jobsForA), runWorker(jobsForB)]);
const total = counts[0] + counts[1];
```

#### 土台を先に作る

「<strong>この後のすべての段階が、これがあることで得をするか</strong>」と問い、答えが「Yes」なら先に作ります。CI、lint、テスト基盤、共有の型が土台の例です。この原則は、こうした土台を <strong>scaffold</strong>（直訳すると「足場」）と呼びます。

機能より準備を、修正よりテストを先にします。また、コミットは小さく、目的を1つに絞ることを優先します。土台が先にあれば、その後の作業すべてがそれを使えるからです。

ただし、<strong>土台を作ることよりも、使われていないコードを消すことを優先します</strong>。

使われていないコードを残したまま土台を作ると、共有の型やテストが、その不要なコードまで支える形になってしまうからです。先に消しておけば、本当に使われている部分だけが見えるので、それに合った土台を作れます。これは、この章の[『Subtract Before You Add』](#%E3%80%8Esubtract-before-you-add%E3%80%8F%E3%81%AF%E3%80%81%E6%A9%9F%E8%83%BD%E3%82%92%E8%BF%BD%E5%8A%A0%E3%81%99%E3%82%8B%E5%89%8D%E3%81%AB%E8%A4%87%E9%9B%91%E3%81%95%E3%82%92%E5%89%8A%E3%82%8B)と同じ考え方です。

また、[第4章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/dc9141)で見たように、コードベースはエージェントにとって記憶でもあるため、間違ったコンテキストが残ることを避けるためにも使われていないコードを消すことを優先している、と本書では読みます。

<a id="%E5%A4%89%E6%9B%B4%E3%82%921%E3%81%A4%E8%A1%8C%E3%81%86%E3%81%9F%E3%81%B3%E3%81%AB%E3%80%81%E3%81%BE%E3%81%A8%E3%81%BE%E3%81%A3%E3%81%9F%E4%BB%95%E7%B5%84%E3%81%BF%E3%82%921%E3%81%A4%E7%BD%AE%E3%81%8F"></a>


#### 変更を1つ行うたびに、まとまった仕組みを1つ置く

変更を1つ行うたびに、まとまった仕組み（複数の箇所から使える共通の関数や部品など）を1つ作るか、今ある共通の関数や部品などの仕組みを、より使いやすくします。

新しい機能を追加するときは、その機能を使う箇所ごとに、例外的な処理をあちこちに追加しません。たとえば、商品一覧に並べ替えの機能を追加するなら、一覧を表示する画面ごとに並べ替えの処理を追加するのではなく、並べ替えを受け持つ部品を1つ作り、各画面はその部品を呼び出して使うようにします。

<strong>新しい機能が1か所にまとまっていれば、読む人も直す人もその1か所を見れば済む</strong>からです。

<a id="%E7%99%BA%E7%81%AB%E6%9D%A1%E4%BB%B6-3"></a>


### 発火条件

- ロジックを書く前（中心になる型やデータ構造を選ぶとき）
- 土台（CI、lint、テスト基盤、共有の型のように、その後のすべての作業が使う仕組み）と機能のどちらを先に作るかを決めるとき
- 並行して動く複数の<strong>主体</strong>が、何を共有するかを考えるとき

<aside class="msg message"><span class="msg-symbol">!</span><div class="msg-content">
<p class="code-line" data-line="403">ここでいう<strong>主体</strong>とは、同時に動いて処理を進めるもののことです。</p>
<p class="code-line" data-line="405">たとえば、キューから仕事を取り出して並行に処理する複数のWorker（処理を受け持つプログラム）や、同じリポジトリで同時に作業する複数のエージェントが主体に該当します。</p>
</div></aside>

<a id="%E3%80%8Eredesign-from-first-principles%E3%80%8F%E3%81%AF%E3%80%81%E6%96%B0%E3%81%97%E3%81%84%E8%A6%81%E4%BB%B6%E3%82%92%E6%9C%80%E5%88%9D%E3%81%8B%E3%82%89%E3%81%82%E3%81%A3%E3%81%9F%E5%89%8D%E6%8F%90%E3%81%A8%E3%81%97%E3%81%A6%E8%A8%AD%E8%A8%88%E3%81%97%E7%9B%B4%E3%81%99"></a>


## 『Redesign from First Principles』は、新しい要件を最初からあった前提として設計し直す

原則『<strong>Redesign from First Principles</strong>』は、変更を今の設計に後付けせず、<strong>その要件が最初からあったかのように設計し直す</strong>ことを求めます。『<strong>Foundational Thinking</strong>』が「新しく何かを作るときの原則」なら、『<strong>Redesign from First Principles</strong>』は「今ある設計に変更を組み込むときの原則」だと、本書では読みます。

<a id="%E3%83%AB%E3%83%BC%E3%83%AB%EF%BC%9A4%E3%81%A4%E3%81%AE%E6%89%8B%E9%A0%86%E3%81%A7%E8%A8%AD%E8%A8%88%E3%81%97%E7%9B%B4%E3%81%99"></a>


### ルール：4つの手順で設計し直す

1. 影響するファイルをすべて読み、今の設計を理解する
2. 「この新しい要件を最初から知っていて、ゼロから書くとしたら、何を作るか」と問う
3. 型、ドキュメント、例、設計の理由を書いた節まで、変更に関わるすべての箇所を新しい設計に合わせて直す
4. 設計し直した全体像を先に考えてから、変更は少しずつ分けて入れる

たとえば、「日本円だけを扱っていた料金計算に、ドルでの支払いを加える」というケースでは以下のように考えられます。

- 後付けの場合、金額を使う箇所ごとに「ドルならこう計算する」という分岐を追加する
- 設計し直すなら、「最初から複数の通貨を扱う前提だったら、どう作るか」と考え、金額を「数値と通貨の組」として持つ形に改める

最後に、設計し直した結果を反映するため、金額を使う箇所、型、ドキュメントをすべてその形に合わせて修正します。

```
// 後付け：金額は円の数値のまま、使う箇所ごとに「ドルなら」の分岐を追加する
function formatPrice(amount: number, isDollar: boolean): string {
  if (isDollar) {
    return `$${amount.toFixed(2)}`;
  }

  return `${amount}円`;
}
```

```
// 設計し直す：金額を「数値と通貨の組」として持ち、使う箇所はすべてこの型を受け取る
type Currency = "JPY" | "USD";
type Money = { amount: number; currency: Currency };

function formatPrice(price: Money): string {
  if (price.currency === "USD") {
    return `$${price.amount.toFixed(2)}`;
  }

  return `${price.amount}円`;
}
```

この原則は、この4つの手順を、<strong>今ある設計に変更を組み込みながら将来の選択肢を残す</strong>ための方法だと説明しています。後付けで済ませると、後から追加した部分と元の設計が食い違ったまま残ります。その後の変更は、この食い違いを避けて書くしかなくなるため、後から選べる設計が少なくなります。

<a id="%E7%99%BA%E7%81%AB%E6%9D%A1%E4%BB%B6-4"></a>


### 発火条件

新しい要件を今ある設計に組み込むときです。

<a id="%E3%80%8Eattack-the-premise%E3%80%8F%E3%81%AF%E3%80%81%E5%90%8C%E3%81%98%E5%89%8D%E6%8F%90%E3%81%AB%E7%AB%8B%E3%81%A4%E4%BF%AE%E6%AD%A3%E3%81%8C%E5%90%8C%E3%81%98%E3%83%86%E3%82%B9%E3%83%88%E3%81%A72%E5%9B%9E%E8%90%BD%E3%81%A1%E3%81%9F%E3%82%89%E5%89%8D%E6%8F%90%E3%82%92%E7%96%91%E3%81%86"></a>


## 『Attack the Premise』は、同じ前提に立つ修正が同じテストで2回落ちたら前提を疑う

原則『<strong>Attack the Premise</strong>』は、同じ前提に立つ2つ以上の修正が、同じ gate で落ちたら、<strong>修正ではなく前提を疑う</strong>よう定めます。

<aside class="msg message"><span class="msg-symbol">!</span><div class="msg-content">
<ul class="code-line" data-line="462">
<li class="code-line" data-line="462">
<strong>gate</strong>・・・ 「関門」という意味があり、修正が通らなければならないテストやチェックのことを指す</li>
<li class="code-line" data-line="463">
<strong>前提</strong>・・・ 修正を書いた人やエージェントが「原因はこれだ」と当然のように考えていたことを指す</li>
</ul>
</div></aside>

たとえば、エージェントが「処理が遅いのはデータ量が多いせいだ」と考えて、1回目も2回目も一度に扱うデータ量を減らす修正を行い、どちらも同じテストに落ちたケースを考えてみましょう。

データ量が原因なら、データ量を減らせばテストは通るはずです。しかし、テストは2回とも通らなかったので、遅さの原因がデータ量ではない可能性が考えられます。そこでエージェントは、3回目の修正を書く前に、「データ量が多いせいだ」という考え自体を疑います。同じ前提に立つ修正が失敗するたびに、<strong>その失敗が前提そのものについての証拠になる</strong>ため、エージェント自身が前提を疑うことができます。

『<strong>Redesign from First Principles</strong>』が新しい要件を中心に設計を組み直すのに対し、この原則は、<strong>今の設計が「当然のこと」として扱っている前提を疑います</strong>。

<a id="%E3%83%AB%E3%83%BC%E3%83%AB%EF%BC%9A%E7%9B%B4%E3%81%99%E5%89%8D%E3%81%AB%E5%89%8D%E6%8F%90%E3%82%92%E6%9B%B8%E3%81%8D%E5%87%BA%E3%81%97%E3%80%81%E5%81%8F%E3%82%8A%E3%82%92%E6%95%B0%E3%81%88%E3%82%8B"></a>


### ルール：直す前に前提を書き出し、偏りを数える

<a id="%E5%89%8D%E6%8F%90%E3%82%92%E6%9B%B8%E3%81%8D%E5%87%BA%E3%81%99"></a>


#### 前提を書き出す

失敗したすべての修正が当然としていた前提を、一文で書き出します。書き出すことで、疑う対象がはっきりします。

<a id="%E6%AC%A1%E3%81%AE%E4%BF%AE%E6%AD%A3%E3%81%AE%E5%89%8D%E3%81%AB%E3%80%81census-%E3%82%92%E5%8F%96%E3%82%8B"></a>


#### 次の修正の前に、census を取る

<strong>census</strong>（直訳すると「人口調査」）は、偏りを、主体（同時に動いて処理を進めるWorkerやエージェント）ごとに数えた内訳です。

たとえば、4つのWorkerで仕事を分けて処理しているなら、Workerごとに未処理の件数を数え、「Worker1は30件、Worker2〜4は2件ずつ」のような内訳を作ります。censusで分かるのは、偏りの大きさではなく、どの主体に偏りが集まっているか（この例ではWorker1）です。

エージェントは、censusを取る処理を、何度でも実行し直せるスクリプトとして書きます。これは、本章の最後で扱う[『Build the Lever』](#%E3%80%8Ebuild-the-lever%E3%80%8F%E3%81%AF%E3%80%81%E6%89%8B%E4%BD%9C%E6%A5%AD%E3%81%A7%E3%81%AF%E3%81%AA%E3%81%8F%E4%BD%9C%E6%A5%AD%E3%82%92%E3%81%99%E3%82%8B%E9%81%93%E5%85%B7%E3%82%92%E4%BD%9C%E3%82%8B)に沿ったやり方です。

<a id="%E5%81%8F%E3%82%8A%E6%96%B9%E3%82%92%E8%AA%AD%E3%82%80"></a>


#### 偏り方を読む

<strong>何度実行しても同じ少数の主体に偏りが集まるなら、設定やコードなどのどこかが、その主体に、偏りを生む役割を割り当てています</strong>。エージェントは、その割り当てを探します。

その割り当てが、次に問うべき「なぜ」です。  
これは、『[<strong>Fix Root Causes</strong>](https://github.com/cursor/plugins/blob/main/pstack/skills/principle-fix-root-causes/SKILL.md)』（「なぜ」を重ねて症状ではなく根本原因を直す原則。[第19章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/1fb019)）の考え方です。

<a id="%E5%81%8F%E3%82%8A%E3%82%92%E5%BE%8C%E3%81%8B%E3%82%89%E8%A3%9C%E3%82%8F%E3%81%9A%E3%80%81%E5%81%8F%E3%82%8A%E3%82%92%E7%94%9F%E3%82%80%E5%89%B2%E3%82%8A%E5%BD%93%E3%81%A6%E3%81%9D%E3%81%AE%E3%82%82%E3%81%AE%E3%82%92%E3%81%AA%E3%81%8F%E3%81%99"></a>


#### 偏りを後から補わず、偏りを生む割り当てそのものをなくす

以下のいずれかの方法で、毎回同じ主体がその役割を持たないようにします。

- 役割を主体の間で順番に交代させる
- 割り当てをランダムにする
- 役割を別の場所へ移す

たとえば、最初の仕事の束がいつも1番目のWorkerに渡る設定なら、渡す相手を毎回替えます。

後から補う仕組みを追加しても、偏りを生む割り当ては残ったままで、実行のたびに余分な仕事が増えるだけだからです（『<strong>Laziness Protocol</strong>』）。後から補う仕組みとは、手の空いたWorkerがほかのWorkerの仕事を取りに行く仕組み、全員で仕事を出し合う共有の置き場、仕事をまとめて受け渡す仕組み、定期的な配り直しなどです。

<a id="%E5%89%8D%E6%8F%90%E3%81%A8census%E3%81%8C%E3%81%A7%E3%81%8D%E3%82%8B%E3%81%BE%E3%81%A7%E3%80%81%E6%AC%A1%E3%81%AE%E4%BF%AE%E6%AD%A3%E3%82%92%E5%A7%8B%E3%82%81%E3%81%AA%E3%81%84"></a>


#### 前提とcensusができるまで、次の修正を始めない

エージェントは、前提を書き出し、censusができあがるまで、次の修正を始めません。censusの内訳が主体の間で均等なら、その前提は原因ではありません。その場合、エージェントは原因を別の場所で探し、censusは証拠として残します。

<aside class="msg message"><span class="msg-symbol">!</span><div class="msg-content">
<p class="code-line" data-line="510">たとえば、複数のWorkerでキューを処理し、「上限時間内にキューが空になる」というテストに2回落ちたケースを考えてみましょう。</p>
<p class="code-line" data-line="512">まず、エージェントは各回で次の処理を追加します。</p>
<ul class="code-line" data-line="514">
<li class="code-line" data-line="514">1回目・・・ 手の空いたWorkerがほかのWorkerの仕事を取りに行く仕組みを追加</li>
<li class="code-line" data-line="515">2回目・・・ 定期的に仕事を配り直す仕組みを追加</li>
</ul>
<p class="code-line" data-line="517">どちらも「一部のWorkerに仕事が溜まるのは、仕事ごとの大きさ（処理にかかる時間）がばらばらだからだ」という同じ前提に立っています。</p>
<p class="code-line" data-line="519">次にエージェントは、3つ目の修正を書く前に、実行ログからWorkerごとの未処理件数を数えるスクリプトを書きます。</p>
<p class="code-line" data-line="521">仕事の大きさのばらつきが原因なら、仕事が溜まるWorkerは実行ごとに変わるはずです。<br/>
しかし、3回の実行のどれでもWorker1の未処理件数だけが多いなら、前提は当たっていない、ということになります。次の「なぜ」は、「何がWorker1にその役割を割り当てているのか？」です。</p>
<p class="code-line" data-line="524">その何かは、たとえば、最初の仕事の束を常にWorker1が受け取る設定などが挙げられます。</p>
</div></aside>

<a id="%E7%99%BA%E7%81%AB%E6%9D%A1%E4%BB%B6-5"></a>


### 発火条件

一つの前提を共有する2つ以上の修正が、同じgateで落ちたときです。

<a id="%E3%80%8Eoutcome-oriented-execution%E3%80%8F%E3%81%AF%E3%80%81%E7%A7%BB%E8%A1%8C%E9%80%94%E4%B8%AD%E3%81%AE%E3%82%B3%E3%83%BC%E3%83%89%E3%81%AE%E6%95%B4%E5%90%88%E6%80%A7%E3%82%92%E4%BF%9D%E3%81%A4%E3%81%9F%E3%82%81%E3%81%AE%E4%B8%80%E6%99%82%E7%9A%84%E3%81%AA%E3%82%B3%E3%83%BC%E3%83%89%E3%82%88%E3%82%8A%E3%80%81%E7%A2%BA%E3%81%8B%E3%82%81%E3%82%89%E3%82%8C%E3%82%8B%E6%9C%80%E7%B5%82%E5%BD%A2%E3%82%92%E5%84%AA%E5%85%88%E3%81%99%E3%82%8B"></a>


## 『Outcome-Oriented Execution』は、移行途中のコードの整合性を保つための一時的なコードより、確かめられる最終形を優先する

原則『<strong>Outcome-Oriented Execution</strong>』は、移行途中のコードをなめらかに動く状態に保つことより、<strong>最後に目指す形（最終形）にたどり着き、それが正しいと確かめられること</strong>を優先するよう定めます。途中のすべての段階を動く状態に保とうとすると、<strong>古い形と新しい形の両方で動かすための一時的な互換コードが生まれ、それが消されずに長く残って負債になりやすい</strong>からです。

たとえば、設定ファイルを古い形式から新しい形式へ移すときに、途中のどの段階でもどちらの形式でも読めるように、古い形式を新しい形式に変換する橋渡しのコードを書くとします。

移行が終われば古い形式は使われなくなり、このコードは要らなくなるはずが、消し忘れられたり、まだ古い形式が残っているかもしれないという懸念から、残りがちです。この原則に従うエージェントは、そうしたコードで途中の整合性を保つより、目指す形へ進みます。そして、検証の境界（あらかじめ決めておいた、正しさを確かめる区切り）で正しさを証明します。

<a id="%E3%83%AB%E3%83%BC%E3%83%AB%EF%BC%9A%E9%80%94%E4%B8%AD%E3%81%A7%E5%A3%8A%E3%82%8C%E3%81%A6%E3%82%88%E3%81%84%E5%A0%B4%E6%89%80%E3%82%92%E5%85%88%E3%81%AB%E6%B1%BA%E3%82%81%E3%80%81%E6%9C%80%E5%BE%8C%E3%81%AB%E5%85%A8%E9%83%A8%E3%82%92%E7%A2%BA%E3%81%8B%E3%82%81%E3%82%8B"></a>


### ルール：途中で壊れてよい場所を先に決め、最後に全部を確かめる

- 途中で一時的に動かなくなることは、それが計画どおりで、範囲が限られていて、元に戻せるときだけ許します。
- どこなら一時的に壊れてよいかを、先に宣言します。たとえば、「移行の途中は、管理画面の検索が動かなくてよい」と計画に書きます。
- 移行の途中でも、いま手を入れている箇所には、問題が起きたらすぐに分かるチェックを残します。
- 計画の最後には、コードを動かさずに行う検証（型のチェックなど）と、実際に動かして確かめる検証を、両方とも完全に通します。

この原則は、途中で壊すことを無条件に許すものではなく、<strong>壊してよい場所を計画に先に書いて宣言する</strong>ことを求めます。

<a id="%E7%99%BA%E7%81%AB%E6%9D%A1%E4%BB%B6-6"></a>


### 発火条件

段階の区切りがあらかじめ決まっている、計画済みの書き直しや移行の最中です。エージェントは、区切りのない普段の小さな修正にはこの原則を使いません。

<aside class="msg message"><span class="msg-symbol">!</span><div class="msg-content">
<p class="code-line" data-line="553">段階の区切り（原文では <strong>phase boundaries</strong>）とは、大きな作業をいくつかの段階に分けたときの、段階と段階の境目のことです。</p>
<p class="code-line" data-line="555">たとえば、設定ファイルの形式を移す場合、以下のように段階を分け、各段階の終わりで、正しく動くかを確かめます。</p>
<ol class="code-line" data-line="557">
<li class="code-line" data-line="557">新しい形式を読めるようにする</li>
<li class="code-line" data-line="558">すべての設定ファイルを新しい形式に書き換える</li>
<li class="code-line" data-line="559">古い形式を読む処理を消す</li>
</ol>
</div></aside>

<a id="%E3%80%8Eexperience-first%E3%80%8F%E3%81%AF%E3%80%81%E5%AE%9F%E8%A3%85%E3%81%AE%E9%83%BD%E5%90%88%E3%82%88%E3%82%8A%E3%83%A6%E3%83%BC%E3%82%B6%E3%83%BC%E3%81%AE%E4%BD%93%E9%A8%93%E3%82%92%E9%81%B8%E3%81%B6"></a>


## 『Experience First』は、実装の都合よりユーザーの体験を選ぶ

原則『<strong>Experience First</strong>』は、<strong>作る側にとって楽な方法と、ユーザーの体験を良くする方法が衝突したら、ユーザーの体験を良くする方法を選ぶ</strong>よう定めます。よく仕上げた3つの機能は、粗い10の機能に勝ります。また、設計の判断は、本番のコードで試すより、使い捨てのHTMLで試すほうが安く済みます。

<a id="%E3%83%AB%E3%83%BC%E3%83%AB%EF%BC%9A%E6%A9%9F%E8%83%BD%E3%82%92%E5%B0%91%E3%81%AA%E3%81%8F%E3%80%81%E3%82%88%E3%81%8F%E4%BD%9C%E3%82%8B"></a>


### ルール：機能を少なく、よく作る

<a id="%E3%81%99%E3%81%B9%E3%81%A6%E3%81%AE%E6%A9%9F%E8%83%BD%E3%80%81%E6%93%8D%E4%BD%9C%E3%80%81%E9%81%B8%E6%8A%9E%E8%82%A2%E3%81%AB%E7%90%86%E7%94%B1%E3%82%92%E6%8C%81%E3%81%9F%E3%81%9B%E3%82%8B"></a>


#### すべての機能、操作、選択肢に理由を持たせる

画面に置くボタンや設定の選択肢の一つひとつについて、なぜ必要かを説明できるようにします。

<a id="%E6%A9%9F%E8%83%BD%E3%82%92%E5%B0%91%E3%81%AA%E3%81%8F%E4%BD%9C%E3%82%8A%E3%80%81%E3%82%88%E3%81%8F%E4%BD%9C%E3%82%8B"></a>


#### 機能を少なく作り、よく作る

粗い機能を10個そろえるより、よく仕上げた3つの機能を作ります。

<a id="%E6%B1%BA%E3%82%81%E3%82%8B%E5%89%8D%E3%81%AB%E3%83%97%E3%83%AD%E3%83%88%E3%82%BF%E3%82%A4%E3%83%97%E3%82%92%E4%BD%9C%E3%82%8B"></a>


#### 決める前にプロトタイプを作る

本番のコードを書く前に、使い捨てのHTMLなどでプロトタイピングし、プロトタイプを触って、実際に確かめてから、どういう設計にするかを決めます。本番のコードで作り直すより、プロトタイプの段階で間違いに気づくほうが安く済むからです。

<a id="%E7%B4%B0%E9%83%A8%E3%82%92%E6%AD%A3%E3%81%97%E3%81%8F%E3%81%99%E3%82%8B"></a>


#### 細部を正しくする

画面の切り替わり方、要素の揃え方、余白、操作への反応、エラー時の表示を正しくします。

たとえば、保存に失敗したときに何も表示しないのではなく、何が起きたかを表示します。

<a id="%E3%83%A6%E3%83%BC%E3%82%B6%E3%83%BC%E3%81%8C%E4%B8%BB%E3%81%AB%E8%A1%8C%E3%81%86%E4%BD%9C%E6%A5%AD%E3%81%AE%E6%B5%81%E3%82%8C%E3%82%92%E4%B8%AD%E5%BF%83%E3%81%AB%E3%81%99%E3%82%8B"></a>


#### ユーザーが主に行う作業の流れを中心にする

すべての機能は、ユーザーが主に行う作業の流れに役立つか、その流れの邪魔をしないか、のどちらかにします。

<a id="%E5%BD%B1%E9%9F%BF%E3%81%AF%E3%83%A6%E3%83%BC%E3%82%B6%E3%83%BC%E3%81%AE%E8%A6%96%E7%82%B9%E3%81%A7%E8%AA%AC%E6%98%8E%E3%81%99%E3%82%8B"></a>


#### 影響はユーザーの視点で説明する

原則のいうユーザーは、作ったものを使う人すべてです。画面ならアプリを使う人、ライブラリや内部APIならそれを import する同僚が該当し、次にそのコードを保守するエンジニアもユーザーに含まれます。

たとえば、「APIの応答の形式を変えた」ではなく、「一覧画面が今までより速く表示される」のように、ユーザーから見て何が変わるかで説明します。

この原則は、2つの原則の役割を分けています。『<strong>Foundational Thinking</strong>』は作業の順番を決め、『<strong>Experience First</strong>』は目指す形を決めます。そのうえで、CI、テスト基盤、共有の型などの土台も、ユーザーの体験を良くするためにあると考えます。

<a id="%E7%99%BA%E7%81%AB%E6%9D%A1%E4%BB%B6-7"></a>


### 発火条件

プロダクト、UX、機能の範囲について、どちらかを取ればどちらかを諦める、トレードオフの選択が出てきたときです。

<a id="%E3%80%8Eexhaust-the-design-space%E3%80%8F%E3%81%AF%E3%80%81%E5%89%8D%E4%BE%8B%E3%81%AE%E3%81%AA%E3%81%84%E8%A8%AD%E8%A8%88%E3%81%A7%E3%81%AF2%E3%80%9C3%E6%A1%88%E3%82%92%E4%BD%9C%E3%81%A3%E3%81%A6%E6%AF%94%E3%81%B9%E3%82%8B"></a>


## 『Exhaust the Design Space』は、前例のない設計では2〜3案を作って比べる

原則『<strong>Exhaust the Design Space</strong>』は、コードベースに前例のない操作や設計判断では、<strong>実装の前に、具体的な代案をいくつか試す</strong>ことを求めます。間違ったものを作ってしまうコストのほうが、3つの案を試すコストより大きいからです。

<a id="%E3%83%AB%E3%83%BC%E3%83%AB%EF%BC%9A%E5%BD%A2%E3%81%AE%E9%81%95%E3%81%862%E3%80%9C3%E6%A1%88%E3%82%92%E4%B8%A6%E3%81%B9%E3%81%A6%E6%AF%94%E3%81%B9%E3%82%8B"></a>


### ルール：形の違う2〜3案を並べて比べる

正解がはっきりしない設計では、エージェントは、互いに競う形の違う案（原文では competing prototypes）を2〜3個作り、比べてから、どの案を採用するかを決めます。案は、実際に触れるプロトタイプか、下書きの形で作ります。この規則は「Design it twice（二度設計せよ）」の別名でもあります。

重要なのは、<strong>案どうしの形が根本的に違うこと</strong>です。1つ目の案を少し変えただけのものは、2つ目の案として数えません。形の違う案を比べてはじめて、どちらの形がユーザーに合っているかが分かるからです。

たとえば、会員登録の画面を作るなら、次の2つは形が違うので、別の案になります。

<img alt="会員登録の2つの案。案Aは1ページに名前・メールアドレス・パスワードの入力欄をまとめて並べ、案Bは1項目ずつ3つの画面を切り替えて順番に聞く" class="md-img" loading="lazy" src="https://static.zenn.studio/user-upload/802fac6e0ca9-20260926.png"/>

一方、案Aのボタンの色や位置を変えただけのものは、画面の形が案Aと同じなので、別の案にはなりません。

<a id="%E7%99%BA%E7%81%AB%E6%9D%A1%E4%BB%B6-8"></a>


### 発火条件

- コードベースにまだ同じような前例がない、新しいUIの操作を作るとき
- 実現できる方法が複数あるアーキテクチャを選ぶとき
- 使い心地が理屈より感覚で決まる、プロダクトの設計を判断するとき

逆に、次の変更には、この原則は当てはまりません。

- やり方が確立した機械的な実装
- 目指す状態がはっきりした不具合修正やリファクタリング
- 制約から、実現できる方法が1つに決まる変更

<a id="%E4%BE%9D%E9%A0%BC%E3%81%AE%E4%BE%8B%EF%BC%9A%E3%83%97%E3%83%AD%E3%83%88%E3%82%BF%E3%82%A4%E3%83%97%E3%82%922%E3%81%A4%E4%BD%9C%E3%81%A3%E3%81%A6%E6%AF%94%E3%81%B9%E3%82%8B"></a>


### 依頼の例：プロトタイプを2つ作って比べる

次の依頼例は、pstackの README にあるものです。この依頼では、エージェントが『[<strong>Prototype</strong>](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/playbooks/prototype.md)』Playbookに入るので、プロトタイプを捨てる前提で作ります。

```
/poteto-mode build two prototypes of the markdown renderer so we can compare. spawn an agent for each.
// 比べられるように、markdown レンダラーのプロトタイプを2つ作って。それぞれにエージェントを1つずつ立てて。
```

<a id="%E3%80%8Ebuild-the-lever%E3%80%8F%E3%81%AF%E3%80%81%E6%89%8B%E4%BD%9C%E6%A5%AD%E3%81%A7%E3%81%AF%E3%81%AA%E3%81%8F%E4%BD%9C%E6%A5%AD%E3%82%92%E3%81%99%E3%82%8B%E9%81%93%E5%85%B7%E3%82%92%E4%BD%9C%E3%82%8B"></a>


## 『Build the Lever』は、手作業ではなく作業をする道具を作る

原則『<strong>Build the Lever</strong>』（直訳すると「てこを作る」）は、作業が簡単でないなら、手でやらずに、<strong>その作業をする道具か、作業が正しいことを証明する道具を作る</strong>よう定めます。

道具を作る利点は2つあります。

1つ目は処理量です。codemod（コードを機械的に書き換えるスクリプト）やスクリプトは、何度実行しても、毎回同じやり方で作業します。そのため、エージェントは、対象のファイルが100個あっても、手作業のように1つずつ時間をかけずに済みます。

途中でやり方を直したときや、対象のファイルが増えたときも、エージェントはスクリプトを実行し直すだけで、すべてのファイルを同じやり方で処理し直せます。

2つ目は正確性です。レビューする人は、道具のコードを読み、実際に実行し直せば、作業が正しいかを自分で確かめられます。

一方、手でやった変更には、どんな手順で書き換えたかが残りません。そのため、レビューする人が正しさを確かめ直すには、同じ作業を自分でもう一度やるしかありません。100個のファイルを手で書き換えた変更なら、レビューする人も100個を1つずつ見直すことになり、時間がかかるうえに、見落としも起きやすくなります。

この原則は、2つ目の利点を、「決定的なスクリプトは「信じて」を「これを実行して」に変える」、とまとめています。

<ul class="code-line" data-line="656">
<li class="code-line" data-line="656">
<strong>決定的なスクリプト</strong>・・・ 同じ入力に対して、毎回同じ結果を出すスクリプトのこと</li>
<li class="code-line" data-line="657">
<strong>「信じて」を「これを実行して」に変える</strong>・・・ 手作業の結果はレビューする人に信じてもらうしかありませんが、スクリプトならレビューする人が自分で実行し直して結果を確かめられる、ということ</li>
</ul>

### ルール：最初の1回を手でやって手順を学んでから道具を作る

<a id="%E6%9C%80%E5%88%9D%E3%81%AE1%E5%9B%9E%E3%81%AF%E6%89%8B%E3%81%A7%E3%82%84%E3%82%8A%E3%80%81%E3%81%9D%E3%82%8C%E3%81%8B%E3%82%89%E9%81%93%E5%85%B7%E3%82%92%E4%BD%9C%E3%82%8B"></a>


#### 最初の1回は手でやり、それから道具を作る

たとえば、100個のファイルで古い関数名を新しい関数名に書き換えるなら、まず1つのファイルを手で書き換えて手順を確かめ、それから書き換えのスクリプトを作ります。

次に、そのスクリプトを最初のファイルに対して実行し、手で書き換えた結果と一致するかを比べて、スクリプトが正しいことを証明します。道具は、何度実行し直しても安全なように作ります。

<a id="%E4%BD%9C%E6%A5%AD%E3%81%AB%E5%90%88%E3%81%A3%E3%81%9F%E9%81%93%E5%85%B7%E3%82%92%E9%81%B8%E3%81%B6"></a>


#### 作業に合った道具を選ぶ

編集にはcodemodかスクリプト、繰り返しの多いファイルにはジェネレータ、分析にはデータをSQLiteに書き出して調べるクエリ、検証には何度でも実行できるスクリプトを使います。

<a id="%E3%82%B9%E3%82%AF%E3%83%AA%E3%83%97%E3%83%88%E3%81%A7%E3%81%A7%E3%81%8D%E3%82%8B%E3%81%93%E3%81%A8%E3%81%AF%E3%82%B9%E3%82%AF%E3%83%AA%E3%83%97%E3%83%88%E3%81%A7%E8%A1%8C%E3%81%84%E3%80%81%E8%A4%87%E6%95%B0%E3%81%AE%E3%82%B5%E3%83%96%E3%82%A8%E3%83%BC%E3%82%B8%E3%82%A7%E3%83%B3%E3%83%88%E3%81%AB%E5%88%86%E3%81%91%E3%81%A6%E4%BB%BB%E3%81%9B%E3%81%AA%E3%81%84"></a>


#### スクリプトでできることはスクリプトで行い、複数のサブエージェントに分けて任せない

スクリプトが一度ですべての単位を処理できるなら、スクリプトを自分で実行します。サブエージェントに1つずつ手作業で行わせるより、同じ結果を毎回出すスクリプトのほうが確実だからです。

<a id="%E3%82%B5%E3%83%96%E3%82%A8%E3%83%BC%E3%82%B8%E3%82%A7%E3%83%B3%E3%83%88%E3%81%AB%E9%85%8D%E3%82%8B%E3%81%A8%E3%81%8D%E3%81%AF%E3%80%81%E6%89%8B%E9%A0%86%E6%9B%B8%E3%82%92skill%E3%81%A8%E3%81%97%E3%81%A6%E6%9B%B8%E3%81%8F"></a>


#### サブエージェントに配るときは、手順書をSkillとして書く

作業をサブエージェントに配るときは、全員が読む手順書をSkillとして書き、作業の手順、確かめ方、触ってはいけない範囲を1つにまとめます。

このSkillは、サブエージェントが書き換えられない場所に置き、サブエージェントが、決めた手順や確かめ方を黙って書き換えられないようにします。

<a id="%E4%BD%9C%E3%82%8B%E3%81%AE%E3%81%AF%E3%83%95%E3%83%AC%E3%83%BC%E3%83%A0%E3%83%AF%E3%83%BC%E3%82%AF%E3%81%A7%E3%81%AF%E3%81%AA%E3%81%8F%E3%80%81%E6%9C%80%E5%B0%8F%E3%81%AE%E3%82%B9%E3%82%AF%E3%83%AA%E3%83%97%E3%83%88%E3%81%AB%E3%81%99%E3%82%8B"></a>


#### 作るのはフレームワークではなく、最小のスクリプトにする

作業をする、または正しさを証明する最小のスクリプトだけを作ります（『<strong>Laziness Protocol</strong>』）。

<a id="%E4%BD%9C%E6%A5%AD%E3%81%8C%E3%82%BB%E3%83%83%E3%82%B7%E3%83%A7%E3%83%B3%E3%82%92%E3%81%BE%E3%81%9F%E3%81%84%E3%81%A7%E7%B6%9A%E3%81%8F%E3%81%AA%E3%82%89%E3%80%81%E9%81%93%E5%85%B7%E3%82%92%E3%82%B3%E3%83%9F%E3%83%83%E3%83%88%E3%81%99%E3%82%8B"></a>


#### 作業がセッションをまたいで続くなら、道具をコミットする

次のセッションでも同じ道具を使えるように残します。

最初の1回から道具で全体を処理するまでの流れを図にすると、次のようになります。

```
1回目を手で行い、手順を学ぶ
   ↓
道具（codemod、スクリプトなど）を作る
   ↓
道具で1回目の再実行をし、手でやった版と出力を比べる
   ↓ 一致したら
道具を自分で実行し、残りのすべての単位を処理する
（サブエージェントに1つずつ手作業で行わせない）
```

<strong>エージェントがこの原則を適用すると、差分に道具のファイルが加わります</strong>。エージェントが原則を引用したのに、差分にcodemod、スクリプト、ジェネレータ、委任用のSkillのどれもなければ、エージェントはこの原則を適用していません。

道具やスクリプトを作る点で、この原則と似た原則が2つあります。取り違えないよう、それぞれが何を対象にするかを示します。

### 発火条件

編集、移行、分析、チェックを問わず、簡単ではないすべての作業です。

エージェントが道具を作らなくてよいのは、見ればすぐ分かる数か所の修正のような、簡単な作業だけです。

また、道具を作るかどうかを、同じ作業を何回繰り返すかではなく、作業が簡単かどうかで決めます。ここでいう簡単な作業とは、変更する箇所が少なく、見ただけで正しいと分かる作業のことです。

変更する箇所が多い作業や、正しいかを確かめる手順が多い作業は、1回きりでも簡単な作業ではありません。そのため、エージェントは、1回きりの作業でも、道具があれば正しさを確かめられるなら、道具を作ります。

### 依頼の例：席を外している間に移行を任せる

pstackの README には、次の依頼例があります。README では `/figure-it-out` の例として挙がっていますが、振る舞いを変えない移行を任せるこの依頼は、道具が役立つ場面だと本書では考えます。

```
/poteto-mode i'm stepping away. migrate every caller from the synchronous store to the new async one, keeping behavior identical. i want to trust it was done right when i'm back.
// 席を外す。すべての呼び出し元を、同期ストアから新しい非同期ストアへ移して。振る舞いは同じに保って。戻ったとき、正しくできたと信じられるようにしたい。
```

## まとめ

- Principleは、今の変更を入れるか、まだ完了ではないかを決める判断の基準です。人間は、依頼に原則の名前を書くことで、エージェントの作業の方向を修正できます。
- コードを減らす原則は、『<strong>Laziness Protocol</strong>』、『<strong>Subtract Before You Add</strong>』、『<strong>Minimize Reader Load</strong>』の3つです。
- 設計の置き方は、『<strong>Foundational Thinking</strong>』（データの形と土台を先に決める）、『<strong>Redesign from First Principles</strong>』（要件が最初からあったつもりで設計し直す）、『<strong>Attack the Premise</strong>』（同じテストに落ち続ける修正の前提を疑う）、『<strong>Outcome-Oriented Execution</strong>』（壊してよい場所を宣言して最終形へ進む）の4つが決めます。
- 何を目指すかは、『<strong>Experience First</strong>』（ユーザーの体験を選ぶ）と『<strong>Exhaust the Design Space</strong>』（前例のない設計では形の違う案を比べる）が決めます。
- 『<strong>Build the Lever</strong>』は、作業を実行し直せる道具に変えます。エージェントが原則を引用しても、差分に道具がなければ、原則を適用したことになりません。

次の[第18章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/cdc49b)では、Architectureの6原則を扱います。どれも、「データや確認をコードのどこに置くか」を決める原則です。
