この章では、[`/tdd`](https://github.com/cursor/plugins/blob/main/pstack/skills/tdd/SKILL.md) を扱います。

`/tdd` は、エージェントが、不具合を直す前に、その不具合があるうちは失敗するテストを先に書くためのSkillです。たとえば、「再試行すると、通知が2通届く」という不具合なら、エージェントは「通知は1通だけ届く」ことを確かめるテストを書きます。このテストは、直す前は失敗し、直した後に通ります。

`/tdd` は、[第29章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/4f9a46)から続く、コードの品質を保つ3つのSkillの2つ目です。`/tdd` で、コードを書いたエージェントの代わりに修正を確かめるのは、修正前に失敗し、修正後に通る回帰テストです。

この章では、`/tdd` を、役割、使いどき、手順、依頼の書き方の4つの観点で解説します。

<a id="%E3%81%93%E3%81%AE%E7%AB%A0%E3%81%AE%E6%A7%8B%E6%88%90"></a>


## この章の構成

この章の構成は次のとおりです。

- 役割：不具合を直す前に、壊れた挙動をテストで再現する
- 使いどき：利用者がTDDを頼んだときか、手軽に書けるテストの当てがあるときだけ
- 手順：直す前に「正しい理由で失敗する」ことを確かめる
- 依頼の書き方：コマンドだけで足りる
- まとめ

<a id="%E5%BD%B9%E5%89%B2%EF%BC%9A%E4%B8%8D%E5%85%B7%E5%90%88%E3%82%92%E7%9B%B4%E3%81%99%E5%89%8D%E3%81%AB%E3%80%81%E5%A3%8A%E3%82%8C%E3%81%9F%E6%8C%99%E5%8B%95%E3%82%92%E3%83%86%E3%82%B9%E3%83%88%E3%81%A7%E5%86%8D%E7%8F%BE%E3%81%99%E3%82%8B"></a>


## 役割：不具合を直す前に、壊れた挙動をテストで再現する

`/tdd` は、不具合を直す前に回帰テスト（直した不具合が再び起きていないかを確かめるテスト）を一つ書き、そのテストが修正前に失敗し、修正後に通ることを確かめるSkillです。

名前はTDD（テスト駆動開発）ですが、`SKILL.md` の題が「TDD Bug Fix」であるとおり、<strong>新機能の設計をテストから進める手引きではなく、不具合の修正だけを扱うSkill</strong>です。

`/tdd` は、テストを必ず先に書くことは求めません。<strong>エージェントがテストを先に書くのは、利用者が頼んだときか、手軽に書けるテストの当てがあるときだけ</strong>です。

<a id="%E4%BD%BF%E3%81%84%E3%81%A9%E3%81%8D%EF%BC%9A%E5%88%A9%E7%94%A8%E8%80%85%E3%81%8Ctdd%E3%82%92%E9%A0%BC%E3%82%93%E3%81%A0%E3%81%A8%E3%81%8D%E3%81%8B%E3%80%81%E6%89%8B%E8%BB%BD%E3%81%AB%E6%9B%B8%E3%81%91%E3%82%8B%E3%83%86%E3%82%B9%E3%83%88%E3%81%AE%E5%BD%93%E3%81%A6%E3%81%8C%E3%81%82%E3%82%8B%E3%81%A8%E3%81%8D%E3%81%A0%E3%81%91"></a>


## 使いどき：利用者がTDDを頼んだときか、手軽に書けるテストの当てがあるときだけ

`/tdd` は `disable-model-invocation: true` の設定を持つので（[第25章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/46bd1f)）、エージェントが会話の内容から `/tdd` を選んで動かすことはありません。

`/tdd` を動かすのは、名前で呼ぶ利用者と、`/poteto-mode` です。[README](https://github.com/cursor/plugins/blob/main/pstack/README.md) は、`/poteto-mode` が、手順の中で必要になったときに `/tdd` を実行すると説明しています。

`SKILL.md` の説明（description）は、`/tdd` を使うのを次のケースだけに絞っています。

- 利用者がTDD、失敗するテスト、回帰テストのどれかの実装を依頼したとき
- 不具合を手元ですぐ実行できるテストで確かめられると分かっているとき

逆に言えば、以下のケースではエージェントは新しいテストを追加しません。

- テストの経路がはっきりしないとき
- 手間がかかるとき
- 多くの部品を組み合わせないとテストを書けないとき
- 頼まれていないとき

「手軽に書けるテストの当てがある」というのは、たとえば、不具合のあるコードにすでに単体テストがあり、そこへテストを1つ追加すれば済む場合などです。

<a id="%E5%A4%A7%E3%81%8C%E3%81%8B%E3%82%8A%E3%81%AA%E6%BA%96%E5%82%99%E3%81%8C%E8%A6%81%E3%82%8B%E3%81%AA%E3%82%89%E3%80%81%E3%83%86%E3%82%B9%E3%83%88%E3%82%92%E8%BF%BD%E5%8A%A0%E3%81%9B%E3%81%9A%E3%80%81%E6%9C%80%E3%82%82%E8%BF%91%E3%81%84%E7%A2%BA%E8%AA%8D%E6%89%8B%E6%AE%B5%E3%81%AB%E5%88%87%E3%82%8A%E6%9B%BF%E3%81%88%E3%82%8B"></a>


### 大がかりな準備が要るなら、テストを追加せず、最も近い確認手段に切り替える

前述した「手間がかかるとき」と「多くの部品を組み合わせないとテストを書けないとき」は、具体的には、テストを書くのに次のようなものが必要になるときです。

- 広い範囲にわたって新しく用意する、テストを動かすための仕組み（ハーネス）
- 実装が少し変わるだけで合わなくなる、壊れやすいモック
- 実行に時間のかかるE2Eテスト（アプリ全体を、ユーザーの操作どおりに通して確かめるテスト）の基盤
- 本番にしかない状態（例：本番のデータベースにだけあるデータ）
- あいまいな再現の手順
- 不具合と関係のない、テスト用データ（フィクスチャ）の大がかりな変更

こうしたものが必要なときは、エージェントは新しいテストを追加せず、最も近い確認手段（スクリプトや手動の再現コマンドなど）に切り替えます。

このような場合に、エージェントがテストを追加しないのは、<strong>こうした準備をして無理に書いたテストは、直ったことの証拠として弱い</strong>からです。

たとえば、壊れやすいモックを使って通したテストは、本物の部品の代わりにモックを確かめているだけなので、本物のコマンドを実行して確かめるより、直ったことを示す力が弱くなります（同梱ガイドの [`docs/guide/10-recipes-and-pitfalls.md`](https://github.com/cursor/plugins/blob/main/pstack/docs/guide/10-recipes-and-pitfalls.md)）。

<a id="%E3%80%8Ebug-fix%E3%80%8Fplaybook%E3%81%AF%E3%80%81%E6%89%8B%E8%BB%BD%E3%81%AA%E3%83%86%E3%82%B9%E3%83%88%E3%81%AE%E5%BD%93%E3%81%A6%E3%81%8C%E3%81%82%E3%82%8B%E3%81%A8%E3%81%8D%E3%81%A0%E3%81%91-%2Ftdd-%E3%82%92%E5%8F%82%E7%85%A7%E3%81%99%E3%82%8B"></a>


### 『Bug fix』Playbookは、手軽なテストの当てがあるときだけ `/tdd` を参照する

`/poteto-mode` も `/tdd` を使います。不具合修正の進め方を定めた『<strong>Bug fix</strong>』Playbookは、手順5で、不具合を再現するコミット（修正前のコードでは失敗するテストなど）を、Gitの履歴の上で、修正のコミットより前に置くよう求めています。そのうえで、手軽なテストの当てがあるときに、`/tdd` を参照しています。

ただし、このPlaybookも、テストに手間がかかるとき、多くの部品を組み合わせないとテストを書けないとき、テストの書き方がはっきりしないときは、`/tdd` を飛ばすよう定めています。

<a id="%E6%89%8B%E9%A0%86%EF%BC%9A%E7%9B%B4%E3%81%99%E5%89%8D%E3%81%AB%E3%80%8C%E6%AD%A3%E3%81%97%E3%81%84%E7%90%86%E7%94%B1%E3%81%A7%E5%A4%B1%E6%95%97%E3%81%99%E3%82%8B%E3%80%8D%E3%81%93%E3%81%A8%E3%82%92%E7%A2%BA%E3%81%8B%E3%82%81%E3%82%8B"></a>


## 手順：直す前に「正しい理由で失敗する」ことを確かめる

<a id="6%E6%AE%B5%E3%81%AE%E6%89%8B%E9%A0%86%E3%81%A7%E3%80%81%E4%BF%AE%E6%AD%A3%E5%89%8D%E3%81%AE%E5%A4%B1%E6%95%97%E3%81%8B%E3%82%89%E4%BF%AE%E6%AD%A3%E5%BE%8C%E3%81%AE%E6%88%90%E5%8A%9F%E3%81%BE%E3%81%A7%E3%82%92%E7%A2%BA%E3%81%8B%E3%82%81%E3%82%8B"></a>


### 6段の手順で、修正前の失敗から修正後の成功までを確かめる

`/tdd`の手順は6段です。

1. <strong>不具合を理解する</strong>・・・ エージェントは、意図した挙動、現在の挙動、不具合を起こす最小の再現（最も短い操作や入力）を特定します。
2. <strong>最も狭い範囲で確かめられるテストを選ぶ</strong>・・・ エージェントは、不具合のあるコードにすでに使われているテストの中から、不具合の箇所を最も狭い範囲で確かめられるテストを選びます。手軽に使えるテストが見つからなければ、この手順をこなすためだけに、新しくテストを一から作ることはしません。
3. <strong>失敗するテストを先に書く</strong>・・・ エージェントは、この不具合を見つけられる最小のテストを1つ追加します。テストの期待値には、本来あるべき挙動を書きます。たとえば、通知が2通届く不具合なら、今のコードが2通送るからといって、期待値を2にはせず、1にします。
4. <strong>修正前にテストを実行する</strong>・・・ エージェントは、テストが、意図した理由（不具合そのもの）で失敗することを確かめます。
5. <strong>不具合を直す</strong>・・・ エージェントは、テストではないアプリ本体のコードに、意図した挙動を満たす最小の変更を入れます。そのとき、周りのコードが前提にしている約束（関数の引数や戻り値の形など）は崩しません。
6. <strong>回帰テストを再実行する</strong>・・・ エージェントは、テストが通ることを確かめます。

手軽なテストが見つからないときと、修正前のテストが意図した理由で失敗しなかったときの分かれ道を図にすると、次のようになります。

### 修正前の実行で、不具合のせいで失敗しているかを見分ける

手順4で修正前にテストを実行するのは、テストが<strong>不具合のせいで失敗しているのか、別の理由で失敗しているのかを見分けるため</strong>です。

別の理由（関数名の書き間違いなど）で失敗しているテストは、不具合があってもなくても失敗します。そのため、この失敗は、そのテストが不具合を見つけられることの証拠になりません。

また、修正前に通ってしまうテストも、不具合を検出できていないので、エージェントはテストのほうを直します。

<a id="%E4%BE%8B%EF%BC%89%E9%80%9A%E7%9F%A5%E3%81%8C2%E9%80%9A%E5%B1%8A%E3%81%8F%E4%B8%8D%E5%85%B7%E5%90%88%E3%81%A7%E3%80%81%E6%AD%A3%E3%81%97%E3%81%84%E7%90%86%E7%94%B1%E3%81%AE%E5%A4%B1%E6%95%97%E3%81%A8%E5%88%A5%E3%81%AE%E7%90%86%E7%94%B1%E3%81%AE%E5%A4%B1%E6%95%97%E3%82%92%E6%AF%94%E3%81%B9%E3%82%8B"></a>


### 例）通知が2通届く不具合で、正しい理由の失敗と別の理由の失敗を比べる

たとえば、「再試行すると、通知が2通届く」という不具合を直すケースで、手順4の修正前の実行を見てみましょう。

テストは、「再試行しても、通知は1通だけ届く」という意図した挙動を確かめます。

```
declare function test(name: string, fn: () => void): void;
declare function expect<T>(actual: T): { toBe(expected: T): void };
// 確かめたい関数：通知を送り、失敗したら再試行する。送った通知の一覧を返す
declare function sendWithRetry(message: string): string[];

// 正しい理由で失敗するテスト：修正前は「1のはずが2だった」で失敗する
test("再試行しても、通知は1通だけ届く", () => {
  const sent = sendWithRetry("注文を受け付けました");
  expect(sent.length).toBe(1);
});

// 別の理由で失敗するテスト：関数名を書き間違えているので、不具合と関係なく失敗する
test("再試行しても、通知は1通だけ届く", () => {
  const sent = sendAndRetry("注文を受け付けました");
  expect(sent.length).toBe(1);
});
```

このように、修正前のテストが不具合とは別の理由で失敗しているなら、エージェントは、実装を直す前に、テストのほうを直す必要があります。

<a id="%E3%83%86%E3%82%B9%E3%83%88%E3%81%8C%E6%9B%B8%E3%81%91%E3%81%AA%E3%81%84%E3%81%A8%E3%81%8D%E3%82%82%E3%80%81%E5%AE%9F%E8%A1%8C%E3%81%A7%E3%81%8D%E3%82%8B%E7%A2%BA%E8%AA%8D%E3%81%AB%E7%BD%AE%E3%81%8D%E6%8F%9B%E3%81%88%E3%82%8B"></a>


### テストが書けないときも、実行できる確認に置き換える

テストを書くのが現実的でないときは、エージェントは、テストを、スクリプト、手動の再現コマンド、ブラウザ自動化、ログに期待した行が出たかの確認などの、実行できる確認に置き換えます。

<strong>エージェントは、テストを書かない場合も、確認そのものは省きません</strong>。確認を省くと、直ったことを示す証拠が何も残らないからです。

<a id="%E6%9C%80%E5%BE%8C%E3%81%AE%E5%A0%B1%E5%91%8A%E3%81%AB%E3%81%AF%E3%80%81%E7%B5%90%E6%9E%9C%E3%81%A0%E3%81%91%E3%81%A7%E3%81%AA%E3%81%8F%E4%BF%AE%E6%AD%A3%E5%89%8D%E5%BE%8C%E3%81%AE%E8%A8%BC%E6%8B%A0%E3%82%92%E6%9B%B8%E3%81%8F"></a>


### 最後の報告には、結果だけでなく修正前後の証拠を書く

エージェントは、最後の報告に、修正前にどのテスト（または確認）がどう失敗したかと、修正後に通った実行を書きます。修正前の失敗を示せなかったなら、その理由と、代わりに使った確認を書きます。

<strong>エージェントは、結果だけでなく、その証拠を報告します</strong>。「直りました」という結果だけでは、報告を読む人が、本当に直ったのかを確かめられないからです。

### 悪いテストを追加するくらいなら、新しいテストは追加しない

`/tdd` は、<strong>悪いテストを追加するくらいなら、新しいテストは追加しない</strong>という立場を取ります。

悪いテストとは、モックばかりを確かめるテストや、今の実装の細部を固定するテストなどです（[第19章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/1fb019)の原則『[<strong>Test Behavior, Not Implementation</strong>](https://github.com/cursor/plugins/blob/main/pstack/skills/principle-test-behavior-not-implementation/SKILL.md)』）。モックばかりを確かめるテストは本物の挙動を確かめておらず、実装の細部を固定するテストは、挙動を変えない書き換えでも壊れます。

2種類の悪いテストと良いテストを、通知が2通届く不具合の例で比べると、次のようになります。

```
declare function test(name: string, fn: () => void): void;
declare function expect<T>(actual: T): { toBe(expected: T): void };
type Transport = { send(message: string): void };
// 確かめたい関数：通知を送り、失敗したら再試行する。送った通知の一覧を返す
declare function sendWithRetry(message: string, transport?: Transport): string[];
// 送信の部品の偽物（モック）。send が呼ばれた回数を数える
declare const mockTransport: Transport & { calls: number };
// 関数の内部で使っている、再試行の回数を数える変数
declare const retryState: { attempts: number };

// 悪いテスト1（モックばかりを確かめる）：偽物の send が呼ばれた回数しか見ておらず、
// 実際に届いた通知の数を確かめていない
test("送信の部品を1回呼ぶ", () => {
  sendWithRetry("注文を受け付けました", mockTransport);
  expect(mockTransport.calls).toBe(1);
});

// 悪いテスト2（実装の細部を固定する）：内部の変数の値に頼るので、
// 届く通知の数を変えない書き換え（例：変数名の変更など）でも壊れる
test("再試行の回数が1回になる", () => {
  sendWithRetry("注文を受け付けました");
  expect(retryState.attempts).toBe(1);
});

// 良いテスト：外から見える挙動（届いた通知の数）を確かめる
test("再試行しても、通知は1通だけ届く", () => {
  const sent = sendWithRetry("注文を受け付けました");
  expect(sent.length).toBe(1);
});
```

エージェントは、テストを意図した挙動に合わせます。間違った実装に合わせてテストを変えることはしません。また、期待する挙動そのものが本当に変わり、その理由がはっきりしている場合を除き、既存のアサーション（`expect(sent.length).toBe(1)` のような、結果が期待どおりかを判定する記述）を弱めません。

```
declare const sent: string[];
declare function expect<T>(actual: T): {
  toBe(expected: T): void;
  toBeGreaterThanOrEqual(expected: number): void;
};

// 前：意図した挙動（通知は1通だけ届く）を確かめる
expect(sent.length).toBe(1);

// 後（してはいけない書き換え）：2通届く間違った実装でも通るよう、アサーションを弱めた
expect(sent.length).toBeGreaterThanOrEqual(1);
```

## 依頼の書き方：コマンドだけで足りる

直したい不具合を確かめる手軽なテストが書けて、その不具合について会話ですでに話していれば、利用者の依頼はコマンドだけで足ります（[`docs/guide/05-build-and-clean.md`](https://github.com/cursor/plugins/blob/main/pstack/docs/guide/05-build-and-clean.md)）。

```
/tdd implement
// /tdd で実装して
```

手軽に書けるテストがあるときだけ `/tdd` を使ってほしいなら、`docs/guide/10-recipes-and-pitfalls.md` にある次の依頼のように、条件を付けて書きます。

```
/poteto-mode repro the duplicate write first. if there's a cheap test path, /tdd it. then fix and rerun.
// まず二重書き込みを再現して。手軽なテストの経路があれば /tdd で。それから直して、再実行して。
```

「if there's a cheap test path」（手軽なテストの経路があれば）という条件が付いているので、手軽なテストがなければ、エージェントは `/tdd` を飛ばして、最も近い確認手段を使えます。

## まとめ

- <strong>確かめる役</strong>・・・ 修正前に失敗し、修正後に通る回帰テストが、修正を確かめます。
- <strong>使いどき</strong>・・・ 利用者が頼んだときか、手軽に書けるテストの当てがあるときだけ、失敗するテストを修正より先に書きます。
- <strong>手順</strong>・・・ 修正前にテストを実行し、不具合のせいで失敗することを確かめてから直します。

次の[第31章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/8960d3)では、コードの品質を保つ3つのSkillの3つ目として、差分のコメントを、書いた本人ではないエージェントに審査させる [`/no-comments`](https://github.com/cursor/plugins/blob/main/pstack/skills/no-comments/SKILL.md) を扱います。
