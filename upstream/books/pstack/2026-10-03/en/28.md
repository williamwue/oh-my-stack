This chapter covers the following four Skills.

1. [`/how`](https://github.com/cursor/plugins/blob/main/pstack/skills/how/SKILL.md)
2. [`/why`](https://github.com/cursor/plugins/blob/main/pstack/skills/why/SKILL.md)
3. [`/teach`](https://github.com/cursor/plugins/blob/main/pstack/skills/teach/SKILL.md)
4. [`/recall`](https://github.com/cursor/plugins/blob/main/pstack/skills/recall/SKILL.md)

All four Skills investigate the current code and past work. <strong>What you want to know decides which Skill you use</strong>.

Choose as follows.

- <strong>How it works now.</strong> Use `/how`, for example to learn which functions a run cancellation passes through and how it changes the database.
- <strong>Why it took that shape.</strong> Use `/why`, for example to learn why the retry limit is five.
- <strong>Both of those, as an explanation a person can follow.</strong> Use `/teach`, for example when you want to understand how this PR changes retries until you are convinced.
- <strong>Where the last session left off.</strong> Use `/recall`, for example to learn how far last week's export work got and what was reverted.

[Chapter 27](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/e23752) covers the Skills that look at what a finished change could break and at the weak points of a diff.

This chapter first lists the four Skills. It then explains each one from three angles: when to use it, its procedure, and its output. For the Skills whose source has example requests, I also show those examples.

At the end, I summarize how to choose between similar Skills and a Playbook.

## How this chapter is organized

This chapter is organized as follows.

- The four Skills at a glance
- `/how` explains code behavior before a change so that you can trace it in your head
- `/why` answers why code has its current shape, and separates reasons the records back from guesses
- `/teach` explains how code works and why, in plain terms, until a person is convinced
- `/recall` gathers the history of recent work so that you can resume from the last point of failure
- Choose among /how, /why, /teach, /recall, and "Session pickup" by the question you hold now
- Summary

All four are <strong>Skills that run only when someone calls them by name</strong>.

Each of the four `SKILL.md` files has a setting, `disable-model-invocation: true`, that stops the agent from picking the Skill on its own from the conversation. So the four run only when the user calls them by name, or when `/poteto-mode` or another Skill names them in its procedure.

The callers of the four Skills split as follows.

- <strong>`/how` and `/why`.</strong> `/poteto-mode` calls them as part of a Playbook's procedure. It also calls `/how` under the rules in the section "[Non-negotiables](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/SKILL.md#non-negotiables)". The user can also call them directly by name.
- <strong>`/teach` and `/recall`.</strong> They appear in none of the "Non-negotiables" rules of `/poteto-mode`, no Playbook procedure, and no other Skill's procedure. So they run only when the user calls them by name.

## `/how` explains code behavior before a change so that you can trace it in your head

`/how` is a Skill that explains code behavior <strong>at the level where a senior engineer new to the subsystem can replay it in their head</strong>.

<aside class="msg message"><span class="msg-symbol">!</span><div class="msg-content">
<p class="code-line" data-line="57"><strong>Subsystem</strong>: the part of an app that handles one coherent feature, such as run cancellation, login, or payments. It often spans several files or modules.</p>
</div></aside>

To replay it in your head means that the reader can trace what starts the process, which function in which file it passes through, and where the data flows, without opening the code.

The goal of the explanation is that the reader grasps the flow. So the explanation does not go into line-by-line detail, like comments attached to every line of source code.

For run cancellation, for example, the goal is that you can explain a flow like the one below without opening the code. The file and function names are examples for the explanation.

<a id="when-to-use-it%3A-explaining-code-behavior-and-asking-where-something-belongs"></a>


### When to use it: explaining code behavior and asking where something belongs

Use it before you change code, when you want to know how a subsystem behaves. For example, you may want to know which functions a run cancellation passes through, in order. Also use it for questions about where code belongs, such as "Where should this live?" or "Is this the right layer?" A layer here is a slice of code split by role, such as the UI, the API, or database access.

When you ask about motive, "Why did we build it this way?", use `/why` instead of `/how`.

<a id="procedure%3A-separate-the-role-that-gathers-facts-from-the-role-that-writes-the-explanation"></a>


### Procedure: separate the role that gathers facts from the role that writes the explanation

If the question is simple, for example a question confined to one module such as "How does function X work?", an <strong>explainer</strong> investigates and explains in one pass.

If the question spans several files or services, for example the structure of a whole subsystem, the agent splits the question into two to four angles and <strong>starts explorers in parallel</strong>. The explainer then combines their results.

An angle is a part of the same subsystem that does not overlap with the other parts when you investigate it separately. For run cancellation, for example, you split it into "accepting the cancellation", "stopping the run", and "updating the database".

If the agent is unsure whether a question is simple or complex, it treats the question as simple and investigates with the explainer alone, without starting explorers.

On either path, the explainer writes the explanation the user reads. The explorers gather only the facts that the explainer builds the explanation from.

An explorer returns a list of facts instead of prose: the components it found, the flow of processing, the files it read, the boundaries with other parts, and anything surprising.

The explainer writes the human-readable explanation separately, so an explorer ignores readability and puts depth and accuracy first.

An explorer does not fill unclear points or untraceable spots with invention. It writes down what it could not find out, for example "I could not tell how X connects to Y."

`/how` explains and changes nothing, so every `/how` subagent runs in a read-only mode that does not change files.

<a id="output%3A-write-under-five-headings%2C-from-overview-to-gotchas"></a>


### Output: write under five headings, from Overview to Gotchas

The goal of the explanation is that a person who does not know the area can start work with confidence after reading it.

So the explainer writes under the following five headings, which move from the big picture to the details and then to where work starts. It leaves out any heading that does not apply. The examples assume someone asked "How does run cancellation work?"

- <strong>Overview.</strong> What the mechanism is, what it does, and why it exists. The reader can read only this part and decide whether to read on. For example, the cancellation mechanism handles everything from the user's action to stopping the run.
- <strong>Key Concepts.</strong> The types and services the reader needs to follow the rest. Examples are the type that represents a run and the service that accepts a cancellation.
- <strong>How It Works.</strong> The longest part. It covers the trigger, the progression, and the data flow. For example, it shows which functions a cancellation request passes through in order and how the request changes the state in the database.
- <strong>Where Things Live.</strong> A short list of which files and directories hold what. It lists only what a person starting work in the area needs to open. For example, it lists `api/runs.ts`, which accepts the cancellation, and `services/runner.ts`, which stops the run.
- <strong>Gotchas.</strong> Points that are hard to notice from reading the code alone, surprising behavior, how the code got its current shape, and easy mistakes. For example, a cancellation does not stop a running process at once. The process stops after it finishes its current stage. So the process keeps going for a few seconds after the UI shows "Cancelled".

When processing spans several components, the explainer also adds a diagram. The diagram exists only to make the flow clearer. If the text alone gets the flow across, the explainer leaves the diagram out.

### Example requests: ask the question you actually have

Many Playbooks call `/how` in their procedures. The main ones are the following.

- "[Bug fix](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/playbooks/bug-fix.md)", which fixes a defect
- "[Feature](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/playbooks/feature.md)", which adds a feature
- "[Refactoring](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/playbooks/refactoring.md)", which reorganizes structure without a change in behavior

The "Non-negotiables" of `/poteto-mode` also say to use `/how` for a non-obvious change, for a design decision, and when you check "Is this really fine?"

Besides Playbooks, three Skills also call `/how` in their procedures: `/teach`, `/architect`, which decides a design ([Chapter 24](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/2df1db)), and `/no-comments`, which has another agent review the comments in a diff ([Chapter 31](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/347946)).

When you call it directly, ask the question you actually have. The example in the [README](https://github.com/cursor/plugins/blob/main/pstack/README.md) is the following.

```
/how do we cancel runs? do we have an n+1 when we look up every run to cancel?
```

The bundled guide [`03-understand.md`](https://github.com/cursor/plugins/blob/main/pstack/docs/guide/03-understand.md) covers `/how`, `/why`, `/teach`, and `/recall`. The guide warns the user not to skip these Skills on the thought that "the agent will read the code anyway".

The guide gives this warning because <strong>an agent that starts editing without tracing the code's behavior tends to fix only the symptom at the first plausible spot it finds, instead of the root cause</strong>. If you fix only the symptom, the root cause stays and the next defect appears ([Chapter 19](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/d3f914)).

The same page also says that a call to `/how` up front costs less than the work that the next defect causes.

## `/why` answers why code has its current shape, and separates reasons the records back from guesses

`/why` is a Skill that answers why code has its current shape, and <strong>separates the reasons that records back from guesses</strong>.

`/how` answers "How does it work?" `/why` answers "What circumstances and decisions produced that shape?"

If `/why` investigates and finds no reason, it answers "unknown" instead of filling the gap with a guess. <strong>If the answer states a guess with confidence, the user takes the guess as fact and makes decisions based on it</strong>.

<a id="when-to-use-it%3A-asking-about-design-reasons%2C-regressions%2C-and-where-thresholds-came-from"></a>


### When to use it: asking about design reasons, regressions, and where thresholds came from

Use it when you ask about a design reason, such as "Why does it work this way?" or "Why did we pick Y?" Also use it when you investigate a regression, a postmortem, or where a threshold came from, for example why the retry limit is five.

If you are asking about runtime behavior, meaning how it works now, use `/how` instead of `/why`.

<a id="procedure%3A-put-one-investigator-on-each-place-evidence-lives%2C-and-investigate-in-parallel"></a>

The agent first checks which MCP servers are connected to the user's Cursor and assigns each one to the category of evidence it can read.

For example, if the Linear MCP is connected, the agent assigns it to "issue and ticket tracking". If the Slack MCP is connected, the agent assigns that MCP to "real-time chat".

Then the agent starts one <strong>investigator</strong> in parallel for each category that has a connected MCP. `/why` always investigates source control history, because git and `gh` can read it without an MCP.

Before it starts the investigators, the agent collects the target lines, commits, and PRs with commands like the following. It hands the collected leads to every investigator, so that each one can start from concrete code.

```
# Show the commit that last changed the target lines
git blame -L <start>,<end> <file>

# Show the PR description and discussion
gh pr view <number> --json title,body,author,createdAt,mergedAt,labels,closingIssuesReferences,comments,reviews
```

A <strong>synthesizer</strong> combines the investigators' results. The flow is as follows.

The investigators search in parallel. If one finds nothing, it returns the result "not found" to the synthesizer.

The synthesizer also records, with reasons, the categories it did not check and the categories where the search found nothing. <strong>"I searched and found nothing" is one result of the investigation. Without that record, the user cannot tell whether a category went unchecked or was checked and held nothing</strong>.

<a id="output%3A-sort-every-claim-into-five-confidence-levels%2C-from-direct-to-unknown"></a>


### Output: sort every claim into five confidence levels, from Direct to Unknown

From code, you can read what it does but not why it exists. The reasons live only in incomplete records, such as commits, PRs, tickets, and chat.

So `/why` sorts every claim into the following five levels by how certain it is.

The examples assume an investigation into why the retry limit is five.

The synthesizer <strong>uses assertions such as "therefore X" only for Direct and Supported claims</strong>. Readers take the assertive form as a claim of cause and effect that has evidence.

For example, a Direct claim asserts "This limit exists because the upstream API rejects the sixth retry and later ones" and attaches the source.

An Inferred claim, on the other hand, uses wording that shows it is an inference, such as "This limit probably follows a team convention."

Even when the user puts a hypothesis into the question, such as "I think it's for performance", `/why` does not accept the hypothesis as is. It treats the hypothesis as one candidate and checks the evidence on its own.

In [Part 2](https://x.com/poteto/status/2097732320606507506) of *The Complete Guide to pstack*, poteto writes that <strong>when you ask an agent for something and do not state your own hypothesis first, you do not steer the agent in the wrong direction</strong>.

If the user plans to change the code after this question, `/why` <strong>turns the findings into Preserve, Change, Avoid, and Risk constraints, so that they can go into the change plan</strong>.

For example, if you investigated the reason for the retry limit because you plan to change it, the constraints look like this.

```
Preserve: Do not exceed the number of retries the upstream API rejects (a record gives this as the reason for the limit)
Change:   Do not hard-code the limit. Decide it in the same place as the upstream API's limit
Avoid:    Removing the limit and retrying until it succeeds
Risk:     If the upstream API's limit has changed, the current value of five no longer fits
```

When you split the findings into these four constraints, you do not unknowingly delete a reason that must stay when you plan the change.

<a id="example-request%3A-%22nobody-wrote-down-the-reason%22-is-also-an-answer"></a>


### Example request: "nobody wrote down the reason" is also an answer

The "[Investigation](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/playbooks/investigation.md)" Playbook and the "Bug fix" Playbook call `/why`. The "Investigation" Playbook answers, with citations, a question that the code or its history can answer. `/recall`, `/teach`, `/architect` ([Chapter 24](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/2df1db)), and `/no-comments` ([Chapter 31](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/347946)) also call `/why` in their procedures.

`03-understand.md` has the following example request.

```
/why was the retry limit set to five? does the reason still hold?
```

The same page treats the result "nobody wrote down the reason" as an answer in itself.

Once the user knows that the reason is written nowhere, they can decide whether to ask the original author or stop investigating. So `/why` also reports the result that it found no reason.

<a id="%2Fteach-explains-how-code-works-and-why%2C-in-plain-terms%2C-until-a-person-is-convinced"></a>


## `/teach` explains how code works and why, in plain terms, until a person is convinced

`/teach` is a Skill that <strong>combines into one plain explanation</strong> what some code or a change is, how it works, and why it was built that way. The goal is not to change anything. The goal is that the other person understands.

In Part 2 of *The Complete Guide to pstack*, poteto writes that to work with the agent, a partner smarter than you, you need the agent to restate things in a form you understand. poteto also writes that this idea led to `/teach`.

<a id="when-to-use-it%3A-when-you-want-real-understanding%2C-not-a-summary"></a>


### When to use it: when you want real understanding, not a summary

Use it when a summary is not enough and you want to understand a change or a subsystem in depth.

<a id="procedure%3A-call-%2Fhow-and-%2Fwhy%2C-and-combine-their-results-into-one-explanation"></a>


### Procedure: call /how and /why, and combine their results into one explanation

<a id="do-not-redo-the-investigation.-combine-the-results-of-%2Fhow-and-%2Fwhy"></a>


#### Do not redo the investigation. Combine the results of /how and /why

`/teach` reads the code itself to get a sense of what to explain and where to start. It does not redo the investigation itself, though. <strong>It calls `/how` and `/why` and combines their results into one explanation</strong>.

For a whole subsystem it calls both. For a small change, one of `/how` and `/why` may be enough.

<a id="ask-%2Fwhy-to-narrow-its-search-by-default"></a>


#### Ask /why to narrow its search by default

When `/teach` calls `/why`, by default it asks `/why` to narrow its search, for example to git and one or two other places. A search of every category takes time, so `/teach` widens the search only when the reason itself is what the other person wants to know.

<a id="decide-a-few-points-to-take-away%2C-and-connect-plain-definitions-to-the-code-at-hand"></a>


#### Decide a few points to take away, and connect plain definitions to the code at hand

When it explains, `/teach` decides the few points the other person should take away, starts from plain definitions, and connects them to the code at hand. It picks those points by reading two things from the conversation: why the person is asking, such as to make a change, to review, or to investigate a defect, and what the person already knows.

For example, it first defines the term in general words, "Virtual scrolling renders only the rows visible on screen", and then connects it to the code at hand, "This app uses virtual scrolling when you open a long chat."

<a id="answer-in-one-or-two-sentences%2C-then-stop-and-wait-for-a-reaction"></a>


#### Answer in one or two sentences, then stop and wait for a reaction

`/teach` makes the explanation a conversation, not a lecture. It gives no quizzes and does not ask the person to restate anything. It returns a minimal answer of one or two sentences, then stops and waits for the person's reaction. If the person wants more, it explains in more depth.

<a id="do-not-draw-everything-in-one-diagram.-redraw-it-in-the-order-it-is-assembled"></a>


#### Do not draw everything in one diagram. Redraw it in the order it is assembled

`/teach` redraws a diagram of a mechanism and adds one part each time. A diagram with every part in one picture can work as reference material, but the reader cannot follow how the mechanism is assembled.

For example, for a flow from the UI to the API and from the API to the database, it draws the following three diagrams in order.

The first diagram goes from the UI to the API.

<a id="output%3A-return-the-explanation-itself%2C-starting-from-the-key-point"></a>


### Output: return the explanation itself, starting from the key point

The reply is the explanation itself, not a report on the work. It starts from the key point and lists topics to investigate further with `/how` or `/why`.

`/teach` may change wording freely for the sake of the explanation, but it keeps `/why`'s confidence words, the levels such as Direct and Inferred.

A hedge such as "probably" is not decoration that can be reworded. It is part of what the investigation found: "the records did not back this up". So `/teach` keeps the confidence words without rewording them.

<a id="example-request%3A-ask-it-to-%22convince-me%22"></a>


### Example request: ask it to "convince me"

`/teach` is a Skill the user calls by name. `03-understand.md` has the following example request.

```
/teach me how this PR changes retries. convince me it fixes the cause and not the symptom.
```

The guide recommends that you ask it to "convince me", because the explanation then becomes an argument you can test by pushing back, instead of a one-way lecture.

[Chapter 37](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/6a59d6) covers how to use `/teach` in practice.

<a id="%2Frecall-gathers-the-history-of-recent-work-so-that-you-can-resume-from-the-last-point-of-failure"></a>


## `/recall` gathers the history of recent work so that you can resume from the last point of failure

Before you start or resume work, `/recall` gathers the history of recent work again, <strong>so that you can resume from the last point of failure</strong>. The history covers what you did, what you decided, and what went wrong. It returns a short answer about how far the work has come and what to do next.

<a id="when-to-use-it%3A-when-you-ask-%22how-far-did-i-get%3F%22"></a>


### When to use it: when you ask "how far did I get?"

Use it before you start or resume work, when you want to ask "Remind me of the work on X" or "How far did I get?"

<a id="procedure%3A-search-chat-history-and-shared-records-in-parallel"></a>


### Procedure: search chat history and shared records in parallel

<strong>The history of the work is split across two records, so `/recall` reads both</strong>.

- <strong>Your own chat history.</strong> It holds what you did and what you decided.
- <strong>Shared records.</strong> They hold what happened around the same code. Examples are symptoms that users keep reporting, fixes that someone reverted after release, and errors that keep appearing in production.

`/recall` has `/why`'s investigators search the shared records. The longer a feature has had defects, the more of its history lives in the shared records instead of your own history.

Here `/recall` has the investigators look not for "why it was built this way" but for "what state it is in now, what was tried and failed, and what users keep reporting".

Before it searches, the main agent decides the time range, the topic, and the workspace. By default, the time range is the last seven days and the workspace is the one open now. The main agent states that scope to the user before it goes on. That way, if the scope differs from what the user had in mind, the user can correct it on the spot.

Unless the user asks, the main agent does not read the history of other projects.

If there are one or two target chats, the main agent searches them directly. If there are more, it has subagents read the history in parallel. The actual history stays inside the subagents, and they return only what they found to the main agent. Because subagents do the reading, long history does not fill the main agent's context ([Chapter 20](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/0ec4d6)).

The main agent checks the actual state of the PRs and branches it found with `git` and `gh`. The chat holds the state at that time, and a merge or revert may have happened since.

If all the user wants is to resume one specific chat, `/recall` passes the request to the "[Session pickup](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/playbooks/session-pickup.md)" Playbook.

<a id="output%3A-capsule%2C-threads%2C-problems%2C-and-next-move"></a>


### Output: Capsule, Threads, Problems, and Next move

The output has four parts that move from an overall summary to the next step, so that the reader can see at once how far the work has come overall and what to do next.

- <strong>Capsule.</strong> Up to five items on what this work is and how far it has come overall. For example, the move to jobs is merged and only the retry problem remains.
- <strong>Threads.</strong> One line for each unit of work done under the topic, such as one PR or one branch. Each line carries exactly one status tag from the table below.
- <strong>Problems.</strong> Up to five items on problems that keep recurring. They include reverted fixes, so that the next attempt can start from the last point of failure.
- <strong>Next move.</strong> The single most useful next step.

For example, for last week's export work, an output that contains all four parts and all six tags looks like this.

```
Capsule
- Moving CSV export from UI-side processing to an asynchronous job
- The move to the job is merged. A problem remains: a retry writes the same rows out again
Threads
- [merged #412] Move export to a job
- [reverted #418] Add retries (reverted because the same rows were written out again)
- [open PR #421] Make writes idempotent with a row key
- [in flight export-progress] Show progress in the UI

```

<a id="choose-among-%2Fhow%2C-%2Fwhy%2C-%2Fteach%2C-%2Frecall%2C-and-%22session-pickup%22-by-the-question-you-hold-now"></a>


## Choose among /how, /why, /teach, /recall, and "Session pickup" by the question you hold now

The question each one answers is as follows.

- <strong>`/how`.</strong> "How does it work now?"
- <strong>`/why`.</strong> "Why is it this shape?"
- <strong>`/teach`.</strong> "I really want to understand this."
- <strong>`/recall`.</strong> "How far did I get?"

To continue one specific chat from where it stopped, use "Session pickup". To load context that spans several chats, use `/recall`.

<a id="summary"></a>


## Summary

- <strong>The four Skills.</strong> All four run only when someone calls them by name. `/poteto-mode` also calls `/how` and `/why` as part of a Playbook's procedure.
- <strong>`/how`.</strong> Separates the role that gathers facts, the explorer, from the role that writes the explanation, the explainer, and explains current behavior under five headings, from Overview to Gotchas.
- <strong>`/why`.</strong> Searches each place evidence lives, such as git, tickets, and chat, in parallel, and sorts claims into five levels, from Direct to Unknown. Only claims that records back get the assertion "therefore X".
- <strong>`/teach`.</strong> Combines the results of `/how` and `/why`, starts from plain definitions, and explains with a diagram that gains one part at a time.
- <strong>`/recall`.</strong> Summarizes the state of the work from chat history and shared records in four parts, Capsule, Threads, Problems, and Next move, and keeps reverted fixes and their reasons in Problems.
- <strong>Choosing.</strong> Choose by the question you hold now. To continue one specific chat from where it stopped, use "Session pickup".
