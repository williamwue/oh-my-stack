pstack is made of <strong>three kinds of parts: Playbooks, Skills, and Principles</strong>.

A Playbook decides the order of the work. A Skill provides an ability that a step uses. A Principle is a rule that guides a judgment during the work in a specific situation. The agent uses Principles for judgments such as keeping a change small, fixing the root cause, and verifying the real thing before it reports that it is done.

This chapter focuses on how the three parts differ and what each one handles. It then looks at `Non-negotiables` and the two subagents that connect the parts. Last, it traces where the parts act in the book's example request.

## The three parts divide the work into "order," "ability," and "judgment"

As I said at the start, the three parts cover different areas. <strong>A Playbook handles the pattern of the work, such as "what to do, and in what order." A Skill handles an ability, such as "how to do this step." A Principle handles a judgment, such as "should I take this move? Am I really not done yet?"</strong>

Inside `/poteto-mode`, the three parts connect as follows.

1. `/poteto-mode` looks at the kind of request and picks one Playbook (the section "[Playbooks](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/SKILL.md#playbooks)" of [`/poteto-mode`](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/SKILL.md))
2. The Playbook gives the steps of that work and their order, for example "reproduce, find the cause, fix, confirm" for a bug
3. Each step of the Playbook says where to use which Skill. The agent calls `/how`, which explains the current state, and `/arena`, which compares several options, when the work reaches that step, not at startup
4. A Principle is a rule for judgment, separate from the steps. When `/poteto-mode` starts, the agent reads only the list of Principles, which this book calls the index. When the current work meets a Principle's condition, the agent reads that Principle's file in full (the section "[Principles](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/SKILL.md#principles)" of the same file)

<a id="a-playbook-decides-the-steps-and-their-order-for-each-kind-of-work"></a>


## A Playbook decides the steps and their order for each kind of work

A Playbook is <strong>a procedure that says "what to do, and in what order" for one kind of work</strong>.

`/poteto-mode` picks the one that fits the request and opens it.

<a id="what-it-handles%3A-the-steps-and-their-order%2C-written-in-three-parts"></a>


### What it handles: the steps and their order, written in three parts

Playbook files mostly share the same shape.

1. <strong>Preamble.</strong> It gives the basic rules for the whole Playbook.
2. <strong>Numbered steps.</strong> The agent copies this part word for word into the TODO list. Each step says where to use which Skill and which Principles apply.
3. <strong>Reply line.</strong> It sits at the end of each Playbook and says what to include in the reply after the work.

<aside class="msg message"><span class="msg-symbol">!</span><div class="msg-content">
<p class="code-line" data-line="60">The <strong>TODO list</strong> is the plan, a list of things to do that the agent makes at the start of the work. In Cursor, the TODO list appears in the chat panel. From this list, the user can check which steps the agent carried out and which steps it skipped. The agent marks a skipped step with <code>skip: &lt;reason&gt;</code> (the bundled guide <a href="https://github.com/cursor/plugins/blob/main/pstack/docs/guide/01-setup.md" rel="nofollow noopener noreferrer" target="_blank"><code>01-setup.md</code></a>).</p>

<a id="a-skill-is-an-ability-that-a-step-calls"></a>


## A Skill is an ability that a step calls

A Skill is <strong>a bundle of abilities or steps for doing one specific job</strong>.

`/poteto-mode` calls most of them when a step needs them. The user calls the rest directly.

<a id="what-it-handles%3A-one-skill-handles-one-kind-of-job"></a>


### What it handles: one Skill handles one kind of job

Each Skill handles one kind of job. For example, `/how` and `/why` handle investigation, `/architect` handles design, and `/arena` compares several options.

The exception is `/figure-it-out`. For work that fits no Playbook, it writes a new Playbook for that work while it runs.  
[Part V](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/fdce40) (Chapters 22 to 35) covers each Skill in detail.

<a id="how-the-user-uses-them%3A-you-can-call-any-skill-by-name%2C-and-you-call-the-10-that-no-playbook-calls"></a>


### How the user uses them: you can call any Skill by name, and you call the 10 that no Playbook calls

Unlike a Playbook, you can call a Skill on its own. When all you want is to look something up, a direct call is sometimes faster.

```
/how do we cancel runs? do we have an n+1 when we look up every run to cancel?
```

<strong>The 10 Skills the user calls are not part of any Playbook's steps</strong>.

<a id="a-principle-is-a-standard-for-judgments-during-the-work"></a>


## A Principle is a standard for judgments during the work

A Principle is neither a step nor an ability. It is <strong>a standard for the judgments the agent makes during the work</strong>.

The agent reads only the index at startup, and reads a Principle's body when it applies the Principle.

<a id="what-it-handles%3A-the-standard-for-judgments-during-the-work"></a>


### What it handles: the standard for judgments during the work

A Principle gives <strong>the standard for judgments during the work</strong>, such as whether to take the current move and whether the work is really not done yet. For example, the principle "[Laziness Protocol](https://github.com/cursor/plugins/blob/main/pstack/skills/principle-laziness-protocol/SKILL.md)" makes the agent prefer to delete code and make the smallest change when it is tempted to add an abstraction or a layer. The principle "Prove It Works" asks, before the agent declares the work done, whether it verified the result with the real artifact.

Each Principle is its own file, and Playbooks and Skills refer to it by name.

[Part IV](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/df0d7d) (Chapters 17 to 21) covers the 23 Principles in detail.

<a id="the-agent-splits-work-with-two-subagents"></a>


## The agent splits work with two subagents

pstack has <strong>two subagents: `poteto-agent`, which works the `/poteto-mode` way, and Comment Sicko, which reviews comments</strong>.

<a id="poteto-agent-is-a-subagent-that-works-the-%2Fpoteto-mode-way"></a>


### `poteto-agent` is a subagent that works the `/poteto-mode` way

`poteto-agent` ([`agents/poteto-agent.md`](https://github.com/cursor/plugins/blob/main/pstack/agents/poteto-agent.md)) is a subagent that reads the `/poteto-mode` rules before it starts work. When a Playbook step starts a subagent, the step uses `poteto-agent` by default.

<a id="comment-sicko-deletes-comments-and-reports-code-that-needs-fixing"></a>


### Comment Sicko deletes comments and reports code that needs fixing

Comment Sicko ([`agents/comment-sicko.md`](https://github.com/cursor/plugins/blob/main/pstack/agents/comment-sicko.md)) is a subagent that reviews the comments in the code. On its own, it deletes the comments that have no reason to stay. It does not rewrite the app's code. Instead, its report marks code as `MUST KILL` when the code's shape should change so that the code makes sense without a comment. That code includes functions, variables, and similar names. `/no-comments` takes that report and fixes the code. You do not call Comment Sicko directly. You use it through `/no-comments`. [Chapter 31](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/347946) covers it in detail.

<a id="the-main-agent-is-responsible-for-the-subagents'-work"></a>


### The main agent is responsible for the subagents' work

<strong>When the agent hands work off to a subagent, the main agent stays responsible for it</strong>.

`/poteto-mode` tells the main agent not to pass a subagent's "done" straight to the user. The main agent looks at the diff first and then reports in its own words.

This rule applies the idea "trust the artifact, not the agent" from [Chapter 2](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/950071) to subagents.

<a id="trace-where-skills-and-principles-act"></a>


## Trace where Skills and Principles act

<strong>Skills appear where the agent "does work," such as reproducing, investigating, designing, and committing. Principles appear where the agent makes a judgment and "decides" something</strong>. Examples of these decisions are how to reproduce, the shape and size of the fix, whether the work is done, and how to order the commits.

The book's example is the following request.

```
/poteto-mode the export writes duplicate rows when a retry lands mid-run. repro first, then fix and verify.
```

`/poteto-mode` routes this request to the "Bug fix" Playbook, and the TODO list starts with that Playbook's six steps. (Step 6 runs "[Opening a PR](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/playbooks/opening-a-pr.md)" to open a PR, so the table below leaves it out.) Here, I trace where each step calls a Skill and where a Principle takes effect.

The table below applies three sets of conditions to this request: the conditions in `playbooks/bug-fix.md`, the Non-negotiables of `/poteto-mode`, and the Principle index of `/poteto-mode`. In real work, the agent decides which Principles to use by checking the index conditions during the work.

<a id="the-agent-does-not-call-a-skill-whose-condition-does-not-apply"></a>


### The agent does not call a Skill whose condition does not apply

For example, `/show-me-your-work` is a Skill that keeps a record of decisions during long work or work you leave. This request does not say that the user will leave, so the condition does not apply. Long work or work you leave would meet the condition. In that case, however, the rule from [Chapter 7](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/55bbdb) may also route the request to `/figure-it-out`.

Even within the same "Bug fix" Playbook, the Skills that the agent calls and the Principles that take effect change with the content of the request and the situations that come up along the way. This design, in which the agent reads only what meets a condition, is the subject of the next chapter, [Chapter 9](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/84aa6e).

<a id="summary"></a>


## Summary

- <strong>How the three parts differ.</strong> A Playbook handles the order of the work. A Skill handles an ability that a step uses. A Principle handles the judgment of whether to take the current move and whether the work is really not done yet.
- <strong>Playbook.</strong> It has three parts: the preamble, the steps, and the Reply line.
- <strong>Skill.</strong> One Skill handles one kind of job. `/poteto-mode` calls most of them as the steps require. The 10 that the user calls are not part of any Playbook's steps.
- <strong>Principle.</strong> It defines a standard for judgment, such as whether to take the current move and whether the work is done. It is not a step or an ability. [Part IV](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/df0d7d) covers the details.
- <strong>Non-negotiables.</strong> They connect the parts by responding to situations during the work and calling Skills across Playbooks.
- <strong>Subagents.</strong> `poteto-agent` is a subagent that works the `/poteto-mode` way. Comment Sicko deletes comments and reports code that needs fixing. The main agent stays responsible for the work it hands off.
- <strong>The example request.</strong> At each step of "Bug fix," the agent calls control Skills, `/how`, and `/why` for reproduction and investigation, `/architect` for the fix, and `/tdd` for the commit. Principles such as "Fix Root Causes" and "Prove It Works" guide the judgments.

The next chapter, [Chapter 9](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/84aa6e), covers when the agent loads these parts. It explains the mechanism that reads only what is needed, only when it is needed, along with the idea behind it and its strengths and weaknesses.
