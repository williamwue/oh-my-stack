In [Part 1](https://x.com/poteto/status/2094457600259842065) of *The Complete Guide to pstack*, poteto names <strong>a verification skill as the first thing</strong> a new pstack user should build. This chapter calls Part 1 "the guide".

A <strong>verification skill</strong> is a project-specific Skill that lets the agent start and operate the app the user is developing, verify that a change works, and leave evidence ([Chapter 26](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/9884cb)).

For example, if you changed a settings screen, the agent itself presses the gear button, opens the settings screen, and saves a screenshot of the changed part as evidence.

This chapter explains how the guide recommends building and using a verification skill. The chapter also checks each point against the pstack source, such as the `SKILL.md` of `/create-verification-skill`.

## Why build a verification skill first

There are two reasons to build a verification skill first.

First, a verification skill is <strong>important infrastructure that multiplies the output of the whole team</strong>.  
Second, many steps in pstack's Playbooks cannot run without <strong>a way to actually operate the app</strong>.

<a id="the-guide-treats-the-verification-skill-as-important-infrastructure"></a>


### The guide treats the verification skill as important infrastructure

The guide's section "Verification is all you need" opens with this sentence.

> The most critical skill to have in your toolbox is a high quality verification skill.

In the guide, verification means <strong>the agent can check its own work</strong>.

In other words, <strong>verification does not mean "I wrote the code" or "the build passed". It means operating the real app the way a real user would and saving the result as evidence</strong>.

An agent that can check its own work can repeat a cycle of failing, fixing, and retrying until the task succeeds. Because no human has to check each step, humans stop being the bottleneck that halts the work.

The guide says that a high-quality verification skill, and the work to keep it up, matter so much that poteto thinks of the skill as important infrastructure, not "just a Skill". This book treats the skill the same way.

The guide goes on to say that <strong>a high-quality verification skill multiplies the output of the whole team, including members who are not engineers</strong>.

<strong>If the agent can verify by itself that a change works, everyone in the organization, including non-engineers, can make changes to the app and verify that those changes work</strong>. The guide says that a well-built verification skill multiplies the output of the whole team by 100 to 1000 times. For that reason, I consider one verification skill per app a requirement.

Without a way to operate the app, such as a verification skill or a control Skill, the agent cannot carry out the steps in the table.

At the start of a task, the agent makes a TODO list that copies the Playbook's steps. For a step it skips, it keeps the line and writes `skip: <reason>` on it ([Chapter 7](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/55bbdb)).

The bundled guide <a href="https://github.com/cursor/plugins/blob/main/pstack/docs/guide/01-setup.md" rel="nofollow noopener noreferrer" target="_blank"><code>01-setup.md</code></a> describes this list.</p>

Take "<strong>Bug fix</strong>" as an example. If there is no way to operate the app, or the available way cannot reach the part to reproduce, this book sees two options left for the agent.

- Leave `skip: <reason>` in the TODO list and skip that step
- Ask the user to reproduce the bug, which "<strong>Bug fix</strong>" allows as an exception

The agent may ask the user to reproduce the bug only when both of the following are true.

- The agent has explained concretely why the available way to operate the app cannot reach the part to reproduce (for example, only accounts on a specific plan can log in to that screen)
- The agent has operated the app itself as far as the available way allows

Whether the agent skips the step or asks the user to reproduce, some part remains that the agent cannot verify by itself. A human has to verify that part.

<a id="what-a-verification-skill-is-made-of"></a>


## What a verification skill is made of

A verification skill centers on two things: <strong>a small CLI that operates the app, and a Feature Map that records how to reach each feature of the app</strong>. For each feature, the Feature Map records where the feature is on the screen or in the commands, and what an end user does to get there.

In pstack version `0.15.5`, the version this book covers, the agent follows the steps of `/create-verification-skill` and creates both inside `.cursor/skills/verify-<app>/`.

For Atlas, the fictional app the guide uses as its example, the result looks like this.

```
.cursor/skills/verify-atlas/
├─ SKILL.md (steps from startup to cleanup)
├─ control-atlas.mjs (the CLI that operates the app)
└─ features/ (Feature Map)
   ├─ README.md (Feature Map index. Links to each feature's file)
   ├─ <feature-a>.md
   └─ <feature-b>.md
```

[Chapter 26](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/9884cb) covered what goes in `SKILL.md`. This section looks at the two parts the guide explains in detail: the <strong>CLI</strong> and the <strong>Feature Map</strong>.

<a id="cli"></a>


### CLI

The CLI of a verification skill turns the steps to operate and debug the app into <strong>commands the agent can rerun</strong>.

<a id="an-application-of-the-principle-%22build-the-lever%22"></a>


#### An application of the principle "Build the Lever"

The guide presents <strong>a CLI for app operations</strong> as an application of the principle "[Build the Lever](https://github.com/cursor/plugins/blob/main/pstack/skills/principle-build-the-lever/SKILL.md)" ([Chapter 17](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/97d863)). That principle says to build a tool that does a task instead of doing the task by hand.

When you apply this principle to a new Skill, the Skill author gives the agent a tool it can run, in addition to steps written in Markdown.

> What this means in the context of creating a skill, is that we prefer to give agents tools rather than just markdown.

For example, if the verification skill's `SKILL.md` says "click the settings button and take a screenshot" only as Markdown text, the agent has to write its own script to do the click every time.

If the verification skill comes with a CLI that has commands like `click` and `screenshot`, the agent needs only to run those commands. In a verification skill, this small CLI for operating and debugging the app is the tool.

The guide lists these benefits of a CLI for app operations.

- <strong>Fewer tokens.</strong> The agent runs one CLI command instead of a throwaway script that clicks one button.
- <strong>Easier to reproduce and test.</strong> The verification skill gives the same result every time it runs. Because the commands are fixed, you can also test whether the verification skill itself works.

<a id="example%3A-commands-for-the-fictional-app-atlas"></a>


#### Example: commands for the fictional app Atlas

The following is part of the guide's example commands for the fictional app Atlas. In the example, Atlas is an app built with Electron.

The agent runs the commands from top to bottom to do three things.

1. Check that the app is ready to operate (`doctor`)
2. Open a new blank conversation (thread) and send "list open tasks in this project" (`new-session`, `send`)
3. Save the resulting screen as evidence to `/tmp/atlas-proof.png` (`screenshot`)

```
# health
node .cursor/skills/verify-atlas/control-atlas.mjs doctor

# open a blank thread and send
node .cursor/skills/verify-atlas/control-atlas.mjs new-session
node .cursor/skills/verify-atlas/control-atlas.mjs send "list open tasks in this project"

# screenshot for evidence
node .cursor/skills/verify-atlas/control-atlas.mjs screenshot /tmp/atlas-proof.png
```

<a id="six-categories-of-commands"></a>


#### Six categories of commands

To help the user decide which commands to provide, the guide gives six categories.

- <strong>Inspection.</strong> Commands that look at the state of the screen, such as `info`, `snapshot`, and `screenshot`.
- <strong>Navigation.</strong> Commands that move between screens, such as `home`, `new-session`, and `scroll`.
- <strong>Interaction.</strong> Commands that type and click, such as `send`, `click`, `type`, and `press`.
- <strong>Performance.</strong> Commands that measure performance, such as `trace`, `profile`, and `perf-metrics`.
- <strong>Streaming.</strong> Commands that capture console and network logs, such as `console` and `network-log`.
- <strong>Health & cleanup.</strong> Commands that check that the app is ready to operate, or that clean up after a run, such as `doctor` and `cleanup`.

<a id="a-cli-that-agents-can-use-well"></a>


#### A CLI that agents can use well

The guide recommends that you first spend time to make the CLI run without errors, before you move on to more advanced uses. <strong>Once the CLI exists, every agent can operate and debug the app with it</strong>.

The agent uses the CLI, not a human, so the CLI has to suit agents.

The guide lists six properties of a CLI that agents can use well.

- Make commands easy to combine (the guide cites deep modules, a simple interface in front of a lot of functionality, from John Ousterhout's book *[A Philosophy of Software Design](https://web.stanford.edu/~ouster/cgi-bin/book.php)*)
- Give commands that may have destructive side effects a `--dry-run` option
- Reveal features step by step through subcommands instead of all at once. For example, `--help` lists only the subcommands, and each subcommand's own `--help` shows its detailed usage
- Make error messages say what to do instead. For example, do not stop at "The app is not running". Add the fix: "Run the start command first."
- Write thorough `--help` text
- Print output in a machine-readable form such as JSON

The guide recommends that the user design a CLI like this, or ask the agent to design it.

<a id="feature-map"></a>


### Feature Map

The <strong>Feature Map</strong> is <strong>a set of Markdown files that records, for each feature of the app, what the feature does, what an end user does to reach it, how to operate it with the verification skill, and what result shows that it works</strong> ([Chapter 26](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/9884cb)).

<strong>The more complex the app, the more the agent needs directions for finding and operating features</strong>. poteto created the Feature Map to give those directions.

`features/README.md` is the Feature Map's index and links to each feature's file.

Before it operates the app, the agent reads the index and opens only the files for the features related to its task.

<strong>Because it reads only the files it needs, the agent saves tokens in its context window</strong>.

#### `How to get to it (user POV)`

An entry point is a way an end user reaches the feature, such as a button, a key press, or a command. The sample lists three entry points: the `New note` button in the toolbar, the `n` key, and the `notes create` command.

```
## How to get to it (user POV)

- Choose the `New note` button in the browser toolbar.
- Press `n` in the browser while focus is outside an editable field.
- Run `notes create --title <title> --body <body>` in a terminal.
```

The sample's `README.md`, which sets the rules for writing each feature's file, says to write this heading as follows.

> `Driving it with <harness>` starts with `Preconditions:` and uses labeled bullets that pair each user action with an exact command and observable result.

Preconditions (`Preconditions:`) are the state that must hold before the steps begin. The sample lists, for example, "Notes is running normally at `http://127.0.0.1:4173`" and "No note titled `Release checklist` exists yet."

- The end user's action
- The command that reproduces the action with the harness
- The observable result that shows the action succeeded

  Choose `New note`.
  Run `control-notes browser click --role button --name "New note"`.

<a id="gotchas"></a>


#### `Gotchas`

The sample lists these pitfalls.

```
- Pressing `n` while a textbox has focus types the character instead of opening a new editor.
- A save status alone is insufficient proof. Reopen the note from the list.
```

The first pitfall is that when a text field has focus, the `n` key types the letter `n` instead of opening the editor.

The second is a warning. A "Saved" message does not prove that the app saved the value, so the message alone is not evidence. The agent must reopen the note from the list to check.

The guide's own Feature Map example, the settings feature, also has this warning under `Gotchas`. Here, a tab is one of the items on the left side of the settings screen that switch the view, such as General, Appearance, Models, and Plan & Usage.

> Some tabs are entitlement-gated. Skip with an explicit account reason.

With this line in the Feature Map, when the agent cannot find, for example, the Plan & Usage tab, it does not mistake the missing tab for a bug. It skips checking that tab and writes the reason: "not shown because of the account's plan."

<a id="the-feature-map-is-memory-the-team-shares"></a>


#### The Feature Map is memory the team shares

The guide calls the Feature Map "<strong>materialized memory</strong>" ([Chapter 4](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/3cc0dd)).

An agent's memory is knowledge from earlier work that the agent keeps so it can use it in the next task.

<strong>The ultimate form of this memory is the codebase</strong>. The code reflects the decisions the team has made, and it is the source of truth for what happened and how things work.

The Feature Map is a condensed version of the codebase-as-memory, made small to save tokens in the agent's context window.

<strong>The Feature Map is Markdown inside a verification skill in the repository's `.cursor/skills/`, so everyone who works on the codebase shares this memory</strong>.

<a id="how-to-build-a-verification-skill-and-keep-it-current"></a>


## How to build a verification skill and keep it current

As [Chapter 26](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/9884cb) showed, the agent builds the verification skill by following `/create-verification-skill`. This section looks at what the guide recommends to the user: the preparation before building and how often to maintain the skill afterward.

<a id="what-the-user-prepares-before-building"></a>


### What the user prepares before building

<a id="choose-the-tech-stack"></a>


#### Choose the tech stack

The guide points out that the choice of tech stack also matters when you set up a way to operate the app from outside. <strong>The harder a tech stack is to debug and operate, the harder it is to use agents productively</strong>.

For example, the agent can operate an Electron or web app through CDP, and an iOS app through the simulator. CDP is the Chrome DevTools Protocol, which lets an outside program use the same features as the browser's developer tools.

If the chosen tech stack has no debugging tools the agent can use, you have two options. You can have the agent build tools, for example with lldb or with your own package that runs alongside the app in the development environment. Or you can work with the tools you have.

poteto, however, considers agent verification so important that he suggests building your own debugging tools or even choosing a different tech stack.

> I personally feel that agentic verification is so important that I would unironically suggest building your own rich debugging tools, or even choosing a different tech stack

I also find verification very important and worthwhile, so if my chosen tech stack had no verification tools, I would take poteto's suggestion.

<a id="prepare-the-developer-experience"></a>


#### Prepare the developer experience

As preparation for running the app, the guide recommends that the user think through three parts of the developer experience.

- How to load seed data into the development database. Seed data is the data you load in advance for development and testing
- How to set up authentication and test users, and how to call APIs in test and staging environments
- How to install and start the development environment with the same steps every time

The guide treats the CLI and these preparations as the agent's main tools for developing the app, so you need to maintain and test them.

When the preparation is done, the user runs `/create-verification-skill`. As a reference, the guide points to [poteto/verification-skill-example](https://github.com/poteto/verification-skill-example), a public sample verification skill built for a fictional app.

<a id="keep-it-current-with-%2Fmaintain-verification-skill"></a>


### Keep it current with `/maintain-verification-skill`

[Chapter 26](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/9884cb) covered the three maintenance results (clean, changed, and blocked) and the rule against editing product code during maintenance. This section looks at how often the guide recommends running it and how to automate that.

<a id="how-often-to-run-it"></a>


#### How often to run it

The `SKILL.md` of `/maintain-verification-skill` does not say how often to run the Skill. An agent that runs `/create-verification-skill` also suggests a frequency only when the user asks. So in this book, I treat it as <strong>the user's decision, based on how often the app changes</strong>.

The guide recommends running it <strong>at least once a day</strong>.

The agent sometimes updates the verification skill while it works on the app, but it often misses some places.

If the user runs `/maintain-verification-skill` once a day, the run finds and fixes the places the agent missed. As a result, the agent always knows how to operate the current app.

<a id="automate-the-daily-run-with-dr-eggbot"></a>


#### Automate the daily run with Dr Eggbot

As a way to automate the daily run, the guide also introduces Dr Eggbot.

Dr Eggbot is a bot that poteto (Lauren Tan) made. It designs and builds Grok Bots, which are AI bot apps ([Chapter 5](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/aa6858)). Its description in xAI's [bot marketplace](https://x.ai/bot/marketplace/bots/dr-eggbot-v2) reads as follows.

> Asks a few preference questions, then creates them with CreateAgent. Coding bots get the poteto-mode bar (one job, unslopped, verified).

<strong>Dr Eggbot ships with pstack</strong>.  
So <strong>Dr Eggbot can teach coding bots how to use pstack. It also builds non-coding bots to the same standard</strong>.

The recommended way to use Dr Eggbot is as follows.

1. Have Dr Eggbot build a bot that plays the engineer
2. Have that bot run `/create-verification-skill`
3. Have the same bot set up a routine that runs `/maintain-verification-skill` once a day

<a id="how-to-use-a-verification-skill-in-requests-and-how-to-expand-its-use"></a>


## How to use a verification skill in requests and how to expand its use

<strong>In a request to the agent, the user writes which verification skill to verify with and what counts as evidence</strong>.

Add the verification skill to Grok Bot routines or Cursor Automations only after you are satisfied with the skill (see ["Use 3: reproduce user reports automatically"](#use-3%3A-reproduce-user-reports-automatically) in this chapter). Cursor Automations is a Cursor feature that runs work at set times or on events.

<a id="ways-to-use-a-verification-skill"></a>


### Ways to use a verification skill

The guide gives three examples of using a verification skill. In the request examples below, `/control-app` is the guide's name for the verification skill built with `/create-verification-skill`.

<a id="use-1%3A-build-a-new-feature"></a>


#### Use 1: build a new feature

When he builds a new feature, poteto uses `/poteto-mode` together with the verification skill and has the agent verify its own changes. The guide's request example is as follows.

```
/poteto-mode build <description of feature, any useful context>. use /control-app to verify your changes and show me a video and screenshots as proof
```

This request adds two things to the feature description: which verification skill to verify with (`/control-app`) and the form of the evidence (a video and screenshots).

<strong>When he sends the request from a Grok Bot, poteto does not have the bot do the work itself. He asks the bot to start an agent in Cloud Agents, a Cursor feature that runs agents in Cursor's cloud</strong>. The following request is an example.

```
spawn a cloud agent to use /poteto-mode to build <description of feature, any useful context>. use /control-app to verify your changes and show me a video and screenshots as proof
```

<strong>poteto keeps the bot out of the work for two reasons. When a cloud agent does the work, the bot can keep working on other things. Also, the bot's context window does not fill up with the work log</strong>.

<a id="use-2%3A-improve-performance"></a>


#### Use 2: improve performance

When he improves performance, poteto <strong>has the agent first measure the current performance with the verification skill, and after the fix, verify the improvement with the same verification skill</strong>. The guide's request example is as follows.

```
spawn a cloud agent to use /poteto-mode to improve the initial loading time of our app. first use /control-app to take a trace of the status quo, and identify opportunities for improvement. then do a targeted fix and use /control-app + a /swarm to confirm the win
```

<strong>This request says to take a trace of the current state with `/control-app` before fixing anything</strong>. The "[<strong>Perf issue</strong>](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/playbooks/perf-issue.md)" Playbook also takes a baseline trace as its first step and asks for the before and after numbers and their difference in the report.

The guide calls `/swarm` ([Chapter 24](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/2df1db)) <strong>one of the Skills that pair best with a verification skill</strong>. `/swarm` runs many Workers, which are agents that run in parallel, and merges their results into one report.

If `/swarm` has many Cloud Agents run the verification skill, you can verify a performance improvement with a large enough sample. You can also use fuzzing to verify that the app does not break. Fuzzing feeds large amounts of random or unexpected input to the app to look for failures.

<a id="use-3%3A-reproduce-user-reports-automatically"></a>


#### Use 3: reproduce user reports automatically

Once you are satisfied with the verification skill, you can add it to Grok Bot routines or Cursor Automations. Both run work at set times or on events.

In the guide's example, a bot takes user feedback that arrives in Slack or elsewhere, one item at a time. For each item, the bot starts a cloud agent and tries to reproduce the reported bug automatically.

In this way, <strong>if the verification skill and the Feature Map are good enough, you can automate even the bug fix</strong>.

<a id="run-agents-in-parallel"></a>


### Run agents in parallel

Once you have merged a few PRs with the help of the verification skill, the next stage is to run more agents in parallel.

If an agent can take a request and carry the work almost to a mergeable state, the user can run other agents in the meantime.

<a id="use-cloud-agents-instead-of-worktrees"></a>


#### Use Cloud Agents instead of worktrees

To run agents in parallel, the guide recommends Cloud Agents over worktrees. A worktree is a git feature that adds an extra working directory to one repository ([Chapter 18](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/e529e4)). This book also recommends Cloud Agents.

The guide does not recommend worktrees because each agent adds one more working directory of the repository. Each extra directory uses a lot of the local machine's storage and resources.

Depending on the size of the repository and the machine's specs, I expect worktrees to support about 10 parallel agents at most.

In my own experience, when I ran agents in parallel locally, each worktree needed a separate directory, and I had to keep the app's ports from colliding. I also had to manage the worktrees I created and remember to delete them.

An agent in Cloud Agents, on the other hand, gets a real computer in the cloud. It can install dependencies, run the app, take videos and screenshots, and operate the app the same way a real user does.

Cursor takes a snapshot of the environment after the first build, so later Cloud Agents start right away. A snapshot is a saved copy of the whole state at one point in time. Each agent also runs on its own machine, so the app instances that the agents run are separate from the start.

<span class="embed-block zenn-embedded zenn-embedded-tweet"><iframe data-content="https%3A%2F%2Fx.com%2Fpoteto%2Fstatus%2F2087977008253071816" frameborder="0" id="zenn-embedded__620a3bddca3ba" scrolling="no" src="https://embed.zenn.studio/tweet#zenn-embedded__620a3bddca3ba"></iframe></span><https://x.com/poteto/status/2087977008253071816>

poteto also gives his reasons for using Cloud Agents in a post on X.

> worktrees are dead. cloud agents are the future. they've allowed me to massively orchestrate swarms of agents, all with their own computer. it's how i've been able to trust that my agents are actually doing what i want them to, because they can run their code, take videos and screenshots, and interact with UIs the same way users do.

Cloud Agents also need some care, though.

An agent in Cloud Agents runs commands automatically without waiting for the user's approval. If it runs a wrong command, only the cloud machine breaks. Your own PC does not.

On the other hand, the repository's code goes to the cloud machine, so the risk that the code leaks remains.  
Secrets such as API keys carry the same risk.

[Cursor's documentation](https://cursor.com/docs/cloud-agent/security-network) also warns about leaks through prompt injection, an attack that hides malicious instructions in text the agent reads. Because the agent runs commands automatically, an attacker can trick it into uploading code to a malicious website.

If your development environment is already in order, the cloud environment takes little work to set up.

In Cursor, you can define how to build the development environment as code and keep it in the repository. Cursor calls this EAC (Environment as Code), and the file is `.cursor/environment.json`.

If you write the startup steps of the development environment you prepared for the verification skill in this file, every agent in Cloud Agents can start work in the same environment. Cursor's [blog post on the cloud agent environment](https://cursor.com/blog/cloud-agent-environment) treats the development environment as a product whose users are agents.

Because agents in Cloud Agents run on cloud machines, the work continues even if the user closes their PC. I am a heavy Cloud Agents user myself.

<a id="what-to-do-as-a-first-step"></a>


## What to do as a first step

The first step is for the user to check whether <strong>the agent has a way to operate and observe the app from outside</strong>.

This book follows the flow of the guide and arranges the steps the user takes, including `/create-verification-skill` and `/maintain-verification-skill`, as follows.

1. Check for a way to operate and observe the app from outside (an existing harness, CDP, a simulator, or a tool you build)
2. Make the development environment start with consistent steps (seed data, test users, test environments, and isolation)
3. Run `/create-verification-skill` and have it generate the CLI and the Feature Map
4. Run the generated artifacts once from start to end and confirm that evidence was saved. Fix the CLI until it runs without errors
5. Decide how often to run `/maintain-verification-skill`
6. In everyday requests, write the verification skill's name and the form of the evidence
7. Once you have merged a few PRs with the verification skill and are satisfied with it, expand to parallel work in Cloud Agents and to routines and automation

At the end, the guide even suggests three things. Keep improving the CLI, invest in the verification skill as you would in important infrastructure, and set up an oncall rotation, a schedule of people who take turns to handle breakages in the verification skill.

I suggest putting a Grok Bot in that oncall role.  
What I have in mind is a Grok Bot that keeps auditing and hands the actual work to Cloud Agents.

<a id="summary"></a>


## Summary

- <strong>Why build it first.</strong> In app development, the guide treats the verification skill as the most important skill, and many pstack Playbooks assume a way to operate the app.
- <strong>What it is made of.</strong> A verification skill centers on a CLI that can be rerun and a Feature Map that records how to reach each feature.
- <strong>How to build it and keep it current.</strong> Before building, the user prepares the tech stack and the developer experience. Afterward, the user runs `/maintain-verification-skill` at least once a day, as the guide recommends, and can automate the run with a routine from Dr Eggbot.
- <strong>How to use it and expand it.</strong> The user writes the verification skill's name and the form of the evidence in requests, and expands to parallel work and automation once satisfied.
- <strong>The first step.</strong> The user starts by checking that the agent has a way to operate and observe the app from outside.
