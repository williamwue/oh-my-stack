<a id="the-conclusion-of-this-book%3A-the-scope-you-can-delegate-depends-on-how-wide-the-environment-for-verification-is"></a>


## The conclusion of this book: the scope you can delegate depends on how wide the environment for verification is

The book's reading of pstack ends here.

So far, this book has used poteto's talk and guide as its starting point and read pstack's Playbooks, Principles, and Skills one by one. The conclusion this book reached is the following sentence.

"<strong>The scope of work you can delegate to the agent depends not on how smart the agent is, but on how wide the environment is in which the agent can verify its own work</strong>"

Put another way, <strong>the wider the range in which the agent can start the app on its own, operate it, and keep the result as evidence, the more work you can hand off without running it yourself to verify it</strong>. That is the conclusion I want to leave you with.

This conclusion starts from poteto's [talk](https://x.com/poteto/status/2102050467505430555) ([Chapter 1](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/15df58)) and *The Complete Guide to pstack* [Part 1](https://x.com/poteto/status/2094457600259842065). <strong>Both consistently put verification first</strong>.

The talk said that <strong>what you trust is the artifact, not the agent, and that a way to verify the artifact is the precondition for trust</strong>. In the section "Verification is all you need", Part 1 named <strong>a high-quality verification skill as the most important skill</strong>.

<a id="the-first-step-is-to-run-one-verification-loop-on-a-small-task"></a>


## The first step is to run one verification loop on a small task

pstack has 23 Playbooks, 23 Principles, and 24 Skills, but <strong>you do not need to master all of them starting tomorrow</strong>.

At first, <strong>one verification loop on a small task is enough</strong>.

<aside class="msg message"><span class="msg-symbol">!</span><div class="msg-content">
<ul class="code-line" data-line="21">
<li class="code-line" data-line="21">
<strong>Verification skill.</strong> A project-specific Skill that the agent uses to start and operate the app and collect evidence.</li>
<li class="code-line" data-line="22">
<strong>Verification loop.</strong> The full cycle of one request. The user writes a request with a finish condition that gives a pass or fail result. The agent verifies the change in the real app, fixes the change until it meets the condition, and returns the evidence.</li>
</ul>
</div></aside>

The rest of this afterword gives a first step for after you finish reading: four steps you can do in one week, and the order in which you then widen the scope you delegate.

The one-week time frame and the structure of four steps are this book's proposal.

That said, the content of [step 1](#1.-pick-one-real-task-that-does-no-harm-if-it-fails) (pick a real task) and [step 2](#2.-write-the-finish-condition-so-it-gives-a-pass-or-fail-result) (write the finish condition so it gives a pass or fail result) also appears in pstack's bundled guide ([`01-setup.md`](https://github.com/cursor/plugins/blob/main/pstack/docs/guide/01-setup.md), [`06-verify-and-ship.md`](https://github.com/cursor/plugins/blob/main/pstack/docs/guide/06-verify-and-ship.md)).

<a id="four-steps-you-can-do-in-one-week"></a>


## Four steps you can do in one week

<a id="1.-pick-one-real-task-that-does-no-harm-if-it-fails"></a>


### 1. Pick one real task that does no harm if it fails

Pick a first task that is "small, harmless if it fails, but needed".

Good examples are a fix for a small display bug, a new CLI option, and a fix for how the app reads a setting. Each one is a small change, and when you run it you can see right away whether the result is correct.

<strong>Avoid practice exercises and pick real work</strong>. The purpose of this week is to verify that the verification loop works in the real app.

<a id="2.-write-the-finish-condition-so-it-gives-a-pass-or-fail-result"></a>


### 2. Write the finish condition so it gives a pass or fail result

Before you write the request, decide the finish condition: "what you need to confirm before the work is done".

<strong>Write the finish condition so that running it gives a pass or fail result, not as "make it nice"</strong>.

In the bundled guide [`06-verify-and-ship.md`](https://github.com/cursor/plugins/blob/main/pstack/docs/guide/06-verify-and-ship.md), the section "State the finish condition up front" uses a task that adds JSON output to a CLI as its example. It writes the finish condition into the request like this.

```
/poteto-mode add json output to this command. text output stays byte-identical, the json parses, both run against the sample project. show me the evidence.
```

Each of the three conditions in this request gives a pass or fail result when you run it.

If you use pstack, put the conditions into the request to [`/poteto-mode`](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/SKILL.md) ([Chapter 7](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/55bbdb)), pstack's entry point, as they are.

If you do not use pstack, you can write a request to any agent the same way.

<a id="3.-ask-the-agent-to-verify-the-change-in-the-real-app-itself"></a>


### 3. Ask the agent to verify the change in the real app itself

This is the most important step.

Do not ask the agent to report whether the tests passed. Ask it to start the app, run the changed feature, and <strong>show the result as evidence</strong>. Passing tests do not mean the real screen or output is correct.

For example, *The Complete Guide to pstack* [Part 1](https://x.com/poteto/status/2094457600259842065) writes a request to build a feature like this ([Chapter 36](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/c9901e)).

```
/poteto-mode build <description of feature, any useful context>. use /control-app to verify your changes and show me a video and screenshots as proof
```

`/control-app` is the name the guide uses for a verification skill made with [`/create-verification-skill`](https://github.com/cursor/plugins/blob/main/pstack/skills/create-verification-skill/SKILL.md).

This request adds two things to the description of the feature: which verification skill to verify with (`/control-app`), and the form of the evidence (a video and screenshots).

Evidence includes the following.

- The output of a command
- A screenshot of the screen
- The result of reading a saved value back

If the agent cannot verify on its own, <strong>remove the cause first</strong>. As long as the agent cannot verify, only you can verify the result, and the scope you delegate does not grow.

In this book, I list <strong>three causes that stop the agent before it can verify</strong>.

- The agent does not know how to start the app
- The agent has no way to operate the app
- The agent has no test users or test data

<strong>If you write down which of the three stopped the agent, you know what to set up next</strong>.

Two of these causes also appear in the Part 1 section "Make it Reproducible": how to start the app, and test users and data.

In this section, Part 1 recommends that you start to think about the following three things as part of the app's developer experience.

> seeding a dev database  
> how to handle auth, test users, API calls against a test/staging environment  
> installing and bringing up your dev environment in a consistent way

A verification skill ([Chapter 26](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/9884cb), [Chapter 36](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/c9901e)) exists to remove the situations in which the agent cannot verify its own work. Chapter 26 gave the reason to set up a verification skill as follows.

> The user sets up a verification skill first for the following reason. <strong>If the agent cannot verify its own work, a human ends up verifying that work piece by piece at the end, no matter how much work you delegate to the agent. The human then becomes the one who stops the flow of work (the bottleneck)</strong>.

If you use pstack, run [`/create-verification-skill`](https://github.com/cursor/plugins/blob/main/pstack/skills/create-verification-skill/SKILL.md), which creates a verification skill, once.

<a id="4.-when-you-give-the-same-correction-twice%2C-keep-it-in-a-mechanism-instead-of-in-text"></a>


### 4. When you give the same correction twice, keep it in a mechanism instead of in text

<strong>If you give the same correction twice in one week, think about whether a tool can detect the mistake automatically. If a tool can, turn the correction into a mechanism</strong>.

This book borrowed this idea from a pstack principle.

The principle "[<strong>Encode Lessons in Structure</strong>](https://github.com/cursor/plugins/blob/main/pstack/skills/principle-encode-lessons-in-structure/SKILL.md)" ([Chapter 21](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/10f4b3)) defines what the agent does when it notices that it has written the same instruction twice.

The agent considers whether it can turn that instruction into one of the following. If it can, it builds the mechanism and deletes the original instruction.

- A lint rule
- A metadata flag, which is a value in a file's settings field
- A runtime check, which tests while the program runs whether a value or state meets a condition
- A script

The principle gives this rule because <strong>a text instruction works only if the reader notices it, remembers it, and follows it</strong>.

The principle's text says the following.

> Textual instructions are easy to miss. They require the reader to notice, remember, and comply.

On the user's side, lint rules, CI checks, and scripts are the mechanisms that replace text instructions.

For example, if you have told the agent twice not to use `any`, add a lint rule that bans `any`.

eslint.config.js

```
// Lint reports an error when code uses any (assumes typescript-eslint is installed)
import tseslint from "typescript-eslint";

export default [
  {
    files: ["src/**/*.ts"],
    languageOptions: { parser: tseslint.parser },
    plugins: { "@typescript-eslint": tseslint.plugin },
    rules: {
      "@typescript-eslint/no-explicit-any": "error",
    },
  },
];
```

Once the correction is a lint or CI check, <strong>from the next week on, the same mistake stops automatically, even if you do not point it out and the agent does not remember it</strong>.

<a id="widen-the-scope-you-delegate-step-by-step"></a>


## Widen the scope you delegate step by step

When you finish the [four steps you can do in one week](#four-steps-you-can-do-in-one-week), you have one area of work where you can say: "for this kind of work, I do not need to verify the diff and the behavior myself every time. I can read the evidence the agent produced".

<strong>Add these areas one kind of work at a time</strong>.

Within one kind of work, you also widen the scope you delegate phase by phase.

In this book, I divide those phases into the following four.

<table class="code-line" data-line="158">
<thead class="code-line" data-line="158">
<tr class="code-line" data-line="158">
<th>Delegation phase</th>
<th>What the user does</th>
<th>What you delegate to the agent</th>
</tr>
</thead>
<tbody class="code-line" data-line="160">
<tr class="code-line" data-line="160">
<td>1</td>
<td>Verifies the diff and the behavior every time</td>
<td>Writing the code</td>
</tr>
<tr class="code-line" data-line="161">
<td>2</td>
<td>Reads the evidence the agent produced</td>
<td>Writing the code, running it, and producing evidence</td>
</tr>
<tr class="code-line" data-line="162">
<td>3</td>
<td>Writes a request with a finish condition and looks only at the finished PR and the evidence</td>
<td>Investigating, fixing, verifying, and opening a PR by a fixed procedure for each kind of work (a Playbook, in pstack)</td>
</tr>
<tr class="code-line" data-line="163">
<td>4</td>
<td>Sets the direction and approves irreversible operations, such as deploys and data deletion</td>
<td>Running several tasks in parallel and merging verified changes</td>
</tr>

A kind of work for which you have finished the [four steps](#four-steps-you-can-do-in-one-week) has reached phase 2 in this table, in which you read the evidence the agent produced.

<strong>Do not skip phases. Move up in order, starting from 1</strong>.

If you move to phase 4 while you still cannot trust the evidence the agent produces in phase 2, all you get is more changes in parallel that nobody can verify.

The "2,500 PRs a month" from the talk also came after the team set up the environment in order, starting with verification of the artifact. [Chapter 1](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/15df58) put it like this.

> In other words, you have to keep this order. First make the artifacts verifiable, then record the knowledge you gain there in the codebase, and then build automation on that base.
>
> The number 2,500 a month is the result of putting these four in place in order.

The four in the quote are also the four themes of the talk: trust, ways to raise trust, the codebase as memory, and automation.

<a id="final-words"></a>


## Final words

pstack is still changing.

This book covers pstack version `0.15.5` as of September 2026.

The names and counts of Playbooks, Principles, and Skills, and the default model, which the agent uses when the user does not choose one, will keep changing.

Even so, in this book I hold that <strong>the value of the direction "first build an environment in which the agent can verify its own work" does not drop as models get smarter</strong>. <strong>The smarter the model, the larger the work you delegate, and the more you need a mechanism to verify it</strong>.

On top of that, even a smart model sometimes states things with confidence without verifying them.

*The Complete Guide to pstack* [Part 2](https://x.com/poteto/status/2097732320606507506), in the section "Building up a mental model", wrote the following about the latest models.

> Even with the latest frontier models, (this also depends on the quality of the harness), in general I find that they still often state things confidently without backing it up with data or actually reading the code needed to build up a mental model of how it works.

Start by running one verification loop on one small task.

From there, the scope you can delegate grows little by little.

Thank you for reading to the end.  
I hope this book is useful to you and makes your development work a little better.

Have a good pstack life!
