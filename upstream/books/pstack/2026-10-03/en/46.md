[Chapter 38](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/006bc8) showed how to design from the way users use something, test solutions with prototypes, and choose a design option.

This chapter covers the stage that follows the test of solutions. In this stage, the agent <strong>settles the design of a large change and turns it into a plan you can execute</strong>, in two steps.

- <strong>Settle the design (`/architect`).</strong> The agent decides the types, the signatures of the public functions, and how to split the modules.
- <strong>Turn it into an executable plan (the "[Multi-phase or multi-PR plan](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/playbooks/multi-phase-plan.md)" Playbook).</strong> The agent splits a large piece of work into several PRs so that each PR holds one change. For example, it splits the work into "a PR that changes the data types" and "a PR that updates the screens to the new types". It then writes a plan document that lists, for each PR, the files to change and how to verify that the PR is finished, such as the steps to check the state of a screen.

This chapter is also based on [Part 2](https://x.com/poteto/status/2097732320606507506) of *The Complete Guide to pstack*, which I call "the guide" from here on.

In [Chapter 37](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/6a59d6), this book summarized the guide in [13 key points](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/6a59d6#the-thirteen-key-points%2C-and-how-key-points-1-to-4-connect).

This chapter explains the remaining key points, 9 to 13.

## Key point 9: compare and merge several designs with /architect

In a large change, the human spends time on the architecture, the data structures, and how systems connect. The agent spends its time on the details of the implementation.

The agent does not start implementing right away, though. <strong>It first compares several design options, merges them into one, and only then implements.</strong>

<a id="the-guide's-view%3A-poteto-spends-time-on-architecture"></a>


### The guide's view: poteto spends time on architecture

In the section "Architecting bigger changes", poteto writes that <strong>for an engineer in the age of agents, it matters more to spend time on the following</strong>.

- Designing the architecture
- Choosing the right data structures
- Deciding how the systems you build connect to each other

poteto also writes that <strong>the agent fills in the details of the implementation</strong>.

The guide names `/architect` as the Skill that moves through a design in clear stages. The example request is this one line.

```
/architect this new <feature request>
```

The guide explains the flow of [`/architect`](https://github.com/cursor/plugins/blob/main/pstack/skills/architect/SKILL.md) in the following five stages.

1. Investigate the problem
2. Sketch skeletons
3. Evaluate and merge
4. Implement against the skeleton
5. Throw the design away if it is wrong

As a diagram, the flow looks like this.

<a id="1.-investigate-the-problem"></a>


#### 1. Investigate the problem

The agent investigates the existing mechanisms that the new code touches with `/how` and `/why`.

<aside class="msg message"><span class="msg-symbol">!</span><div class="msg-content">
<ul class="code-line" data-line="106">
<li class="code-line" data-line="106">
<strong><code>/how</code></strong> is the Skill that investigates how the code works now (<a href="https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/031877" target="_blank">Chapter 22</a>).</li>
<li class="code-line" data-line="107">
<strong><code>/why</code></strong> is the Skill that investigates why the code has its current shape (<a href="https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/031877" target="_blank">Chapter 22</a>).</li>
</ul>
</div></aside>

The agent then gets an accurate picture of which module is responsible for what, and of the existing constraints.

<a id="2.-sketch-skeletons"></a>


#### 2. Sketch skeletons

The agent has several models produce design options in parallel, without showing any model the other models' options (the `SKILL.md` of `/architect` uses `/arena` for this).  
In many cases it uses models from different families.

<aside class="msg message"><span class="msg-symbol">!</span><div class="msg-content">
<p class="code-line" data-line="118"><strong><code>/arena</code></strong> is the Skill that has several agents solve the same task separately (<a href="https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/2df1db" target="_blank">Chapter 24</a>).</p>
</div></aside>

Each model's option is a design package with the following four parts.

- <strong>How the caller uses it.</strong> This is the code on the side that uses what you build. Part 1 of the example code below shows it.
- <strong>The definitions of the central types.</strong> These are the shapes of the data at the center of the design. In part 2 of the example code below, they are `RateLimiterOptions` and `RateLimiter`.
- <strong>The signatures of the public functions.</strong> These are the names, arguments, and return types of the functions that other code can call. In part 2 of the example code below, the first line of `createRateLimiter` is a signature.
- <strong>A short document with the reasons for the design.</strong> This document, about one page long, says why the design has this shape and which other shapes the model considered and rejected. This part alone is prose, not code. The file `references/rationale-template.md` in `/architect` defines how to write it.

The model usually writes the first three parts as skeleton code.

<aside class="msg message"><span class="msg-symbol">!</span><div class="msg-content">
<p class="code-line" data-line="131"><strong>Skeleton.</strong> Code that writes only the shapes of types and functions, without their bodies yet (<a href="https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/2df1db" target="_blank">Chapter 24</a>).</p>
</div></aside>

Each model that produces an option also checks its own option from the following three angles.

- <strong>Depth of the interface.</strong> Does the side that uses it see few functions and types, while those hide a lot of work? (For example, can one call to `tryAcquire` handle both counting requests and resetting the count every minute internally?)
- <strong>Failures when a weaker model works with it.</strong> Check whether a weaker model, which later writes code against the design, produces an implementation that satisfies the design.
- <strong>Matching against the four red flags.</strong> `/architect` has a list of four design red flags ([`references/design-red-flags.md`](https://github.com/cursor/plugins/blob/main/pstack/skills/architect/references/design-red-flags.md)) ([Chapter 24](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/2df1db)). The four are shallow modules, information leakage, temporal decomposition, and pass-through methods. If an option matches any of them, the model fixes or rejects it.

<a id="3.-evaluate-and-merge"></a>


#### 3. Evaluate and merge

A judge evaluates each option against a strict rubric. The judge is a different model from the main agent, the original agent that started the models that produce the options.

The main agent takes the options and their evaluations into account and merges the options into one design.

The bundled guide [`docs/guide/04-design.md`](https://github.com/cursor/plugins/blob/main/pstack/docs/guide/04-design.md) explains how the merging agent works. It reads every option to the end, picks one option as the base, takes in the good parts of the other options, and verifies the result.

<a id="4.-implement-against-the-skeleton"></a>


#### 4. Implement against the skeleton

The agent replaces the placeholder bodies of the skeleton with real code. A placeholder body is code such as `throw new Error("not implemented")` that stands in for the real body.

If the agent finds during implementation that a function needs an argument or state it did not expect, it does not quietly work around the mismatch inside the implementation. It makes the mismatch visible.

The section "Phase D: Implement against the sketch" in the `SKILL.md` of `/architect` then has the agent ask again which of the following is the cause.

- The skeleton was wrong
- A requirement was missed
- The implementation does more than it needs to

<a id="5.-throw-the-design-away-if-it-is-wrong"></a>


#### 5. Throw the design away if it is wrong

If the agent finds during implementation that the skeleton was wrong, it throws everything away and starts over from the beginning ([key point 10](#key-point-10%3A-when-implementation-shows-the-design-is-wrong%2C-revise-the-design)).

<a id="pstack%3A-%2Farchitect-is-for-changes-that-cross-function-boundaries-and-changes-that-move-responsibility"></a>


### pstack: /architect is for changes that cross function boundaries and changes that move responsibility

The bundled guide [`docs/guide/04-design.md`](https://github.com/cursor/plugins/blob/main/pstack/docs/guide/04-design.md) says that most changes do not need design work that compares and merges several options.

It then names <strong>changes that cross a function boundary and changes that move ownership of a responsibility</strong> as the targets of `/architect`. Ownership here means which module is responsible for something.

Here is an example of my own. A change that alters the shape of a function's arguments or return value crosses a function boundary, because the code that calls the function has to change too.

For example, suppose you change the return value of `getPrice`, a function that returns the price of an item, from the amount alone to "the amount and the currency".

```
// price.ts (before): returns only the amount
function getPrice(itemId: string): number {
  // ...
}

// price.ts (after): returns the amount and the currency
function getPrice(itemId: string): { amount: number; currency: string } {
  // ...
}
```

The shape of the return value changes, so the code that calls `getPrice` must change with it.

A change that moves the job of holding a cache from the screen code to the module that fetches data is a change that moves ownership of a responsibility.

Before the change, the screen code holds its own cache.

```
// UserPage.ts (before): the screen code holds the cache
const cache = new Map<string, User>();

async function showUser(id: string) {
  const user = cache.get(id) ?? (await fetchUser(id));
  cache.set(id, user);
  render(user);
}
```

After the change, the module that fetches data holds the cache, and the screen code only calls `fetchUser`.

```
// userApi.ts (after): the module that fetches data holds the cache
const cache = new Map<string, User>();

export async function fetchUser(id: string): Promise<User> {
  const cached = cache.get(id);
  if (cached) return cached;
  const user = await request(`/users/${id}`);
  cache.set(id, user);
  return user;
}

// UserPage.ts (after): only calls it, without caring about the cache
async function showUser(id: string) {
  render(await fetchUser(id));
}
```

The job of holding the cache has moved from the screen code to `userApi.ts`. This kind of change moves ownership of a responsibility.

So a change that reaches beyond one function, into the contract with other code, such as the shapes of arguments and return values, or into the division of jobs, starts from design with `/architect`.

`04-design.md` states that when `/poteto-mode` receives a request, it applies this criterion and decides on its own whether to use `/architect`.

So <strong>the user does not need to decide every time whether to use `/architect`</strong>.

The user calls `/architect` or other Skills directly mainly when they want to check the design more thoroughly, or more briefly, than `/poteto-mode` does by default.

<a id="key-point-10%3A-when-implementation-shows-the-design-is-wrong%2C-revise-the-design"></a>


## Key point 10: when implementation shows the design is wrong, revise the design

During implementation, the agent may find a mismatch with the skeleton or a workaround that keeps coming back. The agent treats either one as evidence that the design is wrong and <strong>revises the design. If needed, the agent throws the skeleton away and redoes the design from the first stage, the investigation of the problem</strong>.

For example, during implementation a function may turn out to need an argument that the skeleton does not have. The missing argument is a mismatch with the skeleton.

When the agent writes `as any` in the same form in many places to read a field that the data type does not have, the repeated `as any` is a workaround that keeps coming back.

<a id="the-guide's-view%3A-the-same-workaround-in-unrelated-places%2C-or-escape-hatches-in-the-types%2C-is-evidence-that-the-design-is-wrong"></a>


### The guide's view: the same workaround in unrelated places, or escape hatches in the types, is evidence that the design is wrong

After it explains the five stages of `/architect`, the section "Architecting bigger changes" sums up when to throw a design away in this one sentence.

> If the same workaround appears across unrelated call sites, or if the types require escape hatches like any or forced casts, that is empirical proof that the architecture is wrong.

The quote names the following two signs.

- The same workaround appears in unrelated call sites
- The types need escape hatches such as `any` or forced casts. An example of a forced cast is `as unknown as User`

Here is how the two signs show up in an example of my own.

The `Order` type that the skeleton defines has no currency field.  
When the agent implements the code, though, three unrelated places all need the currency: the invoice, the email, and the admin screen.

```
// The type decided in the skeleton: no currency field
type Order = { id: string; total: number };

// An order to display or send
declare const order: Order;

// invoice.ts: reads a field the type does not have through a type escape hatch (as any)
const invoiceCurrency = (order as any).currency ?? "JPY";

// mail.ts: writes the same workaround in another, unrelated place
const mailCurrency = (order as any).currency ?? "JPY";

// admin.ts: writes the same workaround in yet another place
const adminCurrency = (order as any).currency ?? "JPY";
```

The agent writes the same workaround in three places <strong>not because the code in each place is badly written, but because the `Order` type in the skeleton has no currency field</strong>.

So when the same workaround or type escape hatch shows up in unrelated places, <strong>you need to revise the design itself, not the individual places</strong>.

<a id="pstack%3A-whether-to-throw-the-design-away-depends-on-whether-the-signs-repeat"></a>


### pstack: whether to throw the design away depends on whether the signs repeat

The [`SKILL.md`](https://github.com/cursor/plugins/blob/main/pstack/skills/architect/SKILL.md) of `/architect` asks the agent to decide whether to throw the design away <strong>by whether a sign repeats in the same form, not by whether it appeared once</strong>.

The same `SKILL.md` asks the agent <strong>not to conclude right away that the design is wrong when it finds a sign</strong>. A few edge-case handlers do not by themselves show that the design is wrong, because the problem itself may be complex.

The guide's quote names type escape hatches as a sign. Under the same `SKILL.md`, though, one `any` that appears once in one place is not by itself a reason to throw the design away.

On the other hand, once the agent starts to write the same workaround in three unrelated call sites, as in the invoice, email, and admin screen example, it treats that workaround as a sign to throw the skeleton away.

The section "Phase E: Scrap when the architecture is wrong" of the same `SKILL.md` also names four more signs as material to decide whether to throw the design away. They come in addition to the two signs above, the same workaround and type escape hatches.

1. Several unrelated edge cases each need their own branch
2. The skeleton said no state is shared, but during implementation the agent thinks "this needs a lock"
3. The caller cannot use the module without knowing its internal rules (for example, an initialization function must be called first)
4. During implementation, a mismatch with the skeleton appears in the same form, independently, two or more times

Below are code examples of these four signs.

<a id="key-point-11%3A-split-the-work-into-small-tasks-you-can-verify"></a>


## Key point 11: split the work into small tasks you can verify

Once the design is settled, the agent uses the planning Playbook "[<strong>Multi-phase or multi-PR plan</strong>](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/playbooks/multi-phase-plan.md)" and <strong>splits the work into small PRs that it can verify one by one</strong>.

For each PR, it then writes in the plan document what the agent must confirm before the PR counts as finished, such as a log line, a screenshot, or a test run result.

<a id="the-guide's-view%3A-the-planning-playbook-usually-comes-after-the-design"></a>


### The guide's view: the planning Playbook usually comes after the design

In the section "Okay but I really want a planning doc", poteto writes that pstack has no planning Skill, but it has a Playbook that plans in several phases.

He adds that, after the agent has produced a design he is satisfied with, <strong>he usually uses this planning Playbook ("Multi-phase or multi-PR plan") to turn the design into a plan that spells out the steps of execution</strong>.  
(An example of a plan document this Playbook produces appears later in "[Example of a finished plan document](#example-of-a-finished-plan-document)".)

The request the guide gives is this one line.

```
/poteto-mode turn this design into a plan
```

With this Playbook, the agent builds each task in the plan around the evidence that shows the task is finished and the way to confirm it, which is verification.

After the human approves the plan, the agent carries it out item by item.  
Each PR in the plan is <strong>small, self-contained, and easy to review</strong>.

<a id="pstack%3A-the-plan-document-lists-the-finish-evidence-and-how-to-verify-it-for-each-pr"></a>


### pstack: the plan document lists the finish evidence and how to verify it for each PR

The file of the "[<strong>Multi-phase or multi-PR plan</strong>](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/playbooks/multi-phase-plan.md)" Playbook (`playbooks/multi-phase-plan.md`) sets out the following five points.

- The plan is the artifact, and the agent does not implement
- Before writing, settle open questions with prototypes
- One change per PR, with its evidence
- Tests alone do not count as verified
- Execute only after the user says to start

At the end, I show an example of a finished plan document that follows these five points.

<a id="the-plan-is-the-artifact%2C-and-the-agent-does-not-implement"></a>


#### The plan is the artifact, and the agent does not implement

<strong>With this Playbook, the agent produces only the plan document and writes no code</strong>.

The execution Playbook that the plan document names carries out the plan.

The execution Playbook is either "<strong>Autopilot-full</strong>" or "<strong>Autopilot-stack</strong>". To run a whole program of work that lasts many days, the agent uses "<strong>Orchestrate</strong>". [Chapter 16](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/3b2bef) covers all three.

<a id="before-writing%2C-settle-open-questions-with-prototypes"></a>


#### Before writing, settle open questions with prototypes

For each open question, such as "which approach is faster", the agent runs the "[<strong>Prototype</strong>](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/playbooks/prototype.md)" Playbook ([Chapter 12](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/4f3e0a)).

It then records the evidence from the prototypes, such as branches, commits, and screenshots, in the appendix of the plan document.

The step follows the same idea as key point 8 (have the agent answer questions with experiments) in [Chapter 38](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/006bc8). Chapter 38 states key point 8 as follows.

> The human does not answer questions that building and running something can answer, and does not make the agent wait for a human reply. <strong>The human has the agent answer them with experiments</strong>.

<a id="one-change-per-pr%2C-with-its-evidence"></a>


#### One change per PR, with its evidence

The plan document describes the PRs one at a time, separated by headings (`##`). For example, a plan document with two PRs has the following shape.

```
# Plan: rate limiting for webhooks

## Build a RateLimiter that counts requests per sender (PR 1)
(Write the fields below for PR 1.)

## Add per-sender rate limiting (PR 2)
(Write the same fields for PR 2.)
```

Under every heading, write the following fields in order. The end of this section shows a finished version with the contents filled in.

- Depends on
- Files to change
- Changes to make
- Observable result, such as a log line or the state of a screen
- Unit tests
- Live verification, in which you operate the running app to confirm the result
- Performance check
- User review ([Chapter 16](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/3b2bef) calls this the "operator" check. Only a PR that changes the flow of what the user does needs it. For any other PR, write "None".)
- Merge

For example, if you write these fields under the PR 2 heading of the outline above, the result looks like this.

```
## Add per-sender rate limiting (PR 2)

**Depends on**: PR 1 (Build a RateLimiter that counts requests per sender)

**Files to change**
- [ ] Edit `src/webhooks/handleWebhook.ts`

**Changes to make**
- [ ] In `handleWebhook`, call `limiter.tryAcquire(senderId)` and return 429 when the limit is exceeded

**Observable result**
- [ ] When the same sender sends 61 requests in one minute, the log shows `rate_limited sender=sender-a` on the 61st

**Unit tests** (tests alone do not count as verified)
- [ ] Add a case "the 61st returns 429" to `handleWebhook.test.ts` and run `npm test`

**Live verification**
- [ ] Send 61 webhooks to the running server and confirm that the 61st gets 429

**Performance check**
- [ ] Compare the processing time per webhook before and after the change

**User review**: None (the user's flow does not change)

**Merge**
- [ ] Merge only after the unit tests, live verification, and performance check are all checked
```

<a id="tests-alone-do-not-count-as-verified"></a>


#### Tests alone do not count as verified

The Playbook makes the following two sentences its rule for verification.

> Tests alone are not sufficient verification. A PR is verified only when its unit, live, and perf boxes are all checked.

<a id="execute-only-after-the-user-says-to-start"></a>


#### Execute only after the user says to start

The agent gives the user the location of the plan document and the result of the format check (`check-plan.mjs`), and stops.

It does not start execution until the user says to start.

<span class="line"><span style="color:#FFAB70">-</span><span style="color:#E1E4E8"> [ ] When the same sender sends 61 requests in one minute, the log shows </span><span style="color:#79B8FF">`rate_limited sender=sender-a`</span><span style="color:#E1E4E8"> on the 61st</span></span>
<span class="line"></span>
<span class="line"><span style="color:#E1E4E8;font-weight:bold">**Unit tests**</span><span style="color:#E1E4E8"> (tests alone do not count as verified)</span></span>
<span class="line"><span style="color:#FFAB70">-</span><span style="color:#E1E4E8"> [ ] Add a case "the 61st returns 429" to </span><span style="color:#79B8FF">`handleWebhook.test.ts`</span><span style="color:#E1E4E8"> and run </span><span style="color:#79B8FF">`npm test`</span></span>
<span class="line"></span>
<span class="line"><span style="color:#E1E4E8;font-weight:bold">**Live verification**</span></span>
<span class="line"><span style="color:#FFAB70">-</span><span style="color:#E1E4E8"> [ ] Send 61 webhooks to the running server and confirm that the 61st gets 429</span></span>
<span class="line"></span>
<span class="line"><span style="color:#E1E4E8;font-weight:bold">**Performance check**</span></span>
<span class="line"><span style="color:#FFAB70">-</span><span style="color:#E1E4E8"> [ ] Compare the processing time per webhook before and after the change</span></span>
<span class="line"></span>
<span class="line"><span style="color:#E1E4E8;font-weight:bold">**User review**</span><span style="color:#E1E4E8">: None (the user's flow does not change)</span></span>
<span class="line"></span>
<span class="line"><span style="color:#E1E4E8;font-weight:bold">**Merge**</span></span>
<span class="line"><span style="color:#FFAB70">-</span><span style="color:#E1E4E8"> [ ] Merge only after the unit tests, live verification, and performance check are all checked</span></span>
<span class="line"></span></code></pre></div>
<p class="code-line" data-line="608">The real Playbook template asks for more detail. For example, the template splits live verification into 10 angles, and each angle gets a screenshot and a pass condition. There is also a section before the PRs that describes how the whole plan proceeds, and an appendix after them that holds the prototype evidence and similar material.</p>
</div></details>

So <strong>the plan document sets the finish evidence and the way to verify it for each PR. The plan runs only after the user says to start</strong>.

<a id="key-point-12%3A-the-plan-document-is-temporary"></a>


## Key point 12: the plan document is temporary

The plan document is a <strong>temporary document</strong>. It serves two purposes: to carry out the work, and to tell other agents about the progress of a large piece of work.

<a id="the-guide's-view%3A-delete-the-plan-document-when-you-finish%2C-as-a-rule"></a>


### The guide's view: delete the plan document when you finish, as a rule

poteto writes that in a large project that takes about a week, he sometimes commits the plan document to the repository for a while so that other agents know about the work in progress.

<strong>When the work is done, though, he usually deletes the plan document</strong>, so that it leaves no confusion in the codebase.

He also writes that he sees no value in a plan document that stays forever.

<a id="pstack%3A-the-plan-document-goes-in-docs%2F-of-the-agent-store"></a>


### pstack: the plan document goes in docs/ of the agent store

The "<strong>Multi-phase or multi-PR plan</strong>" Playbook says to <strong>write the plan document in `docs/` of the agent store</strong> unless the user names a location.

<aside class="msg message"><span class="msg-symbol">!</span><div class="msg-content">
<p class="code-line" data-line="630"><strong>Agent store.</strong> The storage area that the agent uses. The agent's system prompt states where the store is, as the "Orchestrate" Playbook describes.</p>
</div></aside>

<a id="key-point-13%3A-what-to-tell-%2Fpoteto-mode"></a>


## Key point 13: what to tell /poteto-mode

The human does not list steps for `/poteto-mode`. The human tells it <strong>the goal, the constraints, the results they want to see, and when to review</strong>.

<a id="the-guide's-view%3A-%2Fpoteto-mode-alone-is-usually-enough"></a>


### The guide's view: /poteto-mode alone is usually enough

The guide writes that `/poteto-mode` automatically uses many of the Skills the guide introduces, so <strong>the human can usually send the request to `/poteto-mode` alone</strong>.

The section "The workflow in practice" gives an example request for each of four situations.

<a id="example-1%3A-investigating-a-bug-with-an-unknown-cause"></a>


#### Example 1: investigating a bug with an unknown cause

The first is the investigation of a bug in production whose cause is unclear.

```
/poteto-mode investigate why background workers periodically fail with timeout errors. give me a breakdown of what we know, what data you used, and your best hypotheses.
```

Besides the goal, this request specifies the shape of the result: what we know, what data was used, and the best hypotheses.

The agent that receives this request investigates the code, checks metrics and past commits in parallel, and returns its best guesses about where the problem is likely to be.

<a id="example-2%3A-asking-for-a-design"></a>


#### Example 2: asking for a design

The second is a new mechanism that other modules depend on.

poteto asks for a design that adds rate limiting to webhooks that come from outside.

```
/poteto-mode we need to add rate limiting for external webhooks. /architect this first, and answer any open questions with prototypes. let me review before proceeding.
```

<aside class="msg message"><span class="msg-symbol">!</span><div class="msg-content">
<p class="code-line" data-line="666"><strong>Webhook.</strong> A mechanism that tells another system about an event by sending an HTTP request to a URL you specify (<a href="https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/e5f103" target="_blank">Chapter 25</a>).</p>
</div></aside>

Besides how to proceed with the design, this request names a place to stop: "let me review before proceeding".

The agent that receives this request investigates the current webhook mechanism, has several models compete on design options, measures performance with throwaway prototypes, and produces a clean, verified interface.

<a id="example-3%3A-planning-a-migration"></a>


#### Example 3: planning a migration

The third is a plan for a migration that spans many files. poteto asks for a plan, split into several PRs, to move the whole UI library to [StyleX](https://stylexjs.com/), a library for writing styles inside JavaScript code.

```
/poteto-mode create a plan to migrate our entire UI library to StyleX. break the migration into small, verifiable PRs. each PR must have its visual regression tests and live verification steps. i want the final result to be 100% identical compared to the original - bugs included
```

The request states the goal, which is to move the whole UI library to StyleX, but not the steps of the migration. Besides the goal, it specifies the following three things.

- <strong>How to split the migration.</strong> Into small PRs that the agent can verify one by one.
- <strong>The verification each PR must have.</strong> Visual regression tests and steps to confirm the result in the running app.
- <strong>The condition on the final result (a constraint).</strong> Identical to the original, bugs included.

The agent that receives this request splits the work into independent phases and writes a checklist that a person can review. It prepares each phase so that the phase can move safely through build, verification, and merge.

<a id="example-4%3A-fixing-a-bug-reported-in-slack"></a>


#### Example 4: fixing a bug reported in Slack

The fourth is a fix for a bug that someone reported in Slack.

This situation has two requests.

The first request is for when the Slack thread already has enough context.

```
# thread already has sufficient context
/poteto-mode do it
```

The second request specifies the way to reproduce the bug and the evidence.

```
/poteto-mode repro this with /control-app. if it repros on main, fix it and show me a video as proof
```

<aside class="msg message"><span class="msg-symbol">!</span><div class="msg-content">
<p class="code-line" data-line="709"><strong>Verification skill.</strong> A project-specific Skill that lets the agent start and operate the app to collect evidence.<br/>
The agent creates it when the user runs <code>/create-verification-skill</code>.</p>
</div></aside>

`/control-app` is the name the guide uses for the verification skill built in [Part 1](https://x.com/poteto/status/2094457600259842065) of *The Complete Guide to pstack* ([Chapter 36](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/c9901e)).

<a id="what-the-four-examples-share"></a>


#### What the four examples share

So every request in the four situations <strong>hands off the detailed steps to `/poteto-mode` and gives the goal, plus the following as needed</strong>.

- Constraints
- The results you want to see (the shape of the result)
- When to review (where to stop)

Some requests also name the tool to use, such as `/architect` in [Example 2](#example-2%3A-asking-for-a-design) and `/control-app` in [Example 4](#example-4%3A-fixing-a-bug-reported-in-slack).

In the `do it` request of [Example 4](#example-4%3A-fixing-a-bug-reported-in-slack), the goal and the context are in the Slack thread, not in the request.

<a id="pstack%3A-name-a-skill-only-when-you-want-to-override-a-choice"></a>


### pstack: name a Skill only when you want to override a choice

The bundled guide [`docs/guide/02-poteto-mode.md`](https://github.com/cursor/plugins/blob/main/pstack/docs/guide/02-poteto-mode.md) explains that `/poteto-mode` looks at the kind of request, picks a Playbook, and calls the Skills it needs within the Playbook's steps.

So <strong>the user does not have to write in the request which Skills to use in which order</strong>.

The same page recommends that you name a Skill only in the following case ([Chapter 7](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/55bbdb)).

> Name a skill only when you want to override a specific choice.

For a change that adds a new mechanism other modules depend on, as in [Example 2](#example-2%3A-asking-for-a-design), `/poteto-mode` may also pick `/architect` on its own with the following criterion from [key point 9](#key-point-9%3A-compare-and-merge-several-designs-with-%2Farchitect) (compare and merge several designs with `/architect`).

> It then names <strong>changes that cross a function boundary and changes that move ownership of a responsibility</strong> as the targets of `/architect`. Ownership here means which module is responsible for something.

In this book, I read the `/architect` in the request of [Example 2](#example-2%3A-asking-for-a-design) as a way to make sure the agent designs before it implements, instead of leaving the choice of `/architect` to `/poteto-mode`.

<a id="reading-the-13-key-points-as-one-flow"></a>


## Reading the 13 key points as one flow

Lined up, the 13 key points form the three-stage flow shown in the table in "[Chapters in this part](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/c2adb6#chapters-in-this-part)" of [Part VI](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/c2adb6).

1. <strong>Understand the problem</strong> (key points 1 to 4, [Chapter 37](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/6a59d6)). The human gets the agent to understand the problem the way the human does and to carry over the context of past work.
2. <strong>Test solutions</strong> (key points 5 to 8, [Chapter 38](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/006bc8)). The agent tests solutions with documents that describe the usage and with prototypes, and the human chooses a design option.
3. <strong>Settle the solution and turn it into an executable plan</strong> (key points 9 to 13, this chapter). The agent compares several options to settle the design, revises the design based on evidence from implementation, and turns the design into a plan it can verify. The plan document is temporary, and poteto says he usually deletes it when the work is done. The human tells `/poteto-mode`, the entry point, the goal, the constraints, the results they want to see, and when to review, not the steps.

In this book, I read what the three stages share as this: <strong>base decisions on evidence from investigation and on the results of running things, not on a plan made only of prose</strong>.

Specifically, decisions rest on the following two kinds of evidence.

- Evidence from investigating the code and its history ([Key point 3: learn the mechanism and the reasons with /how, /why, and /teach](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/6a59d6#key-point-3%3A-learn-the-mechanism-and-the-reasons-with-%2Fhow%2C-%2Fwhy%2C-and-%2Fteach) and [Key point 4: carry past work into a new conversation with /recall](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/6a59d6#key-point-4%3A-carry-past-work-into-a-new-conversation-with-%2Frecall))
- Evidence from building and running things, such as the results of operating a prototype, measurements, and the same workaround showing up in unrelated places during implementation ([Key point 7: compare prototypes of several options](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/006bc8#key-point-7%3A-compare-prototypes-of-several-options), [Key point 8: have the agent answer questions with experiments](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/006bc8#key-point-8%3A-have-the-agent-answer-questions-with-experiments), and [Key point 10: when implementation shows the design is wrong, revise the design](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/f87769#key-point-10%3A-when-implementation-shows-the-design-is-wrong%2C-revise-the-design))

In its last section, "The art of planning", the guide also writes that <strong>an abstract plan gives the human only the illusion that work is moving forward</strong>. An abstract plan is a plan made only of prose that has not yet taken shape in code.

It also writes that a long plan document makes the human and the agent look as if they worked hard, but probably has little behind it.

The guide then says that pstack <strong>is a tool that combines the following three things</strong>.

- Thorough investigation
- Evidence from trying things
- Rigorous verification

It closes the section with these sentences.

> When you plan this way, engineering with agents stops feeling like a gamble. It becomes predictable and repeatable.

<a id="summary"></a>


## Summary

- <strong>Key point 9: compare and merge several designs with /architect.</strong> In a large change, the human spends time on the architecture, the data structures, and how systems connect. The agent spends its time on the details of the implementation. With `/architect`, the agent first compares several design options, merges them into one, and only then implements.
- <strong>Key point 10: when implementation shows the design is wrong, revise the design.</strong> The agent may find a mismatch with the skeleton, or see the same workaround or type escape hatch keep showing up in unrelated places. It treats either one as evidence that the design is wrong and revises the design. If needed, it throws the skeleton away and redoes the design from the first stage, the investigation of the problem.
- <strong>Key point 11: split the work into small tasks you can verify.</strong> With the planning Playbook, the agent splits the work into small PRs that it can verify one by one. For each PR, the finish evidence includes the results of running the code, in addition to tests. The plan runs only after the user says to start.
- <strong>Key point 12: the plan document is temporary.</strong> The agent uses the plan document as a temporary document to carry out the work and to tell other agents about the progress of a large piece of work. poteto usually deletes it when the work is done.
- <strong>Key point 13: what to tell /poteto-mode.</strong> The human tells `/poteto-mode` the goal, the constraints, the results they want to see, and when to review, not the steps.
- <strong>The flow of the 13 key points.</strong> In this book, I read what every stage shares as this: base decisions on evidence from investigation and on the results of running things, not on a plan made only of prose.
