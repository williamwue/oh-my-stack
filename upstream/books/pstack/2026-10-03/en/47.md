<strong>RGDD</strong> (<strong>README-driven with Grill Driven Development</strong>) is a way of developing that I came up with when I used the ideas in this book and pstack on my personal projects.

In RGDD, the developer puts <strong>the context the agent reads into the codebase before the code</strong>, and develops while the agent reads that context.

<aside class="msg message"><span class="msg-symbol">!</span><div class="msg-content">
<p class="code-line" data-line="5"><strong>Context</strong> is the set of files, mostly in the repository, that the agent reads again each time it works.<br/>
It stays after a conversation ends.</p>
</div></aside>

In [Chapter 4](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/3cc0dd), I treated the codebase as the agent's memory and wrote the following.

> The memory that lets the agent carry forward earlier decisions belongs in the <strong>codebase</strong>, not in the model.

Besides code, RGDD uses the following documents as context.

- <strong>README.</strong> A document that says who uses the software, for what, and how. Usage instructions and a tutorial are examples.
- <strong>`GLOSSARY.md`.</strong> A document that lists domain terms and their definitions, such as what "order" means. A domain term is a word for the business or the things the software deals with.
- <strong>ADR</strong> (Architecture Decision Record). A record of a design decision and the reason for it, such as why the team chose a particular database.
- <strong>Coding standards.</strong> The rules for how to write code, such as the rules in `CODING_STANDARDS.md`.
- <strong>Feature Map and verification skill.</strong> A verification skill is a project-specific Skill that lets the agent start and operate the app to collect evidence. The Feature Map is a document inside that skill. For each feature of the app, the Feature Map says how to reach the feature and how to verify it ([Chapter 36](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/c9901e)).

Of these, the developer puts the README, `GLOSSARY.md`, and ADRs in place before the code. The developer has the agent create the Feature Map and the verification skill after the first feature works.

This appendix explains the ideas behind RGDD and how to carry it out.

<a id="how-this-appendix-is-organized"></a>


## How this appendix is organized

This appendix covers the following topics.

- RGDD builds context with README-driven development and /grill-with-docs, then uses it to develop and verify
- RGDD adds to the context and verifies and updates it in five phases
- The context keeps growing because each phase reads the previous phase's context and adds to it
- Context comes first so that the examples the agent reads are right from the start
- Summary: put the context before the code

<p class="code-line" data-line="36"><strong>The context grows</strong> means that each piece of work adds terms and decisions to the context files, and that the developer and the agent keep verifying, correcting, and updating the content already there.</p>
</div></aside>

## RGDD builds context with README-driven development and /grill-with-docs, then uses it to develop and verify

<strong>In RGDD, the developer combines README-driven development with Matt Pocock's Skill [/grill-with-docs](https://github.com/mattpocock/skills/blob/main/skills/engineering/grill-with-docs/SKILL.md) to build context. The developer then uses that context to develop and verify</strong>.

<aside class="msg message"><span class="msg-symbol">!</span><div class="msg-content">
<p class="code-line" data-line="44"><strong>README-driven development</strong> is a way of developing that starts with a README that explains usage to the intended users, then works backward to the implementation and the architecture.</p>
</div></aside>

I explain README-driven development in ["1. Write the user's view of the app in the README"](#1.-write-the-user's-view-of-the-app-in-the-readme) and `/grill-with-docs` in ["2. Create domain terms and ADRs with /grill-with-docs"](#2.-create-domain-terms-and-adrs-with-%2Fgrill-with-docs).

RGDD rests on the idea from Chapter 4, quoted at the start, that the codebase is the agent's memory.

poteto writes the following in the section "Keep agents smart with Feature Maps" of *The Complete Guide to pstack* [Part 1](https://x.com/poteto/status/2094457600259842065).

> Personally, I think your codebase is the ultimate form of memory. Code is a projection of the decision making you and your team have made and represents the source of truth for what's happened and how things actually work.

In the same section, poteto describes the Feature Map this way.

> A Feature Map is just a more compact form of that, designed to save tokens.

A Feature Map holds the following.

- What features exist and what each one does
- How a user reaches each feature
- How to operate each feature with the verification skill
- What you need to see to say that the feature works

<strong>RGDD widens what the context holds. The README holds "who uses it, for what, and how", `GLOSSARY.md` holds "which words to use", and the ADRs hold "why we decided this way"</strong>.

The five phases do not create the coding standards. The coding standards are rules the agent follows when it writes code with [`/poteto-mode`](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/SKILL.md). So I leave them out of the five phases in the next section. `/poteto-mode` is pstack's entry Skill, which routes each request to the right way of working ([Chapter 7](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/55bbdb)).

Also, <strong>the README does not have to be named `README.md`</strong>.

A specification or another document can play the README's role, as long as it describes usage from the user's side and the other context starts from it.

<a id="rgdd-adds-to-the-context-and-verifies-and-updates-it-in-five-phases"></a>


## RGDD adds to the context and verifies and updates it in five phases

The developer carries out RGDD in these five phases.

1. Write the user's view of the app in the README
2. Create domain terms and ADRs with `/grill-with-docs`
3. Develop with `/poteto-mode`
4. Review with `/thermos`
5. Verify with `/create-verification-skill`

Each phase does one of two jobs. It <strong>adds to the context, or it verifies what the context holds and corrects or updates it</strong>.

For each phase below, I explain what it creates, the tool it uses, and the context it leaves behind.

<a id="1.-write-the-user's-view-of-the-app-in-the-readme"></a>


### 1. Write the user's view of the app in the README

- <strong>What it creates.</strong> A README that gives usage instructions and a tutorial from the point of view of the app's user. It does not cover the implementation yet.
- <strong>Tool.</strong> In RGDD, the developer writes the README by hand, without a Skill, a CLI, or any other tool. [Key point 5](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/006bc8#key-point-5%3A-write-the-usage-first) (write the usage first) of [Chapter 38](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/006bc8) showed a different approach, in which the agent writes the README.

  > Before the implementation, the human has the agent <strong>write the usage in a README or a tutorial</strong>, and has it work backward from that usage to the API and the internals.
- <strong>Context it leaves.</strong> Context about how people use the app, such as "who uses it, for what, and how." The other context starts from it.

### 2. Create domain terms and ADRs with /grill-with-docs

- <strong>What it creates.</strong> A `GLOSSARY.md` that lists the domain terms, and ADRs that record design decisions.
- <strong>Tool.</strong> Matt Pocock's `/grill-with-docs`. The agent does not pick this Skill on its own, so the developer starts it by name.
- <strong>Context it leaves.</strong> Background knowledge, such as domain terms and their definitions (`GLOSSARY.md`), and past decisions, such as design decisions and their reasons (ADRs).

`/grill-with-docs` is <strong>a Skill that asks the developer question after question to settle a plan or a design, and creates ADRs and a glossary (`GLOSSARY.md`) along the way</strong>.

`/grill-with-docs` calls these two Skills as part of its steps.

- <strong>[`/grilling`](https://github.com/mattpocock/skills/blob/main/skills/productivity/grilling/SKILL.md).</strong> It asks the developer question after question about the plan or the design and settles what needs a decision.
- <strong>[`/domain-modeling`](https://github.com/mattpocock/skills/blob/main/skills/engineering/domain-modeling/SKILL.md).</strong> It points out conflicting terms and vague wording, and writes each settled term to `GLOSSARY.md` right away. It offers to record a decision as an ADR only when all three of these are true.
  - Hard to reverse
  - Surprising without context
  - The result of a real trade-off

The following example uses the food-ordering app to explain what each of the three conditions for an ADR means.

In this phase, <strong>the agent can write the domain terms it settles with the developer to a file, `GLOSSARY.md`, instead of leaving them only in the conversation</strong>.

Terms decided in a conversation do not carry over to the next agent once the conversation ends.

Terms written to `GLOSSARY.md`, on the other hand, are there for the next agent to read.

While the developer and the agent settle the design with `/grill-with-docs`, the agent also compares the developer's words with the term definitions in `GLOSSARY.md`.

When the developer uses wording that conflicts with a definition, the agent points out the conflict immediately. The section "Challenge against the glossary" in the [`SKILL.md`](https://github.com/mattpocock/skills/blob/main/skills/engineering/domain-modeling/SKILL.md) of `/domain-modeling` sets this rule. In the quote, "the user" is the person who uses the Skill, which in RGDD is the developer.

> When the user uses a term that conflicts with the existing language in `GLOSSARY.md`, call it out immediately.

The `_Avoid_` list in `GLOSSARY.md` is what helps the agent spot a conflict. The section "Rules" of the [`GLOSSARY-FORMAT.md`](https://github.com/mattpocock/skills/blob/main/skills/engineering/domain-modeling/GLOSSARY-FORMAT.md) of `/domain-modeling` says that when several words name the same thing, you pick the best one as the term and list the others as avoided terms.

> When multiple words exist for the same concept, pick the best one and list the others under `_Avoid_`.

For example, suppose `GLOSSARY.md` defines "order" and lists "purchase" as an avoided term. This example comes from `GLOSSARY-FORMAT.md`.

When the developer says "purchase," the agent points it out as wording that conflicts with the definition.

### 3. Develop with `/poteto-mode`

- <strong>What it creates.</strong> The code.
- <strong>Tool.</strong> The developer uses `/poteto-mode` for development ([Chapter 7](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/55bbdb)). When the developer wants to know how the code works or how it got this way, the developer uses these Skills ([Chapter 22](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/031877)).
  - [`/how`](https://github.com/cursor/plugins/blob/main/pstack/skills/how/SKILL.md) looks into how something works
  - [`/why`](https://github.com/cursor/plugins/blob/main/pstack/skills/why/SKILL.md) looks into the reasons behind a design
  - [`/recall`](https://github.com/cursor/plugins/blob/main/pstack/skills/recall/SKILL.md) gathers the history of recent work from chat history and other sources
- <strong>Context it leaves.</strong> The code itself, and PRs. The agent creates the PR in the last step of a Playbook, such as the one for adding a feature or fixing a bug. A Playbook is a step-by-step procedure for one kind of work ([Chapter 8](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/cd0205)).

In the development phase, <strong>the agent writes code while it reads the context that earlier phases created, and the coding standards if the developer has prepared them</strong>.

For light or routine work, such as feedback, QA, and bug fixes, I have Grok Bot start Cloud Agents to do the work. Grok Bot is an AI bot app ([Chapter 5](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/aa6858)). Cloud Agents is the Cursor feature that runs agents in Cursor's cloud.

Like poteto, I do not have Grok Bot do the work itself. I have it start Cloud Agents.

In [Chapter 36](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/c9901e), I described how poteto works as follows.

> <strong>When he sends the request from a Grok Bot, poteto does not have the bot do the work itself. He asks the bot to start an agent in Cloud Agents, a Cursor feature that runs agents in Cursor's cloud</strong>.

The README, `GLOSSARY.md`, ADRs, and coding standards live in the repository, so every agent that works on the repository can read them, Cloud Agents included.

<strong>The ADRs from [phase 2](#2.-create-domain-terms-and-adrs-with-%2Fgrill-with-docs) also help during development, when the developer asks `/why` for the reason behind a decision</strong>.

`/why` has a file for each kind of source it searches, and each file says how to search that source.

The file for source control history includes a step that looks for ADRs in `docs/adr/` and similar places.

So if an ADR states the reason, `/why` can base its answer on that ADR.

Even for a decision without an ADR, `/why` puts together a reason. It searches source control history, tickets, chat, and other sources in parallel, and uses the clues left there. For tickets and chat, it searches the ones connected through MCP, the mechanism that connects the agent to external tools and data.

If `/why` still finds no clues, it reports what it searched and says that the reason is Unknown.

<a id="4.-review-with-%2Fthermos"></a>


### 4. Review with `/thermos`

- <strong>What it creates.</strong> A list of review findings.
- <strong>Tool.</strong> The Cursor plugin [`/thermos`](https://github.com/cursor/plugins/tree/main/thermos).
- <strong>Context it leaves.</strong> The code after the agent fixes the findings. <strong>The steps of `/thermos` end when it merges the findings into one list</strong>. They do not include code fixes.

`/thermos` has two subagents audit the diff of the code the agent wrote in [phase 3](#3.-develop-with-%2Fpoteto-mode). The two subagents work in parallel.

<aside class="msg message"><span class="msg-symbol">!</span><div class="msg-content">
<p class="code-line" data-line="314">A <strong>subagent</strong> is a separate agent that does work that the main agent, the agent that runs <code>/thermos</code>, hands off.</p>
</div></aside>

The two audits are as follows.

- <strong>A security and correctness audit</strong>, for problems such as bugs, changes that break existing features, and security holes
- <strong>A strict code quality audit</strong>, for problems such as code that is hard to maintain, bloated files, and unneeded abstractions

When both audits finish, `/thermos` removes duplicates and merges the results into one list.

When both subagents point out the same problem, `/thermos` treats that finding as more important.

RGDD has this phase <strong>to remove ad hoc workarounds and hard-to-maintain structures before anyone merges them and they stay in the code</strong>. A workaround is code that avoids a problem for the moment without fixing its cause. If a workaround stays in the code, the next agent takes it for a correct implementation example and copies it.

[Chapter 4](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/3cc0dd) puts it this way.

> You should not keep everything as memory. If you keep an ad hoc workaround, <strong>the next agent takes it for a correct implementation and copies it. The copy then produces the next copy, and an undesirable pattern spreads without anyone noticing</strong>.

<a id="5.-verify-with-%2Fcreate-verification-skill"></a>


### 5. Verify with `/create-verification-skill`

- <strong>What it creates.</strong> A project-specific verification skill that includes a small CLI that operates the app and a Feature Map ([Chapter 36](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/c9901e)).
- <strong>Tool.</strong> pstack's [`/create-verification-skill`](https://github.com/cursor/plugins/blob/main/pstack/skills/create-verification-skill/SKILL.md), and [`/maintain-verification-skill`](https://github.com/cursor/plugins/blob/main/pstack/skills/maintain-verification-skill/SKILL.md), which keeps the verification skill and the Feature Map up to date ([Chapter 26](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/9884cb)).
- <strong>Context it leaves.</strong> Context about what features exist, how a user reaches each one, and how to verify it.

`/create-verification-skill` builds the Feature Map from an index, `features/README.md`, and one file per feature.

The index links to each feature file. Each feature file describes these four things from the user's point of view.

- What the feature is
- How to reach it
- How to operate it with the verification skill's CLI
- What you need to see to say that it works

As development goes on, the developer and the agent keep adding to the context and verifying, correcting, and updating it, as follows.

- <strong>When a new term or decision comes up.</strong> The developer settles the design again with [`/grill-with-docs`](https://github.com/mattpocock/skills/blob/main/skills/engineering/grill-with-docs/SKILL.md). The agent adds the term to `GLOSSARY.md` and offers an ADR for any decision that meets all three of these.
  - Hard to reverse
  - Surprising without context
  - The result of a real trade-off
- <strong>When a review finds a problem in the diff.</strong> The agent fixes the `/thermos` findings before anyone merges the code.
- <strong>When features are added.</strong> The developer runs `/maintain-verification-skill`. If it finds something to fix, such as a feature missing from the Feature Map, the agent puts the fixes into one PR.

The main aim of working this way is <strong>to keep leaving the right context for the agent, past context included</strong>.

This aim comes from the "gardener" idea in [Chapter 4](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/3cc0dd). Chapter 4 described the work to keep the codebase as memory this way.

> The talk compares the work of keeping this environment in shape to a <strong>gardener</strong>'s work. A garden does not stay healthy if you only add plants. You have to keep removing unneeded branches and weeds and keep maintaining it so that the plants you want can grow.
>
> The same is true of a codebase. <strong>You have to keep removing old workarounds and bad implementation examples, in addition to adding knowledge</strong>.

In RGDD, the developer and the agent do this gardener's work on the README, `GLOSSARY.md`, ADRs, and the Feature Map, in addition to the code.

- <strong>Add.</strong> Add newly settled terms and decisions to `GLOSSARY.md` and the ADRs. In the garden, this step is the planting of what you want to grow.
- <strong>Verify, then correct or update.</strong> Check term definitions that have gone stale and a Feature Map that no longer matches the app, and fix them. In the garden, this step is the removal of unneeded branches and weeds.

ADRs do most of the work to keep past context. An ADR records a decision and its reason. Even if you change the decision later, the next agent can read why the team first decided the earlier way.

The [`ADR-FORMAT.md`](https://github.com/mattpocock/skills/blob/main/skills/engineering/domain-modeling/ADR-FORMAT.md) of [`/domain-modeling`](https://github.com/mattpocock/skills/blob/main/skills/engineering/domain-modeling/SKILL.md) allows a Status at the top of an ADR, for when the team revisits a decision. There are four statuses: proposed, accepted, deprecated, and superseded by ADR-NNNN.

Because a "superseded by" status exists, this book reads the format to mean that when you change a decision, you keep the old ADR and add a new one.

<a id="context-comes-first-so-that-the-examples-the-agent-reads-are-right-from-the-start"></a>


## Context comes first so that the examples the agent reads are right from the start

When you keep context, you can pass what you decided on to the next agent.

You put that context in place before the code <strong>so that the examples the agent reads are right from the start</strong>.

In this book, I take the view that if you start with the code, the opposite of RGDD, the only way to create context is to derive it from the code afterward.

Then the context may keep even ad hoc workarounds that got into the code, as if they were correct.

A workaround left in the code becomes an example for the next agent ([phase 4](#4.-review-with-%2Fthermos)).

<a id="summary%3A-put-the-context-before-the-code"></a>


## Summary: put the context before the code

- <strong>What is RGDD?</strong> A way of developing in which you put the README, `GLOSSARY.md`, and ADRs in place before the code, and develop while the agent reads them.
- <strong>In what order does it proceed?</strong> In five phases: README, then `/grill-with-docs`, then `/poteto-mode`, then `/thermos`, then `/create-verification-skill`.
- <strong>Why does the context keep growing?</strong> Because every phase either adds to the context or verifies it and corrects or updates it.
- <strong>Why does the context come first?</strong> So that the examples the agent reads are right from the start.

The final "[Afterword](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/a465a5)" gives the book's conclusion and the first step to take after you finish reading.
