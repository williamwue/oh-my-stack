To build trust, you need to <strong>keep a one-time check in the repository in a form that gives the same result no matter who runs it or how many times</strong>.

In the second theme of the [talk](https://x.com/poteto/status/2102050467505430555), poteto names three ways to build trust.

1. Verify the artifact directly
2. Teach high-quality ways of working
3. Structure the codebase so that it is easy to understand

This chapter explains how the three ways differ, how pstack implements each one, and how to keep the lessons from corrections in a mechanism.

<a id="three-ways-to-build-trust%2C-and-how-they-differ"></a>


## Three ways to build trust, and how they differ

The three ways differ in <strong>how much they rely on the agent's own attention</strong>.  
Here are the three ways, each with an example.

1. <strong>Verify the artifact directly.</strong> Run the app for real. Use the Chrome DevTools Protocol (CDP) to take traces and heap snapshots. A trace records how long each operation took, and a heap snapshot records what is in memory at a point in time. CDP lets a program use the same features as the browser's developer tools.
2. <strong>Teach high-quality ways of working.</strong> Give the agent a pstack Playbook that sets the steps for investigation, reproduction, implementation, and verification.
3. <strong>Restructure the codebase so that it is easy to understand.</strong> Make it possible to tell, from folders, types, and process boundaries, what may be done where, which code runs where, and which imports are allowed.

The talk says that trust does not grow from effort or from the number of conversations. The scope of work you can delegate grows when you keep verification methods, work steps, and structural constraints in a form the agent can refer to.

The difference between the three ways becomes clear when you compare what the agent has to do for each one to work.

- <strong>Way 1 (verification)</strong> works only if the agent runs the tool. A tool that nobody uses checks nothing.
- <strong>Way 2 (steps)</strong> works only if the agent reads the steps and follows them. The agent can miss or misread them.
- <strong>Way 3 (structure)</strong> works even if the agent does not notice it. When types or lint express a boundary, the compiler or the lint step stops a change that crosses the boundary.

So the further you go from way 1 toward way 3, the less quality depends on the agent's attention.

<a id="way-1%3A-turn-the-way-you-verify-into-a-tool-you-can-run-any-number-of-times"></a>


## Way 1: turn the way you verify into a tool you can run any number of times

The first way is <strong>to turn the way you verify into a tool that lets anyone make the same observation any number of times</strong>.

The verification the talk asks for is not a passing compile or the agent's report that it "fixed it". The talk treats the app's behavior when you actually run it as the evidence.

<a id="in-pstack%2C-%22build-the-lever%22-and-the-verification-skill-handle-it"></a>


### In pstack, "Build the Lever" and the verification skill handle it

In pstack, the principle "[Build the Lever](https://github.com/cursor/plugins/blob/main/pstack/skills/principle-build-the-lever/SKILL.md)" and the Skill that builds a verification skill implement this way.

The principle says <strong>not to finish a task by hand, but to build a script or command that a reviewer can read and rerun</strong>. A verification skill is a project-specific Skill that lets the agent start its own app, operate it, and collect evidence.

In pstack, you build a verification skill with [`/create-verification-skill`](https://github.com/cursor/plugins/blob/main/pstack/skills/create-verification-skill/SKILL.md) and keep it current with [`/maintain-verification-skill`](https://github.com/cursor/plugins/blob/main/pstack/skills/maintain-verification-skill/SKILL.md). [Chapter 26](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/9884cb) and [Chapter 36](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/c9901e) cover what a verification skill contains and give command examples.

<a id="build-the-tool-after-one-check-by-hand%2C-and-maintain-it-afterward"></a>


### Build the tool after one check by hand, and maintain it afterward

You build a verification tool after you do the first check by hand, and you keep maintaining it after you build it.

"Build the Lever" sets this way of building a tool: <strong>process one target by hand to confirm the steps, turn those steps into a tool, then process the same target with the tool and check that the results match</strong>. For verification, the order is to do the first check by hand, turn that operation into a command, and compare whether the command reproduces the same check.

The principle's file also says that if you write that you followed this principle but the diff has no codemod, script, or similar tool, you did not apply the principle. If a PR says "verified" but <strong>has no rerunnable command or its output attached, the verification tool does not exist yet</strong> ([Chapter 36](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/c9901e)).

## Way 2: hand over an expert's way of working as steps

The second way is <strong>to give the agent a skilled engineer's pattern of work as steps</strong>. The talk gives pstack's Playbooks as the example of this way.

A Playbook is not the answer itself. It is <strong>a pattern for how to work: "this is how an expert would proceed"</strong>.

Without a pattern, the agent picks a different approach every time. With clear steps, a different agent can work at about the same quality.

<a id="an-example-playbook"></a>


### An example Playbook

For example, the "Bug fix" Playbook ([`playbooks/bug-fix.md`](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/playbooks/bug-fix.md)) sets these steps in a fixed order: reproduce the bug in the same environment, narrow down the cause with evidence, fix it, confirm the fix in the same environment, and create the PR ([Chapter 11](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/ff12ce)).

In pstack, the entry point `/poteto-mode` picks the Playbook that fits the request and copies its steps unchanged to the top of the TODO list ([README](https://github.com/cursor/plugins/blob/main/pstack/README.md)). [Part III](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/0d1535) covers all 23 Playbooks one by one.

<a id="way-3%3A-make-the-structure-of-the-codebase-itself-the-instructions"></a>


## Way 3: make the structure of the codebase itself the instructions

The third way is <strong>to make the rules visible in folders, types, and process boundaries, so that the structure of the codebase itself is the agent's instructions</strong>.

The goal is a codebase where folders, types, and process boundaries alone tell you three things.

- What may be done where
- Which code runs where
- Which imports are allowed

With a codebase like this, the agent can learn the constraints and rules from the structure without reading any explanation.

<a id="in-pstack%2C-the-architecture-principles-handle-it"></a>


### In pstack, the Architecture principles handle it

pstack groups its principles by theme, as the [list of principles in the README](https://github.com/cursor/plugins/blob/main/pstack/README.md#principles) shows. The "Architecture" group holds the principles for shaping code boundaries, types, and state handling into a structure where mistakes are less likely.

This section takes up two of them: "[Boundary Discipline](https://github.com/cursor/plugins/blob/main/pstack/skills/principle-boundary-discipline/SKILL.md)" and "[Type System Discipline](https://github.com/cursor/plugins/blob/main/pstack/skills/principle-type-system-discipline/SKILL.md)".

The README list summarizes the two principles as follows.

- "Boundary Discipline" ([`principle-boundary-discipline`](https://github.com/cursor/plugins/blob/main/pstack/skills/principle-boundary-discipline/SKILL.md)): check values that come in from outside, such as CLI arguments, config files, the network, and external APIs, at the point where the system receives them, and convert them to internal types. Internal code trusts those types and does not repeat the checks.
- "Type System Discipline" ([`principle-type-system-discipline`](https://github.com/cursor/plugins/blob/main/pstack/skills/principle-type-system-discipline/SKILL.md)): make invalid states, such as contradictory ones, impossible to express in the types.

[Chapter 18](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/e529e4) covers the two principles in detail.

<a id="a-rule-that-a-machine-cannot-check-cannot-become-structure"></a>


### A rule that a machine cannot check cannot become structure

Only rules that types or lint can check mechanically can become structure.

For example, you can record the rule "code in this directory runs only in the browser" in two ways.

1. Write one sentence in the README
2. Put the code in its own directory and use lint to forbid imports from other directories

The first works only if the agent reads it. The second works even if nobody reads it. Put any rule that a machine can check in the second form.

Rules that need judgment of the situation, such as "use understated wording on this screen" or "split this kind of change into small pieces", cannot become types or lint. The only way to keep such rules is in writing. The principle "Encode Lessons in Structure" sets how to write them, as [the section on "Encode Lessons in Structure"](#in-pstack%2C-%22encode-lessons-in-structure%22-handles-it) explains.

<a id="keep-lessons-from-corrections-in-a-mechanism%2C-not-in-a-conversation"></a>


## Keep lessons from corrections in a mechanism, not in a conversation

Do not leave the lesson from a correction only in the conversation. <strong>Keep it in one of the tools, steps, or structures that the three ways produce, in the strongest form you can</strong>.  
The talk presents this idea right after the three ways.

Keep the lesson from a correction in one of these places.

- The codebase itself
- Automated checks by lint, the compiler, or CI
- Rules, or Bugbot, which is Cursor's automated code review
- A Skill
- The team's style guide

Then the next agent avoids the problem you pointed out once, without getting the same correction in a conversation.

<a id="in-pstack%2C-%22encode-lessons-in-structure%22-handles-it"></a>


### In pstack, "Encode Lessons in Structure" handles it

In pstack, the principle "Encode Lessons in Structure" ([`skills/principle-encode-lessons-in-structure/SKILL.md`](https://github.com/cursor/plugins/blob/main/pstack/skills/principle-encode-lessons-in-structure/SKILL.md)) sets this rule. In the README list, it is the only principle in the "Meta" group. It does not deal with code itself but with the process of building mechanisms, that is, <strong>how to keep lessons in a mechanism</strong>.

The principle says: <strong>when you notice you are writing the same instruction a second time, ask whether it can become a mechanism such as a lint rule or a runtime check. If it can, build the mechanism and delete the written instruction</strong>. For rules that cannot become a mechanism, that is, the "rules that need judgment of the situation" from the section "[A rule that a machine cannot check cannot become structure](#a-rule-that-a-machine-cannot-check-cannot-become-structure)", make the instruction prominent and add an example of failure.

When you choose a mechanism, choose the strongest one you can, such as types or lint. The agent copies what the surrounding code already does, so a weak mechanism becomes the example for the next code.

If you correct the agent in a conversation and it replies "I'll remember that", no mechanism keeps the lesson. [Chapter 21](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/10f4b3) covers in detail what to do when you write the same instruction a second time, the order of mechanism strength, and how to sort corrections.

<a id="grow-review-triage-criteria-as-a-file-too"></a>


### Grow review triage criteria as a file too

The criteria for judging review comments can also grow as a file that keeps lessons. The "Babysit" Playbook, which carries a PR to a mergeable state ([`playbooks/babysit.md`](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/playbooks/babysit.md)), sorts Bugbot's comments according to a criteria file ([`references/bugbot-triage.md`](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/references/bugbot-triage.md)). When the Playbook dismisses a comment for a reason the team could reuse, it proposes adding that reason to the shared criteria in a separate PR ([Chapter 14](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/8f6c25)).

This way, what one agent learns in one run goes into a file that the next agent reads.

<a id="summary%3A-keep-a-one-time-check-in-a-form-you-can-rerun"></a>


## Summary: keep a one-time check in a form you can rerun

- <strong>The three ways and how they differ.</strong> The three ways the talk names are to verify the artifact directly, to teach high-quality ways of working, and to structure the codebase so that it is easy to understand. They differ in how much they rely on the agent's own attention. A tool works only if someone uses it, steps work only if someone reads them, and structure works even if nobody notices it.
- <strong>Way 1.</strong> As the principle "Build the Lever" says, turn the way you verify into a tool you can rerun. Do the first check by hand, turn it into a command, and when verification fails, first suspect that the tool has gone stale.
- <strong>Way 2.</strong> Hand over a pattern, such as a Playbook, for "how an expert would proceed". In pstack, `/poteto-mode` picks the Playbook that fits the request and copies its steps to the TODO list.
- <strong>Way 3.</strong> As the Architecture principles say, use checks at boundaries and types to stop mistakes through structure. Rules that need judgment of the situation cannot become structure.
- <strong>Lessons from corrections.</strong> As the principle "Encode Lessons in Structure" says, keep them in the strongest mechanism you can. For rules that can live only in writing, make them prominent and add a failure example. "I'll remember that" keeps nothing.

[Chapter 4](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/3cc0dd) takes the direction of "keeping it in the repository" one step further and covers the talk's third theme, "treating the codebase as memory". It explains why knowledge belongs in the repository and how to choose the memory you keep and maintain it over time.
