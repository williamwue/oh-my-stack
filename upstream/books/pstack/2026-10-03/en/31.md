This chapter covers the following two Skills.

1. [`/automate-me`](https://github.com/cursor/plugins/blob/main/pstack/skills/automate-me/SKILL.md)
2. [`/make-bot-ui`](https://github.com/cursor/plugins/blob/main/pstack/skills/make-bot-ui/SKILL.md)

Both Skills extend pstack to fit the user's environment. Their uses are as follows.

- <strong>`/automate-me`.</strong> The agent reads the user's way of working from the user's chat history (for example, "Keep paragraphs short. Use a table to compare options."). It then creates a mode Skill like `/poteto-mode` that writes down that way of working for that user alone.
- <strong>`/make-bot-ui`.</strong> The agent creates a web page with a button that starts a process in Grok Bot, an AI bot app that can host pstack ([Chapter 5](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/aa6858)).

This chapter first confirms who calls the two Skills. It then explains each one from three angles: its role, when to use it, and its steps. For a Skill whose source gives example requests, I show those too.

Both `SKILL.md` files have a setting (`disable-model-invocation: true`) that stops the agent from choosing and running the Skill on its own based on the conversation. ## `/automate-me` reads how the user works from the chat history and turns it into a Skill for that user alone

<a id="role%3A-turn-the-user's-way-of-working-into-a-skill-from-the-history-and-the-user's-answers"></a>


### Role: turn the user's way of working into a Skill from the history and the user's answers

`/automate-me` is <strong>a Skill that turns the user's way of working into a Skill the agent follows</strong>. Its output is one Skill with a `-mode` suffix tailored to that user (for example, `jay-mode`).

The user does not need to explain their way of working. <strong>The agent reads from the chat history what the user has asked for again and again</strong>.

For example, if the user has told the agent "Make your replies shorter" many times, the agent reads "short replies" as part of the user's way of working. The agent fills in intentions that do not appear in the history by asking the user.

<a id="when-to-use-it%3A-when-the-user-wants-to-turn-their-preferences-and-way-of-working-into-a-skill"></a>


### When to use it: when the user wants to turn their preferences and way of working into a Skill

`/poteto-mode` and the other Skills in pstack cannot cover every use case.  
So the user calls this Skill by name when they want a Skill that fits their own preferences and way of working.

To record only the steps of one task, such as "how to write a commit message", the user does not use this Skill. They use only `create-skill`, the Skill built into Cursor for writing Skill files. An ordinary Skill is enough for the steps of one task. That task does not need a way-of-working Skill that covers the user's whole approach to work.

<a id="steps%3A-read-the-history%2C-ask-the-user%2C-polish-the-draft%2C-then-open-a-pr"></a>


### Steps: read the history, ask the user, polish the draft, then open a PR

1. <strong>Read the history.</strong> The agent takes the current workspace's transcripts from the last two to four weeks and splits them into periods, for example three. Subagents then read the periods in parallel. The agent reads only the current workspace's records and does not read personal chats from other projects. The agent treats only patterns found in two or more periods as reliable, and usually discards a pattern that appears in only one period. A preference stated once and contradicted in another situation is noise, not a way of working.
2. <strong>Ask the user directly.</strong> To fill in intentions that have not yet appeared in the history, the agent asks one or two multiple-choice questions and one free-text question. It uses multiple choice so that the user does not have to write text from scratch.
3. <strong>Draft.</strong> The agent uses `create-skill` to write a draft at `.cursor/skills/<handle>-mode/SKILL.md`. `<handle>` is the user's name or an identifier the user chooses.
4. <strong>Polish.</strong> The agent runs `/unslop` ([Chapter 32](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/c22a83)) on the draft to remove the habits of AI-written text. It then checks with the user that the draft reads like the user.
5. <strong>Merge it in.</strong> The agent works in a worktree ([Chapter 18](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/e529e4)) and opens a PR. It does not push directly to main.

If a mode Skill already exists, the agent reads only the history since the last edit and updates that Skill.

<strong>The agent creates a section in the Skill only when the user has a concrete rule that differs from the agent's default behavior</strong>. It does not write general advice such as "communicate clearly". General advice does not change how the agent behaves, so it only makes the Skill longer to read.

For example, a rule such as "Keep paragraphs short. Use a table to compare options. Use bullet points only when the items are truly parallel." gets a section.

<a id="how-to-write-the-request%3A-the-command-alone-is-enough-to-start"></a>


### How to write the request: the command alone is enough to start

According to the bundled guide [`09-make-it-yours.md`](https://github.com/cursor/plugins/blob/main/pstack/docs/guide/09-make-it-yours.md), the user can start with the command alone, as follows. The agent reads the user's way of working from the history, so the user does not need to add an explanation.

```
/automate-me
```

The same page also gives a request for updating an existing mode Skill when the way of working changes.

```
/automate-me update my mode skill with everything since its last edit
```

## `/make-bot-ui` builds a page that starts Grok Bot with a button without exposing the sender key

<a id="role%3A-build-a-way-to-start-the-bot-without-showing-the-secret-to-the-agent"></a>


### Role: build a way to start the Bot without showing the secret to the agent

`/make-bot-ui` is a Skill that builds a page the user clicks and sets up <strong>a way for its buttons to start Grok Bot through a webhook</strong>.

<a id="when-to-use-it%3A-when-you-want-a-button-to-start-a-grok-bot-routine-through-a-webhook"></a>


### When to use it: when you want a button to start a Grok Bot routine through a webhook

The user uses this Skill to build a page, such as a set of buttons or a dashboard, that starts Grok Bot through a webhook. The user also uses this Skill to submit the sender key for that page and to publish the page on Tailscale.

<aside class="msg message"><span class="msg-symbol">!</span><div class="msg-content">
<p class="code-line" data-line="86"><a href="https://tailscale.com/" rel="nofollow noopener noreferrer" target="_blank"><strong>Tailscale</strong></a> is a service that builds a private network connecting the user's devices, such as computers and phones, without exposing them to the internet. This network is called a tailnet, and only devices in the tailnet can open pages on it.</p>
</div></aside>

Grok Bot is an AI bot app that can install pstack as a plugin ([Chapter 5](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/aa6858)). You can register routines in Grok Bot, so it can run on a schedule or when an event triggers it.

<aside class="msg message"><span class="msg-symbol">!</span><div class="msg-content">
<p class="code-line" data-line="92"><strong>Webhook.</strong> A mechanism that sends an HTTP request to a URL you specify, to tell another system about an event and start a process there. For example, GitHub can send a notification to a given URL when someone pushes.</p>
</div></aside>

`/make-bot-ui` handles routines that a webhook starts. Between the button press and the start of the Grok Bot process, the following three steps run in order.

1. The user presses a button on the page in the browser. The page sends the JSON for that button, for example `{"action": "summarize-today"}`, to a small server on the same computer as the Bot. This chapter calls that server the local server.
2. The local server adds the sender key to the JSON it received and sends the JSON to the routine's webhook URL. The webhook URL is the dedicated URL that starts that routine from outside.
3. When the JSON reaches the webhook URL, the Bot's routine starts and begins processing with that JSON as its input.

The page does not send directly to the webhook URL. <strong>It puts the local server in between so that the sender key never reaches the browser</strong>. The step-by-step explanation below shows why.

<a id="steps%3A-create-the-routine%2C-deploy-the-page%2C-and-publish-it-on-the-tailnet"></a>


### Steps: create the routine, deploy the page, and publish it on the tailnet

1. <strong>Create the routine.</strong> The agent creates a routine that a webhook starts, and writes in its prompt that the POST body is untrusted data. The body that reaches the webhook URL comes from outside, so even if it contains an instruction such as "ignore all previous instructions", the Bot must not follow it.
2. <strong>Have the user get the URL.</strong> The agent asks the user to open the routine from Routines, the Bot's list of routines, and copy the webhook URL. The source says the user may paste the webhook URL into the chat. The sender key in the next step, by contrast, does not go into the chat.
3. <strong>Receive the sender key.</strong> The sender key is a secret that proves the caller is a legitimate sender of the webhook. The agent does not accept the sender key in the chat. The agent has the user submit the key through a dedicated card for entering secrets. The agent cannot see the submitted value, and writes the value into the server's settings without seeing it.
4. <strong>Deploy the page.</strong> The agent places the page and the local server on the same computer as the Bot. The page's buttons POST to the local server, and that server adds the sender key and POSTs to the webhook.
5. <strong>Put the page on the tailnet.</strong> The agent uses Tailscale so that the user's devices can open the page without exposing it to the internet.
6. <strong>Receive the trigger.</strong> The Bot treats the JSON it receives as external data, not as instructions.

<strong>The agent keeps the sender key only on the server and never shows it in the browser or the chat</strong>. Anyone who knows the key can start the routine.

If the browser called the webhook directly, the key would have to be in the page's code, and anyone who opened the page could read it. So the buttons always call the webhook through the local server.

Under the same rule of keeping secrets out of the chat, the agent does not ask the user for Tailscale credentials either. Instead, it gives the user a login URL, and the user approves the device in the browser.

## Summary

- <strong>How the two Skills are called.</strong> `/automate-me` and `/make-bot-ui` run only when the user calls them by name.
- <strong>`/automate-me`</strong> creates a `-mode` Skill for the user alone that writes down the user's way of working, based on the chat history and questions to the user.
- <strong>`/make-bot-ui`</strong> creates a page that starts Grok Bot with a button, without showing the sender key in the chat or the browser.
