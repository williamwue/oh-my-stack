poteto built pstack as a plugin that answers the problem that "AI writes too much sloppy code". In the words of the [README](https://github.com/cursor/plugins/blob/main/pstack/README.md), its concept is "<strong>if you want to go fast, go deep first</strong>". It is a tool for building a high-quality product with less code.

This chapter explains the problem pstack addresses and how pstack answers that problem, what pstack contains and how that maps to the four themes of [Part I](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/367ace), and when to use it.

<a id="what-problem-is-pstack-trying-to-solve%3F"></a>


## What problem is pstack trying to solve?

The problem pstack tries to solve is that <strong>AI writes too much sloppy code (slop)</strong>.

pstack is a plugin for Cursor that poteto publishes, and its README opens by stating this problem.

> there's a growing sense that ai writes too much slop code. i agree. i don't want to ship like a team of twenty slop artists. throughput without quality is not a goal i aspire to. if you want to go fast, go deep first.

The README then calls pstack "my answer," meaning poteto's answer.

<a id="how-does-pstack-answer-that-problem%3F"></a>


## How does pstack answer that problem?

pstack's answer is the following three directions:

1. <strong>Write less</strong>
2. <strong>Work deeply with one agent, and parallelize once you trust it to write good, verifiable code</strong>
3. <strong>Assign models by role</strong>

In the README, the three paragraphs that follow the problem statement and start in bold match these three directions:

- <strong>pstack is my answer.</strong> Write less code of higher quality instead of maximizing lines of code.
- <strong>pstack gives you fearless parallelism.</strong> If you work deeply with one agent and trust it to write good, verifiable code, you can parallelize with confidence.
- <strong>cursor gives you the best of all worlds.</strong> Every model has strengths and weaknesses, and pstack can use any model. Many Skills also combine several models to use the strengths of each.

<a id="writing-less-does-not-mean-cutting-evidence"></a>


### Writing less does not mean cutting evidence

The first direction takes the position that maximizing line count works against the goal. Among the principles, "[Laziness Protocol](https://github.com/cursor/plugins/blob/main/pstack/skills/principle-laziness-protocol/SKILL.md)" matches this direction. This principle tells the agent to choose the smallest change and to prefer deletion ([Chapter 17](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/97d863)).

"Write less", however, does not mean cutting the code that provides evidence. The preamble of the "Bug fix" Playbook ([`playbooks/bug-fix.md`](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/playbooks/bug-fix.md)) defines what to cut as follows.

> Every shipped line traces to runtime evidence. Belt-and-suspenders that "might help" is a hypothesis, not a fix.

The agent adds no "just in case" changes. It adds only the changes needed to fix a problem it confirmed by running the code.

At the same time, step 5 of the same Playbook, which orders the commits, asks the agent to commit the failing reproduction test before the fix. The agent can skip this commit when, for example, the test is expensive. <strong>The agent cuts unfounded "just in case" measures and changes. It does not cut code that provides evidence, such as a reproduction test that confirms the bug.</strong>

<a id="parallelize-only-after-you-trust-one-agent's-artifacts"></a>


### Parallelize only after you trust one agent's artifacts

The second direction says that you can parallelize with confidence only after one agent that works deeply has earned your trust that it writes good code you can verify. In [Part 1](https://x.com/poteto/status/2094457600259842065) of *The Complete Guide to pstack*, poteto also writes in this order of "trust, then parallelize". In that order, you consider parallelizing only after you have merged a few PRs with the help of a verification skill.

<a id="assign-models-by-role"></a>


### Assign models by role

For the third direction, the README says that the defaults as of 0.15.5 assign models as follows:

- <strong>Delegates that write code</strong> (Feature, Refactoring, Bug fix, Perf, Hillclimb): Grok (xAI's model)
- <strong>The hardest changes, prose, and judgment</strong>: Opus 5.5 (Anthropic's model)
- <strong>Panels</strong>: Opus 5.5, GPT-5.6 Sol, and Grok. A panel gives the same question to several models and compares the answers.

You can change these assignments with `/setup-pstack`. [Chapter 34](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/c37697) covers how the assignment works.

The use of several models is also more than a matter of taste. The "[Subagents](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/SKILL.md#subagents)" section of [`/poteto-mode`](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/SKILL.md) defines a second opinion as follows.

> A second opinion is the same prompt against a different model. Agreement is high-signal.

The agent gives the same question to a different model and checks whether the answers agree.

For example, you ask Opus 5.5 and Grok 4.7 separately for their diagnosis of a bug's cause. If both name the same cause, that diagnosis is more trustworthy than either answer alone. <strong>In pstack, splitting work across models is one of the ways to verify.</strong>

<a id="there-is-no-skill-for-writing-plan-documents%2C-because-%22the-best-spec-is-code%22"></a>


### There is no Skill for writing plan documents, because "the best spec is code"

pstack has no dedicated planning Skill because poteto treats code, not plan documents, as the spec. The README's "[why are there no planning skills?](https://github.com/cursor/plugins/blob/main/pstack/README.md#why-are-there-no-planning-skills)" section says that Cursor's plan mode works well with pstack and then states that "the best spec is code" ([Chapter 38](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/006bc8)).

The same section also says that if you want a plan, `/poteto-mode` can make one, but not by default. In Part 2 of *The Complete Guide to pstack*, poteto adds that the missing planning Skill does not mean a lack of planning. It means planning through code. poteto also writes about not running adversarial reviews of abstract plans.

Inside pstack, these three parts do the "planning in code":

- <strong>The "Prototype" Playbook</strong> ([`playbooks/prototype.md`](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/playbooks/prototype.md)). It settles design and behavior decisions cheaply with a throwaway prototype. The "[Non-negotiables](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/SKILL.md#non-negotiables)" section of `/poteto-mode` says that <strong>when the agent is about to ask a person for a fact it could observe by running something, it should build a small prototype with this Playbook and decide from the result.</strong>
- <strong>[`/architect`](https://github.com/cursor/plugins/blob/main/pstack/skills/architect/SKILL.md).</strong> A Skill that decides, before implementation, what the caller of a function passes in and gets back, and then designs the types and the module split to fit.
- <strong>The "Multi-phase or multi-PR plan" Playbook</strong> ([`playbooks/multi-phase-plan.md`](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/playbooks/multi-phase-plan.md)). This is where a plan document goes when one is needed. Its first step, however, says to skip the plan when the change fits in one or two files and the direction is clear. Its next step asks the agent to resolve open questions with a prototype before writing the plan document.

The third one, the "[Multi-phase or multi-PR plan](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/playbooks/multi-phase-plan.md)" Playbook, exists to write plan documents. Even so, it asks for a running prototype before any prose. <strong>The position that code is the spec shows in which Skills exist, and it also shows in the Playbook steps.</strong> [Chapter 16](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/3b2bef) and [Chapter 39](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/f87769) cover planning in detail.

<a id="what-work-is-pstack-for%2C-and-how-do-you-use-it%3F"></a>


## What work is pstack for, and how do you use it?

Use pstack for <strong>work that needs rigor</strong>. To get started, you need to know <strong>only two commands: `/setup-pstack` and `/poteto-mode`</strong>.

<a id="it-fits-work-that-needs-rigor"></a>


### It fits work that needs rigor

The README recommends that you use `/poteto-mode` "whenever you're doing anything that requires rigor". Conversely, the `SKILL.md` of `/poteto-mode` says <strong>not to apply it to light exchanges like small talk, which it calls a Casual turn</strong> ([Chapter 7](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/55bbdb)).

On that basis, work divides into what fits and what does not:

- <strong>Work that fits.</strong> Bug fixes that need reproduction and confirmation, features that involve design across function or module boundaries, long tasks you want to hand off while you step away, and similar work.
- <strong>Work that does not fit.</strong> A one-line typo fix, a question with a one-word answer, and similar work.

Even for work that fits, pstack's procedures cannot run without a way to run the app and verify it. The "Bug fix" Playbook requires the agent to "reproduce it yourself" and to "verify on the same surface", meaning the same screen or command where the bug happened. Both requirements assume a way to verify. <strong>So prepare a verification skill first, and then use pstack.</strong>

<a id="summary%3A-pstack-answers-the-sloppy-code-problem-with-%22go-deep-first%22"></a>


## Summary: pstack answers the sloppy-code problem with "go deep first"

- <strong>The problem it tries to solve.</strong> poteto built pstack as an answer to "sloppy code written by AI". The README says "if you want to go fast, go deep first".
- <strong>How it answers the problem.</strong> It takes three directions. Write less. Work deeply with one agent, and parallelize once you trust it to write good, verifiable code. Assign models by role.
- <strong>What it contains and leaves out.</strong> As of 0.15.5, it contains 23 Playbooks, 23 Principles, 24 Skills, 2 subagents, and a 10-page bundled guide. `/deslop`, `control-cli`, and `control-ui` live in `cursor-team-kit`, and `/create-skill` lives in Cursor itself. Without the app-driving Skills in particular, the agent cannot reproduce or verify. There is no planning Skill because pstack takes the position that "the best spec is code", and that position also shows in the steps of the planning Playbook.
- <strong>How it maps to the four themes of the talk.</strong> The four themes are trust, raising trust, the codebase as memory, and automation. Each theme has matching parts.
- <strong>When to use it and how to start.</strong> Use it for work that needs rigor. To get started, you need to know two commands: `/setup-pstack` and `/poteto-mode`.

The next chapter, [Chapter 7](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/55bbdb), looks closely at the entry point, `/poteto-mode`. The chapter explains how to invoke `/poteto-mode` and what happens when you do, the rules that route a request to a Playbook, and how to write a good request.
