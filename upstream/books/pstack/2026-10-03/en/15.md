This chapter covers three Playbooks.

1. [Bug fix](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/playbooks/bug-fix.md)
2. [Perf issue](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/playbooks/perf-issue.md)
3. [Hillclimb](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/playbooks/hillclimb.md)

All three are Playbooks that fix code. When they fix something, <strong>they base the fix on runtime evidence, which is the output, logs, and measurements that come from running the program</strong>.

Which Playbook to use depends on what you want to fix. You choose by whether the result itself is wrong, whether the behavior is correct but slow, or whether you want to push one number up to a target over many attempts.

This chapter explains the rules the three share and then how to use each one.

<a id="how-this-chapter-is-organized"></a>


## How this chapter is organized

This chapter has the following sections.

- The three Playbooks fix code based on runtime evidence, and you choose by what you want to fix
- "Bug fix" reproduces the bug first and then fixes it with the smallest change that evidence shows is needed
- "Perf issue" starts from a measurement before the fix and shows the improvement with a measurement after it
- "Hillclimb" improves one metric by repeating "one change, one measurement, keep or revert"
- Summary

## The three Playbooks fix code based on runtime evidence, and you choose by what you want to fix

The three Playbooks share the rule that <strong>no change stays unless runtime evidence backs it</strong>. You choose among them as follows.

- <strong>The result the user gets is itself wrong.</strong> Use "Bug fix".
- <strong>The behavior is correct but slow, and you want to improve performance with one fix.</strong> Use "Perf issue".
- <strong>You want to push one number up to a target over many attempts.</strong> Use "Hillclimb".

## "Bug fix" reproduces the bug first and then fixes it with the smallest change that evidence shows is needed

<a id="role%3A-reproduce-the-bug-and-find-the-root-cause"></a>


### Role: reproduce the bug and find the root cause

"Bug fix" is <strong>a Playbook that reproduces the reported bug, finds the root cause, and makes only the smallest change that runtime evidence shows is needed</strong>.

A just-in-case change that "might help" is <strong>an unverified hypothesis, not a fix</strong>, so the agent does not make it. If runtime evidence refutes a hypothesis, the agent reverts the changes it made based on that hypothesis.

[The talk](https://x.com/poteto/status/2102050467505430555) says that if you leave an ad hoc workaround in place, the next agent copies it as an example of correct implementation ([Chapter 4](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/3cc0dd)). This book reads the rule to revert changes based on refuted hypotheses as a way <strong>to keep such workarounds out of the code, so the next agent does not imitate them</strong>.

<a id="steps%3A-six-steps-from-the-reproduction-to-the-pr"></a>


### Steps: six steps from the reproduction to the PR

The Playbook has the following six steps.

1. <strong>Reproduce it yourself</strong>
   - Use the control Skill that fits where the symptom appears, such as `control-ui` or `control-cli` from [`cursor-team-kit`](https://github.com/cursor/plugins/tree/main/cursor-team-kit)
   - Ask the user to reproduce it only when there is a concrete reason that the Skill cannot operate that screen or command, and only after you have gone as far as the Skill can
   - If the bug does not reproduce right away, keep trying until the bug happens: trigger the bug artificially, narrow to the conditions where it happens more often, or add instrumentation
2. <strong>Bisect the cause</strong>
   - List hypotheses about the cause and narrow them to one. Run first the checks that eliminate the most remaining candidates
   - Gather candidate hypotheses with two Skills. `/how` explains the mechanism of the affected subsystem, and `/why` searches the history for how something that used to work broke. [Chapter 22](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/031877) covers both Skills
   - If you do not know the program's state, add instrumentation or logs instead of guessing
   - Before you move on, verify with runtime evidence the mechanism that the last remaining hypothesis points to
3. <strong>Plan the fix</strong>
   - If the fix crosses function boundaries, use `/architect` first. `/architect` is a Skill that designs types and module structure before the code ([Chapter 24](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/2df1db))
   - Hand the implementation to a subagent with a concretely narrowed scope
4. <strong>Verify on the same screen or command where the symptom appeared</strong>
   - Verify that the original repro steps now succeed
   - Do not count it as a pass if you verified on a different screen or command, or if the verification was inconclusive
   - A unit test shows the behavior of individual pieces, not that the bug is gone. So unit tests that pass do not by themselves mean that the bug is fixed
5. <strong>Commit a test that reproduces the bug before the fix</strong>
   - Commit the test that fails before the fix first, and put the fix on top of it
   - If you can write a test that runs locally and cheaply, follow `/tdd` ([Chapter 30](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/32928b)), which writes the failing test first
   - You can skip this step if writing the test is costly, if the test depends heavily on an environment that connects several services, or if it is unclear what the test would check
6. <strong>Run "[Opening a PR](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/playbooks/opening-a-pr.md)", which sets the steps for opening a PR ([Chapter 14](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/8f6c25))</strong>

The reply contains the following items.

- What was broken
- The root cause
- The fix
- How the agent verified the fix

The agent also <strong>pastes the repro output that went from failure to success, as is, without summarizing it</strong>.

This book reads the mapping between the steps and the Principles as follows. The principle "[Fix Root Causes](https://github.com/cursor/plugins/blob/main/pstack/skills/principle-fix-root-causes/SKILL.md)" maps to steps 1 to 3, "[Prove It Works](https://github.com/cursor/plugins/blob/main/pstack/skills/principle-prove-it-works/SKILL.md)" maps to step 4 and the reply, and "[Sequence Work into Verifiable Units](https://github.com/cursor/plugins/blob/main/pstack/skills/principle-sequence-verifiable-units/SKILL.md)" maps to step 5 ([Chapter 19](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/d3f914)). Of these, the Playbook text itself names only "Sequence Work into Verifiable Units", in step 5.

<a id="how-to-write-the-request%3A-say-%22reproduce-it-first%22"></a>


### How to write the request: say "reproduce it first"

Write "reproduce it first" in the request. If you want a test, add the condition "if there is a cheap test path". The example in the bundled guide ([docs/guide/10-recipes-and-pitfalls.md](https://github.com/cursor/plugins/blob/main/pstack/docs/guide/10-recipes-and-pitfalls.md)) is the following.

```
/poteto-mode repro the duplicate write first. if there's a cheap test path, /tdd it. then fix and rerun.
```

<strong>A run of the real command shows the fix more accurately</strong> than a forced test built on fragile mocks. For this reason, step 5 lets you skip the test when the test is costly to write.

## "Perf issue" starts from a measurement before the fix and shows the improvement with a measurement after it

<a id="role%3A-measure-the-slowness-and-fix-it"></a>


### Role: measure the slowness and fix it

"Perf issue" is a Playbook that improves measured slowness against a baseline. It starts from a trace of the slowness. A trace is a record of things such as the run time of each operation. It forbids reading the source instead of measuring, and <strong>ties every fix to a measurement</strong>.

<a id="steps%3A-six-steps-that-start-with-a-baseline-trace"></a>


### Steps: six steps that start with a baseline trace

The Playbook has the following six steps.

1. <strong>Take a baseline trace.</strong> Use the control Skill that fits the symptom
2. <strong>Use `/how` to study how the code works, and base hypotheses on it.</strong> Do not decide that "it cannot get any faster" before running and measuring it. Form hypotheses from the eight common improvement patterns, called strategy families, which the table below lists
3. <strong>Plan the fix from the trace.</strong> Hand the implementation to a subagent, review the diff, and take a trace after the fix
4. <strong>Analyze and compare the traces before and after the fix.</strong> Take the diff. For example, load the traces into sqlite and query them. Do not count it as a pass if you measured on a different screen or command, or if the measurement was inconclusive
5. <strong>Quote the measurement results in the PR</strong>
6. <strong>Run "Opening a PR"</strong>

The reply includes these four items.

- The baseline numbers
- The numbers after the fix
- The diff
- The artifact paths

The agent cannot write any of these items without measuring, so <strong>the shape of the reply itself keeps the agent from skipping the measurement</strong>.

The eight strategy families are tools that produce hypotheses, not a checklist. The agent may try a family <strong>only when the trace shows signs that the family will work</strong>. The right column of the table lists those signs. The exception is Elimination. A trace shows where the program is slow, but it does not show whether the agent can remove a piece of work. The agent checks that question with `/how`.

<a id="how-to-write-the-request%3A-give-measured-numbers%2C-not-%22it-feels-slow%22"></a>


### How to write the request: give measured numbers, not "it feels slow"

In the request, write measured numbers instead of "it feels slow". The example in the bundled guide ([docs/guide/05-build-and-clean.md](https://github.com/cursor/plugins/blob/main/pstack/docs/guide/05-build-and-clean.md)) is the following.

```
/poteto-mode startup takes 1.8s on this fixture. trace it, fix the measured cause, show me before and after.
```

If you also want confidence that the improvement is real, ask in the request for the agent to run the verification skill in parallel with `/swarm`. The verification skill is a Skill that operates the app the way the user does and verifies it ([Chapter 3](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/87177c)). The example in *The Complete Guide to pstack* [Part 1](https://x.com/poteto/status/2094457600259842065) is the following.

```
spawn a cloud agent to use /poteto-mode to improve the initial loading time of our app. first use /control-app to take a trace of the status quo, and identify opportunities for improvement. then do a targeted fix and use /control-app + a /swarm to confirm the win
```

`/control-app` is the name of the verification skill built in the guide ([Chapter 36](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/c9901e)). `/swarm` ([Chapter 24](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/2df1db)) is a Skill that runs several agents, called Workers, in parallel and merges their results into one report. Because many agents run the verification skill, you can verify the improvement with a large enough sample. The point is to avoid mistaking the variation of a single measurement for an improvement.

<a id="%22hillclimb%22-improves-one-metric-by-repeating-%22one-change%2C-one-measurement%2C-keep-or-revert%22"></a>


## "Hillclimb" improves one metric by repeating "one change, one measurement, keep or revert"

<a id="role%3A-improve-one-metric-toward-a-target-in-a-loop"></a>


### Role: improve one metric toward a target in a loop

"Hillclimb" is a Playbook that <strong>improves one metric toward a target continuously, in a loop</strong>. One-time fixes belong to "Bug fix" or "Perf issue".

Its core discipline is "one change, one measurement, keep or revert". The agent does not stack untested changes, and does not claim an improvement from reading the code alone. The principle "[Prove It Works](https://github.com/cursor/plugins/blob/main/pstack/skills/principle-prove-it-works/SKILL.md)" sets both rules.

<a id="steps%3A-eight-steps-that-loop-with-one-hypothesis-at-a-time"></a>


### Steps: eight steps that loop with one hypothesis at a time

The Playbook has the following eight steps.

1. <strong>Before you choose the metric, understand the conditions that affect the result and the mechanism of the target</strong>
   - Run `/how` on the target and list the realistic conditions that affect the metric's value, such as data volume, history, state, and concurrency
   - Choose a case that reproduces the user's complaint
   - Decide on one metric and a stop condition
   - Make the stop condition a pair of a target and a minimum number of attempts, such as "at least 50% better than the baseline, and at least 10 attempts". The minimum exists so that a lucky early result does not end the loop
2. <strong>Build the measurement harness, confirm it can tell the cases apart, and then freeze it</strong>
   - Verify that the target case reproduces the symptom and that its measurements differ from an easy case where the symptom does not appear
   - Once the harness passes this check, freeze the measurement method. A frozen method means that you do not change the measured case, the metric, or the measurement command for the rest of the loop
   - After you freeze the method, make one fixed command produce the metric, and take the median of several runs instead of one
   - Before you make any change, record the baseline metric and a result in which all regression gates pass. Regression gates are the required tests that must keep passing. The principle "[Build the Lever](https://github.com/cursor/plugins/blob/main/pstack/skills/principle-build-the-lever/SKILL.md)" asks for this baseline ([Chapter 17](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/97d863))
3. <strong>Open the decision log</strong>
   - Create `decision.tsv` with `/show-me-your-work` ([Chapter 28](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/6638a6)), which keeps a record of decisions
   - `decision.tsv` is a table with one row per attempt: the hypothesis, the change, the numbers before and after, and whether the change was kept or reverted
   - Read `decision.tsv` again before the next attempt
4. <strong>Base each hypothesis on the mechanism understood in step 1</strong>
   - State a concrete mechanism as the hypothesis, such as "X delays the first paint, so move it out of startup"
   - The Playbook does not allow a hypothesis like "try memoizing something"
5. <strong>Loop with one hypothesis at a time</strong>
   - Hand the change to a subagent, as the principle "[Guard the Context Window](https://github.com/cursor/plugins/blob/main/pstack/skills/principle-guard-the-context-window/SKILL.md)" asks
   - If there are several independent hypotheses, give them to parallel subagents, one per worktree, as the principle "[Separate Before Serializing Shared State](https://github.com/cursor/plugins/blob/main/pstack/skills/principle-separate-before-serializing-shared-state/SKILL.md)" asks
   - Measure before and after the change with the harness frozen in step 2
   - Keep the change only when the metric improves by more than chance can explain and all regression gates pass
   - Otherwise, revert the whole change
   - Always write the `decision.tsv` row, whether the change was kept or reverted
   - To run unattended, borrow one mechanism from "[Autonomous run](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/playbooks/autonomous-run.md)" ([Chapter 15](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/305f88)), the Playbook that carries a long task to completion without stopping. Borrow only the mechanism that wakes the agent again on a timer or an event. The stop condition stays the one decided in step 1
6. <strong>Do not stop as soon as the improvement stalls</strong>
   - If reverts keep coming, switch the family of hypotheses, that is, the kind of approach. You can also combine near-miss ideas or try bolder ideas before you conclude
   - Revert a change that improves the metric but breaks behavior
   - Keep a change that simplifies the code while it holds the metric, as the principle "[Laziness Protocol](https://github.com/cursor/plugins/blob/main/pstack/skills/principle-laziness-protocol/SKILL.md)" asks
7. <strong>Stop when the stop condition is met, or when the remaining ideas are no longer worth the effort</strong>
   - Do not loosen the stop condition to call it met
   - Do not stop while cheap hypotheses remain
   - If you get stuck, report instead of repeating the same attempts
8. <strong>Run "Opening a PR"</strong>
   - Stack the kept commits in the order they landed

If it drops to around 80 milliseconds after the change, you can judge that the improvement exceeds the variation. If it changes by only a few milliseconds, it may be measurement noise, and you cannot call it an improvement.</p>

### How to write the request: give the metric, the target, and the minimum number of attempts

According to the bundled guide ([docs/guide/05-build-and-clean.md](https://github.com/cursor/plugins/blob/main/pstack/docs/guide/05-build-and-clean.md)), <strong>if you give the metric, the target, and the minimum number of attempts</strong>, "Hillclimb" uses a harness with a frozen measurement method and tries one hypothesis at a time in a loop.

<a id="summary"></a>


## Summary

- <strong>The shared discipline and how to choose.</strong> The three Playbooks share the discipline that every change they make has runtime evidence behind it. Choose "Bug fix" for wrong behavior, "Perf issue" to improve slowness with one fix, and "Hillclimb" to improve one metric toward a target over many attempts.
- <strong>Bug fix.</strong> The agent reproduces the bug itself, bisects the hypotheses about the cause down to one, and then fixes it. The reply includes the output that went from failure to success, as is.
- <strong>Perf issue.</strong> The agent starts from a baseline trace. It tries each of the eight improvement patterns, the strategy families, only when the trace shows signs that the pattern will work, and it shows the improvement with the numbers before and after the fix.
- <strong>Hillclimb.</strong> The agent builds a harness with a frozen measurement method and repeats "one change, one measurement, keep or revert" under a stop condition that pairs a target with a minimum number of attempts.

It looks at them from the angle of "what must not change".
