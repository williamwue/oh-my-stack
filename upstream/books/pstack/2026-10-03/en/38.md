This chapter covers the following three Skills.

1. [`/unslop`](https://github.com/cursor/plugins/blob/main/pstack/skills/unslop/SKILL.md)
2. [`/bro`](https://github.com/cursor/plugins/blob/main/pstack/skills/bro/SKILL.md)
3. [`/technical-writing`](https://github.com/cursor/plugins/blob/main/pstack/skills/technical-writing/SKILL.md)

All three Skills keep the quality of the text the agent writes high. Each one has its own job.

- <strong>`/unslop`.</strong> The agent removes AI habits from its own text, such as stock phrases like "I hope this helps!"
- <strong>`/bro`.</strong> The agent restates its last reply, shorter and without jargon.
- <strong>`/technical-writing`.</strong> The agent first decides the kind of document, such as a tutorial or a reference, and then writes the technical document.

This chapter first looks at how the three Skills differ in what they target, who fixes the text, and what triggers them. Then it explains each Skill from four angles: its role, when to use it, its rules or steps, and how to write the request.

### The three run only when called by name

All three `SKILL.md` files set `disable-model-invocation: true` ([Chapter 25](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/e5f103)). The agent never picks a Skill with this setting on its own from the content of the conversation. So the three run only when the user calls them by name, or when `/poteto-mode`, a Playbook, or another Skill names them in its steps.

The "[Non-negotiables](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/SKILL.md#non-negotiables)" section of `/poteto-mode` ([Chapter 8](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/cd0205)) sets when the agent calls two of these Skills. The agent calls `/unslop` when it writes any text, and it calls `/technical-writing` when it writes docs, RFCs, READMEs, PR descriptions, or commit messages.

So when you work in `/poteto-mode`, the agent calls these two Skills under the "Non-negotiables" rules, even if you never call them by name.

<a id="%2Funslop-removes-ai-habits-from-text-with-numbered-rules"></a>


## `/unslop` removes AI habits from text with numbered rules

<a id="role%3A-remove-ai-habits-from-text-by-rule"></a>


### Role: remove AI habits from text by rule

`/unslop` is <strong>a Skill with which the agent cuts AI habits from its own text by following rules</strong>.

AI habits are the phrasings and formatting that often appear in AI-written text and tell the reader that a machine wrote it.

The Skill calls these habits "AI tells" or "AI patterns". Examples are a stock phrase at the end of a reply and heavy use of em dashes.

The rules and their examples all target English text. But most of the rules apply to writing in any language, so they still work for Japanese.

The rules work best in English, so it is fair to say "The hottest programing language is English".

<a id="when-to-use-it%3A-apply-it-to-every-piece-of-text%2C-always"></a>


### When to use it: apply it to every piece of text, always

The "Non-negotiables" in `/poteto-mode` require the agent to apply this Skill to <strong>all text, including the agent's replies</strong>.

The description in `SKILL.md` also says "Must always apply". But `/unslop` sets `disable-model-invocation: true`, so the agent does not call `/unslop` on its own after reading this description. The Skill applies every time because the "Non-negotiables" rules call `/unslop`, and so do the steps of the other Skills and Playbooks shown next.

##### `/technical-writing`: hands the list of AI habits to `/unslop`

`/technical-writing` does not keep its own list of habits such as AI vocabulary and filler. It hands that list to `/unslop`. So it applies `/unslop` to every document it writes or reviews.

##### `/teach`, `/show-me-your-work`: write the way you would talk to a coworker

`/teach` ([Chapter 22](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/031877)) is a Skill that explains the work in plain words so that a person really understands it. `/teach` tells the agent to write every reply in plain spoken language, the way you would explain something to a coworker. `/teach` then applies `/unslop` to those replies.

`/show-me-your-work` ([Chapter 28](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/6638a6)) is a Skill that records the agent's decisions and their reasons in a file, one per line. `/show-me-your-work` tells the agent to write each line of the decision log the way you would tell a teammate what you did, without AI phrasing or abstract jargon. It then applies `/unslop` to the sentences of the decision log too.

##### `/recall`, `/blast-radius`: write reports handed to the user

`/recall` ([Chapter 22](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/031877)) is a Skill that rebuilds the state of the user's recent work from sources such as the chat history. `/blast-radius` ([Chapter 27](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/e23752)) is a Skill that looks, before a release, for what a change might break elsewhere.

Both Skills pass the report they hand to the user through `/unslop`. The `/recall` report says how far the work has come and what to do next. The `/blast-radius` report says what the change might break and what to verify before the merge.

##### `/automate-me`: fixes the text of the user's personal Skill with `/unslop`

`/automate-me` ([Chapter 25](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/e5f103)) is a Skill that reads the user's working preferences from their recent transcripts and drafts a personal Skill named `<user name>-mode` for that user. `/automate-me` applies `/unslop` to each line of that draft.

##### "Investigation" Playbook: the reply with the findings is itself the artifact

"[Investigation](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/playbooks/investigation.md)" ([Chapter 10](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/b77ae2)) is a Playbook that researches and answers a question without changing code. This Playbook returns a sourced explanation or recommendation instead of a code change. <strong>The Playbook defines that reply as the artifact of the investigation</strong>.

At the end of its steps, this Playbook applies `/unslop` to that reply.

<a id="rules%3A-ai-habits-in-seven-categories-with-fixed-numbers"></a>


### Rules: AI habits in seven categories with fixed numbers

The rules take up most of `SKILL.md`. The Skill has only the following two steps.

1. Look for the spots that match a rule
2. Rewrite them, keep the meaning, and match the tone the writer intended

The rules have numbers, and each number is a fixed ID that other Skills use to point at a rule. For example, `/poteto-mode` points at the rule against using colons as mid-sentence connectors by number, as "unslop rule 14".

`SKILL.md` says that when the maintainers remove a rule, its number stays empty. In the `SKILL.md` of pstack version `0.15.5`, numbers 1, 2, 4, 6, and 21 are empty.

<a id="how-to-write-the-request%3A-call-it-with-the-text-to-fix-and-extra-rules"></a>


### How to write the request: call it with the text to fix and extra rules

The bundled guide's [`docs/guide/05-build-and-clean.md`](https://github.com/cursor/plugins/blob/main/pstack/docs/guide/05-build-and-clean.md) gives the following example, which calls the Skill with the text to fix and an extra rule.

```
/unslop the readme changes, no emdashes
```

In this request, "the readme changes" is the text to fix, and "no emdashes" is the extra rule.

The same page says that even with a short request like the following, the agent reads the intent and fixes the text with this Skill.

```
unslop that, tighten it
```

"that" points at the text the agent just wrote.

<a id="%2Fbro-restates-a-hard-to-follow-reply-without-jargon"></a>


## `/bro` restates a hard-to-follow reply without jargon

<a id="role%3A-restate-the-last-reply-without-jargon"></a>


### Role: restate the last reply without jargon

`/bro` is <strong>a Skill with which the agent restates its last reply without jargon</strong>. With a body of only three sentences, `/bro` is the shortest Skill in pstack.

`/bro` differs from `/unslop` in the unit it fixes. `/unslop` fixes only the spots that match a rule, such as stock phrases. `/bro` uses no rules and restates the whole last reply in plain words.

Unlike `/unslop` and `/technical-writing`, `/bro` appears in no step of `/poteto-mode`, a Playbook, or another Skill. So `/bro` runs only when the user calls it by name.

<a id="when-to-use-it%3A-the-reply-is-detailed%2C-but-you-cannot-tell-what-it-says"></a>


### When to use it: the reply is detailed, but you cannot tell what it says

The user uses this Skill when the agent's reply is technically detailed but the user cannot tell what it says.

<a id="steps%3A-the-three-sentences-of-the-body-are-the-instruction"></a>


### Steps: the three sentences of the body are the instruction

The body of `/bro` is only these three sentences.

> Restate your last message. Stop using jargon and speak coherently. State it more simply and concisely, like one human talking to another.

`SKILL.md` has no steps section, and the agent takes these three sentences as the instruction itself.

<a id="how-to-write-the-request%3A-%22%2Fbro%22-alone-is-enough"></a>


### How to write the request: "/bro" alone is enough

The bundled guide's [`10-recipes-and-pitfalls.md`](https://github.com/cursor/plugins/blob/main/pstack/docs/guide/10-recipes-and-pitfalls.md) lists only the following single word as the prompt.

```
/bro
```

The three sentences of the body are the instruction, so the user does not need to add how to restate the reply.

<a id="%2Ftechnical-writing-makes-the-agent-decide-the-kind-of-document-before-it-writes"></a>


## `/technical-writing` makes the agent decide the kind of document before it writes

<a id="role%3A-make-the-agent-write-technical-documents-by-layered-standards"></a>


### Role: make the agent write technical documents by layered standards

`/technical-writing` is a Skill that gives the standards the agent follows when it writes technical documents. The Skill splits the standards into four layers, from the kind of the whole document down to how to write one sentence. <strong>The goal is writing a tired engineer understands on the first read</strong>.

In *The Complete Guide to pstack* [Part 2](https://x.com/poteto/status/2097732320606507506), poteto explains what led him to build this Skill.

The story started when poteto had the agent write the README for Dune, a framework for desktop apps inside Cursor, without this Skill. According to the guide, the resulting README mixed a tutorial, a how-to, a design explanation, and an API reference into one. The agent also wrote it in fancy prose full of AI habits, so the README was hard to read.

<a id="when-to-use-it%3A-when-the-agent-writes-or-reviews-documents"></a>


### When to use it: when the agent writes or reviews documents

The description in `SKILL.md` names these occasions: when the agent writes docs, RFCs, READMEs, PR descriptions, or commit messages, and when it reviews them.

But `/technical-writing` also sets `disable-model-invocation: true`, so the agent does not call `/technical-writing` on its own after reading this description. The agent uses the Skill on these occasions because the "Non-negotiables" rules tell the agent to use it when it writes these documents.

Among the Playbooks, "Opening a PR", which opens a PR, tells the agent to write the PR title, the PR description, and the commit bodies with this Skill. "Multi-phase or multi-PR plan", which writes a plan document, also tells the agent to write the plan document with this Skill.

<a id="rules%3A-four-layers-and-the-rules-outside-them"></a>


### Rules: four layers and the rules outside them

Besides the standards of the four layers, `SKILL.md` also sets rules that sit outside the layers. I look at the rules outside the layers first, then at the four layers one at a time.

<a id="three-rules-that-take-priority-over-the-four-layers"></a>


#### Three rules that take priority over the four layers

Apart from the four layers, the agent follows these three rules, and they take priority over every layer.

- Cut every word whose removal leaves the meaning of the sentence unchanged. For example, "In order to" becomes "to".
- Use short, everyday words. For example, write "use", not "utilize".
- If a rule makes a sentence worse, fix the sentence another way or leave it alone. The rules exist for the reader. A sentence that follows every rule but reads as if a machine wrote it has failed.

<a id="use-the-names-in-the-codebase-as-they-are%2C-and-do-not-invent-jargon"></a>


#### Use the names in the codebase as they are, and do not invent jargon

The agent writes the names of the symbols, files, flags, and commands that exist in the codebase as they are, without rewording them.

The agent also does not invent new jargon. It uses the words a developer says out loud. For example, to say that code moves to another place, it writes "move", not "evacuate".

On the other hand, when an established design or approach already has a widely used name, such as "the Strangler Fig pattern", the agent uses that name.

But the agent adds the meaning where the name first appears in the document. For example, it writes "migrate with the Strangler Fig pattern (an approach that replaces an old system with a new one piece by piece)".

Rule 26 of `/unslop`, which covers abstract metaphor nouns, lists words like "evacuate" that the agent should replace. When the agent finds a word that is not on that list, it does not edit `/unslop` itself. Instead, it writes a proposal in its reply, with the diff, to add the missing word and its replacement to the list.

<a id="mix-sentence-lengths-and-be-specific"></a>


#### Mix sentence lengths and be specific

This Skill asks for the following four things about sentence length and specificity.

- <strong>Mix sentence lengths on purpose.</strong> Use short sentences to land a point, and longer ones to state a fact with its condition or consequence.
- <strong>Decide whether to split a sentence by the number of thoughts, not by its length.</strong> "One thought per sentence" does not mean "make every sentence short". Split a sentence that carries two thoughts, but keep a sentence that carries one, even if it is long.
- <strong>In an explanation, give the writer's view.</strong> In an explanation, do not stop at listing pros and cons. Also say what the writer makes of them. A reference, on the other hand, holds no views, only facts.
- <strong>Be specific, not vague.</strong> Instead of a safe phrase like "schema changes can cause issues", say what happens, as in "a column rename fails the build".

The reason is that <strong>a text can follow every standard of the four layers and still read as machine-written if it is all clipped short sentences with nothing specific in it</strong>.

<a id="keep-a-pr-description-short-enough-to-read-in-under-a-minute"></a>


#### Keep a PR description short enough to read in under a minute

The agent keeps a PR description short enough that a reviewer can read it in under a minute. So it links the run logs of `/swarm` ([Chapter 24](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/2df1db)), lists of commit SHAs, and metric tables instead of pasting them into the body.

#### Diátaxis: decide the kind of document first

<strong>Diátaxis, the first layer, decides the kind of document first</strong>. The reason is that a document that mixes kinds becomes hard to read, like the Dune README from ["Role: make the agent write technical documents by layered standards"](#role%3A-make-the-agent-write-technical-documents-by-layered-standards) earlier in this chapter.

Two questions decide the kind: "Is the document for action or for understanding?" and "Is it for learning or for work?"

`SKILL.md` describes the four kinds as follows.

- <strong>tutorial.</strong> A document in which a first-time user learns hands-on by building something. It shows the finished result first, and for each step it says what should appear on the screen or in the output.
- <strong>how-to.</strong> A set of steps with which a user who already knows the tool solves the problem in front of them. It skips the basics and lists only what to do, in order.
- <strong>reference.</strong> A document to look things up in when you need an exact fact. It lists specifications and settings, with no steps and no writer's opinion.
- <strong>explanation.</strong> A document for understanding why a mechanism or design is the way it is. It covers design decisions, history, constraints, and alternatives. It is the only kind in which the writer gives opinions.

When a document mixes the four kinds into one, like the Dune README, the agent splits it into four documents and links them to each other.

But the agent does not apply this layer to PR descriptions and commit messages. It applies only the other three layers to them.

<a id="google-developer-style%3A-talk-to-the-reader"></a>


#### Google developer style: talk to the reader

The agent calls the reader "you" and writes instructions in the imperative, as in "Click Submit."

The agent also puts the condition before the instruction, as in "To delete the document, click Delete." When the condition comes first, the reader can skip instructions that do not apply to them.

For headings, the agent states the point of the section, not only what the section is about.

For example, instead of a heading like "Modes" that shows only the topic, it writes a heading like "Pick the mode first" that tells the reader what to do.  
Here, "mode" means a Diátaxis kind of document.

<a id="ste%3A-put-only-one-thought-in-a-sentence"></a>


#### STE: put only one thought in a sentence

The agent writes only one instruction per sentence. Here, an instruction is a sentence that makes the reader do something, such as "Install the component."

The agent also splits long sentences in two. The limit is about 20 English words for an instruction and about 25 for other sentences.

The agent keeps the English articles "the" and "a". For example, "Remove backup file" reads two ways, but "Remove the backup file" reads only one way.

The agent also uses the same word for the same action throughout the document. If it writes "start" in one place, it does not switch to "initiate" in another.

<a id="global-english%3A-remove-sentences-that-read-two-ways"></a>


#### Global English: remove sentences that read two ways

The agent puts "only" and "not" right next to the word they change. Their position changes the meaning. "Only fails on growth" and "fails only on growth" say different things.

The agent also calls one thing by one name everywhere. A document that calls one mechanism "the gate", "the ratchet", and "the budget check" makes the reader think there are three things.

<a id="example%3A-rewriting-one-paragraph-by-the-rules"></a>


#### Example: rewriting one paragraph by the rules

`SKILL.md` includes one rewriting example. Here is the paragraph before the fix.

> Configuration of the proto import ratchet budget script parameters is performed via budget.json. Note that it's important to remember that running with --write, which updates the committed budget to reflect the current count, should only be done when lowering it. If exceeded, CI fails.

Here is the paragraph after the fix.

> `budget.mjs` reads the committed budget from `budget.json` and counts the files that import protos. If the count exceeds the budget, CI fails. Run `budget.mjs --write` only to lower the budget.

The rewritten paragraph makes the following changes to the original.

- Drops the noun string "proto import ratchet budget script" and uses the real file names `budget.mjs` and `budget.json`
- Drops the passive "is performed via", makes `budget.mjs` the subject, and says what it does
- Cuts empty words such as "Note that it's important to remember that"
- Drops the metaphor "ratchet". A ratchet is a gear that turns in only one direction, and here it stood for "a limit that can only go down"
- Turns the passive warning "should only be done" into the imperative instruction "Run `budget.mjs --write` only to lower the budget."

### How to write the request: name the Skill in the request

The bundled guide's [`docs/guide/09-make-it-yours.md`](https://github.com/cursor/plugins/blob/main/pstack/docs/guide/09-make-it-yours.md) gives the following request example.

```
/technical-writing review the readme changes
```

The same page says that the user can use this Skill to review a document that the user or the agent finished. The user can also put the Skill's name at the start of a request for a new document.

<a id="summary"></a>


## Summary

- <strong>How the three differ.</strong> With `/unslop` and `/technical-writing`, the agent that wrote the text fixes it by rule. With `/bro`, the agent restates its reply when the user calls it.
- <strong>`/unslop`.</strong> It removes AI habits from every piece of text with 28 rules whose numbers never change.
- <strong>`/bro`.</strong> It restates the last reply, shorter and without jargon.
- <strong>`/technical-writing`.</strong> It first limits each document to one kind, and makes the document something a tired engineer understands on the first read.
