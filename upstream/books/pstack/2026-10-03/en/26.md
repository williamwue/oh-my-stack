This chapter covers the following principle.

1. [Encode Lessons in Structure](https://github.com/cursor/plugins/blob/main/pstack/skills/principle-encode-lessons-in-structure/SKILL.md)

This principle asks the agent to build fixes that keep coming back into structure instead of written instructions. A fix that keeps coming back is a fix for the same mistake, made again and again. Structure here means tools, code, metadata, and automation.

When the agent ends up writing the same caution twice, it stops adding that caution as text and <strong>turns it into a lint rule or a runtime check so that a machine enforces it</strong>.

The bundled guide's page [`docs/guide/08-principles.md`](https://github.com/cursor/plugins/blob/main/pstack/docs/guide/08-principles.md) sets this principle apart on its own as the meta principle.

The role of this principle differs from that of the other 22 principles.

The other principles decide what the agent does within individual pieces of work, such as fixing the cause instead of the symptom, or moving reversible work forward without waiting for confirmation.  
"Encode Lessons in Structure", on the other hand, turns the lessons that the agent finds during work into the structure of the next piece of work, such as a lint rule.

This principle calls <strong>every error, every human correction, and every unexpected result a learning signal</strong>.

When the agent picks up a learning signal, it sends the signal to the right place, such as a lint rule for a fix that repeats. It does not stop at recording the signal. It either fixes the problem now or creates a concrete todo. For details, see ["Feedback loop: three stages that turn a correction into structure"](#feedback-loop%3A-three-stages-that-turn-a-correction-into-structure).

In [the talk](https://x.com/poteto/status/2102050467505430555), poteto also said to keep the lessons from corrections in the repository in a reusable form, not only in the conversation ([Chapter 3](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/87177c), [Chapter 4](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/3cc0dd)).

This chapter explains this one principle in this order: the rule, the trigger conditions, and how pstack itself uses it.

<a id="rule%3A-turn-a-repeated-correction-into-the-strongest-structure-and-delete-the-instruction"></a>


## Rule: turn a repeated correction into the strongest structure and delete the instruction

The principle "Encode Lessons in Structure" asks the agent to enforce repeated cautions with structure instead of written instructions.

When the agent notices it has written the same caution twice, it <strong>builds structure that enforces the caution and deletes the written instruction</strong>.

The principle asks for this because <strong>readers often miss written instructions</strong>.

A written instruction works only when the reader notices the sentence, remembers its content, and follows it.

Corrections that the agent received in the conversation of an earlier session do not carry over to a new session. Even if the agent answers "I'll remember that", that promise does not survive into the next session.

Structure works even when the agent does not remember. So when the agent replaces a written instruction with structure, the agent in the next session follows the same rule too.

<a id="steps%3A-delete-the-written-instruction-once-it-is-structure"></a>


### Steps: delete the written instruction once it is structure

There are three steps.

1. Ask whether the instruction can become a lint rule, a metadata flag, a runtime check, or a script
2. If it can, turn it into structure and delete the instruction
3. If it cannot, because a machine cannot decide it and it needs judgment, make the instruction prominent and add an example of the failure that happens when nobody follows the instruction

<a id="turn-an-instruction-a-machine-can-check-into-a-lint-rule-and-delete-the-text"></a>


#### Turn an instruction a machine can check into a lint rule and delete the text

The caution from the start of this chapter, "Do not import modules in `internal/` from outside it", falls under step 2.

A rule file is a file, such as `AGENTS.md`, that holds rules for the agent. When a rule file contains the following sentence, the agent adds a lint rule that checks imports and deletes the sentence from the rule file.

AGENTS.md

```
Before: written as text in the rule file
- Do not import modules in internal/ from outside internal/
```

eslint.config.js

```
// After: add the following config and delete the sentence from the rule file (assumes typescript-eslint is installed)
import tseslint from "typescript-eslint";

export default [
  {
    files: ["src/**/*.ts"],
    languageOptions: { parser: tseslint.parser },
    // Allow imports between files inside internal/
    ignores: ["src/internal/**"],
    rules: {
      "no-restricted-imports": ["error", {
        patterns: [{
          group: ["**/internal/**"],
          message: "Do not import modules in internal/ from outside internal/",
        }],
      }],
    },
  },
];
```

With this config, lint reports an error when a file outside `internal/` imports a module in `internal/`. So the rule file no longer needs the same caution.

<strong>When a machine can check an instruction, the structure enforces it, and the written instruction is no longer needed</strong>.

<a id="make-an-instruction-a-machine-cannot-check-prominent-and-add-a-failure-example"></a>


#### Make an instruction a machine cannot check prominent and add a failure example

In contrast, "Write error messages so that the user knows what to do next" falls under step 3.

A machine cannot easily judge whether a message is good, so the agent keeps this instruction as text in a prominent place and adds an example of a bad message.

AGENTS.md

```
## Must follow

- **Write error messages so that the user knows what to do next**
  - Failure example: "An error occurred." The user does not know what to do next
```

When a machine cannot check an instruction, the only option is to keep the instruction as text. So the agent needs to make it prominent and add a failure example.

<a id="if-structure-can-fix-it%2C-use-only-structure"></a>


#### If structure can fix it, use only structure

The principle asks that <strong>if structure can fix a problem, the agent uses only structure</strong>.

If the agent keeps both the structure and the instruction, someone has to manage the same rule in two places. When someone updates only one of them, the two disagree. So the principle asks the agent to delete the written instruction once it becomes structure.

For example, if the agent updates only the lint rule and forgets to update the sentence in the rule file, an agent that reads the rule file writes code that follows the old rule.

<a id="writing-the-same-instruction-again-and-again-is-a-symptom-of-missing-structure"></a>


#### Writing the same instruction again and again is a symptom of missing structure

The source calls a written instruction a "symptom".

In this book, I read an instruction written again and again as a symptom of missing structure to enforce the rule.  
Under that reading, the principle asks the agent <strong>to build the missing structure, which is the cause, instead of adding more instructions, which are the symptom</strong>.

<a id="order-of-strength%3A-pick-the-strongest-structure-available"></a>


### Order of strength: pick the strongest structure available

When several kinds of structure are available, the agent <strong>picks the strongest one the situation allows</strong>.

From strongest to weakest, the four kinds of structure are as follows.

1. <strong>Unrepresentable state.</strong> Use types so that a state that breaks the rule cannot be written. A rule violation causes a compile error.
2. <strong>Lint or banned APIs that fail CI.</strong> When lint detects code that breaks the rule or an API that is banned, CI fails and the change cannot be merged.
3. <strong>A canonical helper.</strong> Provide a shared function that holds the required way of doing something, and have the code call that function. `formatDate()` later in this chapter is an example.
4. <strong>A runtime check.</strong> Verify the condition while the code runs. Even if code breaks the rule, nobody notices until that part actually runs.

The agent picks the strongest one because <strong>the agent writes code by copying the patterns the surrounding code already uses</strong> ([Chapter 4](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/3cc0dd)).

If the agent puts in a weak guard, meaning a low-ranked kind of structure that enforces a rule, that weak guard becomes the template the next agent copies.

For example, suppose that only a runtime check enforces the date display format.

The code for the order list screen formats the date itself and, right before displaying it, verifies that the date has the form `2026/09/26`. When the next agent builds the shipment list screen, it copies this code, formats the date itself in the same way, and adds the same runtime check.

```
type Order = { id: string; orderedAt: Date };
type Shipment = { id: string; shippedAt: Date };

// Order list screen: formats the date itself and verifies its form right before displaying it
function orderRow(order: Order): string {
  const d = order.orderedAt;
  const mm = String(d.getMonth() + 1).padStart(2, "0");
  const dd = String(d.getDate()).padStart(2, "0");
  const text = `${d.getFullYear()}/${mm}/${dd}`;

  if (!/^\d{4}\/\d{2}\/\d{2}$/.test(text)) {
    throw new Error(`Wrong date format: ${text}`);
  }

  return `${order.id} ${text}`;
}

// Shipment list screen: the next agent copies the code above and adds the same formatting and the same runtime check
function shipmentRow(shipment: Shipment): string {
  const d = shipment.shippedAt;
  const mm = String(d.getMonth() + 1).padStart(2, "0");
  const dd = String(d.getDate()).padStart(2, "0");
  const text = `${d.getFullYear()}/${mm}/${dd}`;

  if (!/^\d{4}\/\d{2}\/\d{2}$/.test(text)) {
    throw new Error(`Wrong date format: ${text}`);
  }

  return `${shipment.id} ${text}`;
}
```

On the other hand, if there is a canonical helper `formatDate()` and lint bans date formatting that bypasses the helper, the pattern the next agent copies is a call to `formatDate()`.

```
type Order = { id: string; orderedAt: Date };
type Shipment = { id: string; shippedAt: Date };

// date.ts: date formatting happens in one place only, the canonical helper formatDate()
function formatDate(d: Date): string {
  const mm = String(d.getMonth() + 1).padStart(2, "0");
  const dd = String(d.getDate()).padStart(2, "0");
  return `${d.getFullYear()}/${mm}/${dd}`;
}

// Order list screen
function orderRow(order: Order): string {
  return `${order.id} ${formatDate(order.orderedAt)}`;
}

// Shipment list screen: the next agent also copies the code above and calls formatDate()
function shipmentRow(shipment: Shipment): string {
  return `${shipment.id} ${formatDate(shipment.shippedAt)}`;
}
```

```
// Add the following config to eslint.config.js to ban date formatting code outside date.ts (assumes typescript-eslint is installed)
import tseslint from "typescript-eslint";

export default [
  {
    files: ["src/**/*.ts"],
    languageOptions: { parser: tseslint.parser },
    ignores: ["src/date.ts"],
    rules: {
      "no-restricted-properties": ["error", {
        property: "getFullYear",
        message: "Use formatDate() to format dates",
      }],
    },
  },
];
```

As a result, date formatting gathers in one place, `formatDate()`, and a new screen no longer adds another copy of the same runtime check.

Because the next agent copies the pattern of whatever structure is in place, the agent needs to pick the strongest structure available.

<a id="feedback-loop%3A-three-stages-that-turn-a-correction-into-structure"></a>


### Feedback loop: three stages that turn a correction into structure

The agent turns a correction into structure in the following three stages.

- <strong>Catch the correction.</strong> When a human steps in and fixes the work, or when a test fails, the agent decides whether the correction is a one-off or a recurring pattern.
- <strong>Route to the right layer.</strong> It sends a one-off to a brain note, a recurring fix to a Skill or a lint rule, and a system-wide problem to a Principle.
- <strong>Finish handling the correction.</strong> Instead of only recording it, the agent either applies it now, for example by adding the lint rule, or creates a concrete todo such as "Add a lint rule that bans imports of `internal/`".

If the process stops at any of the three stages, the correction does not reach the next piece of work.

The source lists the following three anti-patterns to avoid.

- <strong>Acknowledging without recording.</strong> Even if the agent answers "I'll remember that", those words do not survive into the next session.
- <strong>Recording without routing to the right layer.</strong> Suppose the agent writes the lint rule it should build into a note but never implements the rule. CI then does not fail when the next agent makes the same mistake, and a human has to give the same correction again. So the note is wasted.
- <strong>Fixing one instance without generalizing.</strong> If the agent fixes only the one place that imported `internal/` from outside and adds no lint rule, the next agent writes the same import somewhere else. A fix to one instance leaves in place the pattern that produces the same mistake.

<a id="trigger-conditions"></a>


## Trigger conditions

When <strong>the agent catches itself writing the same instruction a second time</strong>, or notices that <strong>the same correction keeps coming back</strong>.

<a id="this-principle-differs-from-two-others-that-also-lead-to-a-script"></a>


### This principle differs from two others that also lead to a script

This principle and two others, "[Build the Lever](https://github.com/cursor/plugins/blob/main/pstack/skills/principle-build-the-lever/SKILL.md)" and "[Prove It Works](https://github.com/cursor/plugins/blob/main/pstack/skills/principle-prove-it-works/SKILL.md)", can all lead the agent to build a script.

The source of "Build the Lever" distinguishes the three principles as follows.

- "Build the Lever" finishes the task at hand faster and in a form that is easier to review
- "Prove It Works" turns verification itself into a script
- "Encode Lessons in Structure" turns a repeated instruction into a lasting guardrail

In this book, I sort the three principles by the question the script answers.

- <strong>"How do I finish this task in front of me?"</strong> That is "Build the Lever" from [Chapter 17](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/97d863). An example is a codemod that renames in bulk.
- <strong>"Did this task finish correctly?"</strong> That is "Prove It Works" from [Chapter 19](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/d3f914). An example is a script that checks the lines of a written file.
- <strong>"How do I keep the same mistake from ever happening again?"</strong> That is "Encode Lessons in Structure". An example is a lint rule that bans imports of `internal/`.

<a id="pstack-itself-is-built-with-this-principle"></a>


## pstack itself is built with this principle

<strong>pstack also keeps its own lessons in structure, not in text</strong>. The main examples follow.

- <strong>`/reflect` ([Chapter 33](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/7c5f9e)).</strong> `/reflect` gathers lessons from conversations. It does not add a lesson to a Skill's text when lint or a script can enforce the lesson more reliably. Instead, it files such lessons in the team backlog as tasks to implement the lint rule or script.
- <strong>`preferences.md`.</strong> The "[Orchestrate](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/playbooks/orchestrate.md)" Playbook ([Chapter 16](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/3b2bef)) writes standing instructions, such as which model to use or which paths not to touch, in this file, one per line. The Playbook pastes them as is into every subagent when the subagent starts and when it resumes. Instructions tend to drop out at each resume, and every time one drops out, the human has to give it again. When the agent <strong>notices it is repeating the same instruction, it adds that instruction to this file as one line before it continues the work</strong>.

<a id="summary"></a>


## Summary

- <strong>Rule.</strong> When the agent writes the same instruction twice, such as "Do not import modules in `internal/` from outside it", it asks whether the instruction can become structure such as a lint rule or a runtime check. If it can, the agent builds the structure and deletes the written instruction. It picks the strongest structure available. From strongest to weakest, the order is types, lint that fails CI, a canonical helper, and a runtime check. For an instruction that cannot become structure, it makes the instruction prominent and adds a failure example.
- <strong>Trigger conditions.</strong> When the agent writes the same instruction a second time, or notices that the same correction keeps coming back.
- <strong>How pstack itself uses it.</strong> `/reflect` files lessons that can become structure, and the "Orchestrate" Playbook pastes the standing instructions in `preferences.md` into every subagent each time.

In the talk, poteto said that trust grows with the amount of verification methods, work procedures, and constraints left in the repository, not with the amount of conversation. Of these three, "Encode Lessons in Structure" adds to the constraints, such as lint rules and types, with every correction.
