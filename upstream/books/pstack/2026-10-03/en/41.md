<a id="what-%2Fpoteto-mode-is"></a>


## What `/poteto-mode` is

The "Router" in the chapter title refers to the job of `/poteto-mode`, which is to route each request to the Playbook that fits it. The bundled guide also gives its `/poteto-mode` page, [`02-poteto-mode.md`](https://github.com/cursor/plugins/blob/main/pstack/docs/guide/02-poteto-mode.md), the title "Route work through `/poteto-mode`".

Besides the rules that route requests to Playbooks, `/poteto-mode` holds <strong>rules that apply to all the work after routing</strong>. Here are some examples:

- Before you write code, decide the shape of the data, as the principle "[<strong>Model the Domain</strong>](https://github.com/cursor/plugins/blob/main/pstack/skills/principle-model-the-domain/SKILL.md)" says.
- Always stop before an irreversible operation.
- Write replies in short, declarative sentences.

The `description` in the frontmatter of `SKILL.md` calls `/poteto-mode` "poteto's agent style" and lists five things that style aims for:

- concise, detailed responses
- deliberate subagents
- unslopped prose
- simple code
- verified work

After the user installs pstack ([Chapter 34](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/c37697)), they <strong>hand work requests to `/poteto-mode`</strong>.

`/poteto-mode` has the setting `disable-model-invocation: true`, so it starts only when the user calls it by name. <strong>After one call, it stays active for the later turns of the same conversation without the `/poteto-mode` prefix, until the user says to stop</strong> ([README](https://github.com/cursor/plugins/blob/main/pstack/README.md), [Chapter 7](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/55bbdb)). While it is active, the agent follows a Playbook's steps only when the request fits a Playbook or needs rigor.

The body of `SKILL.md` has seven sections, from "Non-negotiables" to "Playbooks".

<a id="%22non-negotiables%22%3A-what-the-agent-must-always-do"></a>


## "Non-negotiables": what the agent must always do

"[Non-negotiables](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/SKILL.md#non-negotiables)" is a list of rules of the form "in this situation, always do this". We saw the main rules in [Chapter 8: What do Playbooks, Skills, and Principles each handle?](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/cd0205#non-negotiables-connect-the-three-parts).

"Non-negotiables" opens with these rules, which apply to every item in the list:

- In its reply, the agent names each principle that affected a decision and the choice that principle changed.
- The agent may name only principles whose Skill file it read in full during this session.

Take the example from [Chapter 8](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/cd0205), a bug where a retry in the middle of a run made the export write duplicate rows. After the fix, the reply contains a passage like this:

```
Per Fix Root Causes, I fixed the code that wrote already-exported rows again on every retry. I did not add a step that removes duplicates after export.
Per Make Operations Idempotent, I changed the write to overwrite by row key. Running the same job twice leaves the row count unchanged.
```

A reply like the following does not meet those two rules:

```
I followed Fix Root Causes and Make Operations Idempotent
```

A reply that only lists principle names does not say what the agent decided by following them. And if the agent cannot write what it decided, it may not have used the principle at all.

When the user sees the principle names next to the agent's decisions, the user can check which standard the agent applied and what it decided.

<a id="before-asking%2C-separate-facts-from-judgments"></a>


### Before asking, separate facts from judgments

Of the rules in the table, <strong>the source explains the first one, "classify before asking", at the greatest length</strong>.

When the agent is about to ask the user "which approach is better" or "how should this be built", it first classifies which of the following the answer is:

- <strong>A fact that running something would reveal.</strong> Examples are behavior, processing time, layout, output, and performance. The agent does not ask a person. It verifies the fact itself. How it verifies depends on the Playbook that `/poteto-mode` routed the request to:
  - Any Playbook other than "[<strong>Investigation</strong>](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/playbooks/investigation.md)". The agent tries it with the "[<strong>Prototype</strong>](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/playbooks/prototype.md)" Playbook and decides from the result.
  - The "<strong>Investigation</strong>" Playbook. The agent builds no prototype. It continues the investigation and answers from evidence that it finds in code and other sources.
- <strong>A judgment that a person makes.</strong> A product decision or a preference that no experiment can settle. The agent asks a person only about this kind of judgment.

"<strong>Investigation</strong>" builds no prototype because "Investigation" is an inquiry that does not change code. "Investigation" gives the user an answer with evidence attached ([Chapter 10](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/b77ae2)).

<a id="when-the-user-hands-off-the-whole-job"></a>


#### When the user hands off the whole job

When the user hands the whole job to the agent, the agent makes the decisions that come up during the work on its own, without asking the user, and keeps going. At the end of the work, it reports the decisions it made.

What goes into the report depends on the kind of decision:

- <strong>Decisions within the delegated scope.</strong> Decisions the agent made during the work, such as where to put the tests or how to split a function. The report says which option the agent chose.
- <strong>Judgments that a person makes.</strong> Product decisions or preferences that no experiment can settle. The report says which option the agent chose, why it chose it, and the words the user can say to undo the choice, such as "revert that".

Even when the job is handed off, the agent stops and waits for the user's decision in two cases:

- A checkpoint where the user asked in advance for the agent to stop, such as before a merge.
- An item on the "Always pause" list, which this chapter covers in [the "Autonomy" section](#%22autonomy%22%3A-where-the-agent-proceeds-without-asking-and-where-it-stops). These are irreversible operations such as a force-push to a shared branch or a deploy.

## "Subagents": the rules for delegation

"[Subagents](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/SKILL.md#subagents)" holds the rules for when the main agent delegates part of a task to a subagent. It sets two things:

- <strong>The delegate.</strong> Which subagent receives the work.
- <strong>The defaults.</strong> The settings the main agent uses every time it launches a subagent.

First, the delegate. When the main agent launches a subagent during a Playbook's steps, it uses `poteto-agent` by default. But `/how`, `/why`, `/interrogate`, `/reflect`, and `/swarm` choose their own subagents so that they can review with several models. The main agent does not replace the subagents those Skills choose with `poteto-agent`.

<aside class="msg message"><span class="msg-symbol">!</span><div class="msg-content">
<p class="code-line" data-line="188"><strong><code>poteto-agent</code></strong> is a subagent that ships with pstack (<a href="https://github.com/cursor/plugins/blob/main/pstack/agents/poteto-agent.md" rel="nofollow noopener noreferrer" target="_blank"><code>agents/poteto-agent.md</code></a>). Before it starts work, it reads the <code>/poteto-mode</code> <code>SKILL.md</code> in full, including the Principle index. As a result, it works under the same <code>/poteto-mode</code> rules as the main agent.</p>
</div></aside>

Next, the defaults. Whichever subagent the main agent launches, it uses the same settings every time. There are four defaults:

- <strong>Run in the background.</strong> The main agent can keep working without waiting for the subagent to finish.
- <strong>Run in agent mode.</strong> Agent mode is the mode that can edit files and run tools. In a read-only mode, the subagent cannot use MCP tools.
- <strong>Put file paths in the prompt, not file contents.</strong> The subagent opens and reads the files at the paths it receives.
- <strong>Set a model for each role.</strong> The main agent states which model runs the subagent for each role. [Chapter 34: Install pstack and choose a model for each role](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/c37697#the-list-of-roles) lists the roles and their default models. `/setup-pstack` can change those models.

<strong>The agent follows these defaults in every delegation</strong>.

The fourth default, setting the model, has a rule for handing off coding work. The main agent picks the delegate's model by how hard the change is:

- <strong>The hardest changes</strong> go to the model with the best judgment, which is `claude-opus-5-5-max` by default. Examples are designs that span several places, tangled concurrency, and algorithms where small errors are hard to spot. The main agent sends a hardest change to this model whether the instructions are vague and need judgment or the steps are detailed and the delegate only needs to follow them.
- <strong>Trivial mechanical edits</strong>, such as renaming, go to a fast-responding coding model, which is `grok-4.7-xhigh-fast` by default.

The rule file that `/setup-pstack` writes can change the delegate's model. Depending on what it delegates, the agent reads one of these lines in the rule file to pick the model:

- <strong>When the agent delegates the hardest changes.</strong> The `hardest tasks` line.
- <strong>When the agent delegates code for a Playbook.</strong> That Playbook's line, which is `feature, refactoring`, `bug-fix`, `perf-issue`, or `hillclimb`.
- <strong>When the agent delegates prose and judgment.</strong> The `judgment and prose` line.

A role with no line in the rule file keeps its default model. A role whose line says `inherit-parent` or `auto` runs on the model of the parent chat ([Chapter 34](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/c37697)).

"Subagents" also sets how to treat the results that subagents return.

First, the section defines a second opinion, which we saw in [Chapter 6](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/3a7791), as giving the same prompt to a different model. It states that <strong>when a different model gives the same answer, that agreement is a strong, reliable signal</strong>.

The main agent also sometimes stops a working subagent and resumes it. When the main agent stops and resumes a subagent many times, the subagent can silently drop part of the instructions, or context, that it first received.

So when a subagent that was stopped and resumed many times reports "done", the main agent does not trust that report. Instead, the main agent rewrites all the work to be done, the original instructions included, into one prompt and gives it to a new subagent.

<a id="%22writing-the-reply%22%3A-how-to-write-replies"></a>


## "Writing the reply": how to write replies

"[Writing the reply](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/SKILL.md#writing-the-reply)" says that <strong>the agent follows the reply rules while writing, not after it finishes</strong>.

> Write the reply clean as you draft it. A cleanup pass after drafting does not remove these patterns.

"Writing the reply" says that a review pass after drafting leaves behind writing that breaks the rules in the following table.

The "patterns" in the quote are these seven rules:

<td>Write lists and headings as sentences too, not joined with dashes. For example, write "<code>main.js</code> handles saving." instead of <code>main.js — saving</code>

<tr class="code-line" data-line="235">

<td>The same as unslop rule 14 (<a href="https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/c22a83" target="_blank">Chapter 32</a>). A colon before a list is fine</td>

Every Playbook ends with a reply written under these rules.

For example, the [README](https://github.com/cursor/plugins/blob/main/pstack/README.md) has a sample request about scroll drift:

```
/poteto-mode this pr has a subtle bug where the scroll drifts every 750ms even when idle. repro first, then fix and verify.
```

Here is the agent's reply after it fixes the bug from the scroll drift request, once in a form that breaks the rules and once in a form that follows them:

```
Before: Fixed: the cause was a timer so I stopped it, probably fine now I think.

After: The scroll no longer drifts while idle (measured).
The cause was a timer that rewrote the position every 750ms (measured).
The next owner of this code needs to check, when adding a timer, that it does not rewrite the position while idle (inferred).
```

The first reply has a colon in the middle of a sentence and three points in one sentence, and it does not say whether "Fixed" was measured or guessed. The second reply first says what changed for the app's users, then says what the next owner of the code takes over, and labels each claim.

A reply written under these rules lets the user read, sentence by sentence, what changed and how the agent verified it.

<a id="%22comments%22%3A-how-to-write-comments"></a>


## "Comments": how to write comments

"[Comments](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/SKILL.md#comments)" applies the reply rules from [the "Writing the reply" section](#%22writing-the-reply%22%3A-how-to-write-replies) to code comments as well. As with replies, <strong>the agent follows the rules while it writes comments, not by fixing them afterward</strong>.

"Comments" also says that <strong>a comment may record only a reason the code cannot show</strong>. A comment that records a reason such as "to work around a bug in the library" fits this rule.

The rule also covers verification and test scripts.

Scripts get no comments that narrate the stages of the process, such as `// Phase 1: add cards`. The script shows what it checks through assertions and through the strings it logs. An assertion is a statement that checks a condition and fails the script if the condition does not hold.

The following example is a script that adds two cards, restarts the app, and checks that the cards are still there.

```
// Before: comments that narrate the stages show the steps
async function checkBefore() {
  // Stage 1: add cards
  await addCards(2);
  // Stage 2: restart the app
  await restartApp();
  assert((await countCards()) === 2, "failed");
}

// After: the assertion string shows what was checked
async function checkAfter() {
  await addCards(2);
  await restartApp();
  assert((await countCards()) === 2, "cards are still saved after a restart");
}
```

In the first version, a failed assertion prints only "failed". You have to read the comments to know what the assertion was checking.

In the second version, a failure tells you from the output string that the check "cards are still saved after a restart" did not pass.

When the description of a step goes into the assertion string instead of a comment, the description also appears in the output.

The "Comments" rules apply to every file the agent creates, not only to test scripts. They also cover code changes the agent has a subagent write.

`/no-comments` ([Chapter 31](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/347946)), which runs before review, verifies whether each comment is needed.

## "Playbooks": the index of Playbooks

"[Playbooks](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/SKILL.md#playbooks)" is the index that the agent uses to pick the Playbook that fits a request. <strong>Each entry gives the Playbook's name, the work it is for, and the location of its file</strong>. The agent picks the Playbook that fits the request from the index, opens its file, and copies the steps word for word into the TODO list.

They are the core rules of `/poteto-mode`, so I show them here as well.

<a id="how-to-use-a-playbook"></a>


### How to use a Playbook

The agent uses a Playbook in this order:

1. Pick the Playbook that fits the request from the index and open its file.
2. Create a TODO list and copy the Playbook's steps word for word into the first item. If the request needs work the Playbook's steps do not cover, add that work after the copied steps. For example, for a request to add a `--json` flag, add "verify that the text output has not changed by a single byte".
3. Keep the steps you decide not to do. Do not delete them. Add one line to each in the form `skip: <reason>`.

The work in the second and third rows goes to `/figure-it-out` even when it fits a Playbook such as "Feature".

`/figure-it-out` is a Skill that designs a Playbook for that one piece of work alone. Instead of tracing fixed steps, it does three things for each job:

- It decides how strictly to verify. The larger the work and the bigger the impact of a failure, the stricter it gets.
- It splits the work into small units that can land one at a time and starts with the most uncertain unit.
- It records what it decided at each stage with `/show-me-your-work`.

The source does not say why the second row sends large work there. In this book, I infer that large work needs a level of rigor and a way of splitting that match its size.

The third row sends work the user wants to check later to `/figure-it-out` because the user checks all the results together after the work ends. The bundled guide [`07-overnight.md`](https://github.com/cursor/plugins/blob/main/pstack/docs/guide/07-overnight.md) gives this reason. So the user must be able to trace afterward what the agent decided and why. `/figure-it-out` designs the approach before it writes code and keeps a record of its decisions, so it meets that need.

The difference from "Orchestrate" is that `/figure-it-out` designs the approach for one job, while "Orchestrate" runs the whole of a job that lasts many days.

<a id="fit-it-to-your-own-style"></a>


## Fit it to your own style

`/poteto-mode` is poteto's style, so it may not fit the user as it is.

<strong>If it does not fit, you need to either create your own mode with [`/automate-me`](https://github.com/cursor/plugins/blob/main/pstack/skills/automate-me/SKILL.md) ([Chapter 25](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/e5f103)), or fork pstack</strong>. Your own mode is a Skill that captures your style, as `/poteto-mode` captures poteto's.

`/automate-me` finds the user's recurring habits in recent transcripts. The habits cover areas such as replies, delegation, verification, code, and writing. `/automate-me` then drafts a `<your-name>-mode` Skill, such as `tomato-mode`.

With `/automate-me`, the user keeps pstack as the base and gets a personal Skill that routes requests alongside `/poteto-mode`.

If you want to rewrite the Playbooks or Principles themselves, this book recommends that you fork pstack and keep your own version.

The README opens with "fork it. improve it. make it yours." and welcomes forks and improvements.

<a id="summary"></a>


## Summary

- <strong>The role of `/poteto-mode`.</strong> It is pstack's entry point, the Router, which routes requests to Playbooks. Its `SKILL.md` also holds rules for all the work after routing.
- <strong>"Non-negotiables".</strong> A list of what the agent always does in each situation. For example, before asking the user, the agent classifies whether the answer is a fact that running something would reveal or a judgment that a person makes.
- <strong>"Principles" and "Playbooks".</strong> The indexes of the 23 principles and the 23 Playbooks. The agent picks the matching entries from an index, opens their files, and reads them.
- <strong>"Autonomy" and "Subagents".</strong> The agent always stops before an irreversible operation. It follows the defaults in every delegation. The defaults are the settings that the main agent uses every time it launches a subagent.
- <strong>"Writing the reply" and "Comments".</strong> The agent follows the rules for replies and comments while it writes, not after it finishes.
- <strong>How to change it to your own style.</strong> Create your own mode with `/automate-me` or fork pstack.
