## What Part IV covers

For each Principle, Part IV explains three things:

- What each Principle chooses, what it avoids, and why the choice is necessary (for example, "[<strong>Prove It Works</strong>](https://github.com/cursor/plugins/blob/main/pstack/skills/principle-prove-it-works/SKILL.md)" does not count a passing build as done and verifies the written files or the screen directly).
- The situations each Principle applies to and the ones it does not (for example, "[<strong>Outcome-Oriented Execution</strong>](https://github.com/cursor/plugins/blob/main/pstack/skills/principle-outcome-oriented-execution/SKILL.md)" applies to a planned migration but not to everyday small fixes with no phase boundaries).
- How to use a Principle's name in a request to change the direction of the agent's work (for example, write `apply prove it works.` to ask the agent to run the real import and show the written records).

A Principle is <strong>a standard for the decisions the agent makes in the middle of its work</strong>. A Playbook sets the order of the work. Inside each step, the agent still has decisions to make, such as "should I add this abstraction?" or "now that it compiles, can I call it done?" In those moments, the agent uses the Principles to decide whether to make a change and whether it can call the work done yet.

The 23 Principles fall into five groups by the kind of decision they cover. With these groups, a reader can choose a chapter by the kind of decision they are unsure about.

The user does not call a Principle explicitly. <strong>The agent judges whether the work fits a Principle's situation and then reads it</strong>.

`/poteto-mode` is the Skill you use to start work ([Chapter 7](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/55bbdb)). It reads the Principle index at the start of any work with several steps.

The index is a list in the `SKILL.md` of `/poteto-mode`. It gives each Principle's name and the situation it applies to on one line. For example, the line for "Prove It Works" gives the situation "after finishing the work, before declaring it done". When the work fits a Principle's situation, the agent reads that Principle's own `SKILL.md` in full before applying it. In its reply, the agent names the Principles it applied and the decisions they changed.

<strong>At the start of the work, the agent reads only the list of Principle names and their situations</strong>. It reads a Principle's body only when the work fits that situation, and it uses the body to decide. So the agent does not load the bodies of all 23 Principles every time, and it does not waste context.

The user can also trigger this mechanism directly by <strong>writing a Principle's name in the request</strong>. Suppose the agent misses a situation that applies. One Principle name in the request then makes the agent correct its work to follow the rule that the name points to.

A single Principle name states the request more precisely than a long instruction. The name points to the complete rule written in that Principle's `SKILL.md`, so the user does not need to restate what the Principle says.

For example, suppose the agent is about to declare the work done because the build passed. The bundled guide, which ships with pstack in `docs/guide/` ([Chapter 6](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/3a7791)), has an example for this case in [`docs/guide/08-principles.md`](https://github.com/cursor/plugins/blob/main/pstack/docs/guide/08-principles.md). Write a request like that example:

```
apply prove it works. run the real import flow and show me the written records.
```
