This chapter covers [`/no-comments`](https://github.com/cursor/plugins/blob/main/pstack/skills/no-comments/SKILL.md).

`/no-comments` is a Skill that, before review, <strong>hands the comments in a diff to Comment Sicko, a different agent that did not write them</strong>. Comment Sicko deletes comments that explain surprising behavior in the team's own code. One example is a comment on a save function that also sends a confirmation email. Comment Sicko reports that function as a spot to fix. <strong>The original agent then fixes the code, by renaming functions or splitting them, so that the behavior is clear without the comment. Comments that explain behavior forced by something the team cannot change, such as an external library, stay</strong>.

`/no-comments` is the third of the three code-quality Skills that start in [Chapter 29](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/00dce1). In `/no-comments`, Comment Sicko, which did not write the comments, verifies them in place of the agent that wrote the code.

`/no-comments` reviews the comments in a diff. It also reviews suppression directives for lint and type checks, such as `eslint-disable` and `@ts-ignore`.

## Role: have Comment Sicko, an agent that did not write the comments, review them

`/no-comments` is a Skill that removes comments before review.

This Skill starts Comment Sicko ([Chapter 8](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/cd0205)) and fixes the findings from Comment Sicko that it accepts. When a comment asserts a constraint such as "do not change the wording", this Skill also proposes a way to express that constraint in code, such as a test.

This Skill <strong>treats a comment that explains surprising behavior in the team's own code as a mark of code that needs fixing</strong>. The reason is that renaming or extracting a function can make such behavior clear from the code alone, with no prose explanation.  
The section ["Replace a comment with a function name, using the example of a save function that also sends a confirmation email"](#replace-a-comment-with-a-function-name%2C-using-the-example-of-a-save-function-that-also-sends-a-confirmation-email) below gives an example of a comment that explains surprising behavior.

The bundled guide [`docs/guide/05-build-and-clean.md`](https://github.com/cursor/plugins/blob/main/pstack/docs/guide/05-build-and-clean.md) explains why comment review goes to a different agent, as follows.

> Comments need their own pass, and not from the agent that wrote them. An author defends its comments the way you'd defend yours.

When an agent checks comments it wrote itself, <strong>it defends its own comments and keeps them even when they are not needed</strong>. So Comment Sicko, which did not write the comments, does the review.

<a id="when-to-use-it%3A-call-it-on-the-diff-before-review"></a>


## When to use it: call it on the diff before review

`/no-comments` has the setting `disable-model-invocation: true` ([Chapter 25](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/e5f103)), so the agent never picks and runs `/no-comments` on its own from the conversation. The Skill runs when the user calls it by name, or when a rule of `/poteto-mode` or a step in a Playbook calls it.

The rules in the section "[Non-negotiables](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/SKILL.md#non-negotiables)" of `/poteto-mode` ([Chapter 8](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/cd0205)) say to call `/no-comments` before review. Playbooks such as "[Opening a PR](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/playbooks/opening-a-pr.md)", which opens a PR, say the same.

`/no-comments` looks at the files or the diff that the caller passes. If the caller passes nothing, it looks at the diff against the base branch, which is `main` by default, including uncommitted changes.

`/no-comments` and two other Skills that do similar cleanup split the work by target, as follows.

- <strong>Clutter in code.</strong> `/deslop` removes clutter such as comments that only narrate what the code does, unfounded defensive checks, and leftover compatibility paths that nothing uses. `/deslop` ships in [`cursor-team-kit`](https://github.com/cursor/plugins/tree/main/cursor-team-kit) and is not part of pstack.
- <strong>Habits in prose.</strong> `/unslop` ([Chapter 32](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/c22a83)) removes AI writing habits from prose such as READMEs and PR descriptions.
- <strong>Comments.</strong> `/no-comments` has an agent that did not write the comments review them.

<a id="playbooks-that-create-prs-also-call-%2Fno-comments"></a>


### Playbooks that create PRs also call `/no-comments`

Every Playbook that calls `/no-comments` uses it <strong>to remove comments from the diff before the PR goes out for review or verification</strong>. The situation and the reason for each caller are as follows.

<a id="%22opening-a-pr%22%3A-tidy-up-a-diff-that-looks-unfinished-before-review"></a>


#### "Opening a PR": tidy up a diff that looks unfinished before review

"Opening a PR" is the Playbook that opens a PR, and every other Playbook calls it at the end. This Playbook says to run `/no-comments` before review. The subagent that opens the PR also runs `/no-comments` before it posts the PR's URL.

The bundled guide `05-build-and-clean.md` explains why you cannot skip the cleanup of a diff. <strong>A diff that still has comments that only narrate the code, or unneeded defensive code, looks unfinished to the reviewer</strong>. The same page also says that <strong>leftover unneeded code becomes the place where the next defect hides</strong>.

<a id="%22autopilot-full%22-and-%22autopilot-stack%22%3A-settle-the-code-before-handing-it-to-verification"></a>


#### "Autopilot-full" and "Autopilot-stack": settle the code before handing it to verification

In "[Autopilot-full](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/playbooks/autopilot-full.md)" and "[Autopilot-stack](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/playbooks/autopilot-stack.md)" ([Chapter 16](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/3b2bef)), each PR has an owner, a cloud agent that handles one PR's change from start to finish. The owner runs `/deslop` and `/no-comments` to completion. Once the code to merge is in its final form, the owner reports that commit's SHA. After that, the owner's own verification and CI run alongside independent verification by `/swarm` ([Chapter 24](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/2df1db)).

<a id="%22multi-phase-or-multi-pr-plan%22%3A-put-it-in-the-plan-document's-checklist"></a>


#### "Multi-phase or multi-PR plan": put it in the plan document's checklist

The plan document that "[Multi-phase or multi-PR plan](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/playbooks/multi-phase-plan.md)" ([Chapter 16](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/3b2bef)) creates is a checklist. Each PR's owner works through the checklist one item at a time. The operator, the person who starts the plan, verifies each item by inspecting its evidence. The template for the plan document includes an item common to every PR: "Run `/deslop` before every commit, and `/no-comments` before review."

## Rules and procedure: review what Comment Sicko flags

<a id="comment-sicko-reviews-and-deletes-comments%2C-and-does-not-rewrite-app-code"></a>


### Comment Sicko reviews and deletes comments, and does not rewrite app code

Comment Sicko ([`agents/comment-sicko.md`](https://github.com/cursor/plugins/blob/main/pstack/agents/comment-sicko.md)) only deletes comments and reports code to fix. It does not rewrite app code.

Comment Sicko's definition is written in the exaggerated voice of "someone who hates comments to an unhinged degree". The rules for which comments may stay are strict, though.

<strong>Comment Sicko keeps only the following five kinds of comments, and deletes any comment it is unsure about</strong>.

- Legal and license headers
- Explanations of non-obvious behavior forced by an external dependency or platform that the team cannot change
- `// prettier-ignore`, and suppressions of lint rules that are wrong in themselves, too nitpicky, or only about style
- Doc comments that define the contract of a public API
- Links to an issue or an RFC that explains a constraint code cannot express

<a id="delete-explanations-of-surprising-behavior-and-suppressions-of-important-lint-rules%2C-and-list-them-as-must-kill"></a>


### Delete explanations of surprising behavior and suppressions of important lint rules, and list them as MUST KILL

Comment Sicko deletes comments that explain surprising behavior in the team's own code. In its report, it lists the symbol that has that behavior, such as a function, variable, or type name, as `MUST KILL`. A `MUST KILL` finding asks for a fix that makes the behavior clear without prose, through renaming, extraction, typing, or a redesign.

Some suppression directives, such as `eslint-disable`, `@ts-ignore`, or `@ts-expect-error`, silence a lint rule that catches real bugs or protects correctness or safety. Comment Sicko also deletes those suppression directives. It lists the symbol that causes the lint warning as `MUST KILL`.

<a id="replace-a-comment-with-a-function-name%2C-using-the-example-of-a-save-function-that-also-sends-a-confirmation-email"></a>


### Replace a comment with a function name, using the example of a save function that also sends a confirmation email

In this example, a save function also sends a confirmation email.

```
type User = { name: string; email: string };

// Before: a comment explains surprising behavior in our own function
// Note: besides saving, this function also sends a confirmation email
function saveUser(user: User) { /* ... */ }
```

```
type User = { name: string; email: string };

// After: extract the two jobs into two functions whose names say what they do
function saveUser(user: User) { /* ... */ }
function sendConfirmationMail(user: User) { /* ... */ }
```

The comment in the "before" code does not explain behavior forced by an external dependency. It explains surprising behavior in the team's own code. So Comment Sicko deletes this comment and lists `saveUser` as `MUST KILL`.

Comment Sicko does not fix the code itself. When `/no-comments` extracts two functions as in the "after" code, the names tell you which function does what, with no comment.

So when a comment explains surprising behavior in the team's own code, you need to delete the comment and fix the code so that the names show the behavior.

<a id="%2Fno-comments-reviews-comment-sicko's-report-instead-of-accepting-it-as-is"></a>


### `/no-comments` reviews Comment Sicko's report instead of accepting it as is

`/no-comments` does not accept Comment Sicko's report, or the changes Comment Sicko made, as they are. It reviews them in the following three stages.

1. Reject a report with errors and have Comment Sicko redo it once
2. For a judgment on a warning comment that gives no reason, check with `/how` or `/why` before accepting it
3. If a fix needs a new code shape, decide the shape with `/architect` before fixing

<a id="1.-reject-a-report-with-errors-and-have-comment-sicko-redo-it-once"></a>


#### 1. Reject a report with errors and have Comment Sicko redo it once

Comment Sicko's report and changes can contain errors such as the following.

- <strong>Findings outside the given scope.</strong> Findings about code outside the files or diff that `/no-comments` asked it to review.
- <strong>Rewrites of app code.</strong> Changes that rewrite app code, when Comment Sicko may only change comments.
- <strong>Deletion of comments that may stay.</strong> Changes that delete a comment of one of the five kinds that may stay, listed in ["Comment Sicko reviews and deletes comments, and does not rewrite app code"](#comment-sicko-reviews-and-deletes-comments%2C-and-does-not-rewrite-app-code).
- <strong>A wrong reason for `MUST KILL`.</strong> A finding where the reason given for fixing a `MUST KILL` symbol does not match the actual code. For example, it lists a function that sends no confirmation email as one that "also sends a confirmation email".
- <strong>Wrong findings about intended code.</strong> Findings that list code someone wrote on purpose and decided to keep as something to fix.

When `/no-comments` finds a report with such errors, it reverts Comment Sicko's changes, says what was wrong, and has Comment Sicko review once more. If the second report also has errors, `/no-comments` reports the problem as unresolved and ends its run as a failure.

<a id="2.-for-a-judgment-on-a-warning-comment-that-gives-no-reason%2C-check-with-%2Fhow-or-%2Fwhy-before-accepting-it"></a>


#### 2. For a judgment on a warning comment that gives no reason, check with `/how` or `/why` before accepting it

Code sometimes has short warning comments that give no reason, such as "IMPORTANT" or "do not remove".

If Comment Sicko judged such a comment as "delete" or "keep", `/no-comments` runs `/how` or `/why` on the symbol that the comment belongs to before it accepts the judgment. [Chapter 22](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/031877) covers both Skills. `/how` shows how the code works now, and `/why` shows why the code took that shape. With those answers, `/no-comments` can verify whether the warning's claim still holds.

Take the following warning, for example.

```
declare function sleep(ms: number): Promise<void>;
declare function saveDraft(): Promise<void>;

async function onClose(): Promise<void> {
  // IMPORTANT: do not remove
  await sleep(100);
  await saveDraft();
}
```

If `/why` finds that this wait works around a bug in an old library that has since been fixed, the warning's claim no longer holds. In that case, `/no-comments` accepts Comment Sicko's "delete" judgment.

If the investigation cannot settle the question, `/no-comments` deletes the comment.

<a id="3.-if-a-fix-needs-a-new-code-shape%2C-decide-the-shape-with-%2Farchitect-before-fixing"></a>


#### 3. If a fix needs a new code shape, decide the shape with `/architect` before fixing

For accepted findings that need only small fixes, such as deleting unused logic, removing an unneeded argument, or switching to the correct API, `/no-comments` makes the fix directly.

Some findings need a decision about a new shape for the code, such as how to split functions or how to build types, before anyone can fix them. In that case, `/no-comments` passes all the accepted findings to `/architect` ([Chapter 24](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/2df1db)) in one call, and `/architect` decides the shape. `/architect` stops once the shape is decided, and `/no-comments` makes the actual code fixes.

<a id="fix-accepted-findings-at-the-root-cause"></a>


### Fix accepted findings at the root cause

`/no-comments` fixes the findings it accepted in review at the root cause. This rule follows the principle "[Fix Root Causes](https://github.com/cursor/plugins/blob/main/pstack/skills/principle-fix-root-causes/SKILL.md)" from [Chapter 19](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/d3f914).

For example, if Comment Sicko deleted a comment that explains the reason for a workaround, `/no-comments` also deletes the workaround code and fixes the root cause that made the workaround necessary.

`/no-comments` does not fix code outside the scope it was given, though. If the root cause lies outside the scope, it makes only the smallest fix possible inside the scope and reports the rest as unresolved.

<a id="for-a-comment-that-asserts-a-constraint%2C-propose-a-way-to-enforce-it-in-code-and-wait-for-approval"></a>


### For a comment that asserts a constraint, propose a way to enforce it in code and wait for approval

A comment that asserts a constraint is a comment written like "do not remove", "do not change wording", or "talk to X before changing".

For such a comment, `/no-comments` <strong>proposes one way to enforce the constraint in code instead of a comment, and waits for the user's approval</strong>. There are four candidate methods, and `/no-comments` picks the one that takes the least effort within the given scope.

- <strong>Types.</strong> Code that violates the constraint becomes a compile error.
- <strong>Runtime check.</strong> A violation raises an error at runtime.
- <strong>Test.</strong> A violation makes a test fail.
- <strong>Lint.</strong> Lint warns about code that violates the constraint.

For example, for a comment that says "do not change the wording", `/no-comments` proposes writing a test that fails if the wording changes. With that test in place, the constraint holds without the comment.

```
// Before: only a comment asserts the constraint
// Do not change the wording
function stockLabel(count: number): string {
  return count === 0 ? "Out of stock" : `${count} left`;
}
```

```
// Register one test
declare function test(name: string, fn: () => void): void;
// Check a value
declare function expect(value: unknown): { toBe(expected: unknown): void };

// After: express the constraint as a test and delete the comment
function stockLabel(count: number): string {
  return count === 0 ? "Out of stock" : `${count} left`;
}

test("the wording for zero stock stays \"Out of stock\"", () => {
  expect(stockLabel(0)).toBe("Out of stock");
});
```

So when a comment asserts a constraint, you need to express that constraint in code, such as a test.

If the user approves, `/no-comments` expresses the constraint in code and then deletes the comment. If the user does not approve, it still deletes the comment and reports the constraint as unresolved.

## Summary

- <strong>Who verifies.</strong> Comment Sicko, which did not write the comments, reviews the comments in the diff.
- <strong>When to use it.</strong> Call it on the diff before review.
- <strong>How it fixes.</strong> It deletes comments that explain surprising behavior and fixes the code so that the behavior is clear without them.
