This chapter covers the following two Playbooks.

1. [Authoring or modifying a skill](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/playbooks/authoring-a-skill.md)
2. [Eval](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/playbooks/eval.md)

Both deal <strong>with Skills, which decide how the agent works</strong>, instead of app code.

You use "Authoring or modifying a skill" when you write or fix a Skill (`SKILL.md`), and "Eval" when you measure whether a change to that Skill had an effect.

This chapter explains how the two split the work, and how to use each, in order.

## The two Playbooks split the work into writing a Skill and measuring its effect

The bundled guide's "Make it yours" page ([`docs/guide/09-make-it-yours.md`](https://github.com/cursor/plugins/blob/main/pstack/docs/guide/09-make-it-yours.md)) asks two things about Skills.

- <strong>Hold text for agents to a higher standard than text for humans.</strong> Even a useless sentence becomes an instruction that some agent will follow in the future.
- <strong>Test Skill edits as experiments.</strong> A Skill edit affects every future session.

"Authoring or modifying a skill" handles the writing, and "Eval" measures the effect.

The steps of Authoring or modifying a skill have no instruction to use several agents.  
Eval, on the other hand, needs the following three things.

- <strong>Candidates.</strong> These agents work in an environment with the change in place.
- <strong>A judge.</strong> This agent is separate from the candidates and scores the candidates' output.
- <strong>A work environment with the cues removed.</strong> The cues are what would reveal an evaluation, such as directory names and file names.

## "Authoring or modifying a skill" writes a Skill through set steps and keeps only instructions that change decisions during the work

"Authoring or modifying a skill" is the Playbook you go through <strong>when you write a new `SKILL.md` or fix one</strong>.

The bundled guide lists a `SKILL.md` written freehand as a common mistake, and says that this Playbook puts the Skill through verification and review.

### The key point is the writing discipline "when in doubt, delete"

The key point of this Playbook is the <strong>writing discipline</strong> that follows the steps.

> When in doubt, delete. Keep only prose that changes a decision.

The agent that writes a Skill asks of each sentence, "which of the agent's decisions does this sentence change?" and deletes any sentence for which it has no answer.

The main rules of the discipline are as follows.

- <strong>Leave out explanations of why.</strong> Write instructions around "what to do," and explain the reason only when the instruction's meaning or the conditions for applying it are unclear without it.
- <strong>Point to the source instead of copying its contents.</strong> Point to sources that exist in the codebase, such as types, the README, and configuration files. The principle "[Encode Lessons in Structure](https://github.com/cursor/plugins/blob/main/pstack/skills/principle-encode-lessons-in-structure/SKILL.md)" asks for these pointers ([Chapter 21](https://zenn.dev/sc30gsw/books/7ff701b9811d04/viewer/10f4b3)).
- <strong>Defer to other Skills.</strong> Do not copy another Skill's contents. Give that Skill's path and let it do the job.
- <strong>Turn repeated work into a Skill.</strong> If you keep doing the same work, propose a new Skill.

If the agent notices a broken Skill partway through its work, it does not stop the work, and it does not quietly work around the problem either. <strong>It fixes only that Skill and opens a PR for it.</strong>

The reason is that reviewers tend to miss a Skill edit mixed into a feature PR, and "Eval" cannot measure its effect.

## "Eval" measures the effect of a change on the agent's behavior without letting the agent notice the evaluation

"Eval" is the Playbook that <strong>tests, before you adopt it</strong>, how a change to a Skill, a structure, or a prompt affects the agent's behavior.

The agent that runs "Eval" designs the experiment and summarizes the results. In this experiment, other agents use the changed Skill in real work, and a judge scores how they do.

The experiment starts several agents that solve a task. pstack calls these agents <strong>candidates</strong>.

- <strong>Give each candidate its own working directory.</strong> Put the changed Skill and the project skeleton in each directory. Separate directories keep the candidates from affecting each other's work.
- <strong>Use a different model for each candidate.</strong> For example, run the first on Opus and the second on Grok. Each model has its own biases, and if you test with only one model, its biases mix into the result.
- <strong>Give all of them the same request.</strong> If the requests differ, you cannot tell whether a difference in results comes from the change or from the request.

When the candidates finish, a <strong>judge</strong> that runs on a model different from the candidates scores the output without knowing which candidate produced it.

You can also compare two versions, before and after the change. In that case, one judge scores both versions' output at once, on the same criteria, without knowing which version each came from.

<a id="seven-steps"></a>


### Seven steps

The Playbook has the following seven steps.

1. <strong>Frame the experiment.</strong> Write down the change under test and the behavior that counts as success. Build a scoring rubric for the judge with 3 to 6 items, and do not show it to the candidates
2. <strong>Prepare an environment with the evaluation cues removed.</strong> Prepare a working directory for each candidate and put the change under test in it. Also include the context a real task would have, such as the project skeleton and the Skills a candidate would naturally read
3. <strong>Write one natural prompt.</strong> Make it a request the user would plausibly give, and do not reveal what you are measuring
4. <strong>Start N candidates in parallel.</strong> Follow the steps of [`/arena`](https://github.com/cursor/plugins/blob/main/pstack/skills/arena/SKILL.md) and use a different model for each candidate
5. <strong>Start one blind judge.</strong> Use a model family different from the candidates', and do not show model names
6. <strong>Verify from the records, not from self-reports, whether the candidate followed the instructions.</strong> Score whether a candidate followed, in order, the files the Skill pointed to. Base the score on the files that the conversation record shows the candidate opened, and on the shape of its code
7. <strong>The agent that designed the experiment reads every output itself.</strong> It compares them with the judge's verdict, treats any disagreement as a sign of model bias or an ambiguous rubric, and writes up the conclusion

<a id="the-key-point-is-the-blinding-rules%2C-placed-before-the-steps"></a>


### The key point is the blinding rules, placed before the steps

According to the bundled guide, pstack built this Playbook around one failure: "an agent that knows it is being evaluated behaves differently." The name for this failure is the <strong>observer effect</strong>.

The blinding rules fall into three groups, one for each path through which information can leak.

- <strong>Strings the candidates see.</strong> Do not put words such as `eval`, `test`, or `judge` in directory names, file names, or prompts. Use names the user would plausibly choose, and make the prompt look like an ordinary request.
- <strong>What the candidates answer.</strong> Do not have them list which Skills or files they used, and do not tell them other candidates exist.
- <strong>Information the judge sees.</strong> Show the output with labels that do not reveal which model produced it, and hide model names. When the judge compares two versions, one judge scores both in a single pass, on the same scale.

<a id="how-to-write-the-request%3A-give-both-versions-the-same-task-and-keep-the-candidates-blind"></a>


### How to write the request: give both versions the same task and keep the candidates blind

The bundled guide's example request compares two versions, before and after a change. It says to give both versions the same task and to keep the candidates blind.

```
/poteto-mode run the eval playbook on this skill change. same task for both variants, candidates stay blind.
```

<a id="summary"></a>


## Summary

- <strong>How the two Playbooks split the work.</strong> "Authoring or modifying a skill" creates and edits Skills, and "Eval" measures their effect.
- <strong>Authoring or modifying a skill.</strong> Write with `create-skill`, verify mechanically, and open a PR. The key point is "When in doubt, delete. Keep only prose that changes a decision." Fix a broken Skill in a separate PR that contains only the fix to that Skill.
- <strong>Eval.</strong> Before you adopt a change, verify its effect on behavior. The candidates do not know that anyone is evaluating them, and the judge does not know the model names. The score relies on the conversation records that show which files each candidate opened, not on the candidates' self-reports.
