## npm 包

t3-pstack 用 `npx -y github:` 运行安装器。npm 12 默认拒绝从 git 拉包，所以 OMS 把安装器发布为 npm 包 `oh-my-stack`。`t3-installer/` 打包前运行 `scripts/stage.mjs`，按仓库路径复制安装器、`plugins/pstack` 和许可证。生成器把 `VERSION` 写进 `t3-installer/package.json`。`tests/t3-installer.test.mjs` 打包后检查文件齐全，并从解压的包运行 `doctor`。

推送 `v<VERSION>` tag 后，`.github/workflows/release-oms-npm.yml` 用 npm trusted publishing 发布，并附带 provenance。npm 上的 trusted publisher 配置指向这个工作流文件。

## 入口

生成器在 poteto-mode、Codex 映射和各角色技能开头指向 T3 映射。T3 的派发工具、模型表、工作区选择和派发记录都按这份映射执行。Feature 和 Bug 修复的正文取自 pstack-claude，T3 专用步骤按映射中的 t3-pstack 原文执行。setup-pstack 的入口指向 T3 配置流程。

pstack-claude 的原生模型名和技能外路径检查跳过两份 T3 参考文件。Cursor 词汇检查也跳过 T3 模型表脚本，以保留迁移使用的旧模型 ID。豁免文件列在 `T3_QUOTED`。

## T3 模型设置

没有个人模型表或缺少某个角色时，T3 使用内置 medium 档。安装器保留或迁移已有的个人模型表。要覆盖角色、选用其他档位或调整 session hook，在 T3 会话运行 `pstack:setup-pstack`。已填写的角色优先于默认值。使用 `doctor --catalog <file>` 可核对有效角色的 provider、model 和 options。Catalog 需要包含有效角色使用的模型。用 `orchestrator_capabilities` 搜索补齐缺少的条目。

## hook 信任

安装器只信任 `tools/frozen-hooks.json` 中记录了摘要的 hooks 文件，这是 t3-pstack 的原有机制。修改 hooks 文件后，生成器会要求更新摘要和 `changedIn`，并在 CHANGES 里提醒用户重新运行安装器。

## 维护与同步

pstack-claude：设置 Git remote，fetch 审核过的 tag 后 `git merge`。冲突多数出在生成行，取对方版本后运行 `bun tools/generate.mjs`。OMS 独立维护 VERSION；Codex hook 内容变更时需递增 OMS 版本、更新摘要，并在 CHANGES 中提醒重新运行安装器。

t3-pstack：

```sh
git -C <t3-pstack 克隆> diff 11a71d2..<新 tag> -- plugins/pstack/models.json plugins/pstack/skills plugins/pstack/agents tools/install.mjs tools/install tools/frozen-hooks.json
```

把上游的派发和安装改动合入上表对应文件，保留 OMS 的模型配置。T3 默认模型改在 `plugins/pstack/models.t3.json`，再运行 `bun tools/generate.mjs` 更新派发和设置表。同步完成后更新本页的提交号。

## 检查

```sh
bun tools/generate.mjs --check
bun test tests/
cd plugins/pstack/skills/poteto-mode/scripts && bun run typecheck && bun test watch-pr && bunx prettier@3.6.2 --check .
```

原生 Windows 上有一批测试因环境原因失败（符号链接、文件权限、CRLF、shell 假程序），判断是否由改动引入前，先在同一台机器上跑一遍未修改的同版本上游。安装器的端到端测试需要 `T3_PSTACK_E2E=1`，会调用真实的 claude 和 codex。夹具测试、原生宿主检查和 T3 实机调用分开记录。

验收自动派发时，用返回的 `taskId` 关联请求、子任务结果和父会话验收。分别记录请求席位和回执确认的实际模型；缺少实际模型证据时记为“未确认”。
