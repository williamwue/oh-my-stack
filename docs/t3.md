# T3 Code 适配

## 基线

| 来源 | 版本 | 提交 | 进入 OMS 的方式 |
| --- | --- | --- | --- |
| michael-denyer/pstack-claude | v0.9.145 | `ce7df681bda9568801bd1de77d5c5ea34442cc44` | 带历史的 `git merge` |
| chhoumann/t3-pstack | 2.5.3 | `a9cd5ab33d370fa152dbdf5df6c04448f5ad90bc` | 只手工移植 T3 部分，提交记在 `tools/t3-upstream.json` |
| cursor/plugins pstack | 0b46ec3 | `0b46ec399d55f2829e88822998f53b84944837d3` | 通过 pstack-claude 间接进入 |

两个项目基于同一个上游提交。pstack-claude 把 Cursor 的机制改写成各原生宿主的写法，t3-pstack 把同一处改写成 T3 的写法。OMS 以 pstack-claude 为主体，把 T3 作为与 Codex、OpenCode 并列的一种宿主适配接入。

## 组合方式

| 部分 | 位置 | 来源 |
| --- | --- | --- |
| T3 派发规则 | `poteto-mode/references/t3-tools.md` | t3-pstack 的 Subagents 段及各技能的 T3 改写 |
| T3 模型配置流程 | `setup-pstack/references/t3.md` | t3-pstack 的 setup-pstack |
| 模型表校验 | `setup-pstack/scripts/t3-sheet.mjs` | t3-pstack |
| T3 角色默认值 | `models.json` 的 `t3` 段 | t3-pstack 的 models.json，按 pstack-claude 的角色名逐一对应 |
| 子任务是叶子节点 | `poteto-mode/worker.md` 中的一条规则 | t3-pstack |
| PR 评审静默窗口 | `watch-pr/settle.ts`，`--settle` | t3-pstack |
| 安装器 | `tools/install.mjs`、`tools/install/` | t3-pstack，改为安装 `pstack@oms` |

入口：生成器在 poteto-mode、Codex 映射和每个有角色的技能开头写一行条件入口，"有 T3 工具时先读 T3 映射"。setup-pstack 的入口指向 T3 配置流程。没有 T3 工具时条件不成立，技能按 pstack-claude 原文执行。

T3 模型表沿用 t3-pstack 的路径和格式：

| 项目 | 值 |
| --- | --- |
| 路径 | `~/.config/t3-pstack/models.md`（设置了 `XDG_CONFIG_HOME` 时放在其下） |
| 行格式 | `<角色>: <providerInstanceId>/<modelId> <选项>=<值>`，panel 角色用逗号分隔多项 |
| 继承父会话 | `inherit-parent` 或 `auto` |
| 校验 | `node setup-pstack/scripts/t3-sheet.mjs <表> <catalog.json>` |

OMS 2.x 的 `~/.t3/pstack-models.md` 不再读取。setup-pstack 会把其中的行当作用户选择，改写成新格式。

## 安装器的 hook 信任

安装器会自动信任 Codex 的 session-start hook，但只在 hooks 文件的摘要等于 `tools/install/hook-pin.json` 中记录的值时才信任。修改 `plugins/pstack/hooks/codex-hooks.json` 后，生成器会报错并给出新摘要。审核 hook 命令后把新摘要写入该文件，安装器才会信任新的 hook。

## 维护与同步

pstack-claude：设置 Git remote，fetch 审核过的 tag 后 `git merge`。冲突多数出在生成行，取对方版本后运行 `bun tools/generate.mjs` 重新生成。OMS 自己的 VERSION 和清单版本号保持不变。

t3-pstack：

```sh
bun tools/t3-upstream.mjs <t3-pstack 克隆>                     # 列出自上次移植以来改动的 T3 文件
bun tools/t3-upstream.mjs <t3-pstack 克隆> <ref> --advance     # 移植完成后记录新提交
```

只移植与 T3 派发、T3 模型表、settle 或安装器有关的改动。上游 pstack 的改动经由 pstack-claude 进入，不从 t3-pstack 重复移植。

## 检查

```sh
bun tools/generate.mjs --check
bun test tests/
cd plugins/pstack/skills/poteto-mode/scripts && bun run typecheck && bun test watch-pr && bunx prettier@3.6.2 --check .
```

原生 Windows 上有一批测试因环境原因失败（符号链接、文件权限、CRLF、shell 假程序）。判断某个失败是否由改动引入前，先在同一台机器上跑一遍未修改的同版本上游。安装器的端到端测试会调用真实的 claude 和 codex，只在 `OMS_E2E=1` 时运行。夹具测试、原生宿主检查和 T3 实机调用分开记录，不能互相替代。

## 官方依据

这是遵循 T3 工具契约的 OMS 适配，不是 T3 官方发布的方案。[官方编排文档](https://github.com/pingdotgg/t3code/blob/main/docs/orchestration-v2/orchestrator-mcp-server.md)说明了委派的上下文、模型选项、工作区隔离和完成回传契约；[官方技能说明](https://github.com/pingdotgg/t3code/blob/main/docs/user/composer.md#commands-and-skills)说明了 provider 技能发现，以及更新后需要重启会话。具体行为以当前宿主提供的 schema 为准。
