## 入口

生成器在 poteto-mode、Codex 映射和每个有角色的技能开头写一行条件入口："有 T3 工具时先读 T3 映射"。setup-pstack 的入口指向 T3 配置流程。没有 T3 工具时条件不成立，技能按 pstack-claude 原文执行。

pstack-claude 的模型名检查、技能外路径检查和 Cursor 词汇检查不扫描这两份 T3 文件（`T3_QUOTED`），因为其中是 t3-pstack 的原文，而 T3 总是以完整插件安装。

## hook 信任

安装器只信任 `tools/frozen-hooks.json` 中记录了摘要的 hooks 文件，这是 t3-pstack 的原有机制。修改 hooks 文件后，生成器会要求更新摘要和 `changedIn`，并在 CHANGES 里提醒用户重新运行安装器。

## 维护与同步

pstack-claude：设置 Git remote，fetch 审核过的 tag 后 `git merge`。冲突多数出在生成行，取对方版本后运行 `bun tools/generate.mjs`。OMS 自己的 VERSION 和清单版本保持不变。

t3-pstack：

```sh
git -C <t3-pstack 克隆> diff d444bf1..<新 tag> -- plugins/pstack/models.json plugins/pstack/skills plugins/pstack/agents tools/install.mjs tools/install tools/frozen-hooks.json
```

把有变化的原文或代码复制到上表对应位置。如果 poteto-mode 的 Subagents 段或 Models 段变了，更新 `t3-tools.md` 里对应的段落。完成后更新本页的提交号。

## 检查

```sh
bun tools/generate.mjs --check
bun test tests/
cd plugins/pstack/skills/poteto-mode/scripts && bun run typecheck && bun test watch-pr && bunx prettier@3.6.2 --check .
```

原生 Windows 上有一批测试因环境原因失败（符号链接、文件权限、CRLF、shell 假程序），判断是否由改动引入前，先在同一台机器上跑一遍未修改的同版本上游。安装器的端到端测试需要 `T3_PSTACK_E2E=1`，会调用真实的 claude 和 codex。夹具测试、原生宿主检查和 T3 实机调用分开记录。
