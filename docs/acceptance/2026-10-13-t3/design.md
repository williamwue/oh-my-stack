# Selected T3 design

## Caller usage

```bash
node tools/generate.mjs --orchestration t3 --output-root .tmp/t3
```

The build retains the four existing package targets. Only Codex and Claude Code select T3 bindings. Default generation and OMP/Pi output remain byte-identical. The selected build is detached from default release inputs.

## Synthesis decision

Candidate 1 is the base. Both independent candidates preferred an explicit orchestration axis over an additive content extension. The independent cross-judge agreed with Candidate 1's single domain owner, ordered arrays, and immutable requests. Its two grafts are explicit option provenance and pure reconciliation of prior task observations.

The alternative extension can distribute a standalone entry but cannot rebind existing workflows without adding a second behavior selector. A fifth native adapter confuses installation with orchestration. Session facades, persistent slot identifiers, granular panel-edit APIs, a generic registry framework, and a new daemon are rejected.

## Data shape and boundaries

- A catalog records exact provider instances, opaque model identifiers, typed model options, execution constraints, and source provenance. Native model inventory schemas remain unchanged.
- T3 resolution uses `.oh-my-stack/t3/resolution.json` in user or project scope. The nearest project file shadows the whole user configuration. Same-preset refresh preserves exact ordered entries. Explicit overrides replace only requested selections.
- Each target is either explicit provider/model/options or parent inheritance. Options retain string or boolean types. Omitted options remain explicitly unpinned in audit metadata, never claimed fully resolved.
- Selected role contracts derive from canonical roles and target-effective routes. They are generated for both hosts with schemaVersion 1, orchestration t3, host, keyed roles, and keyed routes.
- One Node domain module prepares complete child briefs and requests. The host invokes actual T3 tools. It owns no credentials or remote transport.
- Request identity includes parent, run, step, round, role/route, and panel member. Retry uses the saved request. Reusing its identity with another payload fails. New review rounds receive new identity and carry the original requirement, findings, responses, and unresolved objections.
- Original published result and later child-thread work remain separate. A wait timeout is not failure. A cancellation request is not observed cancellation. Requested options remain unverified until independent runtime evidence exists.

## Binding contract

Selecting this build makes its delegated workflow units explicitly T3-owned. They use delegate_task, including same-provider units. The default build retains native delegation. There is no duplicate automatic-dispatch policy in the helper.

PR creation retains authorization and immediately links every layer. Monitoring uses the host watch and ends the turn. A settled thread must be unsettled using the actual available interface before watching. Handback removes the watch. Top-level threads require an explicit user request.

Scheduler support prepares drafts only. Same-project schedules default to the current thread. Another project cannot bind to this thread. Fresh-thread schedules require explicit user intent. Structured triggers and booleans retain their native types. No unsupported provider/model overrides are added.

Browser and device instructions use current host tools, observed ownership, and the exact returned device launcher. No fixture or opened tool alone establishes UI acceptance.

## Verification and limitations

Focused tests cover catalog/options, configuration isolation/order, full briefs, retries/fresh rounds, result/cancellation states, scheduler request shapes, deterministic selected generation and preserved default bodies. The repository check remains mandatory.
