# Independent architecture verdict

Review scope: frozen rubric, both completed candidates, grounding, supplied T3 tool contracts, and architect design-red-flags.md. This is an architectural review, not implementation or live-host acceptance. Only this verdict artifact was written.

Use **Candidate 1 as the base**, with the two bounded grafts below and the contract corrections listed here. Its single domain owner, immutable receipts, whole-array panel replacement, and existing-native-package binding are the simplest viable shape for the stated intent. Candidate 2 reaches essentially the same architecture but adds a native/T3 automatic dispatch policy, persistent slot identities, patch operations, a second importable implementation module, and a public scheduler domain that are unnecessary for this local implementation.

## Required corrections

1. **Specify omitted options before implementation.** Candidate 1 must either materialize supported current/default values for explicitly pinned choices or record explicit inheritance for omitted values, including the evidence gap. Unknown current/default values must not be invented. Preserve boolean false. This follows delegate_task's documented inheritance; partial options are legal, but silently treating them as a fully pinned selection is not.
2. **Make scheduler destination truthful and authorized.** Default the same-project draft to the current thread. Use a fresh top-level thread only when the user asks for that outcome. Reject another-project/current-thread combinations or return a clear proposed fresh-thread outcome requiring the corresponding user intent; never promise a binding the tool cannot create. Do not add provider/model/runtime override fields. For this task, produce local drafts and fixtures only.
3. **Include the settled-thread watch prerequisite.** Candidate 1's guide must instruct discovery of the actual unsettle interface before starting a new watch on a settled thread, alongside its existing unwatch discovery. Missing interfaces yield an unavailable capability, not guessed calls.

## Red-flag screen

- **Shallow/pass-through:** Candidate 1's retryT3Child(receipt): PreparedChild needs a substantive integrity check or should disappear. Reusing the immutable receipt is already the retry operation. Candidate 2's public helpers must own policy rather than forwarding identical structures into t3-contract.
- **Information leakage/importable internals:** Candidate 1 appropriately confines MCP serialization to the CLI. Candidate 2 calls a normal sibling tools/t3-contract.mjs file private without a build/import restriction. Keep those internals in the domain module initially, or enforce the restriction; comments do not establish encapsulation.
- **Temporal decomposition:** Neither candidate requires a load/validate/transform/save module chain. Keep that property during implementation.
- **Split ownership:** Both assign configuration and receipts to one parent owner and derive roles from canonical sources. Preserve this; no shared writable child ledger is needed.
- **Two ways to do one task:** Candidate 2's ownership=auto introduces a second native-dispatch decision and proof obligation within the selected binding. Explicitly T3-selected delegated units can simply be T3-owned, which the supplied delegate_task contract expressly permits. Existing default native output remains its own established path.
- **Hand-synced lists:** Both reject copied role/model lists. The new binding descriptor should list only binding-specific facts; obtain canonical roles, routes, and native target identities from their existing owners.
- **Overengineering:** Do not add persistent slot IDs, insert/remove/reorder patch verbs, a read-only aggregate subsystem, a generic orchestrator registry framework, or a new scheduler API unless a concrete implementation caller needs them. Ordered arrays and whole-panel replacement meet this rubric.

## At most two grafts from Candidate 2

1. **Explicit option resolution and provenance:** bring its current/default/explicit distinction into Candidate 1, with an explicit inheritance alternative where desired. Do not import a blanket host-required completeness claim.
2. **Prior-observation result reconciliation:** bring its small pure reduction for duplicate observations and immutable published results into Candidate 1's existing domain owner. Add prior observation only where needed; do not create a separate state service or public protocol module.

## Unsupported capability claims and evidence limits

Neither candidate claims completed live execution, installation, publication, or cross-provider success. Both correctly treat the captured catalog as advertised state, retain Claude as unavailable, avoid exactly-once guarantees, and leave effective runtime options unverified. The concrete unsupported capability is Candidate 2's representable cross-project/current-thread scheduling outcome. Candidate 1's partial-option policy is an underspecified reproducibility claim, not evidence of unsupported option syntax. The missing unwatch/unsettle/request_secret schemas must remain discovery requirements, never invented serializers.

Implementation acceptance should prove byte-identical default trees and pinned bodies, deterministic selected Codex/Claude output, unaffected OMP/Pi output, isolated configuration and retained panel order, exact native request fixtures, retry/round identities, lifecycle reduction, and the corrected scheduler/watch behavior. Run npm run check and distinguish existing failures from change-caused failures. No local fixture can establish provider execution, option enforcement, cancellation delivery, native installation, PR watch operation, or actual browser/device acceptance.
