# Local failure and security boundaries

Durable run stores coordinate cooperative writers on one local filesystem with an exclusive `run.json.lock` file. An append validates the event, acquires the lock, rereads and validates the current store, checks its generation and next revision, then atomically replaces the store file. An identical event replay is idempotent. A stale or gap revision, conflicting event ID, terminal run, invalid credential field, or path that resolves outside the configured root is rejected without writing the event. Lock contention is retried for at most two seconds and then reports `STORE_LOCKED`.

An orphaned lock is never removed automatically based on its age. If a process crashes while holding a lock, an operator must inspect the store, the lock, and possible active writers, then remove the lock manually only after confirming no writer remains. The lock and rename protocol assumes cooperating processes and a local filesystem with exclusive file creation and atomic replacement semantics. It is not a distributed lock. Path containment is checked again before append and immediately before replacement, but a malicious concurrent directory replacement can still race those checks; this does not claim safety against a hostile host or filesystem administrator.

Runtime probes bound both version discovery and the actual command to a time limit and a combined stdout/stderr byte limit. Timeout and excess output terminate the child and produce failed results with explicit reasons. A missing runtime remains `unknown` or declared `unsupported`, distinct from those failures. Probe output is not trusted to overwrite observed command or runtime metadata.

Run evidence binds receipts to a run generation, revision, and source commit. A reserved receipt ID is rejected before an evidence store is created. Stale receipts do not verify a changed run or source. These records describe local observations; they do not reattach to an existing native worker after a process restart.
