# Alpha.4 installed direct-entry acceptance

## Result

The full-body acceptance gate did not pass. Codex discovered all 49 installed
public entries and accepted their structured selections, but only 45 persisted
instruction bodies exactly matched the installed files. Four records ended at
approximately 8,000 characters. Correct names and headings did not prove that
the remaining instructions were available.

| Skill | Installed characters | Recorded characters |
| --- | ---: | ---: |
| `reproduce-and-fix-issues` | 14,486 | 8,000 |
| `setup-benny` | 13,448 | 8,000 |
| `technical-writing` | 10,772 | 7,999 |
| `triage-issue-reports` | 10,511 | 8,000 |

Lengths use JavaScript string length. Every incomplete record matched the
corresponding file's prefix. This observation alone does not distinguish a
runtime injection limit from truncation in persisted history. It does prevent
a claim that all 49 complete bodies were verified as loaded.

## Method and evidence

The run used Codex CLI 0.155.1 app-server on the installed alpha.4 plugin,
not repository `.agents/skills` copies. OpenAI Docs guided protocol selection:
[the official app-server documentation](https://learn.chatgpt.com/docs/app-server#skills)
describes `skills/list` and structured `skill` input for explicit invocation.
The local runtime's actual output, rather than the documentation, determines
the acceptance result here.

Five fresh persisted sessions selected batches of 10, 10, 10, 10, and 9 entries.
Each request included text markers and structured Skill name/path items.
Sessions used read-only sandboxing and approval policy `never`. The request
explicitly prohibited workflow execution, tools, delegation, configuration,
automation, and publication. Each response contained only names and headings.

Root verification established:

- `skills/list` returned the exact public catalog, with 49 enabled alpha.4
  paths. The 12 internal probes were absent from that plugin listing.
- All five turns completed. Returned names and first level-one headings matched
  the installed files for all 49 entries.
- Persisted `skills.selected_skill_instructions` records covered all 49 names
  exactly once, using installed plugin paths.
- Completed item types were only `userMessage`, `reasoning`, and `agentMessage`.
  No tool or delegated action item was observed.
- Forty-five full bodies matched exactly; four matched only prefixes.
- The installed package passed the generic `verify` command against the saved
  alpha.4 manifest. Installation corruption is not supported by this check.

The first full-body verifier exited 1 at `reproduce-and-fix-issues`, reporting
`full body not injected`. That is the verifier's failed assertion text, not a
confirmed diagnosis of where truncation occurs. The failed verifier remains
unchanged. A separate audit checked all remaining entries and produced the
[per-entry results](0.2.0-alpha.4-direct-entry-results.json).

Local scripts and raw logs are retained in `.tmp/direct-entry-acceptance`.
`run.mjs` performed discovery and selection; `verify.mjs` contains the failing
full-body assertion. `native.jsonl` records native responses and notifications.
The public results include its SHA-256 and session IDs, but not private paths
or full runtime logs. No implementation, installation, or release changed.

## Boundaries and next work

This is batched explicit-loading evidence, not 49 standalone behavior runs.
It does not prove automatic routing or Desktop picker interaction. The latter
remains pending because the earlier computer-use attempt was explicitly denied.
Claude Code live checks remain deferred.

The next corrective task is to determine the exact boundary for long Skill
bodies and make complete instructions reliably available. A candidate design
keeps every direct entry, moves long procedures into packaged references, and
requires the entry to read those references before execution. That design needs
its own change, provenance checks, and live acceptance; it is not implemented
by this audit. Shortening descriptions alone cannot resolve this body mismatch.
