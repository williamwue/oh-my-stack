# Alpha.4 installed-Skill feature acceptance

## Scope and workflow

On 2026-09-23, the next real feature acceptance task added a read-only `verify`
action to the generic release installer. This closes an actual user-facing gap:
installation already verified staged files, but no CLI action exposed that check
for an existing installation without reinstalling it.

The current Codex Desktop-hosted root session read the installed alpha.4
`feature` and `how` Skills directly from the plugin cache. The simple `how` path
traced `install-release.mjs` through manifest target selection to
`verifyInstalledTree` and `packageInventory` in `release-lib.mjs`, then checked
the release CLI tests. This inspection changed no files. The later feature
implementation reused that exact verifier; no new inventory format was needed.

- `how/SKILL.md`:

## Design and throughput checkpoint

- Data contract: the selected release artifact's existing `files` inventory.
- Direct design: branch after manifest lookup and before archive reading; invoke
  the existing read-only verifier, print success, and return.
- Tradeoff: mismatch errors remain directory-level summaries. Per-file repair,
  diff output, signature verification, and native plugin registration are outside
  this feature's scope.
- Gate: demonstrate the absent action with a real CLI test before implementation.
- Shared mutable state: CLI and release tests overlap existing uncommitted work;
  use one root writer and preserve earlier hunks.
- Decomposition: test first, small CLI change, root verification, documentation.
  Independent agent work offered no useful separation for this bounded change.

## Before and after

The unchanged acceptance command was:

```bash
node --test --test-name-pattern='release installer CLI verifies installed files' tests/release.test.mjs
```

Before implementation it exited 1 because `verify` was rejected with
`action must be install, update, or uninstall`. After implementation it exited
0 with one passing test covering all three target artifacts.

For each target the test installs a package in a temporary tree, removes its
archive, and checks that verification succeeds. It then checks modified,
missing, and additional files independently: each verification exits 1. File
inventories of the entire temporary tree match before and after each verify
invocation. A nonexistent destination is rejected without being created.
Mutation and cleanup occur only in test-owned temporary directories.

The root also ran the new command against the actual installed Codex plugin,
using the local saved release manifest:

```bash
node tools/install-release.mjs verify \
  --manifest "$HOME/.local/share/oh-my-stack/releases/v0.2.0-alpha.4/release-manifest.json" \
  --target codex \
  --destination "$HOME/.codex/plugins/cache/oh-my-stack/oh-my-stack/0.2.0-alpha.4"
```

Result: exit 0, `Verified codex package` at the selected installed directory.
No installation update was performed. The root reviewed the implementation
diff and ran `npm run check`: generation, conformance, reproducibility, schema,
Markdown, and all 82 tests passed.

## Evidence boundary

This is root-only feature acceptance using installed Skill content, not a new
test of structured selection, automatic routing, Desktop picker interaction,
or delegation. Testing the Claude Code artifact does not verify a Claude Code
runtime or require an account. Live Claude Code use remains deferred.

The command compares against a trusted manifest; it does not authenticate that
manifest, prove runtime loading, or provide an atomic filesystem snapshot under
concurrent writes. No global capability level is advanced by this record.

The feature remains uncommitted and unpublished in the source working tree;
the installed alpha.4 package was not modified. Refactoring acceptance remains
a separate pending task: adding this behavior is not a behavior-preserving
refactor, and no extra structural edit was made just to claim that milestone.
