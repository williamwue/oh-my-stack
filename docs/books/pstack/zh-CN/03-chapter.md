每月 2,500 个 PR 并不是刻意追求的数字。<strong>它是在建立一个能够放心把工作交给 Agent 的环境之后，随之产生的数字</strong>。

本章探讨「为什么不能把数量定为目标」，以及「数量究竟代表什么」。

## 为什么不能把数量定为目标

原因有两个。

第一个原因是，如果只增加数量，<strong>增加的不是成果，而是未经验证的变更</strong>。

只要人仍在逐一阅读 Agent 所写变更的差异，并操作应用来验证，PR 数量的上限就取决于人能检查多少。

在这种状态下，即使决定「本月把 PR 翻倍」，也只是把发给 Agent 的请求翻倍。负责检查的人手没有增加，因此多出来的变更会未经验证地堆积起来。

<strong>哪些变更正确、哪些出了问题，要等以后有人逐一验证才会知道</strong>。

另一个原因是，<strong>数量是很容易操纵的数字</strong>。  
同一个功能，如果合并成一个大 PR，就是 1 个；如果拆成五个，就是 5 个。

如果把数量定为目标，即使变更内容完全相同，也能仅凭拆细 PR 让数字看起来更好。

## 数量所代表的事

我认为，数量真正代表的是<strong>从人手中转移到 Agent 一侧完成的检查量</strong>。

如上一节所述，如果所有事情都由人验证，数量就无法超过人的检查能力。反过来说，如果数量远远超出人的检查能力，大部分检查工作应当由人以外的主体承担。

poteto 也在《The Complete Guide to pstack》的 [Part 1](https://x.com/poteto/status/2094457600259842065) 中，将验证（verification）定义为「<strong>Agent 能够检查自己的工作</strong>」，并写道这样人就不会成为瓶颈。

那么，要把检查工作从人手中转移出去，需要什么？

需要以下四项，它们也是 poteto [演讲](https://x.com/poteto/status/2102050467505430555)的四个主题。

1. 信任
2. 提高信任的方法
3. 将代码库视为记忆
4. 自动化

特别重要的是，这四项并不是相互独立的提示；前一项是后一项的前提和基础。

也就是说，必须遵守这样的顺序：首先让成果物处于可验证的状态，将由此获得的知识保存在代码库中，再在此基础上推进自动化。

每月 2,500 个 PR，是依次建立这四项条件后的结果。本书的[第 2 章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/27a183)到[第 5 章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/b6ac2d)会分别讨论这四项，每章讨论一项。

## 小结：将视角从「数量」转向「能够委派工作的条件」

- <strong>不能把数量定为目标的原因</strong>……如果负责检查的人手没有增加，增加 PR 数量只会增加未经验证的变更。数量也很容易随着 PR 的拆分方式而变化。
- <strong>数量所代表的事</strong>……从人手中转移到 Agent 一侧完成的检查量。其背后是信任、提高信任的方法、作为记忆的代码库、自动化这四项条件齐备的状态。

下一章[第 2 章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/27a183)讨论四项中的第一项「信任」。演讲提出，信任的对象是 Agent 制作的成果物，而不是 Agent 本身。我们将看看 pstack 如何将这一思路付诸实践。
